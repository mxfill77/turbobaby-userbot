# guard-quote-price — карта расхождения quote ↔ текст клиенту

Родитель #310, шаг 1/5. Разведка: где считается quote, где формируется текст с ценой,
откуда LLM/шаблон берёт числа и где они могли разойтись с котировкой.

Кейс-провал: окно `504608015`, «NMAX 155 **на 5 дней — 2 245 ฿**» вместо **1 685 ฿** из
quote. Ключ: `449 × 5 = 2245`, где `449 ฿/день` — суточная ставка NMAX 155 (сетка-ориентир
и/или `day_price` котировки), а `1 685 ฿` — period-total из Календаря (тариф со скидкой за
срок, ≈337 ฿/день). То есть период-итог из quote заменён наивным «дневная ставка × дни».

---

## 1. Модуль расчёта quote (источник ИСТИНЫ)

**`pricing.py`** — read-only котировка из «Календаря бронирования» через Bridge (GET, без
записи, любые ошибки → `None` → честный фолбэк).

- `quote(bike, date_start, date_end)` (`pricing.py:75`) → dict-котировка или `None`.
  `_normalize` (`pricing.py:51`) отдаёт поля: `day_price`, `total`, `deposit`, `available`,
  `season`, `days`, `text`, `cap_active`, `cap_price`. **`total` — это цена за ВЕСЬ период
  (с дисконтом за срок), `day_price` — суточная ставка.** Они НЕ связаны `total = day_price ×
  days` при сроке со скидкой (в кейсе `total=1685`, `day_price=449`, `days=5`).
- `quote_for_model(model, ds, de)` (`pricing.py:170`) — резолв модель→конкретный байк парка
  (`fleet` + `_candidates`) и котировка; статусы `ok|none_available|no_candidates|error`.
- `sanity_days_ok(quote_days, hint_days, monthly)` (`pricing.py:132`) — гард согласованности
  `days` котировки со словами клиента (>1 дня расхождения → режем цену). Сверяет ДНИ, но
  **не сумму** — наивный пересчёт суммы этим гардом не ловится.

Вывод: quote отдаёт правильный `total=1685`. Расхождение возникает НЕ в `pricing.py`, а
ниже по потоку — в сборке текста и/или в генерации LLM.

---

## 2. Формирование текста цены клиенту (`suggest.py`)

Поток: `build_pricing_note` → `_resolve_model_price` → `_client_price` → `make_system_prompt`
(вставка в промпт) → LLM `generate_draft` → `postcheck_draft` (страховка).

- **`build_pricing_note(hints, lang)`** (`suggest.py:2036`) — собирает инструкцию-блок ЦЕНА.
  Одиночная модель (наш кейс) → `products` длиной 1 → ветка `suggest.py:2086`.
- **`_resolve_model_price(model, ds, de, hint_days, monthly)`** (`suggest.py:1493`) — зовёт
  `_safe_quote_for_model` → `pricing.quote_for_model`; при `status==ok` возвращает
  `("ok", _client_price(q), q)`.
- **`_client_price(q)`** (`suggest.py:1458`) — КЛЮЧЕВОЕ место сборки фразы:
  - если есть `q["text"]` (J-текст Календаря) → берётся **дословно** + депозит;
  - иначе собирается `«{day_price} ฿/день; итого {total} ฿; депозит {deposit} ฿»`
    (`suggest.py:1481-1490`).
  **В обоих случаях в блок ЦЕНА попадает и суточная ставка (449), и период-итог (1685)** —
  т.е. у LLM перед глазами оба числа, из которых `449 × дни` даёт неверный итог.
- **`_wrap_single(kind, phrase)`** (`suggest.py:1531`) — оборачивает: «ЦЕНА из Календаря
  бронирования (использовать ДОСЛОВНО, не пересчитывать и не округлять): …». Инструкция «не
  пересчитывать» есть, но она текстовая (LLM), не гард.
- **`make_system_prompt(...)`** (`suggest.py:2147`) — вставляет `pricing_note` в промпт
  (`price_block`, `suggest.py:2239`), ниже — ценовая политика «СТРОГО» (`suggest.py:2196`).
- **`generate_draft` / `regenerate_draft`** (`suggest.py:2764` / `2788`) — `call_llm` рождает
  текст, затем `postcheck_draft`.

## 3. Второй источник суточной ставки в промпте (утечка сетки)

**`CRITICAL_FACTS`** (`suggest.py:142`, строка `suggest.py:148`):
`… NMAX155 449/3000 …` — прайс-ОРИЕНТИР ДЛЯ МЕНЕДЖЕРА (฿/день, депозит), в промпт **ВСЕГДА**.
Помечен «клиенту цену не называть», но физически даёт LLM суточную ставку `449` даже когда
`_client_price` отдал J-текст без явного `day_price`. `449 × 5 = 2245` берётся отсюда легко.

---

## 4. Пост-чек черновика (последний рубеж) и его дыра

**`postcheck_draft`** (`suggest.py:2689`) → `_pc_classify` (`suggest.py:2635`): детерминированно
клеймит числа-итоги вне белого источника и переписывает сегмент в «уточню».

- Белый источник — `_pc_wl_price_numbers(pricing_note)` (`suggest.py:2586`): ВСЕ числа из блока
  ЦЕНА (включая `449`, `1685`, `3000`). Число `2245` в белый источник НЕ входит → в теории
  должно клеймиться.
- Итог-цена ловится `_PC_PRICE_TOTAL_RE` (`suggest.py:2559`) через `_PC_PERIOD`
  (`suggest.py:2558`): **`за\s+\d… (дн|день|нед|мес|days|weeks|months)`**.

**ДЫРА (почему 2245 дошёл до клиента):** живая фраза «NMAX 155 **на** 5 дней — 2 245 ฿»
использует предлог **«на»**, а `_PC_PERIOD` требует **«за»**. Регэксп не матчит → итог-за-
период не распознан → `2245` (которого нет в белом источнике) проходит мимо гарда. Дополнительно
уязвимы формулировки: разделитель «—» без «за», EN-форма «for 5 days» (в `_PC_PERIOD` нет
«for»), «5 дней — сумма» с обратным порядком.

---

## 5. Где именно числа расходятся с quote (итог разведки)

1. **LLM-пересчёт**: имея в промпте суточную ставку `449` (из `_client_price` `day_price`
   и/или из сетки `CRITICAL_FACTS`) и срок 5 дней, модель считает `449 × 5 = 2245` вместо
   того чтобы взять `total=1685` из quote. Инструкция «не пересчитывать» (`_wrap_single`) —
   мягкая, не гард.
2. **Пост-чек не ловит** этот итог из-за узкого `_PC_PERIOD` («за», без «на»/«—»/«for»).

Наименьшие по объёму точки фикса для следующих шагов #310:
- `_PC_PERIOD` / `_PC_PRICE_TOTAL_RE` (`suggest.py:2558-2562`) — расширить предлоги/разделители
  («на», «—», EN «for»), чтобы любой итог-за-период сверялся с белым источником.
- опц. `_client_price` (`suggest.py:1481`) — не подавать LLM голую суточную ставку рядом с
  period-total, или явно помечать `total` как «итог за весь срок, не умножать».
- опц. golden-тест по ПРАВИЛУ-КЛАССУ CLAUDE.md: дословная фраза провала «NMAX 155 на 5 дней —
  2 245 ฿» (позитив-клейм) + парафразы RU/EN, негатив — корректный `1 685 ฿` из quote.
