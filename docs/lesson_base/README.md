# База обучения клиентского бота — датированные снимки (ШАПКА СНИМКОВ)

**ЭТО СНИМКИ ДЛЯ ВОССТАНОВЛЕНИЯ, А НЕ ВТОРОЙ КАНОН И НЕ ИСТОЧНИК.**
Правила бот читает по-прежнему ИЗ КНИГИ — `manager-bot/docs/playbook.md`
(`suggest.PLAYBOOK_FILE`). Ни один код не читает файлы этой папки и читать не должен:
их единственное назначение — вернуть книгу, если она пропадёт с диска.

**РИСК, КОТОРЫЙ ЗДЕСЬ ГЛАВНЫЙ: хранимая копия отстаёт от оригинала МОЛЧА.** Книга растёт
сама (`suggest.append_playbook_rule` пишет в неё при каждом принятом уроке), снимок — нет.
Снимок с датой позавчера выглядит ровно так же авторитетно, как сегодняшний, и ничто
в системе о расхождении не скажет. Судить о содержании базы обучения — по книге и только
по книге; снимок отвечает на один вопрос — «что было на названную дату».

## Почему шапка здесь, а не внутри файла снимка

Снимок обязан совпадать с оригиналом ПОБАЙТНО, чтобы восстановление было простым
копированием без разбора и вырезания. Шапка внутри файла это ломает дважды: снимок
перестаёт быть побайтной копией, а восстановление копированием впечатало бы служебный
текст в замороженные бизнес-данные. Поэтому шапка живёт отдельным файлом, а payload —
чистый.

## Побайтность и переводы строк

Книга лежит с CRLF, а в репозитории `core.autocrlf=true` — свежий чекаут вернул бы копию
с чужими переводами строк, и «побайтная» она была бы только на словах. Снимки закрыты
правилом `docs/lesson_base/playbook-*.md -text` в `.gitattributes` (седьмой случай того же
класса — там же лежат шесть прежних). Проверять побайтность надо КРУГОМ ЧЕРЕЗ ФИЛЬТР,
а не сравнением хеша блоба с хешем диска:

```
git cat-file --filters HEAD:docs/lesson_base/playbook-2026-09-03.md | sha256sum
sha256sum manager-bot/docs/playbook.md
```

## Зачем снимок вообще заведён

До 03.09.2026 книга правил была ЕДИНСТВЕННОЙ КОПИЕЙ НА ДИСКЕ: путь закрыт правилом игнора
`manager-bot/` (`.gitattributes` ни при чём — см. `.gitignore:22`), во вложенном
репозитории `manager-bot/.git` файл значится неотслеживаемым, `git ls-files` → 0 в обоих.
Потеря файла означала потерю всей выученной базы без следа и без отката.
