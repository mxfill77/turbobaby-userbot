## 2. Адрес приговора, порог и от чего отсчитывается «сердцебиение»

**Кто объявляет заход мёртвым.** `pc_orchestrator.process_stuck_singles`
(`pc_orchestrator.py:5143-5253`), витком `poll_once` (`:5262`). Приговор — две строки:

```
pc_orchestrator.py:5234   if alive is False:
pc_orchestrator.py:5235       detail = (f"СИРОТА: живого исполнителя нет — {why}. …")
pc_orchestrator.py:5242   msg = fail_result(FAIL_HEARTBEAT_TIMEOUT, detail, since=started, now=now)
pc_orchestrator.py:5243   _complete(tid, "failed", msg)
```

**По какому порогу.** Порогов два, и выбирает их вердикт об исполнителе (`:5218`):

| порог | значение | адрес | когда применяется |
|---|---|---|---|
| `PC_ORPHAN_STALE` | **300 с** (5 мин) | `pc_orchestrator.py:222` | вердикт **«ДОКАЗАНО нет исполнителя»** (`alive is False`) |
| `PC_SINGLE_STALE` | **5400 с** (90 мин) | `pc_orchestrator.py:204` | «есть» и **«не знаю»** |
| `TASK_TIMEOUT` (для сверки) | **2700 с** (45 мин) | `pc_orchestrator.py:132` | предел одного прогона |

Ряд 134 упал по первому: лог 20.09 16:58:14 — `stuck-single: id=134 СИРОТА (дочерний процесс
claude (PID 2968) мёртв) in_progress 1946с > 300с → failed`.

**От чего отсчитывается сердцебиение — и есть ли оно вообще.** Возраст берётся здесь:

```
pc_orchestrator.py:5209   age = _age_sec(task.get("updated"), now=now) or 0
```

то есть от поля **`updated` РЯДА ОЧЕРЕДИ** (`_age_sec`, `:1416-1425` — простая разность
`now − updated`), а не от какого-либо сигнала исполнителя. Метку `updated` двигает только запись
в ряд. В демоне существует настоящий пульс ряда — `bc.task_heartbeat(tid)`, — и зовут его **ровно
в одном месте**: `process_lesson_waits`, `pc_orchestrator.py:3755`, и только для ждущих low-уроков
(комментарий там же: «держим `updated` свежим → реапер одиночек не тронет»).

**Следствие, названное числом: идущий заход Штаба не подаёт сердцебиения НИ ОДНОГО РАЗА.** Между
`CLAIM` и `COMPLETE` ряд молчит по построению — до 2700 с прогона плюс хвост. Код провала зовётся
`heartbeat_timeout` («задача перестала подавать признаки жизни», `pc_orchestrator.py:1447`), но
подавать их этой задаче нечем: прибора нет, меряется возраст расписки о взятии.

**Сверка порога с замеренной длительностью живых заходов за сутки.** Корпус — строки
`METRICS … lane=pc` живого `pc_orchestrator.log`, 21 заход (ряды 109, 110, 112, 117, 118, 120–133,
135, 136; у 111 и 134 строки `METRICS` нет — они до неё не дожили):

| величина | число | в минутах |
|---|---|---|
| минимум | 351.8 с (#124) | 5.9 |
| **медиана** | **766.5 с** (#129) | **12.8** |
| **максимум** | **2558.0 с** (#120) | **42.6** |

Сказано прямо числом: **порог сироты 300 с ниже медианы живого захода в 2.56 раза**
(300 / 766.5 = 0.39) и составляет **11.7 %** от максимума. Больше того — **300 с ниже самого
короткого живого захода за сутки** (351.8 с), то есть **21 заход из 21 в любую минуту своей
работы уже старше порога сироты.** Защищает их не порог, а единственное условие выше него —
`_is_running(tid)` (`:5198`). Длинный порог `PC_SINGLE_STALE` = 5400 с, напротив, лежит **в 2.11
раза выше** наблюдённого максимума и живой заход не задевает.

**Что случилось с 134 на самом деле** (последовательность прочитана в `pc_orchestrator.log`):

```

16:46:08  ← артефакт 32207 Б лёг на диск (mtime файла)
16:53:03  watchdog: идёт объявленный заход (1596с из 4500с) — демон работает, не трогаю
16:58:05  watchdog: продукта нет … и процессов демона НЕТ — поднимаю через schtasks
16:58:06  singleton: устаревший лок (PID 22688) — процесса с номером 22688 в системе НЕТ

```

Умер **демон** (PID 22688), и через три секунды после собственного рождения новый демон объявил
сиротой чужую задачу. Причина в одну строку: **`_is_running` — это оперативная память процесса**
(`_RUNNING_TIDS = set()`, `pc_orchestrator.py:2293`; наполняется в `run_task`, `:2942`, чистится
`:2951`). Рестарт демона стирает её начисто — и единственный замок, который держал 300-секундный
порог в стороне от живого захода, исчезает вместе с процессом. Прежний демон умер вместе со своим
ребёнком; новый увидел `in_progress`, не нашёл себя в исполнителях, спросил про PID 2968, получил
«мёртв» — и выдал приговор через **1946 с** при пороге **300 с**, при том что продукт уже двенадцать
минут как лежал на диске.

## 3. Слово «сирота»: что его поднимает — и почему признак негоден

**Адрес.** Слово ставится в `process_stuck_singles:5235` при условии `alive is False`, а сам
`alive` выдаёт `_executor_verdict` (`pc_orchestrator.py:5066-5140`). Значение `False` рождается
ровно в четырёх местах, и все четыре несут один из трёх литералов (`:5056-5058`):

| литерал | адрес возврата | чем поднимается |
|---|---|---|
| `NO_EXEC_NEVER_RAN` «прогон на этом ПК не начинался ни разу (отметки старта нет)» | `:5103` | **в реестре отметок нет ключа задачи** |
| `NO_EXEC_CHILD_DEAD` «дочерний процесс claude (PID {pid}) мёртв» | `:5127`, `:5129` | **проба процесса сказала «мёртв»** (либо номер занят другим запуском) |
| `NO_EXEC_NOT_MINE` «её вёл ЭТОТ процесс демона и уже не ведёт — дочернего claude нет» | `:5137` | метка `proc` в отметке равна метке текущего процесса, а задачи нет в `_RUNNING_TIDS` |

Ряд 134 получил **второй** — `NO_EXEC_CHILD_DEAD`, PID 2968.

**Третий вопрос к признаку: можно ли поднять его, не совершив события?** Событие, которое признак
обязан доказывать, — «исполнитель бросил работу недоделанной». Ответ по каждому:

* **«дочерний процесс claude мёртв»** — поднимается **у каждого без исключения завершённого
  захода**: ребёнок, доделавший работу и вышедший с кодом 0, мёртв ровно так же, как рухнувший.
  За сутки таких смертей **21** (все `METRICS`-заходы), и ни одна из них не есть событие. Признак
  не отличает «умер, не доделав» от «доделал и вышел» ни одним битом — **негоден**.
* **«отметки старта нет»** — поднимается потерей файла, а не событием. Частично прикрыт
  (`_task_started_covers`, `:5101`), но сама дыра названа в коде `:1536`.
* **«её вёл ЭТОТ процесс и уже не ведёт»** — поднимается опустошением множества в памяти.

Общее у всех трёх: **они меряют не судьбу работы, а память и учёт демона.** Чем они становятся
приговором — тоже видно по адресу: разделяет живой заход и сироту единственная строка `:5198`
(`if _is_running(tid): continue`), то есть **переменная в оперативной памяти того самого процесса,
чья смерть и создаёт весь класс.** Наблюдатель здесь живёт на том, за чем следит, — прямое
нарушение правила 4 слоя ожиданий (`CLAUDE.md`, О1–О4).

**Продукт при этом виден коду — и приговора не касается.** `fail_result`
(`pc_orchestrator.py:1929-1978`) СОБИРАЕТ улики работы и ставит их в текст итога: заголовок
«НЕ ЗАКРЫТА, но В ОКНЕ ЗАДАЧИ ЕСТЬ РАБОТА». Но собирает он ровно два вида улик —
`_git_commits_between` и `_journal_writes_between` (`_work_evidence`, `:1888-1903`), —
и **рабочего дерева не смотрит ни одной строкой**. У 134 весь продукт был именно там:
артефакт и четыре файла кода, ни один не закоммичен. Поэтому итог получился внутренне
противоречивым — «есть работа» рядом с «коммитов 0», — а на исход ряда улики не влияют вовсе:
`_complete(tid, "failed", msg)` уже решён строкой выше, улики меняют только ТЕКСТ.

## 4. Что считает серия: по какому полю ряд попадает в зачёт и по какому рвёт череду

**Счёт живёт в `contour_digest.series` (`contour_digest.py:919-1023`).** (Модуль `series_pc.py`
даёт ему только признак служебного корня, `:980`; собственный файл счёта
`series_pc.state.json` мёртв с 17.08 — `chains: 0`, `streak: 0`.)

**Попадает в зачёт — `is_clean` (`contour_digest.py:907-916`), два условия И:**

```
contour_digest.py:915   return (is_closed_done(one.get("outcome"))
contour_digest.py:916           and judged_of(one.get("id"), judged, goal=one.get("goal")) == JUDGE_PROVED)
```

* **поле `outcome` ряда очереди** — `is_closed_done` (`:788-802`) спрашивает **ровно одно слово**:
  `return outcome == "done"`;
* **вердикт судьи закрытия** — `judged_of` (`:846-867`) по имени `ключ#номер` в реестре
  `tmp/done_judge_pc/judged.json`; `proved is True` → `JUDGE_PROVED`.

**Рвёт череду — обход хвоста (`contour_digest.py:1003-1013`):**

```
contour_digest.py:1004   for row in reversed(window):
contour_digest.py:1005       if is_unknown(row):  continue      # outcome == OUT_UNKNOWN
contour_digest.py:1007       if is_unsure(row):   continue      # outcome is None
contour_digest.py:1009       if not is_clean(row, judged): break
contour_digest.py:1011       streak += 1
```

Льгот ровно две, и обе спрашивают то же поле `outcome`: `is_unknown` — слово судьи
(`:870-883`), `is_unsure` — **отсутствие значения**, `outcome is None` (`:886-904`).

**Ответ на прямой вопрос п.4 — адресом, а не рассуждением.** Заход с готовым продуктом по
названному адресу, закрытый провалом, **череду РВЁТ**. Цепочка адресов:

1. `_complete(tid, "failed", msg)` — `pc_orchestrator.py:5243` — кладёт в ряд слово `failed`;
2. `is_closed_done("failed")` → `False` — `contour_digest.py:802`;
3. `is_unknown` → False (слово есть и оно не `OUT_UNKNOWN`), `is_unsure` → False
   (`outcome` не `None`) — обе льготы мимо;
4. `if not is_clean(row, judged): break` — `contour_digest.py:1009-1010` — **обрыв**.

Это написано и прозой, в докстринге самой льготы (`contour_digest.py:900-902`):
«ГРАНИЦА НАЗВАНА: „не сверен“ — это НЕ „упало без причины“. Упавший ряд несёт слово `failed`,
поставленное ПРОЧИТАННЫМ ответом очереди, и **остаётся обрывом**.»

**Ни один из четырёх адресов продукта не спрашивает.** Ни файл по адресу результата, ни рабочее
дерево, ни размер, ни первая строка артефакта в счёт серии не входят: единственный вход продукта
в этот счёт — через `judged`, а судья закрытия зовётся **только на пути `done`**
(строки `V0-DONE id=…` в логе стоят рядом с `COMPLETE … status=done`). Ряд, закрытый провалом,
судье не показывают вовсе — и в реестре его нет: `68v.2009#134` → **`None`** (замер реестра, 266 записей).
У ряда 134, таким образом, **оба условия `is_clean` ложны сразу**, и второе — необратимо.

## 5. Цена за сутки числом

Корпус тот же: 23 закрытых ряда слепка, вердикты — реестр судьи (`tmp/done_judge_pc/judged.json`,
266 записей). Имя ряда поднимается `row_name` = `ключ#номер` (`contour_digest.py:814-843`).

**Разбор 23 рядов:** зачтённых (`done` + `proved`) — **16**; обрывов — **7**; неизвестных — 0;
несверенных — 0 (16 + 7 = 23, сходится).

Семь обрывов по причинам — и класс разбора виден сразу:

| ряд | почему обрыв | это разбираемый класс? |
|---|---|---|
| #109 | `done`, но судья: `addressed: False` → «адрес результата не назван задачей» (`JUDGE_BLIND`) | нет |
| #110 | `done`, записи судьи нет → `JUDGE_SILENT` | нет |
| #111 | `failed` (`heartbeat_timeout`, работы не было) | нет |
| #112 | `failed` (`unbacked_red`, продукт в git) | нет |
| #126 | `done`, записи судьи нет → `JUDGE_SILENT` | нет |
| **#134** | **`failed` (`heartbeat_timeout` · СИРОТА, продукт целиком на диске)** | **ДА** |
| #136 | `failed` (`unbacked_red`, продукт в git) | нет |

**Ход серии по суткам, посчитанный обходом `contour_digest.series` по прочитанным полям:**

```
109 обрыв → 0      117 →1  118 →2  120 →3  121 →4  122 →5  123 →6  124 →7  125 →8
110 обрыв → 0      126 обрыв → 0
111 обрыв → 0      127 →1  128 →2  129 →3  130 →4  131 →5  132 →6  133 →7   ← СЕМЬ
112 обрыв → 0      134 обрыв → 0
                   135 →1                                                   ← ОДИН
                   136 обрыв → 0                                            ← сейчас
```

Число премисы «упала с семи до одного» **воспроизведено расчётом**, а не принято на слово:
133 замкнул седьмую, 134 обнулил, 135 отсчитал первую. На момент этого захода серия уже **0** —
её добил 136 (другой класс).

**Потеряно на разбираемом классе за сутки:**

* **зачётных цепочек — 1** (сам ряд 134: продукт по адресу есть, в зачёт не вошёл и войти уже не
  может — судья его не судил, записи в реестре нет);
* **накопленных подряд — 7** (череда 127→133 обнулена);
* **показание серии на момент замера Штаба — 1 вместо 9**, то есть **минус 8**.

**Какой была бы серия без класса** (тот же обход, единственное изменение — 134 считается чистым):
133 → 7, 134 → 8, 135 → **9**, далее 136 обрывает по своей причине → 0. То есть к минуте, когда
Штаб смотрел на витрину, стояло бы **9**, а стояло **1**.

**Допущение названо, а не спрятано:** «134 считался бы чистым» требует, чтобы судья закрытия его
ДОКАЗАЛ. Прочитано: артефакт лежит по названному адресу, первой строкой несёт слова адреса, и у
всех 16 соседних рядов суток судья выдал `proved: True`. Не прочитано: собственного вердикта по
134 не существует и существовать не может — на пути `failed` судья не зовётся. Поэтому **«минус 8»
есть вывод при названном допущении, а «минус 1 зачётная цепочка» и «семь обнулены» — прочитанное.**

Отдельным числом, потому что оно меняет вес класса: за сутки провалов 4, и лишь **1 из 4**
(25 %) — разбираемый класс. Остальные три серию рвут тоже, но по другим причинам: два
`unbacked_red` (законная остановка на красном) и один без работы вовсе.
