и «приход был, продукт не родился». Здесь различитель **есть**, поэтому источник называет состояние
ПОЛОЖИТЕЛЬНО — «собрано, дальше не ушло» — и честный исход **НЕ ПРОШЛО**, то есть отказ, а не
неизвестность. Вердикт задачи 33 подтвердился в работе, а не на слово.

### §5. Почему пункт 5 провален — два независимых факта

**5а. Неполный результат выглядит честной бронью.** На самой корневой строке:

```
полей, которые build_intake умеет выдать : 7  [Клиент, Модель, Даты, Контакт, Доставка, Шлемы, Депозит]
из них ПОПАЛО в пост                     : 4  [Клиент, Модель, Даты, Контакт]
из них НЕ попало                         : 3  [Доставка, Шлемы, Депозит]
хвост «❗ Не хватает» сказал              : 'точка (гео/Maps); фото паспорта (…)'
НЕ попало И НЕ названо в хвосте          : 3  [Доставка, Шлемы, Депозит]
```

Это не свойство фикстуры, а устройство кода: хвост «❗ Не хватает» строится из
`suggest.collected_facts` и умеет называть **РОВНО два факта — `geo` и `passport`**
(`booking_draft.py:578-595`). Остальные пять видов пропажи он не покрывает **ни одной веткой**.
Наружу уходит карточка, у которой отсутствие поля неотличимо от «поля и не требовалось».
Это ровно провал **E2.6**, объявленный артефактом сценариев предметом экзамена, — воспроизведён живьём.

**5б. Два одинаковых нуля поллера (S6).**

```
очередь пуста, всё разобрано              → poll_and_post_intake вернул 0
источник МЁРТВ (ветка suggest.py:6939-6942) → вернул 0
различимы ли эти два исхода по возврату?  → False
```

«Нечего постить» и «источник недоступен» дают **один и тот же** наблюдаемый ноль. Различие живёт
только строкой лога; **в источнике истины следа нет**.

## 6. ШАГ 3 — ОДИН СЛОМ. **ЭКЗАМЕН ПРОВАЛЕН**

Сломан **ровно один** переход — тот, что помечает исход поста (`suggest.py:6963-6964`). Ветка
боевая, не инъекция: при `poster=None` идёт `sent = await client.send_message(...)`, затем
`mid = getattr(sent, "id", None)`. Транспорт ответил **без ошибки** объектом без атрибута `.id` —
это «результат пуст при внешне успешном шаге».

**Дословное чтение источника ДО и ПОСЛЕ:**

```
ДО:     id=11 | status=pending | posted_msg_id=NULL | reason=NULL | client_id=990000003 |
              created_ts=2026-08-15T17:41:34.215825+00:00 | updated_ts=2026-08-15T17:41:34.224342+00:00
ПОСЛЕ:  id=11 | status=posted  | posted_msg_id=NULL | reason=NULL | client_id=990000003 |
              created_ts=2026-08-15T17:41:34.215825+00:00 | updated_ts=2026-08-15T17:41:34.234856+00:00
```

**Что сделал оркестратор:**

| наблюдение | значение |
|---|---|
| `send_message` отработал без ошибки, вызовов | 1 |
| возврат поллера («обработано») | **1** — засчитал как УСПЕХ |
| `status` в источнике истины | **`posted`** |
| `posted_msg_id` | **NULL** — продукта нет |
| `reason` | **NULL** — причина не названа |
| **следующий шаг цепочки** (пересылка фото паспорта) стартовал | **ДА** (+1 вызов `photo_finder`) |

**Сказано прямо: ОРКЕСТРАТОР ПРОДОЛЖИЛ КАК НИ В ЧЁМ НЕ БЫВАЛО — это ОТКАЗ ЭКЗАМЕНА.** Пустой
результат записан как успех, причина не названа, счётчик «обработано» вырос, и следующий шаг
цепочки стартовал, хотя карточки, за которой он должен слать фото, не существует.

Прибор при этом сработал верно: **НЕ ПРОШЛО**, «ложный зелёный (S10): `status='posted'` при
`posted_msg_id IS NULL`». То есть **прибор видит то, чего не видит оркестратор** — различитель
годен, а вот сам конвейер на этом переходе слеп.

**Историческая поправка, чтобы не завысить тревогу:** по замеру задачи 33 на боевом корпусе форма
`status='posted' AND posted_msg_id IS NULL` встречалась **0 раз** из 2 живых заявок. Ветка кода
реальна и достижима, но живых случаев на этой полосе пока не было.

## 7. Ошибка ПРОВЕРЯЮЩЕГО, найденная и исправленная по ходу (называется честно)

Первый прогон подал в `build_intake` фикстуру парка в виде **длинных имён листа**
(`"VULCAN 650CC S PHUKET 5065"`) и получил на пункте 5а обвинение: «модель была в экстракции, в
пост не попала». Контроль показал, что обвинение родилось **из моего мока**, а не из конвейера:

```
живой park_allowlist_status(имена листа) → ['NMAX 155','XMAX 300','ADV 350', … ,'VULCAN 650S','CLICK 125']
```

то есть боевой allowlist — это **КОРОТКИЕ канонические имена `KNOWN_MODELS`**, а не имена листа
(`suggest.py:575`: `allow = [disp for disp, key in KNOWN_MODELS if any(key in k for k in keys)]`).
Формат мока разошёлся с форматом источника — ровно тот класс, который правило полосы запрещает,
и проверяющий нарушил его сам.

**Как исправлено:** фикстура больше не пишется руками — она **получается из боевого кода**
(`PARK = suggest.park_allowlist_status(getter=lambda: SHEET_NAMES)[0]`), прогон повторён целиком.
Пункт 5а переформулирован на утверждение, **не зависящее от фикстуры** (7 полей против хвоста из
2 фактов), и остался провальным уже по существу. Исходы шести пунктов между прогонами не
изменились. Оба вывода сохранены: `exam_booking_run_output.txt` (прогон 1, кривая фикстура) и
`exam_booking_run_output_pass2.txt` (прогон 2, верная).
