### Чего находка НЕ учитывает — три вещи, каждая проверяема

**(а) Напечатанное число берётся из ЭФФЕКТИВНОГО интервала, а не из константы.** Опасность, ради
которой канал предлагает «один источник», на дороге демона уже закрыта: `contour_digest.py:677` и
`:725` печатают `interval_words(report.get("interval", INTERVAL_SEC))`, а `report["interval"]`
кладёт раннер из ПЕРЕДАННОГО значения (`contour_digest_run.py:479`), которое демон берёт из
ручки (`pc_orchestrator.py:9627` `interval=CONTOUR_DIGEST_SEC`). Константа здесь — только
`.get`-подпорка. **Правка `CONTOUR_DIGEST_SEC=7200` меняет и окно, и напечатанное число разом;
разойтись им на дороге демона нечем.**

**(б) Есть ЧЕТВЁРТОЕ место, и вот оно расходится по-настоящему.** CLI раннера объявляет
`--interval` с дефолтом `cd.INTERVAL_SEC` (`contour_digest_run.py:566-567`) и **ручку
`CONTOUR_DIGEST_SEC` не читает вовсе**. Значит при выставленной ручке ручной `--dry`/`--status`
покажет «интервал 4 ч», пока демон живёт по другому окну, а ручной `--send` будет троттлиться по
чужому числу (`contour_digest_run.py:520`). Канал этого места не назвал — а именно оно и есть
живое расхождение. Это довод ЗА направление находки, но по другой причине, чем она приводит.

**(в) «Один источник в раннере» упирается в замок чистоты.** Инвариант `CONTOUR_DIGEST_PURE`
(`test_contour_digest.py:60-74`, обход AST) запрещает чистому модулю часы/диск/сеть/`getenv`.
Поэтому «значение, полученное из `CONTOUR_DIGEST_SEC`» физически не может жить в
`contour_digest.py`, а `interval_words(sec=INTERVAL_SEC)` (`:266`) и обе `.get`-подпорки требуют
какого-то дефолта. Дешёвая форма правки поэтому не «убрать константу», а **перевернуть
направление**: дефолт `os.getenv("CONTOUR_DIGEST_SEC", cd.INTERVAL_SEC)` завести в РАННЕРЕ (руки,
env им не запрещён), демону передавать его же, а текстовую скрепку в тесте заменить на сверку
ЗНАЧЕНИЙ. Литерал тогда останется ровно один — в чистой логике.

## 3. Пункт 2 — посылка ЛОЖНА: `--dry` не показывает того, что показывает `--status`

Канал: «`--dry` уже обязан показать то, что сводка видит и сформирует».

**Замер кода говорит обратное.** `--dry` идёт через `tick(force=True)` → `cd.render()`, а `render`
на СПОКОЙНОМ контуре схлопывает тело в одну фразу и разделы не печатает вовсе
(`contour_digest.py:680-682`, закон 4 «спокойно — это одна строка»). `--status` печатает каждую
тему, у которой есть строки (`contour_digest_run.py:574-584`). **На спокойном контуре — а он и
есть проектный дефолт этой сводки — `--dry` показывает ОДНУ строку тела, `--status` показывает
все темы.** Это не дубль команды, а разные вопросы: «что уйдёт владельцу» против «что источники
сейчас говорят».

Второе, что канал не учёл: у `render` есть ветка `raise AssertionError` при теме без строк
(`contour_digest.py:689`). То есть `--dry` может УПАСТЬ ровно тогда, когда владельцу нужнее всего
посмотреть, что видно источникам, — а `--status` в этом случае отработает.

Честная половина в пользу канала: побочного действия у `--dry` действительно нет — метка окна
двигается ТОЛЬКО при удавшейся отправке (`contour_digest_run.py:537-541`), так что довод «убрать
ручку ради безопасности» не нужен и не заявлялся. Потребителей `--status` вне самой команды в
git-дереве **0** (З3) — сам этот вопрос канал честно оставил в «неизвестно», и разведка отвечает:
по дереву ноль, **вне дерева (руки владельца, планировщик) — НЕИЗВЕСТНО, не проверяли**.

## 4. Пункт 3 — посылка ЛОЖНА: у расписки одноимённое поле, но ДРУГОЙ предикат

Канал предлагает вместо трёх меток читать «один уже существующий структурированный источник —
например, расписки цепочек». В расписке действительно есть поле с подходящим именем:
`"operational_change": true` (видно прямо в выдержке пакета).

**Это ловушка одного слова.** Два предиката спрашивают разное:

| | `contour_digest.changes_state` (`contour_digest.py:476-483`) | `review_auto.operational_change` (`review_auto.py:210-223`) |
|---|---|---|
| вопрос | это строка, которую контур поставил СЕБЕ ради чтения? | объявленный в отчёте коммит НАШЁЛСЯ в дереве? |
| вход | текст корня строки очереди | `claimed` / `verified` списки коммитов |
| исходы | 2 (метка есть / нет) | 3 (`commit_verified` / `commit_unverified` / `no_commit_claimed`) |

Следствие проверяемо на этой самой задаче: **строка разведки `[разведка …]`, которая пишет
артефакт и коммитит его, получит в расписке `operational_change: true` (коммит подтверждён), а
`changes_state()` честно скажет `False` — она читала.** Подстановка «структурированного» поля
перевернула бы счёт «меняли состояние N» ровно на тех строках, ради исключения которых признак и
заводился. Ошибка была бы МОЛЧАЛИВОЙ: оба поля булевы, оба называются одинаково.

Второе, чего канал не учёл: метки **не набраны литералами**, а ВЫВЕДЕНЫ из модулей-владельцев
(`contour_digest.py:467-473` возвращает `review_intake.CLAIM_MARK`, `recon_auto.TASK_MARK`,
`recon_auto.ASK_MARK`). Связанность с «внутренним форматом чужих читающих строк», которой канал
опасается, здесь уже разорвана: правка метки в модуле-владельце едет сюда сама, расхождения двух
экземпляров не бывает по построению.

Третье: расписка пишется только для исходов `done`/`failed` (`review_auto.py:79`
`REPORTED = {"done": …, "failed": …}`), и её 14 полей не несут ни ожиданий, ни красного, ни осей —
то есть источником для ОСТАЛЬНЫХ тем сводки она быть не может. Канал сам пометил это «неизвестно»;
разведка отвечает: **не может**. Объёма при этом хватает (42 расписки на диске против серии 30,
З6) — этот встречный довод снят как неверный.
