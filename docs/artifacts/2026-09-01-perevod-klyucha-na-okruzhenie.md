## 1. Каким путём ЖИВЫЕ userbot и moderbot получают ключ

Из трёх исходов задания — **ОКРУЖЕНИЕ** (наполняется файлом `.env` через `load_dotenv`),
а на фактически исполняемом маршруте генерации — **не используют вовсе**.

### 1.1 Литерал исключён, и не «сейчас», а исторически

| проба | результат |
|---|---|
| `git log -S 'sk-ant' -- suggest.py` | **0 коммитов** |
| откуда взялась строка чтения | `d9e719b` — первый коммит, вносивший LLM-путь suggest |
| `Anthropic(` в трекаемом коде | `suggest.py:5506`, `collect_booking.py:128` — обе с переменной, не с литералом |

Ни одна версия трекаемого `suggest.py` литерала не держала. Поэтому **возраст живого процесса
здесь не важен**: сколь угодно старая его версия всё равно читала `os.getenv`.

### 1.2 Единственный источник в коде

```
suggest.py:232   ANTHROPIC_API_KEY = os.getenv("ANTHROPIC_API_KEY", "").strip()
```

Наполняется он до импорта, обоими детьми одинаково:

```
userbot_listen.py:34,38,42   from dotenv import load_dotenv / load_dotenv() / import suggest
moderation_bot.py:27,29,31   from dotenv import load_dotenv / load_dotenv() / import suggest
                             # комментарий в коде: «после load_dotenv — читает конфиг из окружения»
```

Ни `userbot_listen.py`, ни `moderation_bot.py`, ни `moderation_core.py` имени
`ANTHROPIC_API_KEY` не содержат вовсе — ключ они видят **только** через `suggest`.

**Важная поправка к слову «окружение»:** процессы стартуют с чистым env, а значение в
`os.environ` кладёт `load_dotenv()` из файла `.env` репо. То есть механизм — окружение,
а **хранилище — файл**. Для отзыва ключа это и есть адрес.

### 1.3 На боевом маршруте ключ не используется вовсе

Ветку выбирает флаг, тоже из окружения:

```
suggest.py:5496   return _cli_llm if SUGGEST_LLM_VIA_CLI else _default_llm     # generate_draft
moderation_core.py:33   fn = suggest._cli_llm if suggest.SUGGEST_LLM_VIA_CLI else suggest._default_llm
moderation_bot.py:394   llm = suggest.default_llm_caller()
```

`_cli_llm` (`suggest.py:5712`) идёт через `claude` CLI по подписке Max и **вычищает ключ**:

```
suggest.py:5724   env.pop("ANTHROPIC_API_KEY", None)   # ← ключ НЕ утекает: CLI идёт по подписке Max
suggest.py:5725   env.pop("OPENAI_API_KEY", None)
```

Живое подтверждение маршрута (строку `SUGGEST: голова=` печатает **только** `_cli_llm`,
`suggest.py:5744`):

| проба по `logs/userbot_stderr.log` (86 838 строк, append через все рестарты) | число |
|---|---|
| `SUGGEST: голова=…` | **63** |
| `credit balance` / `authentication_error` / `invalid x-api-key` | **0** |

То есть каждая наблюдаемая генерация клиентского контура шла CLI-маршрутом, и ни разу —
платным ключом.

### 1.4 Что здесь ЧЕСТНО неизвестно

- **Текущий процесс ещё ни разу не генерировал.** Живой userbot поднят

(`pc_orchestrator.py:2335-2338`):

```

```

**Три оговорки, каждая — готовый ложный шаг:**

1. **Рычаг выкатывает ТЕКУЩИЙ HEAD, а не 768729b.** HEAD сейчас `3b1143d`, над S1 стоят ещё

2. **«рестартни userbot» ≠ «выкати».** Рычаг рестарта (`pc_orchestrator.py:2327-2328`) поднимает
   бота прямо сейчас **мимо всех проверок**; «выкати» — это основание, после которого применение
   идёт штатным путём со всеми гейтами (`pc_orchestrator.py:2331-2333`).
3. **Выигрыш от выкатки по ключу — ноль.** Путь ключа у детей уже окружение (п.1), а
   `_default_llm` на боевом маршруте не вызывается вовсе. S1 добавляет страховку на случай,
   если флаг CLI когда-нибудь снимут.

## 5. Подготовка безопасного отзыва старого ключа

Отзыв — это правка `.env`, красная операция; здесь только подготовка адресов.

  выбрасывает. После S1 даже случайный уход в `_default_llm` даёт понятную ошибку без значения,
  а не `credit balance too low` из недр SDK;

  пропущена)», сама не упадёт.

**Файлы, где значение ключа может лежать** (имена, без чтения; получено `grep -rl` по образцу

## 8. Что владельцу делать — и это НЕ красная операция

Ключ №1 берётся ОДНОЙ штатной задачей в полосу `pc`, весь текст которой — команда:

```
выкати
```

Путь по коду: `pc_orchestrator.py:3117` `_match_command` → `:2335` `_CMD_RELEASE` →
`:2405` `_exec_release_client` → `client_contour.approve(HEAD)`. Ни `taskkill`, ни
`schtasks`, ни правки `.env` — обычная задача очереди. Три оговорки:

1. **Выкатится HEAD, а не 768729b.** Над S1 сейчас стоят ещё **восемь** коммитов

   диска ЦЕЛИКОМ, поэтому и одобряется коммит, а не файл.
2. **«рестартни userbot» ≠ «выкати».** Первое поднимает бота прямо сейчас мимо всех проверок
   (`pc_orchestrator.py:2331-2333`), второе — основание, после которого применение идёт со
   всеми гейтами.
3. **Запрет грязного дерева выкатке сейчас не мешает:** трекаемой грязи ровно две строки —
   `CLAUDE.md` и `todo.md`, и ни один из этих файлов не входит в карту
   `_FILE_PROCESS_RULES` (`pc_orchestrator.py:5650`), по которой считается грязь бота.

**Но есть препятствие, которого не было видно первому заходу — см. §10: `test_suggest` красен.**

## 9. ЧТО ДОБАВЛЕНО КОДОМ: второе доказательство, которого S1 не принёс

ТЗ `docs/tasks/s1-suggest-secret-containment.md` §3.4 требовало **двух** доказательств:

1. отсутствие ключа даёт value-free fail-fast до провайдера — S1 это принёс;
2. «`suggest.py` contains no hard-coded secret-like literal» — **S1 этого не принёс**.

Почему второе не роскошь: существующий `test_anthropic_key_is_read_only_from_environment`
сверяет ЗНАЧЕНИЕ в рантайме и потому проходит даже у кода вида
`os.getenv(...) or "<литерал>"` — при заполненном окружении обе ветки дают одно и то же.
Инвариант «источник только окружение» проверяем **по тексту файла**:

```
test_suggest.TestSuggestCredentialContainment
  test_suggest_source_holds_no_secret_like_literal   — детектор собран из кусков (ТЗ §3.5),
                                                       непрерывного образца в тексте теста нет
  test_key_binding_in_source_is_environment_only     — привязка ANTHROPIC_API_KEY в файле
                                                       ровно одна и ровно os.getenv(...)
```

Прогон: `python -m unittest test_suggest.TestSuggestCredentialContainment -v` → **Ran 4 tests, OK**.

**Отрицательная проба** (правило полосы: тест обязан доказать, что кусается) — `tmp/verify_s1_neg.py`,
мутирует ТЕКСТ в памяти, боевой `suggest.py` не трогает:

```
детектор секрета на живом файле: []
детектор секрета на мутации `or "<секрет>"`: 1 совпад.
привязка на мутации `open("key.txt").read()`: отличается от живой
ИТОГ: инварианты КУСАЮТСЯ
```

## 10. ПОБОЧНАЯ НАХОДКА: `test_suggest` красен на main — и это гейт выкатки

Полный прогон ТЗ-командой `python -m unittest test_suggest`:

```
Ran 637 tests … FAILED (failures=5)
```

Все пять — в `TestRunLiveSmoke`, и это **НЕ вклад этого захода**: доказано прогоном копии
`test_suggest.py`, снятой с HEAD (`git show HEAD:test_suggest.py`) — те же 5 падений без
единой моей строки.

Причина одна на все пять — **фикстура протухла по дате**. Ожидание голдена
`2400 ฿ за 5 дней (Скидка за срок 15%, 480 ฿ в день)`, факт —
`307 ฿/день; итого 1535 ฿` и приписка «Названная дата уже прошла — подскажите актуальные»;
в диффе смоука видно пробу `NMAX 155 2026-08-…`. Даты фикстуры остались в августе, сегодня
01.09 — код честно ушёл на другую ветку расчёта, а голден остался на старой.

Почему это важно именно здесь: `test_suggest` — ровно тот модуль, которым гейтится любая
правка `suggest.py` перед рестартом ботов (`_affected_test_modules` → `_gate_test_modules`,
`pc_orchestrator.py:6143`). Пока фикстура не поправлена, путь авто-применения после дев-задачи
даст «код запушен, рестарт отложен: тесты красные». Правку голдена этот заход **не делал**:
это денежный путь (скидка за срок), трогать его мимо владельца нельзя.
