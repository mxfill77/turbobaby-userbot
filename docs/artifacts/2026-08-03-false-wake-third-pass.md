## 2. Чем мерить сон

Подтверждаю прошлые заходы своим замером. **`kernel32.QueryUnbiasedInterruptTime`** — несмещённые
часы прерываний, в S3/гибернации не тикают; `time.monotonic()` на Windows = `GetTickCount64`,
смещённые, проспанное в них есть. Разница двух часов и есть сон числом.

```
GetTickCount64             = 360 019,0 c
QueryUnbiasedInterruptTime = 327 734,4 c
разница                    =  32 284,6 c
```

Сверка с журналом Windows: с загрузки (30.07 01:17:00) в аптайм попадает **только** сон 30.07,
32 286 с ⇒ **расхождение 1,4 с**. Сон 26.07 (11 511 с) в счётчики не входит — он до этой загрузки.
*(Честно: в первом прогоне я сложил оба сна и получил «расхождение 11 512 с». Ошибка моя,
арифметическая, а не источника; исправлена сверкой с `LastBootUpTime`.)*

Спутать с залипанием сети **невозможно по конструкции**, а не по порогу: висящий сокет жжёт
несмещённые часы ровно так же, как настенные, — разница остаётся 0.

Источник **уже в файле**: `awake_monotonic()` — `pc_orchestrator.py:1067`, `slept` считается на
строке **6785**. Но решение принимает `_woke_from_sleep` (**5513**, зовётся с **6779**) по
`(now-prev) > POLL_SEC + WAKE_JUMP_MARGIN`, и часов бодрствования оно не видит: правильный
инструмент лежит на две строки НИЖЕ неправильного решения.

Внешний журнал — только постфактум. **`Kernel-Power 107` для момента пробуждения непригоден**:
в моём же запросе он отстоит от 42 на **1 с** при сне 8 ч 58 м. Годно: **42** — когда машина
уходила в сон; **Power-Troubleshooter id=1** — интервал целиком.

## 4. Две мины, на которых я поймал себя (для следующего захода)

1. **Формулировка строки лога сменилась ПОСЕРЕДИНЕ окна.** Подъёмы вотчдога до 31.07 пишутся как
   `МЁРТВ (смерть 1/3, лог 182с назад)`, после — `МЁРТВ (лежал 435с, смерть 1/3)`. Мой первый греп
   по `МЁРТВ (лежал` дал **2** подъёма вместо **4** — и это выглядело как расхождение с прошлым
   заходом, хотя прошлый заход был прав. Живой экземпляр класса «grep по одному шаблону врёт»:
   в окне, где менялся код, шаблон обязан быть по инварианту (`МЁРТВ`), а не по нынешней фразе.
   Настоящие подъёмы в окне: 30.07 01:20:08 moderation_bot · 31.07 12:58:42 pc_agent (лежал 1103 с)
   · 31.07 15:13:05 userbot (435 с) · 31.07 15:33:36 userbot (**1229 с** при проектных 300 с).
2. **Разбивка «холостой виток / работа» зависит от набора признаков, а доля лжи — нет.**
   Узкий набор (`CLAIM/RUN/STEP/COMPLETE/шаг`) даёт **585 / 88**, широкий (плюс
   `id=/задача/гейт/коммит/claude`) — **522 / 151**. Цифру 87 % холостых надо приводить вместе с
   набором признаков, иначе она необоснованно точная. На вывод это не влияет: сном не является
   ни один вариант — у 320 из 321 измеренных строк стоит `из них сна 0с`.

`??` до проверки грязи. Строки «рабочая копия грязная» в отрезках скачка — про tracked-правки.
