## §3 Почему цепочки разные — четыре независимых основания

1. **В задаче ровно одно действие.** `pc_remote_control.task.xml` (шаблон TurboBabyRC) содержит
   один `<Exec>`: `wscript.exe //B //Nologo rc_remote_control.vbs`. Ни pc_agent, ни оркестратора
   в её `<Actions>` нет.
2. **У pc_agent СВОЯ задача Планировщика.** `pc_agent.py`: `TASK_NAME = "pc_agent"`, само-рестарт
   идёт через `schtasks /Run /TN pc_agent` (строки 501–520). Это другое имя задачи.
3. **Разошлись по времени ЖИВЫМ фактом.** pc_agent перезапущен в 19:53:11, оркестратор — в
   21:23:56, а супервизор всё это время жив с 01:17:19. Будь они одной задачей, рестарт увёл бы
   всех троих. Совпадение «все трое в одну минуту» из формулировки задачи — это общий
   `<LogonTrigger>` трёх РАЗНЫХ задач в 01:17, а не одна задача; PID 9376/16792 из формулировки
   уже мертвы (текущие — 6612 и 19208).
4. **Исполнитель висит не на той ветке.** PID 4204 (эта сессия) — ребёнок 19208
   (pc_orchestrator), а не 9232/11168. Планировщик гасит только дерево действия своей задачи.

## §7 Как проверить после рестарта (порог в памяти, а не в файле)

1. Новый PID супервизора + строка `супервизор стартовал (pid=…)` в `rc_remote_control.log`.
2. `venv\Scripts\python.exe -c "import rc_supervisor as s; print(s.NAMED_SPEC['max_age'])"` → 43200.
   Модуль читает константы ОДИН раз на импорте, hot-reload в CPython нет ⇒ процесс, стартовавший
   после последней правки файла, держит в памяти ровно это число.
3. Решающее — поведение: канал обязан пережить 1290-ю секунду. Старый код гасил там
   детерминированно (333 жизни из 359). Живой канал возрастом ≥ 1400с при тех же 0 соединений и
   протухшем логе иначе как порогом в памяти не объясняется.
4. Если снос всё же случится — новая строка НАЗОВЁТ порог числом (`> порога 43200с`), и это
   тоже отчёт процесса о своей памяти.

**Видно будет через ~22 минуты** после рестарта (1290с + один тик 30с). Полная тишина ветки
`named-channel` в логе за это окно = фикс в силе.
