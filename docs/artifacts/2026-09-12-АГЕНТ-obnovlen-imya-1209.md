## 2. Имя бота — первым и дешёвым действием (пункт 3)

Имя ЧТЕНИЕМ КОДА не узнаётся вовсе: в репозитории лежит только имя ПЕРЕМЕННОЙ с токеном
(`AGENT_BOT_TOKEN`), а @-имя и номер живут на стороне Telegram и меняются владельцем бота без
единой правки здесь. Догадка по имени переменной именем не является, а владельцу имя нужно ровно
затем, чтобы **добавить бота в группу**, — промах здесь стоит добавления ЧУЖОГО бота.

Штатной двери `getMe` в полосе не было ни одной — заведена:

```
venv\Scripts\python.exe dispatch_notify.py --whoami
✅ бот отправки агента: @turbobaby_pcagent_bot «TurboBaby PC Agent» id=8939023481
```

**Куда её положить — решал не вкус.** Дверь живёт в `dispatch_notify.py` по двум причинам,
каждая проверяемая: замок 1 этого модуля (05.09) пускает в сеть **только боевые точки входа в
корне репозитория**, то есть проба из `tmp/` молча получила бы отказ вместо имени; и токен читает
ровно этот модуль — отдельный скрипт был бы ВТОРЫМ местом, где секрет может утечь.

**Токен не печатается ни одной веткой**, и это не обещание, а код: всё, что уходит наружу,
проходит `_scrub_token` — он вычищает ЗНАЧЕНИЕ токена из строки, даже если чужой ответ вернёт его
в описании ошибки. Отдельный отрицательный тест подставляет заведомо не-секретное значение и
проверяет, что в ответе двери его нет. Telegram сегодня токена в описании не повторяет, но
«сегодня не повторяет» гарантией не является, а цена промаха односторонняя: секрет, раз попавший в
отчёт владельца, оттуда не вынимается.

Отдельно отмечено словами: `getMe` — вызов **самому себе**. Наружу не ушло ни одного сообщения,
ни один чат и ни один участник следа не увидел; набор сторожит это отдельной проверкой
(`test_nothing_is_sent_on_any_path`: метод ровно один и это `getMe`).

**Что владельцу делать с этим именем.** В группу «Тренеровка» (`-5193185299`) добавлять надо
именно `@turbobaby_pcagent_bot` — это тот самый бот, чьим токеном уедет карточка кейса и чей
процесс поймает тап. Членство сегодня НЕ перемерялось: задание разрешило ровно одну служебную
пробу **самому себе**, а `getChat` по группе — проба про чужой чат. На 11.09 бота в группе не было.

## 3. Чем поднять обратно — записано ДО всего остального (пункт 4)

Дверь владельца — единственный путь его команд к машине, поэтому способ возврата назван раньше
любого действия и снят с ЖИВОГО процесса, а не из головы:

| что | значение |
|---|---|
| дословная командная строка живого процесса (CIM `Win32_Process`) | `"D:\turbobaby-bot\venv\Scripts\python.exe" pc_agent.py` |
| рабочий каталог | `D:\turbobaby-bot` |
| штатный подъём (им же пользуется само-рестарт агента, `pc_agent.py:581`) | `schtasks /Run /TN pc_agent` |
| чем доказано, что этот путь рабочий | родитель живого процесса — **`svchost.exe` (PID 2588)**, то есть агента поднял **Планировщик**, а не рука; PID 17436 — результат этого подъёма |
| второй, независимый путь владельца с телефона | слово **«обновись»** в тему 205: `git pull --ff-only` → гейт кода → помощник ждёт смерти старого PID → `schtasks /Run /TN pc_agent` |

Сильнее этого доказательства «команда рабочая» у захода не было бы и после перезапуска: живой
процесс **и есть** результат выполнения названной команды.

## 5. Перезапуск НЕ сделан. Три довода, и первый снимает задачу целиком

### Довод 1: агент УЖЕ на нынешнем коде — поднимать не на что

Вчерашний процесс (**2660**) умер сам, и Планировщик поднял новый **до** нашего захода. Это не
догадка по времени, а строка его собственного лога:

```
2026-09-11 20:55:04 | pc_agent.lock: СТУХШИЙ, забираю — процесса с номером 2660 в системе НЕТ
                      (OpenProcess: номера 2660 в системе нет)
2026-09-11 20:55:04 | pc_agent ЗАПУСК — слушаю HQ/тему 205, команды только от разрешённого id.
```

Дальше меряется не «свежесть вообще», а **замыкание импортов**: Python читает исходник один раз,
на импорте, поэтому судить надо по ВСЕМ локальным файлам, которые процесс втянул при старте, а не
по одному `pc_agent.py`. Обход по `ast` дал 8 файлов — `pc_agent`, `client_contour`,
`decision_waits`, `deploy_voice`, `io_utf8`, `log_setup`, `proc_identity`, `selfupdate_gate` — и
**новее старта нет ни одного**. Самый свежий из них правлен 11.09 в 20:31:24, старт — 20:55:03.

Проверено и с другой стороны: `git status --porcelain` по файлам агента пуст, то есть дерево
совпадает с HEAD, а `exam_show.py --agent` (прибор вчерашнего захода, замок свежести ловца)
отвечает **«ДА — живой агент (pid 17436) стартовал позже правки, кнопку он знает»**.

Отдельно: `dispatch_notify` — та самая правка сегодняшнего дня — **в замыкание импортов агента не
входит**: агент зовёт его ОТДЕЛЬНЫМ ПРОЦЕССОМ (`deploy_voice.DNOTIFY`), а значит новая дверь
`getMe` доступна ему сразу и без всякого перезапуска.

### Довод 2: перезапуск тронул бы клиентского ребёнка — а это прямой запрет задания

`pc_agent.main()` (`:1529–1545`) при КАЖДОМ старте зовёт `UB.status()` и, если `userbot` не жив,
**поднимает его** — «авто-реадопшн, ФИКС 2». Это не гипотеза: ровно так и произошло на живом
старте 20:55:04, строками ниже в том же логе —

```
userbot не запущен при старте агента — поднимаю (авто-реадопшн).
userbot запущен агентом, PID 14880
подъём мимо ворот: userbot поднят в БЕЗОПАСНЫЙ РЕЖИМ — SUGGEST_TEST_MODE=1 … контур ЗАМОРОЖЕН
```

Задание запрещает трогать `userbot` и модербот **ни одной командой**. Команда перезапуска агента —
это команда со встроенной веткой подъёма userbot: разрешение «на один процесс» исполнилось бы
действием над вторым. Довод снимается только отдельным разрешением владельца на обоих.

### Довод 3: класс операции красный для headless-полосы

Снятие живого процесса (`taskkill`) и `schtasks` — красные операции, их делает владелец. Обхода не
искал: строка NEEDS_APPROVAL в отчёте кнопкой не является и классом не одобряет.

**Пункт 7 задания при этом не сработал** и сработать не мог: дверь владельца НЕ роняли ни на
секунду, восстанавливать нечего. Честная формулировка исхода — не «обновление не состоялось», а
**«обновление уже состоялось без нас, и мы это доказали»**.
