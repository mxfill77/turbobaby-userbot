## §1. Пять мест: факт, цена, вердикт

### A-30 — `pretool_guard.py:_py_write_call` (ПК). ПОЧИНЕНО

**Чей текст и почему он там.** Тело неотслеживаемого не-теста `.py`, которое пишет модель, плюс
скан самой команды. Текст там потому, что боевую запись Bridge из скрипта гард иначе не видит
вовсе: аргументы вызова вычисляются в рантайме, до запуска существует только исходник. С 31.07
место судит уже не по имени, а по ЧЕТЫРЁМ ФОРМАМ ВЫЗОВА — но формы всё равно ищутся в тексте.

**Что ломается конкретно.** Дыра названа в разведке дословно и она ОТКРЫВАЕТ:

```python
from bridge_client import create_booking as cb
cb(client='Иван', bike='5580', ds='2026-08-10', de='2026-08-17')
```

Подстроки `create_booking(` в тексте нет ВООБЩЕ, поля `action=` нет, кавычек вокруг имени нет —
мимо всех четырёх форм. То же у файловой семьи: `from shutil import rmtree as nuke; nuke(p)`,
`from os import remove; remove(p)`, `import os as o; o.remove(p)`. Замер: 6 таких входов из 9
голденов получали `defer` без карточки (§2).

**Можно ли судить по действию/данным.** Да, и это не шестой регексп. Тело скрипта — не проза, а
ФОРМАЛЬНАЯ ГРАММАТИКА: у неё есть канонический разбор, как SQL у `_RE_SQL_WRITE`. `ast` строит
дерево, псевдоним резолвится ПО ПРИВЯЗКЕ ИМЕНИ (`import … as`, `from … import …`, `x = модуль.оп`),
решает узел `Call`. Место переходит из «совпадения» в «полуконтракт» — ровно как A-11.

**Как сделано.** `_py_write_call_ast(py_srcs)` вызывается на ПУСТОТЕ подстрочного разбора:
`tok = _py_write_call(blob) or _py_write_call_ast(py_srcs)`. Слой ТОЛЬКО ДОБАВЛЯЕТ красное —
асимметрия та же, что у имени базы в A-2: добавить вопрос можно, снять нельзя. Разбор не удался
(не питон, обрывок, чужой синтаксис) → `None` → прежнее поведение байт-в-байт. Куски питона
разбираются ПОРОЗНЬ (тело файла, инлайн `-c`): склейка кусков синтаксисом не является.
`def create_booking(` вызовом не считается и здесь — в дереве это `FunctionDef`, то есть правило
держится структурой, а не отрицательным регекспом.

**Названный предел.** Объект карточки прежний: `_py_call_args` ищет вызов ПО ИМЕНИ токена, и у
вызова под псевдонимом текста `create_booking(` нет — объект не извлечётся, карточка высшего вида
не выпишется. РЕШЕНИЕ при этом красное, операция не исполняется: fail-closed, а не тишина.

### A-36 — `pc_orchestrator.py:_owner_reply` / `_approved_scope` (ПК). ПОЧИНЕНО ЧАСТИЧНО

**Чей текст и почему он там.** Два слоя чужого: имена восьми полей — схема МОСТА (Apps Script),
значение — свободный ответ ВЛАДЕЛЬЦА. Список кандидатов появился потому, что имя поля никто не
обещал: демону надо было достать текст ответа, а контракта на него нет.

**Что ломается конкретно — и это уже случилось.** Перепроверено чтением обеих полос 02.08: ни одно
из восьми имён не встречается ни в одном файле ни ПК, ни VPS (кроме самого модуля и его теста);
devbot на «да» шлёт `approve_task(qid, "Filipp")` (`devbot.py:384`, `:1178` — снимок VPS), то есть
названный владельцем объект сверяется НА СЕРВЕРЕ и выбрасывается; ПК-ответчик текст на мост не шлёт
СОЗНАТЕЛЬНО (блок `APPROVAL_LEDGER`, `pc_orchestrator.py:2346`). Значит поля ответа в ряду нет
вообще, и высший вид не открывается НИКОГДА.

Само по себе это fail-closed и правильно. Цена лежала в другом месте — **в диагнозе владельцу**:
✋-карта советовала «ответь «да <объект из карточки>»», то есть предлагала сделать то, чего сделать
НЕЛЬЗЯ никаким ответом. Владелец, послушавшись, отвечает по кругу и каждый раз получает ту же
карту. Дословно, замер против HEAD (§2):

```
✋ провал […]: одобрено, но шаг снова упирается в красное — выполни вручную [необратимая операция
(live_sheet) подтверждается ТОЛЬКО ответом с объектом — короткое «да» её не открывает; ответь
«да <объект из карточки>»]
```

**Можно ли судить по действию/данным.** Восстановить КАНАЛ с ПК нельзя: объект должен нести мост,
а это полоса VPS + Apps Script. Но СОВЕТ можно выбирать по ДАННЫМ, а не по пустоте текста:
`_reply_channel(item)` смотрит, есть ли в ряду очереди хоть одно из восьми ПОЛЕЙ (значение не
важно). Поле есть и пусто — «владелец не назвал объект», прежний совет верен. Поля нет —
«назвать объект не выйдет НИКАКИМ ответом; эту операцию сегодня делают руками».

**Что НЕ сделано и почему.** Высший вид как был закрыт, так и остался: правка не открывает ничего
и не смеет — «да» с ПК высшую цену не открывает by design. Настоящее лечение (мост несёт текст
ответа) — правка `devbot`/Bridge на полосе VPS, отсюда недоступная: §4.

**Отдельно замечено (не правилось).** `test_pc_orchestrator.py:670` кладёт в фальшивый ряд поле
`owner_reply`, которого живой транспорт не производит — тот самый класс «мок ≠ живой формат»
(CLAUDE.md). Тесты не тронуты: они описывают поведение НА СЛУЧАЙ канала и полезны, но опираться на
них как на доказательство «канал настроен» нельзя. Новый голден это прямо фиксирует.

### B-5 — `orchestrator_daemon.py:_is_headless_impossible` (VPS). ОСТАВЛЕНО, полоса недоступна

**Чей текст.** Сразу и модели, и владельца: `what` — строка `op=… | …`, которую печатает
исполнитель; `orig` — ТЗ владельца ДОСЛОВНО (`_convert_other_approved`, вызов на `:3427`).

**Что ломается конкретно.** 15 альтернатив `_HEADLESS_IMPOSSIBLE_RE` (IGNORECASE). Модель
перефразировала («деплой Apps Script» вместо `clasp`) — задача уходит в конверт и упирается в то же
красное, то есть петля, ради разрыва которой ветка заведена. Обратно: слово в прозе ТЗ владельца
(«`clasp` не трогай») ПОСЛЕ его «да» закрывает задачу терминальной картой `_manual_card` — без
кнопки, ре-approve невозможен — не попробовав ни разу.

**Можно ли судить по действию.** Здесь — нет, и это честный предел, а не лень: ветка работает ДО
запуска исполнителя, действия ещё не существует. Единственная доступная альтернатива тексту —
попытка (конверт) с гардом внутри, а она и есть та самая петля. Разумное направление — судить по
КЛАССУ из карточки (`kinds_from_card`), а не по словам в прозе, но это правка VPS-полосы.

**ПК-полоса той же строки чиста.** `pc_orchestrator.py:3264` держит зеркало регекспа, но зовёт его
ровно один раз — `_dec_red_note` (`:3324`), 🔴-пометка красных шагов плана «только дисплей в result
родителя, тексты шагов не трогаем». Ни одного места, где эта строка распоряжается «да», на ПК нет
(грепом: 2 вхождения — определение и дисплей). Значит здесь чинить на ПК нечего.

### B-3 — `pretool_guard.py:_detail_parts` (VPS). ОСТАВЛЕНО, полоса недоступна

**Чей текст.** Модели: аргументов вызова Bridge гард не видит вовсе, читается исходный текст;
объект и число тянутся регекспами `ключ=значение` по blob.

**Что ломается конкретно.** Переименован именованный аргумент или значение — переменная
(`amount=total`, `wallet=w`) → объект пуст → `card_gate` False → **карточки владельцу нет, строка
уходит в журнал**. Исключение только деньги: `_ALWAYS_CARD` = ровно два (`void_last`,
`add_transaction`) — там карточка родится, но с «Объект: —».

**Можно ли судить по данным.** Канона нет by design, и на VPS это направление ПРОПУСКА. Но
класс-фикс уже существует — на ПК: там пустой объект НЕ глотает карточку, а меняет исход
(`pretool_guard.py:1156–1174`: «цель не извлеклась — объекта НЕТ; у высшего вида карточка не
выписывается ВОВСЕ, решение гарда при этом прежнее — красное, операция не исполняется»). То есть
лечится не новым регекспом, а переносом правила «пустой объект → не тишина, а fail-closed» с ПК на
VPS. Правка полосы VPS: §4.

## §3. Фикстура `test_trainer` протухла по календарю

**Факт.** `test_window_is_cumulative_across_events` держит реплику клиента «аренда с 1 по 8 августа
на 7 дней» и проверяет `collected_facts(t)["dates"]`. С 02.08 старт «1 августа» стал ПРОШЛЫМ, а
прошедший старт `collected_facts` собранной датой СОЗНАТЕЛЬНО не считает (гейт как раз просит его
уточнить). Тест краснел от смены СУТОК, а не от смены кода, и валил весь гейт.

**Чем починено.** Ни фразой, ни кодом контура: фраза клиента осталась ДОСЛОВНОЙ (правило голденов
детекта), закреплён ВТОРОЙ вход обеих функций — `today`, он для того и заведён
(`collected_facts(transcript, hints=None, today=None)`). Проверяемое в голдене — КУМУЛЯТИВНОСТЬ
окна, к календарю отношения не имеющая.

**Клиентский контур не задет:** `suggest.py` не менялся, поведение прошедшего старта осталось
прежним (оно верное). Изменён только файл теста.

**Страж добавлен.** `test_why_today_is_pinned_and_that_it_stays_pinned` показывает МЕХАНИЗМ (тот же
вход при `today=2026-07-25` даёт `dates=True`, при `today=2026-08-09` — `False`, а `term` остаётся
`True`) и сторожит сам пин через `inspect.getsource`: уберут `today=` обратно — упадёт СРАЗУ, а не
через сутки на чужом гейте.

**Соседняя фикстура проверена:** `_transcript_with_geo_and_photo` (`:389`) держит ту же фразу, но
даты не утверждает ни разу (проверяются гео/паспорт/зона) — по календарю не протухает, не тронута.

5. **A-36 → канал объекта.** Точки касания: `devbot.py:384` и `:1178`

## §5. Границы

* Полоса VPS читалась ПО КЛОНУ-СНИМКУ от 01.08 03:26: рабочее дерево сервера и непушенные ветки в
  нём не видны. Утверждения §1 про B-1/B-3/B-5 — про этот снимок, а не про живой сервер.
* «Мост не несёт поля ответа» доказано ОТСУТСТВИЕМ восьми имён в коде обеих полос и константой
  `"Filipp"` в `approve_task`, а не опросом Моста: ответ Моста фактом здесь не считается.
* Прогоны «до» — это HEAD-код, поднятый под тем же именем модуля (`REPO`/`PROJECT` в обоих модулях
  константы, а не путь файла, поэтому подмена места файла поведения не меняет). Для A-30 «до»
  получено выключением ровно нового слоя: остальные строки правки решений не принимают.
* Объект карточки у вызова под псевдонимом не извлекается — названный предел §1, не регресс.
* Контракт (B-7), полуконтракты (A-11, B-8), чужой конфиг (A-10) и чужая схема не трогались.
  Замок происхождения, изоляция проб, «одна карточка — одна операция», объектный гейт денег — не
  ослаблены ни одной строкой.
