## §1. Что платформа предлагает из коробки

Слово «память платформы» покрывает **три разные вещи**. Путать их — готовый ложный диагноз.

### A. Memory tool (`memory_20250818`) — ГА, но хранилища не даёт

`shared/tool-use-concepts.md:343-352`, `platform-availability.md` (строка «Bash, text editor, memory» = ✅ 1P/P-AWS/Bedrock/Vertex).

- Клиентский инструмент: команды `view` / `create` / `str_replace` / `insert` / `delete` / `rename`
  над каталогом `/memories`.
- **Бэкенд хранения реализуешь ТЫ.** Платформа не хранит ничего.
- Следствие: версий, аудита, отката из коробки **нет вовсе** — ровно столько, сколько сделаешь сам.
- Справка прямо предупреждает: «The reference implementations have no built-in access control».

Как хранилище журналов это не ответ — это тот же наш `cowork_log_append.py`, только с чужой схемой.

### B. Memory stores (Managed Agents) — настоящее хранилище платформы

`shared/managed-agents-memory.md` целиком. Бета-заголовок `managed-agents-2026-04-01`.

| объект | id | область | ограничение |
|---|---|---|---|
| Memory store | `memstore_…` | рабочее пространство (workspace) | **макс. 8 на сессию**, привязка только в момент создания сессии |
| Memory | `mem_…` | стор | **≤ 100 KB на документ**, адресуется путём; справка советует «prefer many small files» |
| Memory version | `memver_…` | документ | неизменяемый снимок на КАЖДУЮ мутацию |

- **Как видит агент:** FUSE-монтирование в контейнер сессии по `/mnt/memory/<store-name>/`,
  работа обычными файловыми инструментами (`bash`, `read`, `write`, `edit`, `glob`, `grep`).
  `access: "read_only"` держится на уровне ФС.
- **Как видит хост:** обычный REST — `POST/GET/PATCH/DELETE /v1/memory_stores/{id}/memories[/{mem}]`.
- **Срок хранения:** TTL не задан — документы живут до удаления. Стор можно `archive`
  (становится read-only, новые сессии его не подхватят) — **разархивации нет**.
- **Поиск:** host-side поиска по СОДЕРЖИМОМУ нет. `ListMemories` фильтрует по `path_prefix`,
  `depth`, сортирует `order_by`/`order`; `view="full"` подтягивает тело. Полнотекст возможен
  только `grep`-ом ВНУТРИ контейнера сессии Managed Agents.
- **Конкурентная запись:** `precondition: {content_sha256}` на `update` → `409
  memory_precondition_failed_error` при расхождении. Это честный CAS, которого у нас нет.
- **Доступность:** Managed Agents — **β**, только первопартийный Claude API и Claude Platform on
  AWS. Bedrock/Vertex/Foundry — ❌ (`platform-availability.md`). Нужен **API-ключ рабочего
  пространства**.

### C. Files API — не про журналы

`python/claude-api/files-api.md:9-13`: 500 MB на файл, **100 GB на организацию**, файлы живут до
удаления, операции (upload/list/delete) бесплатны, содержимое биллится как входные токены при
попадании в сообщение. Версий и аудита нет. Для журнала-который-дописывают не годится: правки нет,
только перезалив нового файла.

**Итог §1: единственный кандидат — вариант B.**

### 3.2. Влезаем ли в формат

**Нет, ни одним куском.** Лимит memory — 100 KB на документ:

| наш док | байт | во сколько раз над лимитом |
|---|---|---|
| `cowork_log` живой | 280 175 | **2,8×** |
| `cc_log` живой | 142 545 | 1,4× |
| `cowork_log_archive` | 1 142 016 | 11,4× |

Более того, **посуточная нарезка тоже не влезает**: прирост 134 КБ/сут > 100 KB. Значит минимум —
почасовые корзины (24 файла/сут, ~5,6 КБ каждый → **8 760 файлов в год**) либо запись-в-файл
(**≥ 101 000 файлов в год** при 277 записях в сутки). Оба варианта справка допускает («prefer many
small files»), но это уже не «перенесли журнал», а другая схема хранения.

### 3.3. Сколько стоит хранить

Хранение как таковое в локальной справке **не тарифицировано** — цены memory stores там нет
(**проверить на странице цен, это сеть**). Ориентир соседнего продукта: Files API — 100 GB на
организацию, операции бесплатны. Наши 47,8 МБ в год — **0,05 %** от такой квоты. То есть по объёму
хранение бесплатно или неразличимо дёшево. **Деньги не здесь.**

### 3.5. Кэш — и почему он сейчас не работает, а после нарезки заработал бы

`shared/prompt-caching.md:138`: чтение из кэша ~0,1× базовой входной цены, запись 1,25× (TTL 5 мин)
или 2× (TTL 1 час); окупаемость — 2 и 3 запроса соответственно.

Нынешняя схема **враждебна кэшу по построению**: `compose()` кладёт новую строку **сверху**
(`cowork_log_append.py:298-312`), а любая вставка в начало инвалидирует весь кэшированный префикс.
При 277 записях в сутки док меняется в среднем раз в 5 минут — то есть ровно на границе дефолтного
TTL. Нарезка на неизменяемые файлы-записи (что лимит 100 KB и так вынуждает сделать) убирает эту
проблему: старые файлы перестают меняться и кэшируются устойчиво. Это **единственный пункт, где
переезд объективно дешевле нынешнего**.

### 4.6. Организационный барьер, который бьёт раньше технических

Managed Agents требуют **API-ключ рабочего пространства**
(`managed-agents-core.md:50`: «`{workspace}` is the workspace the API key belongs to»).
ПК-контур сознательно живёт на подписке Max через `~/.claude/.credentials.json`, и появление
`primaryApiKey` в `.claude.json` **уже ломало демона** (класс «credit too low»). То есть подключение
памяти платформы — это не «включить флажок», а второй платёжный контур в среде, где эти грабли
уже наступали. Плюс статус **β** (`managed-agents-2026-04-01`) — ломающие изменения ожидаемы.

## §5. ВЕРДИКТ (5 строк)

1. **Полная миграция — нет.** Не из-за цены: цена хранения ~0,05 % квоты Files-яруса и практически
   ноль. Убивает то, что Штаб читает журнал Drive-коннектором, а к memory stores коннектора нет —
   перенос ослепляет главного читателя, и правило «нет строки — работы не было» перестаёт работать.
2. **Формат не влезает как есть:** 100 KB на документ против 280 KB живого `cowork_log` и 134 KB
   суточного прироста. Журнал придётся резать минимум почасово (8,7 тыс. файлов/год) или
   по-записно (≥101 тыс. файлов/год) — это смена схемы, а не переезд.
3. **Поиск хуже нынешнего:** host-side полнотекста нет, только фильтр по путям; `grep` живёт лишь
   внутри контейнера сессии Managed Agents. Сегодняшний «прочитать док целиком» дешевле и проще.
4. **Аудит и откат — единственное, ради чего это стоит трогать,** и здесь платформа честно сильнее
   нас: версия на каждую мутацию с актором, фильтры по `session_id`/`api_key_id`/времени, след
   удаления, `redact`, CAS по `content_sha256` вместо нашей эвристики `ShrinkGuard`. Откат при этом
   не кнопка, а два вызова (`GetMemoryVersion` → `UpdateMemory`).
5. **Пилот стоит того только в узкой форме — «теневой аудит-приёмник»:** Drive остаётся источником
   для Штаба и кода, а `cowork_log_append.py` после успешной записи дополнительно кладёт запись
   отдельным memory-файлом. Тогда мы получаем версии и откат, не теряя ни одного читателя из §4.
   **Условие владельца:** API-ключ живёт внутри отдельного процесса-писателя (как сейчас секреты
   Bridge внутри `brain_writer`), а не в окружении демона — иначе повторим класс «credit too low».

## 6.2. Пропущенная поверхность: «Synced project memory» — память платформы **внутри самого Claude Code**

§1 разобрал три варианта (memory tool / Managed Agents memory stores / Files API) и назвал
кандидатом только Managed Agents с ключом рабочего пространства. **Есть четвёртый, и он ближе всех
к нам:** сам CLI 2.1.218 умеет **синхронизировать файловую память с общим memory store**.

Что извлечено из кода дословно:

- переключатель в настройках: `id: "orgMemoryRead"`, подпись «**Synced project memory (this
  directory; applies next session)**», значение по умолчанию **включено** (`?? !0`); парный
  `orgMemoryWrites` показывается только при организационном разрешении;
- «`You have a persistent, file-based team memory directory at … It is synced at the start of every
  session and shared with the other users who work in this project.`»;
- в части сессий стор монтируется **только на чтение**: «`Team memory cannot be changed this
  session, but your private memory directory at … still persists`»;
- синхронизируются файлы `.md`, `.txt`, `.json`, `.jsonl`;
- работает **тот же серверный контракт**, что у Managed Agents: та же карта ошибок
  `store_full` / `content_too_large` (102 400) / `content_secret` / `invalid_path`.

Практический смысл для нас: **пилот не обязательно требует второго платёжного контура**. Первый
проход считал единственной дверью Managed Agents + API-ключ рабочего пространства (§4.6, класс
«credit too low»). Дверь «Synced project memory» открывается организационной настройкой, а не
ключом в окружении демона. Здесь она **не включена**: в `~/.claude/settings.json` ключей памяти
нет вовсе (`agentPushNotifEnabled`, `inputNeededNotifEnabled`, `permissions`,
`skipWorkflowUsageWarning`, `theme`), в `.claude/settings.json` слово `memory` встречается только
в двух правах на **приватный** каталог автопамяти. Общего каталога team memory на диске нет.

## 6.3. Две новые арифметические отсечки — и обе бьют раньше лимита 100 KB

**(а) Индекс памяти обрывается на 200 строках / 25 000 байт.** Константы в коде:
`av="MEMORY.md", $oe=200, axe=25000` и правило «`The index file is loaded into your conversation
context — lines after ${$oe} will be truncated`». Наша живая автопамять даёт масштаб: **28 файлов
+ индекс, 105 328 байт**, индекс `MEMORY.md` = **9 100 байт на 28 записей ≈ 325 байт на строку**.

Отсюда схема «одна запись журнала = один файл памяти», которую лимит 100 KB и так навязывает:

| порог индекса | сколько записей влезает | при 272 записях в сутки |
|---|---|---|
| 25 000 байт | 25 000 / 325 ≈ **77** | **≈ 6,8 часа** |
| 200 строк | **200** | **≈ 17,6 часа** |

То есть **индекс переполняется меньше чем за сутки** — раньше, чем упрётся любой файл. Всё, что
за обрывом, для отбора памяти не существует. За год такая схема даёт ещё и **≈ 99 000 файлов**
при недокументированных лимитах стора (`store_full` в карте ошибок существует в двух видах —
«reached its memory limit» и «reached its size limit», числа в справке не названы).

**(б) Платформенная память рассчитана на другой порядок потока.** Наша автопамять копится с 09.06
по 01.08 (53 суток): **105 328 байт / 28 файлов** = **≈ 1,99 КБ и 0,53 файла в сутки**. Журнал за
те же сутки: **≈ 134 КБ и 272 записи**. Разрыв — **67× по объёму и 513× по числу единиц**. И это
не «мы неправильно пользуемся»: продукт прямо инструктирует «`Organize memory semantically by
topic, not chronologically`» и «`Do not write duplicate memories`». **Журнал хронологичен и
принципиально допускает повторы** — он противоположен тому, для чего эта память сделана.

## 6.4. Новый класс: запись, которую хранилище имеет право НЕ ПРИНЯТЬ (и потерять молча)

Сегодня Drive принимает любой текст. Memory store — нет. В карте ошибок:

- `content_secret` — «`memory content appears to contain a credential or API key; remove it before
  writing. If the credential is real, rotate it.`»; на клиентской стороне то же: «`Content contains
  potential secrets (…) and cannot be written to team memory.`»;
- `invalid_path` — путь ≤ 1024 байт, ≤ 20 сегментов, без `.`/`..`, без управляющих символов,
  NFC-нормализованный.

Для журнала это прямое попадание: у нас есть правило 6 «боевые токены **называть словами**» — оно
писалось против внешнего слоя защиты, и теперь встречает **второй эвристический сканер уже на
приёме**. Строка отчёта, где процитировано что-то похожее на ключ (кусок URL, хеш, `id=…`),
получит отказ **вместо записи**.

Хуже отказа — режим тишины у CLI-синхронизации: «`Memory sync is paused for this file's memory
store … This write was saved locally but is NOT being persisted to shared memory`» и «`…will be
lost when this session's machine is recycled`». Наш канал в такой ситуации **спулит и повторяет**
(`cowork_log.spool`, реестр, обратное чтение с дословной сверкой); их — сохраняет локально и
теряет при переработке машины. **Для журнала, где «нет строки — работы не было», это худший из
возможных отказов.**

## 6.5. Что второй проход меняет в вердикте

Направление §5 подтверждается, формулировки уточняются:

1. **Полная миграция — по-прежнему нет,** и теперь не только из-за слепого Штаба: схема
   «файл на запись» ломает **индекс памяти за 6,8 часа**, а хронологический журнал прямо
   противоречит правилу продукта «организуй по темам, не хронологически».
2. **Организационный барьер ниже, чем считал первый проход:** есть дверь «Synced project memory»
   без ключа рабочего пространства в окружении демона. Но она открывается **не нами** и здесь
   выключена.
3. **Появился риск, которого нет у Drive:** приёмник вправе отказать (`content_secret`,
   `invalid_path`) и вправе молча не досылать (пауза синхронизации). Любой пилот обязан оставлять
   Drive **первичным** приёмником, а память — вторичным, иначе теряем записи.
4. **Аудит платформы всё так же сильнее нашего** — это единственная причина вообще это трогать.
5. Форма пилота из §5 («теневой аудит-приёмник») остаётся верной; к её условиям добавляется:
   **писать в память не построчно, а корзинами** (час/сутки в один файл ≤ 100 KB) — построчная
   схема убивает индекс, а суточная корзина 134 КБ не влезает в файл.
