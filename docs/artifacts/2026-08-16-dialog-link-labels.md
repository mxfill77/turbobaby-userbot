# Сцепка диалогов с бронями ПО МЕТКАМ обезличивания (read-only, замер 17.08.2026)

Имя файла задано постановкой (`2026-08-16-…`) и расхождением с датой замера **не является**:
замер шёл 17.08.2026 по местному времени Пхукета, то есть 16.08 по UTC — в той же зоне, в
которой штампует записи `cowork_log_append.py` (строка этого захода легла `2026-08-16 17:39:46`).

Заход проверяет ОДНУ гипотезу штаба: ноль сцепок 15.08
([`2026-08-15-dialog-intent-pairs.md`](2026-08-15-dialog-intent-pairs.md), коммит `b3ebda2`)
мог быть свойством ограничения захода, а не мира — сравнивались обезличенные метки корпуса с
исходными телефонами базы, то есть заведомо несравнимые вещи. Предложенное лекарство:
применить ТУ ЖЕ функцию к телефонам и никам базы и сравнивать метку с меткой.

**ВЕРДИКТ ОДНИМ СЛОВОМ: ОПРОВЕРГНУТА.**

И раздельно, потому что гипотеза составная:

- **диагноз гипотезы ВЕРЕН** — 15.08 действительно сравнивал несравнимое;
- **лекарство НЕВОЗМОЖНО** — функции «личность → метка» не существует. Метка обезличивания
  есть функция **НОМЕРА СТРОКИ в корпусе**, а не человека. Применять её к телефону из базы
  нечем: телефон в неё не входит аргументом.

Пригодных пар эталона — **0** при пороге 30. Вердикт эталона прежний (**НЕ СУДИМО**), но
причина названа другая и более сильная, чем 15.08: ключ не «стёрт в моём срезе», а
**уничтожен в момент записи корпуса**, и никакая функция его не восстановит.

## 1. Воспроизводима ли функция — ДА, и именно это её и хоронит

Функция — `anonymize_corpus.anonymize_record` (боевой модуль репозитория).

**Секрета не требует.** Ни ключа, ни соли, ни значения из конфига: метка собирается
форматированием счётчика. Ветка постановки «требует секрета — остановись» **не сработала**,
`.env` не открывался.

**Воспроизводимость доказана самым сильным способом из возможных — метки живого корпуса
пересобраны из ВЫДУМАННОГО входа:**

```
шапок корпуса ВОСПРОИЗВЕДЕНО функцией (username): 710 из 710
                                        (name)  : 710 из 710
                                        (peer_id): 710 из 710
                                        (phone) : 710 из 710
```

На вход подавались синтетические телефон и ник, объявленные в тексте замера
(`_scratch_linklabels_0816/measure_labels.py`, константы `SYN_*`). Ни одного боевого телефона
и ника заход не читал вовсе — **и всё равно получил все 710 меток корпуса дословно.** Это и
есть доказательство: если метку можно собрать, не зная человека, то метка о человеке **не
несёт ничего**.

**От чего метка зависит — замер, а не чтение кода:**

| проба | результат |
|---|---|
| 1000 РАЗНЫХ выдуманных лиц при ОДНОМ номере строки (5) | **1** разная метка → метка КОНСТАНТНА по личности |
| ОДНО выдуманное лицо при номерах строки 1..710 | **710** разных меток → одно лицо получает столько меток, сколько строк |

```
строка   5:  «мой номер <телефон_005> пишите на @@профиль_005»
строка 300:  «мой номер <телефон_300> пишите на @@профиль_300»
```

Вход в обеих строках ОДИН И ТОТ ЖЕ. Меняется только номер строки.

Устройство корпуса это подтверждает по всем 710 записям: `peer_username` равен
`профиль_<номер строки>` — **710 из 710**, `peer_name` = `Клиент_<номер строки>` — **710 из
710**, `peer_id` **перезаписан номером строки** — 710 из 710, `peer_phone` **пуст** — 710 из 710.

Так и задумано, и модуль говорит это прямо (докстринг `anonymize_corpus.py:13–16`): метки
устойчивы ВНУТРИ диалога, «между диалогами устойчивости НЕТ СОЗНАТЕЛЬНО: `Лицо_1` в записи 5
и в записи 300 — разные люди, и связать их нечем». **Посылка гипотезы — «устойчивая метка
значит, что один человек всегда получает одну и ту же метку» — для этого обезличивателя
ложна.** Устойчивость у него внутридиалоговая, а не сквозная.

Самый дорогой из уничтоженных ключей — `peer_id`: telegram-id был бы идеальным ключом сцепки
(точный, неизменный, есть с обеих сторон), и он **затёрт номером строки**, а не помечен.

## 2. Три исхода сцепки числом

Единица счёта — как 15.08. Метка брони требует аргумента «номер строки корпуса»; у брони его
нет. Перебор всех строк даёт каждой брони 710 меток, и каждая метка делится со ВСЕМИ прочими
бронями (§1).

**По нику** (цель — `peer_username`, 710 меток корпуса):

```
ОДНОЗНАЧНАЯ  :   0
НЕОДНОЗНАЧНАЯ:   все (403 ника базы, замер 15.08), кратность 710 у каждого
НЕ НАЙДЕНА   :   0
```

**По телефону** (цель — `peer_phone`):

```
цель ПУСТА у 710 записей из 710 — сравнивать не с чем
ОДНОЗНАЧНАЯ  :   0
НЕОДНОЗНАЧНАЯ:   0
НЕ НАЙДЕНА   :   все (644 телефона базы, замер 15.08)
```

Разница с 15.08 содержательная, и её стоит назвать: тогда сцепка провалилась **промахом**
(710 «НЕ НАЙДЕНА»), сейчас по нику она проваливается **попаданием во всё сразу**. Оба исхода
одинаково непригодны, но ошибиться в диагнозе они дают по-разному: «ноль совпадений» звучит
как «не там искал», а «совпало со всеми» — это уже прямо «ключа нет».

## 3. Потолок гипотетического хода через текст — тоже мимо порога

На случай возражения «метка в ТЕКСТЕ могла быть устроена иначе» — замерено по корпусу:

| что | сколько |
|---|---|
| диалогов, где в тексте есть СВОЙ номер собеседника | **8** из 710 |
| диалогов, где в тексте есть СВОЙ ник собеседника | **1** из 710 |
| диалогов с ЛЮБОЙ меткой телефона | 126 |
| диалогов с ЛЮБОЙ меткой ника | 85 |
| **разных строк-меток телефона во ВСЁМ корпусе** | **16** |

Последняя строка — независимое подтверждение §1: 126 диалогов содержат телефоны, а разных
меток на весь корпус **шестнадцать**. При метке от личности их было бы под сотню и больше;
шестнадцать выходит ровно потому, что метка — счётчик внутри диалога, и почти везде это
`<телефон_1>`.

Даже если бы метки были сквозными, потолок этого хода — **8** пар по телефону и **1** по нику
при пороге 30. Ход мёртв дважды.

## 6. Чего заход НЕ делал и почему

**Боевые телефоны и ники базы не читались вовсе** — и это не осторожность, а следствие
замера. Функция доказано КОНСТАНТНА по личности (§1, проба на 1000 лиц), поэтому подстановка
настоящих телефонов дала бы те же самые метки, что и выдуманных: ноль новой информации при
ненулевой выдаче ПДн в память. Живой вызов моста за контактами не делался ни разу.

Регрессия не строилась, тренажёр не запускался и не правился, кейсы не заводились, бот не
трогался, цены из текста диалогов не брались. Мутаций ноль: сетевых вызовов нет вовсе.

## 8. Побочное наблюдение (не чинилось)

В тексте корпуса метка ника выходит с **двойной собакой** — `@@профиль_NNN`, в **85 диалогах
из 710** (то есть во всех, где метка ника вообще есть). Причина: шаблон замены уже содержит
`@`, а подстановка идёт в группу 1 регулярного выражения, оставляя исходный `@` слева
(`anonymize_corpus.py:422` против `me_user` на `:523`). Модуль сам предупреждает об этом риске
для поля шапки (`:536–538`) и там его обходит, а в тексте — воспроизводит.

Дефект **косметический**: обезличиванию он не вредит (метка остаётся меткой), на выводы этого
захода не влияет. Не чинился сознательно — задача поставлена read-only и с одной целью.
Записан как остаток.
