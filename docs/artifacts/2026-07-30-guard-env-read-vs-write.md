## ДЕФЕКТ — карточка `env` на чистом чтении памяти процесса

Владелец снимает модель/эффорт у живых процессов (userbot, демон, suggest) СПЕЦИАЛЬНО через PEB,
чтобы **не читать файл `.env`**: скрипт `peb_env.py <pid> THINKER_MODEL SUGGEST_MODEL …` открывает
процесс `OpenProcess(QUERY_INFORMATION|VM_READ)` и читает окружение из памяти
`ReadProcessMemory` — ни одного байта файла `.env` при этом не открывается.

Но в докстринге скрипта дословно стоит «Читает ОКРУЖЕНИЕ живого процесса из PEB (**не из файла
.env**)». `_scan_python` читает тело скрипта, `_RE_ENV` бьёт по слову `.env` в докстринге, вид
`env` стоит в `_HARD_CARD` — и на ЧИСТОМ ЧТЕНИИ рождалась карточка «Хочу обратиться к .env /
секретам». Живой факт (`pretool_guard.log`): `19:26:06` и `19:52:34`, обе `ask | env`.

Дополнительная причина, почему тело считалось «обращением к содержимому»: дисквалификатор
`_RE_PY_NOT_PROBE` содержал голое `\.read`, и `k32.ReadProcessMemory` матчил его как файловое
`.read`. Чтение ПАМЯТИ процесса — не чтение файла.

## Развод по ДЕЙСТВИЮ

| Действие | Было | Стало |
|---|---|---|
| `python peb_env.py <pid> VAR…` (OpenProcess+ReadProcessMemory, PEB) | карточка `env` | тихо (`defer`, вид `env_probe`) |
| `python -c "…ReadProcessMemory()… # PEB, not file .env"` | карточка `env` | тихо |
| `Get-Content .env`, `cat .env`, `type .env` | карточка | **карточка (hard-блок)** |
| `Select-String -Path .env`, `-LiteralPath .env` | карточка | **карточка** (дыра остаётся закрытой) |
| `grep/findstr … .env`, `open('.env').read()`, `load_dotenv('.env')` | карточка | **карточка** |
| `Set-Content .env`, `echo … >> .env`, `Copy-Item …→.env` | карточка | **карточка** |
| `Read`/`Edit` инструментом по `.env` | карточка | **карточка** (`read_secret`/`edit_secret`) |
| **ReadProcessMemory (декой) + `open('.env').read()`** | карточка | **карточка** (одна улика `open(` отменяет послабление) |

### Как это сделано (границы, каждая намеренная)

* `_RE_PY_PROC_ENV` — позитивный ПОИМЁННЫЙ маркер PEB-чтения
  (`ReadProcessMemory` / `NtQueryInformationProcess` / `PROCESS_VM_READ`), зеркало `_RE_PY_EXISTS`
  для проверки наличия: послабление даётся за ДОКАЗАННОЕ чтение памяти, а не за отсутствие улик.
* `_py_reads_process_env(code)` = есть `.env` **и** есть PEB-маркер **и** НЕТ ни одной улики
  файлового доступа/мутации (`_RE_PY_NOT_PROBE`: `open(`, файловое `.read()`/`read_text`,
  `dotenv`, `os.environ`, `subprocess`, `exec`, …). Одна улика → False (красное).
* `_py_env_readonly(code)` = `_py_env_probe_only` (наличие) **или** `_py_reads_process_env` (PEB).
  Оба несут один fail-safe: любой файловый доступ отменяет послабление.
* `\.read` в `_RE_PY_NOT_PROBE` сужено до `\.read\b`: `f.read()` ловим, `ReadProcessMemory` — нет.
  `.readline/.readlines/.read_text/.read_bytes` перечислены отдельно и остаются красными.
  `\.write` НЕ сужено — `WriteProcessMemory` это мутация, ей краснеть правильно.
* Точки применения: `_scan_python` (`cmd_ok`/`body_ok`) и `_env_probe_only` (python-сегмент).
  Вид в логе — `env_probe` (прозрачность: смягчение видно как пробу, не безликий прочерк).

**Что послабление НЕ открывает:** чтение файла `.env` (Get-Content/cat/grep/Select-String/
open().read()/dotenv) — красное; запись/правка `.env` — красное; `Read`/`Edit` по `.env` —
красное; PEB-маркер как отмычка (ReadProcessMemory + open('.env')) — красное; `os.environ`
текущего процесса остаётся в `_RE_PY_NOT_PROBE` (в нём могут жить боевые токены — читать его
файлом-секретом не считаем, но и зелёным не делаем).

### Сверка с числами владельца (CLAUDE.md п.7 — верим числам)

Владелец назвал «29 карточек, 18 из них env». Воспроизводимый факт за календарный день
2026-07-30: сырых `ask`-строк в логе = **29** (совпало), из них вид `env` = **14** (не 18).

## ОСТАТКИ (с точками касания)

1. **`os.environ` текущего процесса.** Оставлен в `_RE_PY_NOT_PROBE` (красное при со-упоминании
   `.env`): в окружении claude-процесса живут боевые токены, читать его — не то же, что снять
   модель у чужого процесса через PEB. Если владелец захочет разрешить и это — точка касания
   `_RE_PY_NOT_PROBE` (убрать `os.environ`/`getenv`), но это ослабляет защиту секретов в env.
2. **Тело heredoc сообщения коммита** (перенесён из артефакта 30.07): `git commit -F - <<'EOF' …`
   с «.env» в тексте всё ещё даёт карточку `env`. Требует heredoc-aware сегментации
   (`_split_segments`/`_scan_text`) — отдельным заходом.
3. **Класс-фикс на ВТОРУЮ полосу (CLAUDE.md п.9).** На VPS PEB-специфики нет (Linux `/proc`),
   но общий принцип «упоминание пути в докстринге ≠ файловый доступ» стоит зеркалить в
   `_RE_PY_NOT_PROBE` серверной полосы. Репозиторий чужой (боевой сервер) — решение владельца.
