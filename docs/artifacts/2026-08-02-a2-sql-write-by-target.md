# A-2 закрыто: слово в комментарии больше не снимает красное с SQL-записи

**Дата:** 2026-08-02. **Тип: правка кода + голдены.** Коммит — в конце файла. `.env` не
открывался, на сервер не ходили, процессы не трогали, боевых записей нет, ничего не удалялось.
Правка узкая: одно место разбора (`_scan_python`), остальные девять мест разведки не тронуты.

**Основание:** [`2026-08-02-root-a-contract-or-coincidence.md`](2026-08-02-root-a-contract-or-coincidence.md)
§1 строка 1 (A-2) — «единственное из десяти, что ОТКРЫВАЕТ».

## §1. Что было (замер ДО правки, живой формат)

Проба `tmp/a2-sqlwrite-probe-0802a`: два НЕотслеживаемых не-теста `.py` во временной зоне,
тела отличаются ровно одной строкой комментария. Ни один не исполнялся — снимался вердикт
`decide()`.

| скрипт | тело | вердикт ДО | карточка |
|---|---|---|---|
| `write_with_mention.py` | `# сверялся с memory.db …` + `connect('moderation_ipc.db')` + `UPDATE meta SET …` | **`defer` / вид пуст** | **нет** |
| `write_plain.py` | то же БЕЗ комментария | `ask` / `sqlite` | есть, объект `moderation_ipc.db` |

То есть **решала проза**: слово в комментарии снимало красное с настоящей записи в живую
локальную базу ПК. Признак стоял в коде так:

```python
if _RE_SQL_WRITE.search(blob) and ".db" in blob.lower() and "memory.db" not in blob.lower():
```

Обе половины условия — совпадение подстроки: и то, что краснит (`".db" in blob`), и то, что
открывает (`"memory.db" not in blob`). Скан читает не только команду, а **тело скрипта целиком**
(до 400 000 символов), поэтому «где угодно» здесь буквально: докстринг, строка данных, цитата
журнальной строки — любое из трёх снимало красное со ВСЕХ SQL-записей файла разом (проверено
голденом `test_word_anywhere_in_the_body_decides_nothing`, три места, все три до правки красные).

## §2. Ответ фактом: зачем послабление заводилось и есть ли база

**Зачем.** Порт доктрины VPS. Строка пришла в ПК-гард первым же коммитом гарда —
`2f3ddca` от 03.07.2026 («PreToolUse-хук (порт VPS)»), дословно вместе с формулировкой из
архивной копии в3: *«memory.db через python-код → defer (своя БД бота; sqlite3 CLI остаётся ask
в settings)»* и *«memory.db — своя БД (зелёная доктрина 02.07)»*
(`docs/artifacts/2026-07-23-guard-v3-files/pretool_guard.py:17,825`). На VPS у имени есть смысл:
`memory.db` — база агента Splinter (`manager-bot/memory.py` → `DB_PATH`), её читают `bot.py`,
`splinter.py`, `auditor.py`, `claude_client.py` (клон-снимок `tmp/srv-audit-2`, 10 ссылок).

**Есть ли такая база на ПК — поправка к разведке.** В разведке 02.08 стояло «Баз с именем
`memory.db` на ПК — **0**». Замер по всему дереву (`find -name "*.db"`, а не `ls *.db` в корне)
даёт **два** файла:

| файл | размер | mtime | кто открывает |
|---|---|---|---|
| `moderation_ipc.db` | 1 404 928 | **02.08.2026 11:16** — живая | боевой контур модерации |
| `manager-bot/memory.db` | 253 952 | **01.06.2026 19:52** | **никто на ПК** |

Второй — часть замороженного снимка июньского VPS-кода `manager-bot/` (вне git, под
`.gitignore`; тот самый каталог, который **сносить нельзя** — в нём живёт растущий
`docs/playbook.md`). Открывает его только код VPS-снимка (`manager-bot/memory.py`), который на
ПК не запускается. Боевой `suggest.py` ходит в `manager-bot/` за тремя **docs**-файлами
(`turbobaby_faq_v1.md`, `park_list.md`, `playbook.md`) — до базы не касается.
`git grep 'memory.db' -- '*.py'` по ПК-репо даёт **только** сам гард, его тесты и архивную
копию в3 — ни одного боевого файла.

**Вывод: послабление на ПК не нужно вовсе, и оно снято целиком.** Законно оно не срабатывало
ни разу (боевого обращения к `memory.db` с ПК не существует), незаконно — с одного упоминания.

**Третий факт, решающий спор о доктрине:** ТЗ владельца №4 от 30.07 уже отменило это
послабление — но только для ТЕКСТА КОМАНДЫ. `_sqlite_decide` карве-аута не имеет вовсе, и
голден зовётся `test_live_db_write_always_red` с дословной подписью *«живые базы на ЗАПИСЬ
краснеют всегда — включая memory.db, которой тело-скан исторически давал поблажку»*. Но мерил
он **только CLI-форму** (`sqlite3 <база> "…"`), а тело скрипта осталось со старой доктриной.
Правка не заводит новое правило, а доводит уже принятое решение до второго текста.

## §3. Что стало

```python
if _RE_SQL_WRITE.search(blob):
    return ("ask", "sqlite", _sql_write_object(blob))
```

* **Решает действие** — оператор записи SQL (`UPDATE|DELETE FROM|INSERT INTO|REPLACE INTO|
  DROP TABLE…|ALTER TABLE|CREATE TABLE…`), формальная грамматика, а не имя в прозе.
* **Имена баз решения не принимают вовсе** — они только называют объект карточки. Правило
  асимметрично: имя в тексте может ДОБАВИТЬ вопрос, снять — никогда.
* **Цель не определилась — красное** (fail-closed), и так и подписано: объект берётся по
  цепочке «цель по вызову `connect('…')` → имя базы в тексте → таблица из запроса →
  `цель записи не определена`».
* **Списка «своих» баз вместо карве-аута нет сознательно**: список имён — тот же разбор по
  подстроке, он снова стал бы отмычкой. Ни одна база ПК блокового зелёного не получила.
* **Чтение не тронуто**: `select`/схема/`mode=ro` в `_RE_SQL_WRITE` не входят и до этой ветки
  не доходят — голден `test_mention_without_a_write_stays_green` это стережёт.

Побочно закрыта тихая щель того же места: `_extract_db(blob) or ""` мог отдать **пустой**
объект (подстрока `.db` в тексте есть, имени файла нет — например `x.dbg`), а вид `sqlite` в
`_HARD_CARD` не стоит, и правило `card_gate` увело бы НАСТОЯЩУЮ запись в журнал **молча** —
ровно та дыра, которую 31.07 закрыли живому листу. Теперь объект пустым не бывает.

## §4. Регресс: красный до правки, зелёный после

Новый класс голденов `TestSqlWriteJudgedByTargetNotMention` (9 тестов) прогнан **дважды одним
и тем же файлом тестов**: против копии гарда из `HEAD` (`tmp/a2-sqlwrite-probe-0802a/before/`,
3742 строки) и против правленого (3807 строк).

```
ДО ПРАВКИ:    Ran 9 tests — FAILED (failures=6, errors=2)
              ('defer', '') != ('ask', 'sqlite')  ← на всех формах упоминания
              errors=2 — новых функций (_sql_write_object/_connect_db_literal) в HEAD нет
ПОСЛЕ:        Ran 9 tests — OK
```

Вердикты живой пробы после правки — обе формы решаются ОДИНАКОВО:

| скрипт | вердикт ПОСЛЕ | карточка |
|---|---|---|
| `write_with_mention.py` | `ask` / `sqlite` / `moderation_ipc.db` | 🔴 Хочу записать в базу данных moderation_ipc.db |
| `write_plain.py` | `ask` / `sqlite` / `moderation_ipc.db` | то же |

**Гейт полный:** `python -m unittest` по 39 тест-модулям — **2786 тестов, 1 провал**
(`test_pretool_guard` отдельно: **313 OK**). Единственный провал —
`test_trainer.TestTrainerAccumulation.test_window_is_cumulative_across_events`, к правке
отношения не имеет и **найден календарём, а не диффом**: фикстура содержит «аренда с 1 по 8
августа», сегодня 02.08 — даты в прошлом, `collected_facts` их не берёт. Проверено заменой
чисел: `с 1 по 8 августа` → `False`, `с 20 по 27 августа` → `True`. Тест-модуль импортирует
`trainer`/`suggest`/`moderation_ipc` и гард не импортирует вовсе; клиентский контур заморожен,
поэтому фикстура НЕ правилась — записано в остатки.

## §5. Остатки (с точками касания)

1. **Голден с абсолютной датой протухает по календарю** — `test_trainer.py:867`
   («аренда с 1 по 8 августа»). Класс: фикстура, привязанная к абсолютной дате, краснеет сама
   по себе; лечится относительной датой (`сегодня+N`). Клиентский контур заморожен — не тронуто.
2. **Карточка команды называет УПОМЯНУТУЮ базу, а не целевую.** Замер 02.08:
   `python -c "import sqlite3  # memory.db\nc=sqlite3.connect('moderation_ipc.db')\nc.execute(
   'insert into meta …')"` → красное (правильно), но объект — **`memory.db`**, потому что
   `_extract_db` берёт ПЕРВОЕ имя, похожее на базу, в любом месте текста. Владелец подтверждает
   запись не в ту базу, что названа. Точки касания: `pretool_guard.py` → `_extract_db` (:388),
   `_sqlite_decide` (:927), `_card_fields` (:3163). В теле скрипта это уже вылечено
   (`_connect_db_literal` предпочитает цель по вызову) — командную половину не трогали, чтобы
   не расширять правку на соседние места разведки.
3. **Класс-фикс на ВТОРУЮ полосу не перенесён:** та же строка живёт в гарде VPS
   (`pretool_guard.py:1319` и `:1362` в клоне-снимке `tmp/srv-audit-2`, обе половины — по
   подстроке). Там у `memory.db` референт ЕСТЬ, поэтому решение не механическое: либо цель по
   вызову `connect('memory.db')`, либо снятие послабления и там. На сервер не ходили.

## §6. Границы

* Правка касается ОДНОГО места (`_scan_python`, ветка SQL-записи) и его объекта. Замок
  происхождения (`_is_repo_tracked`/`_is_test_target`), изоляция проб, правило «одна карточка —
  одна операция» и объектный гейт денег не тронуты — 313 голденов гарда это подтверждают.
* Направление изменения — только в сторону вопроса: команда, которая раньше проходила молча,
  теперь спрашивает; ни одна раньше красневшая не позеленела.
* Утверждения про VPS сделаны по клону-снимку `tmp/srv-audit-2` (`main` `7298787` от 01.08),
  рабочее дерево сервера в нём не видно.
* Пробные файлы `tmp/a2-sqlwrite-probe-0802a/` — untracked, в git не идут; ни один не исполнялся
  (первой строкой у каждого `raise SystemExit`).
