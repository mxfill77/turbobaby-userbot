## 1. Признак клиентского контура

`userbot_listen.py` и `moderation_bot.py`. Замыкание считается ПО ФАКТУ с диска (`ast`, все узлы
`Import`/`ImportFrom`, включая импорты внутри функций), кэш инвалидируется по mtime/размеру
файлов корня. Модуль — `client_contour.py`.

в репозитории — комментарий к `_FILE_PROCESS_RULES` утверждает «userbot booking* не импортит», а
`userbot_listen.py:46` его импортирует (мост тренажёра добавили позже). Граф это видит, список нет.

**Срез на чужих процессах** (единственное исключение, принципиальное): обход не идёт сквозь
входные точки других живых процессов — `pc_orchestrator.py` и `pc_agent.py`. Без среза граф
схлопывается: `moderation_core._default_lesson_enqueue` ЛЕНИВО импортирует демона ради

и владелец держит демона внутренним. Список тут — по ПРОЦЕССАМ (их три, новый заводят осознанно),

## 2. Ворота на ВЫХОДЕ — три точки авто-применения

Все три жили на одной карте `_FILE_PROCESS_RULES` и на ТЕСТОВОМ гейте, ручного одобрения не было:

| точка | что делала | где ворота |
|---|---|---|
| `maybe_update_bots()` | рестарт ботов после done дев-задачи | до гейта тестов, по всему диффу задачи |
| `_selfupdate_restart_children()` | рестарт детей после self-update демона | перед циклом по ботам |
| `reconcile_children_tick()` | **рестарт на ЛЮБОЙ новый коммит** (это она сработала 01:53) | держит весь тик, метку не двигает |

Общий узел — `_client_block()`: карточка владельцу ровно ОДИН раз на пару «коммит + состав
клиентских файлов» (реконсиляция приходит каждые 60 с). Метка `_last_child_commit` при удержании
НЕ двигается, `_child_reconcile_rejected` НЕ ставится — придёт «да», следующий тик применит ЭТОТ
ЖЕ коммит.

### Основания пропуска — ровно два
1. **«да» владельца** — команда-рычаг `выкати` / `выкатывай` / `да, выкати` / `применить коммит`
   (якорный паттерн: совпадает, только когда ВЕСЬ текст задачи и есть команда). Пишет основание в
   `pc_orchestrator.client_release.json` (gitignored). Сам рестарт идёт ШТАТНЫМ путём — гейт
   тестов, анти-флап и запрет грязного дерева остаются на месте: «да» это решение о ПРАВЕ
   выкатить, а не обход гейтов.
2. **Зелёный прогон через тренажёр — ЗАГЛУШКА, и вот почему.** Тренажёр связан с этим контуром в
   ОДНУ сторону: НАДЗОР-урок дописывает класс в `docs/revizor_checklist.md` (вход ревизора).
   Обратной связи «прогон зелёный → можно выкатывать» в коде нет — ни `trainer.py`, ни
   `trainer_log.py`, ни `lesson_router.py` никакого реестра прогонов не пишут. Основание выключено
   по умолчанию (`PC_TRAINER_GREEN`, дефолт off). Интерфейс заложен: когда тренажёр научится
   отдавать вердикт, он кладёт его в `pc_orchestrator.client_trainer_green.json` — ворота
   откроются без правки ворот.

Ручной рычаг «рестартни userbot» под ворота НЕ попадает — там решает человек (та же граница, что
у запрета грязного дерева 28.07).

## 3. Ворота на ВХОДЕ — ревизор

Находка `action=task`, чья правка попадает в клиентский контур, становится **owner-карточкой**, а
не зелёной задачей дирижёру (`_revizor_route`, плюс last-resort в `_revizor_enqueue_tasks` — чтобы
клиентская находка НИКОГДА не встала зелёной задачей). По внутренним файлам ревизор работает как
работал.

Точка контроля честно слабая, и мы это признаём вслух: ревизор ставит ТЕКСТ дев-ТЗ, а не список
файлов. Судим по именам, названным в тексте — ловим и `suggest.py`, и голое `suggest` (обход
формулировкой не работает). Не названо ни одного файла репозитория → контур неопределим →
fail-closed → owner-карточка.

**Практическое следствие называем прямо:** почти все task-находки станут карточками — именно
потому, что почти каждая из них по замыслу правит клиентского бота (промпт SUFFIX ревизора велит
думателю писать дев-ТЗ на «правку кода/промпта suggest»). Это вариант A из разведки, и он выбран
осознанно.

## 5. Что такое «рычаг авто-реконсайла» (вопрос владельца)

Термин из разведки (§2.1 и §5) — это НЕ отдельный флаг и не команда. Так названа **пара функций
демона, которая деплоит и рестартит живые боты на ЛЮБОЙ новый коммит по ТЕСТОВОМУ гейту, без
ручного одобрения**:

* `maybe_update_bots()` — рестарт после done дев-задачи (диапазон `head_before..HEAD`);
* `reconcile_children_tick()` / `maybe_reconcile_children()` — «реконсиляция детей на ЛЮБОЙ новый
  коммит», троттлинг `PC_CHILD_RECONCILE_SEC` (дефолт 60 с);
* плюс `_selfupdate_restart_children()` — та же карта после self-update демона.

Откуда взялся: класс-фикс `c6d8a30`. До него свежий код детей применялся, только если правку принёс
дев-таск ИЛИ вместе с ней сменился блоб `pc_orchestrator.py`. Коммит, тронувший ТОЛЬКО файлы детей
и пришедший вне дев-таска (ручной коммит, `git pull`), оставлял живых ботов на старом коде — так
`c6d8a30` (только suggest.py) не подхватился. Реконсиляцию и завели, чтобы этого не было.

Зачем это знать: разведка назвала жало класса ДВУМЯ рычагами — (1) ревизор порождает коммит в
`suggest.py`, (2) авто-реконсайл его молча выкатывает. Варианты A и B из разведки били только по
(1). **Эта задача бьёт по (2)** — и по (1) тоже (часть 3). Именно рычаг (2) сработал 30.07 в 01:53:
`реконсиляция детей: userbot рестартнут до 452891745, PID [7064]`.

## 6. Что применится само после коммита этой правки

Правка живёт в `pc_orchestrator.py` + новый `client_contour.py` — оба **ВНУТРЕННИЕ**. Ирония на
месте и она правильная: ворота выкатятся автоматически. Триггер — смена блоба `pc_orchestrator.py`
→ self-update демона (гейт `code_gate` + `unittest test_pc_orchestrator test_pc_local_dec`) →
эстафета новому процессу. Живые `userbot`/`moderation_bot` при этом НЕ трогаются: их файлы в
диффе отсутствуют, а с этого момента ещё и ворота бы их удержали.

## 8. Остатки (честно, с точками касания)

1. **Контур-вотчдог** (`_client_watch_state`, `CLIENT_WATCH_SEC`) поднимает МЁРТВОГО бота — и
   поднимет его с текущего диска, то есть с неодобренным кодом. Ворот там нет намеренно: мёртвый
   бот должен ожить. Точка касания — `_client_raise` / `client_watch_tick`.
2. **`lesson_router.py` не в `_FILE_PROCESS_RULES`** (см. §1): правка только этого модуля не
   рестартит никого, живые боты доживают на старом коде. Класс `dae330a`. Точка касания —
   `_FILE_PROCESS_RULES` в `pc_orchestrator.py`.
3. **Данные контура** ловятся по строковым литералам: имя файла, собранное в рантайме, не найдётся.
4. **Ворота входа судят по тексту**, а не по факту правки. Честный контроль — гард на слое записи
   внутри ревизорской сессии; это отдельная работа (разведка §5, вариант B, минусы).
