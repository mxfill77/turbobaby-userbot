# Фактическое ценообразование по базе броней (read-only, 15.08.2026)

Артефакт для решения владельца. **Ничего не менялось, цен не утверждалось, в рабочие таблицы
не писалось.** Правок кода нет, коммита нет. Корпус диалогов не открывался ни разу — источник
цены здесь только база броней.

## 0. Где база и чем её читали

**База броней = вкладка «клиенты» таблицы MANAGER** («менеджеру Байки»), она же источник
«Календаря бронирования». Не файл в репозитории: локально её нет ни в каком виде — греп по
дереву на `pay_per_day` даёт только доки, а не данные.

Читали **боевым клиентом моста, одолженным у демона** (`queue_snapshot_pc._guard_test_logs` →
`pc_orchestrator.bc`), одним GET-экшеном `clients` с `filter=all`. Секреты моста берёт САМ
импортируемый модуль — скрипт разведки их не читает и не видит (запрет класса 328). Мутаций
ноль: `_get` — это GET, `create_booking`/`close_booking`/`add_transaction` не звались.

**Персональные поля отброшены ДО записи на диск** (`fetch_bookings.py` → `PII`): имя (D),
контакты (U), примечание (V), booking_id (Y). Проверено по факту, вывод `pii.py`:

```
ключи среза: auto_cancel, bike, date_end, date_start, days_overdue, debt, deposit, duration, helmets, is_active, is_fresh, is_overdue, paid, pay_per_day, row, status, to_pay, type
  поле name        в срезе: 0 строк
  поле contacts    в срезе: 0 строк
  поле note        в срезе: 0 строк
  поле booking_id  в срезе: 0 строк
  поле passport    в срезе: 0 строк
  поле phone       в срезе: 0 строк
  телефон (+66/8xx, 9-15 цифр)   совпадений: 2756  примеры: 0967741935484, 142857142857, 1428571428571, 2001-01-01 00, 2022-09-08 00, 2022-09-13 00
  e-mail                         совпадений: 0
  телеграм-ник                   совпадений: 0
  кириллица вне статуса/типа     совпадений: 1  примеры: шлема
```

2756 «телефонов» — ложные срабатывания на мантиссах дробных цен и датах, проверено адресно:
`0967741935484` — это хвост `"pay_per_day": 387.0967741935484`. Контактных полей в срезе нет
вовсе.

**Чего мост НЕ отдаёт**, хотя колонки в листе есть (`Config.CLIENT_COLS` против
`ReadClients.getClients`): **L «платёж в месяц»**, M «платёж в день», N пробег. Значит «цена за
месяц» отдельным полем недоступна — месячный тариф виден только как H×30.

Три поправки к постановке, каждая — числом:

1. **Глубина базы — почти 4 года, а не полтора.** 2022-09 .. 2026-07. Полтора года — это
   окно 2025-03..2026-07 и 484 брони из 1243; сезонность считалась по ВСЕЙ базе (больше стыков
   октябрь→ноябрь), ценовые таблицы — по окну.
2. **Отменённых броней в базе НЕТ ВОВСЕ.** Ни одной строки со статусом «Отменена», и
   `auto_cancel=ON` у нуля строк из 1278. Отмена в этой базе не хранится — её либо удаляют
   строкой, либо не заводят. Ответить «сколько отменено» по этой базе **нельзя**, и это факт
   базы, а не пробел разведки.
3. **Открытых 12**: 11 «В аренде» + 1 «Бронь». Плюс 6 строк мусора в колонке статуса
   («долг» ×3, «гера ниндзя» ×2, «гера» ×1) — в расчёт не брались.

**Что считалось ценой суток.** Колонка **H «платёж в день»** — формульная колонка самого листа.
Для суточных аренд это оплачено/срок, для месячных — месячный тариф/30. Это и есть цена, по
которой реально взяли деньги.

**Срок берётся из колонки G, а не из разности дат** — и это не мелочь: E пишется как 00:00, а F
с часом выдачи («16:00»), поэтому разность превращает «4 Д» в 3.8 суток. Все 484 брони окна
вышли дробными, и корзина «1-3 сут» молча съедала четырёхдневные.

**Закономерность числом: скидка за срок — это не лестница, а ОДНА СТУПЕНЬ на месяце.** До 13
суток цена суток не снижается вовсе (96% / 101% / 100% — разброс внутри шума), на 14–29 сутках

месячный тариф ≈ половина недельного. NMAX 1-3 сут = 48% — это 5 броней, продления месячного
клиента, а не суточный прайс; на выводе не сказывается.

Голая медиана по месяцу здесь врала бы: в разные месяцы едут разные модели и на разный срок.
Поэтому каждая бронь превращена в **индекс** — своя цена суток, делённая на медиану своей пары
(модель, корзина срока) по всей базе. Индекс 1.00 = «как обычно за такой байк на такой срок».

**Ответ: граница видна, и 1 ноября — лучшая из всех двенадцати возможных.** Разрыв полугодий
+30% против +27% (октябрь), +19% (декабрь), +18% (сентябрь). Правило владельца данными
подтверждено.

**Но это склон, а не обрыв, и это важнее самого подтверждения.** Дно — июнь-июль (0.72–0.74),
пик — январь (1.12), а сам стык октябрь→ноябрь даёт всего **+8%**: октябрь уже наполовину
«высокий» (0.94). По отдельным годам стык скачет: +15% / **0%** / +7% / +19% — то есть в 2023
границы 31 октября в деньгах не было вообще. Календарная дата описывает середину склона, а не
ступеньку.

## 7. Что этими данными проверить НЕЛЬЗЯ (честно)

- **Отмены** — базой не хранятся вовсе (см. §1), доля сорвавшихся броней отсюда не считается.
- **Глобальная скидка и потолок низкого сезона** — отдельными полями мост не отдаёт; в цене они
  уже растворены и от «просто низкой цены» неотличимы. `cap_active`/`cap_price` живут в ответе
  `quote_price`, а не в базе броней.
- **Зазор на торг** — прямого поля нет; его косвенная мера здесь — остаточный rIQR §3 (8% ячеек
  за пределами 0.30 после снятия срочной скидки).
- **Цена за месяц отдельным числом** — колонка L мостом не отдаётся, месячный тариф выводится
  как H×30.
- **Надбавка высокого сезона** измерена как **+30%** к низкому по индексу (§5), но это медиана
