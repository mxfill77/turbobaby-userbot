## 1. Что делает каждый механизм

### 1.0 Общий движок — думатель `_thinker_exec` (`:2363-2415`)

Один на оба флага. `claude -p` со своей парой голов: `THINKER_MODEL=claude-opus-5`,
`--fallback-model claude-opus-4-8` (`:2246-2247`, оба прогнаны через `_norm_model_id` — фикс
класса #194 «короткий алиас → 404»). Ключевое: это **чистый генератор**, не исполнитель —
`--max-turns 1`, `--allowed-tools ''`, `cwd=tempfile.gettempdir()` (нейтральный каталог, чтобы CLI
не подхватил `.claude/settings.json` и `pretool_guard` репо). Глубина мышления возвращается
явно из того же `settings.json` через `repo_thinking_settings()` (`:2342`): `--effort xhigh`,
`MAX_THINKING_TOKENS=31999`. `ANTHROPIC_API_KEY` вычищен из env → подписка, не платный API.

**Красное не ослаблено ни на грамм:** думатель ничего не выполняет, файлы не читает, инструментов
не имеет; `needs_approval` отсекается раньше (`process_new`), в думатель попадает только
исполнительский `failed`.

**FAIL-SAFE везде:** запуск не удался / exit≠0 / таймаут / не-JSON / `verdict` вне словаря /
бюджет claude занят → `None` → вызывающий откатывается к ПРЕЖНЕМУ поведению (голый `failed`
для одиночки, `halt` для цепи, `keep` для адаптации).

### 1.1 STEP_SELFHEAL — точка 1: одиночная задача lane=pc

`process_new :1905` → `_maybe_selfheal :2482` → `_maybe_task_selfheal :2434`.

Гейты «не зовём думателя» (в порядке проверки):

| гейт | строка | причина |
|---|---|---|
| `frm == Filipp-pcloc-dec` | `:2486` | это шаг локальной цепи, им владеет надзор цепи |
| флаг off | `:2491` | короткое замыкание |
| `fail_text` начинается с `⏱` | `:2493` | переформулировка не ускорит зависший claude |
| текст начинается с `[конверт одобренной заявки` | `:2497` | перерождение сдвинуло бы маркер → сломало бы разрыв петли ре-конвертов |
| текст уже `^[самопочинка задачи N, попытка M]` | `:2440` | вторая попытка запрещена → терминальный `failed` |

Иначе — промпт `TASK_THINKER_PREAMBLE` (`:2272`) + текст задачи дословно (≤2000) + суть провала
(≤1200) → строгий JSON `{verdict: retry|halt, fixed_task, reason}`.

* `halt` или пустой `fixed_task` → `failed` с диагнозом думателя.
* `retry` → в очередь lane=pc встаёт НОВАЯ задача `[самопочинка задачи {tid}, попытка 1] {fixed}`
  (`:2465`, `frm` наследуется), **а исходная закрывается `done`** с 🩹-карточкой (`:2475`).

### 1.2 STEP_SELFHEAL — точка 2: шаг локальной цепи

`process_local_chains :3410` → `_loc_chain_tick :3390` → `_loc_after_fail :3202`.

Гейты: `result` начинается с «отклонено Филиппом» / `⏱` / `✋` → сводка без думателя (`:3214`);
шаг уже несёт `[самопочинка шага i, попытка 1]` → 🛑-карточка + сводка (`:3217`); флаг off →
прежний halt-on-fail (`:3223`).

Иначе `_loc_selfheal_consult :3155`: промпт `THINKER_PREAMBLE` + **цель родителя дословно + весь
план шагов** (читается из очереди, `_loc_parent_context :3140`) + упавший шаг + провал. `retry` →
в очередь `[шаг i/N родитель pid] [самопочинка шага i, попытка 1] {fixed}` + 🩹-карточка. `halt`
или любой сбой → карточка с диагнозом + сводка, цепь встаёт (в sequential-модели halt = просто не
релизить следующий шаг).

### 1.3 STEP_SELFHEAL — точка 3 (о ней легко забыть): плановый рестарт ≠ падение

`_run_task_impl :1131`. Под ТЕМ ЖЕ флагом работает `_killed_by_planned_restart :2292`: если claude
задачи оборвался (`rc≠0`) в окне управляемого self-update-рестарта демона — задача становится
**`done`**, а не `failed`. Четыре обязательных признака: `rc≠0` + HEAD-блоб `pc_orchestrator.py` ≠
`RUNNING_BLOB` + текст задачи про сам демон + взведён `pc_orchestrator.stop`. К думателю отношения
не имеет — это отдельная семантика, приезжающая тем же рубильником.

### 1.4 PLAN_ADAPT — адаптация плана после КАЖДОГО удачного шага

`_loc_chain_tick :3390` → `_loc_after_done :3308`. Зовётся **на успехе**, а не на провале.

Пропуски: последний шаг (`i >= total` → сводка, думатель не тратится); план не восстановился из
очереди → ⚠️-карточка + halt; ревизорская цепь уступает owner-задачам (`:3334`); шаг сам родился
из свежей коррекции (`last_base == i`) или пара `(pid,i)` уже в `_loc_adapted`.

Промпт `ADAPT_PREAMBLE :2544` = цель родителя + исходный план + сжатые результаты сделанных шагов
(первая строка каждого, ≤300) + оставшиеся шаги. Вердикты:

* **keep** (дефолт при любом сомнении) → релиз следующего шага прежнего плана;
* **adjust** → `adjusted_steps` = НОВЫЙ полный список оставшихся; в очередь ложится synthetic-карточка
  `[коррекция плана родитель pid] после шага i (K=k)` с нумерованным остатком в `result`
  (restart-proof носитель нового плана), затем релизится первый скорректированный шаг с маркером
  `[коррекция плана K]`. `K > 2` → 🛑 «план дрейфует» + halt. `i + len(new) > 8` → fail-safe keep;
* **finish** → 🏁-карточка «цель достигнута досрочно» + сводка, остаток не релизится.

## 2. Что произойдёт при включении

**Кого затронет.**

| механизм | триггер | охват сегодня |
|---|---|---|
| STEP_SELFHEAL, точка 1 | `failed` одиночки lane=pc | все дев-ТЗ/задачи 328/829/Dispatch, кроме ⏱ и конвертов |
| STEP_SELFHEAL, точка 2 | `failed` шага цепи `Filipp-pcloc-dec` | цепи локального дирижёра (он ВКЛЮЧЁН: 274, 4, 5, 44 в логе) |
| STEP_SELFHEAL, точка 3 | обрыв claude в окне self-update | самомод-задачи демона |
| PLAN_ADAPT | КАЖДЫЙ `done`-шаг цепи, кроме последнего | те же цепи; по 5–6 консультаций на цепь из 6 шагов |

**Что случится с упавшим шагом.** Ровно одна попытка. Думатель получает цель + план + текст шага +
ошибку и возвращает переформулировку ≤400 символов. Новая задача — САМОДОСТАТОЧНОЕ ТЗ: исполнитель
увидит ТОЛЬКО её текст. Упавший шаг остаётся в очереди со статусом `failed`, перерождение получает
тот же номер шага и больший id; сводка и надзор берут при дублях номера последнюю запись по id
(`_loc_summary_counts :2942`, `_loc_chain_tick :3395`) — то есть в отчёте виден результат
перерождения, а не провала. Повторный провал перерождённого — терминальный, петля структурно
невозможна.

**Может ли пересобрать план сам.** Да, но только ХВОСТ и в жёсткой рамке: заменяются лишь
оставшиеся шаги (сделанные не трогаются), итог плана ≤8 шагов, коррекций ≤2 на цепь, третья =
остановка «план дрейфует». Полномочие закрыть цепь досрочно (`finish`) тоже есть — без спроса
владельца, карточкой постфактум.

## 3. Риски

### Р1. Ворота по метке `from` закрыты только с ОДНОЙ стороны (главный риск)

`_maybe_selfheal :2486` исключает единственную метку — `Filipp-pcloc-dec`. Но по полосе `pc` ходит
ВТОРОЙ вид цепей: шаги ПК-театра `from=Filipp-pc-dec`, чей дирижёр живёт на VPS
(`dec_port_spec.md:31,49-56`; в коде это признано «чужим на полосе»: `:2851`, `:3412`; в тестах —
`test_pc_local_dec.py:567`, `test_pc_orchestrator.py:3696`). Такой шаг исполняет ЭТОТ демон, и при
включённом флаге его провал уйдёт в ОДИНОЧНУЮ самопочинку:

1. перерождение получит текст `[самопочинка задачи N, попытка 1] …` — **маркер `[шаг i/N родитель
   pid]` теряется** (`:2465` клеит маркер самопочинки ПЕРВЫМ, префикса шага не сохраняет) → для
   VPS-надзора это больше не шаг цепи;
2. исходный шаг закрывается **`done`** (`:2475`) → VPS-надзор `_pc_after_done`
   (`dec_port_spec.md:55`) прочитает его как успешный и релизнет СЛЕДУЮЩИЙ шаг.

Итог: цепь VPS-театра перешагивает через провал, а рядом отдельной одиночкой крутится оторванное
перерождение. Регресс-тест на это есть только для локальной метки
(`test_chain_step_failure_not_hijacked_by_single_selfheal`, `test_pc_orchestrator.py:3721` —
проверяет ровно `frm=PC_LOCAL_DEC_FROM`).

Это класс №9 свода («класс-фикс сразу на ОБЕ полосы») в зеркальном виде: одна метка закрыта,
вторая — нет.

**Условие материализации:** по полосе должны реально идти цепи `Filipp-pc-dec`. Проверить это
чтением с ПК нельзя — очередь живёт в Bridge, а живой снимок по метке `from` отсюда read-only не
снимается. **Это вопрос владельцу до включения, а не после.**

### Р2. Зацикливание — закрыто

Одиночка: якорь `^` в `_HEAL_TASK_RE :2250` (маркер обязан стоять ПЕРВЫМ — страховка от ТЗ, где он
лишь упомянут). Шаг: `_HEAL_RE :2533` через `search` (маркер идёт ПОСЛЕ `[шаг i/N]`). Вторая
попытка = терминал. Адаптация: `K` считается из карточек коррекций В ОЧЕРЕДИ (restart-proof), лимит
2; плюс потолок 8 шагов; плюс дедуп `_loc_adapted`. Дедуп живёт в памяти процесса — после рестарта
демона возможен максимум ОДИН лишний keep-вопрос на цепь (та же оговорка в спеке, `:55`).

### Р3. Лимиты

Каждая консультация — отдельный `claude -p` на `claude-opus-5`, `--effort xhigh`,
`MAX_THINKING_TOKENS=31999`. Дорог не самопочинка (провалы редки), а **PLAN_ADAPT: он бьёт по
каждому УСПЕШНОМУ шагу**. Порядок величины по живому логу: цепи 274 (7 шагов), 4 (6), 5 (6), 44 (6)
за восемь дней ⇒ ≈20 дополнительных вызовов думателя. Бюджет процессов защищён:
`_claude_budget_gate :995` зовётся с `wait_sec=0` (`:2378`) — если лимит `MAX_CLAUDE_PROCS=2` занят,
думатель просто пропускается (fail-safe), очередь ожиданий не растёт.

### Р4. Задержка тика

Консультация синхронна внутри `poll_once`: до 180 с на вызов, несколько цепей в тике — сумма.
`process_local_chains` стоит ПЕРЕД `process_new` (`:2063` против `:2065`) ⇒ ровно на это время
откладывается взятие owner-задач. Ложного рестарта вотчдогом при этом НЕ будет: `watchdog() :5860`
после протухшего heartbeat проверяет живость процесса (класс-фикс 13.07) — но `HEARTBEAT_STALE=180`
и `PLAN_ADAPT_TIMEOUT=180` совпадают до секунды, и вся защита держится на второй проверке.

### Р5. Очередь и повторная работа

Перерождения и карточки — обычные задачи lane=pc; отказ enqueue везде откатывается в fail-safe
(голый `failed` / halt), подвисания нет. Настоящий риск другой: **перерождение исполняет ТЗ заново
целиком**. Ни преамбула, ни промпт не сообщают думателю, что уже успело произойти (в контексте
только текст задачи и текст ошибки), — если упавшая задача успела закоммитить или отправить часть
работы, перерождение может сделать её второй раз.

### Р6. Отчётность

Исходная задача закрывается `done`, и владелец получает карточку `_human :1192` —
«✅ Оркестратор: задача #N выполнена — самопочинка: перерождена задачей #M». Слово «выполнена» при
провале — правда только в теле карточки. Любой подсчёт по статусу после включения завышает `done`.

## 4. Как включить и как выключить

Читатель у каждого ключа ровно один, сравнение строгое (`== "1"`), поэтому:

```powershell
# ВКЛЮЧИТЬ (красное, класс env — исполняет человек)
Add-Content -Path D:\turbobaby-bot\.env -Value 'STEP_SELFHEAL=1' -Encoding utf8
Add-Content -Path D:\turbobaby-bot\.env -Value 'PLAN_ADAPT=1'    -Encoding utf8

# ВЫКЛЮЧИТЬ (то же красное): любое значение, кроме "1"
#   строку правим на STEP_SELFHEAL=0 / PLAN_ADAPT=0 — этого достаточно,
#   поведение возвращается байт-в-байт прежним (короткое замыкание в _selfheal_on/_plan_adapt_on)
```

**Одной командой — не получится: нужен рестарт демона.** `.env` читается ровно один раз, на старте
процесса (`load_dotenv`, `:88-90`), а `_selfheal_on()` смотрит `os.environ` уже загруженного
процесса. Два пути поднять новый:

* **зелёный, штатный** — NOOP-коммит, меняющий только блоб `pc_orchestrator.py` (комментарий):
  self-update на следующем поллинге прогоняет гейт и передаёт эстафету свежему процессу, который
  `load_dotenv`-ит `.env` и видит флаг. Это документированный рецепт репо (`:26-28`) — ровно так
  12.07 включали `PC_LOCAL_DEC`;
* **красный** — `python pc_orchestrator.py --stop` + `schtasks /Run /TN pc_orchestrator`.

**Флаг не горячий:** выключение НЕ отзывает уже стоящие в очереди перерождения — они дорабатывают
как обычные задачи lane=pc.

## 5. Как понять, что сработало

**След в `pc_orchestrator.log`** (уровень INFO/WARNING, тег в начале сообщения):

| тег | пример строки | смысл |
|---|---|---|
| `task-selfheal:` | `id=N перерождён задачей M (retry)` | одиночка перерождена |
| `task-selfheal:` | `id=N → думатель halt (<причина>)` | думатель отказался чинить |
| `task-selfheal:` | `id=N (перерождение задачи K) упал ПОВТОРНО → терминальный failed` | попытка исчерпана |
| `pcloc-selfheal:` | `ответ думателя не распарсился (fail-safe halt)` | сбой JSON |
| `pcloc-dec:` | `шаг i/N родителя P перерождён задачей M (retry)` | шаг цепи перерождён |
| `pcloc-plan-adapt:` | `родитель P adjust K=k после шага i → релиз скорректированного шага` | план пересобран |
| `pcloc-plan-adapt:` | `родитель P finish после шага i (<причина>)` | цепь закрыта досрочно |

**Второй след — строка METRICS**: `task_metrics.selfheal_count :214` считает маркеры
`[самопочинк(а|и) … попытк(а|и) N]` в тексте задачи, поэтому у перерождения в METRICS будет
`selfheals=1`. Сегодня во ВСЕХ 63 строках METRICS живого лога стоит `selfheals=0`; по всем `*.log*`
репозитория `selfheals=[1-9]` — **ноль совпадений**.

**Третий след — очередь и Telegram:** synthetic-задачи `[карточка родитель pid]` с 🩹 / 🛑 / 🏁 / ⚠️,
карточка коррекции `[коррекция плана родитель pid]` с 🧭, строки NOTE в `cowork_log`
(`задача #N → самопочинка retry, перерождена #M`).

### Две ловушки при проверке следа

1. **Грепу по ротированному логу верить нельзя.** В `pc_orchestrator.log.1` (04.07–22.07) лежит
   3269 строк с этими тегами: `task-selfheal:` — 1164, `pcloc-selfheal:` — 334,
   `pcloc-plan-adapt:` — 1771. Все до одной — **шум юнит-тестов**: пачки в пределах одной
   миллисекунды, `id=1`/`id=2`, `bridge down`, `{"verdict":"…"}`. Это старый класс «тесты сорят в
   боевой лог демона», позже закрытый `log_setup.is_test_context()` (`:206-209`). Живой
   `pc_orchestrator.log` (2057 строк, с 22.07) по тем же тегам даёт **0**.
2. **Баннер старта факт включения НЕ подтверждает.** ПК печатает при старте lane/poll/таймауты
   (`:5699`), флаги тест-гейта (`:5704`) и бюджет claude (`:5708`) — но НЕ `selfheal`/`plan_adapt`.
   На VPS такая строка есть (`selfheal=1, plan_adapt=1`, см.
   `docs/artifacts/2026-07-25-approve-layers-repair.md:186`). Значит после включения на ПК до
   первого срабатывания **доказательства подхвата не будет вовсе** — только косвенно, отсутствием
   строк. Это ровно тот класс, который недавно закрывали в RC-супервизоре (коммит 3a097a9,
   «супервизор называет свой порог на старте»); кандидат в задачу на 3 строки лога.

## 6. Зеркало

**ПК-полоса — это и есть порт.** `pc_orchestrator.py` содержит механику целиком: думатель, обе
преамбулы, обе ветки самопочинки, адаптацию, маркеры, карточки, восстановление плана из очереди.
Покрытие — 23 юнит-теста (`test_pc_orchestrator.py` — 20, `test_pc_local_dec.py` — 3), включая
прямые регрессы «флаг off → поведение байт-в-байт прежнее»
(`test_selfheal_off_prior_haltonfail_byte_identical :3843`, `test_adapt_off_keep_byte_identical
:3982`). Состояние: **код жив и зелён, рубильник отсутствует**.

Важная поправка к формулировке «выключенная самопочинка»: выключен ТОЛЬКО думательный слой.
Дирижёр вокруг него работает — `PC_LOCAL_DEC=1`, в живом логе цепи 274 (7 шагов, 23.07), 4 и 5
(6 шагов, 28.07), 44 (6 шагов, 30.07, с уступкой owner-задачам). То есть цепи строятся, шаги
релизятся, сводки пишутся — просто упавший шаг никто не чинит, а план никто не пересматривает.

**VPS-полоса — источник порта, и там механизм ВКЛЮЧЁН.** `docs/dec_port_spec.md:69,79` описывает те
же два флага для `orchestrator_daemon`, а баннер живого VPS-демона от 25.07 печатает
`selfheal=1, plan_adapt=1` (`docs/artifacts/2026-07-25-approve-layers-repair.md:186`). Проверить это
сегодня отсюда не удалось: клон VPS-репозитория лежит ЗА пределами проекта (`D:\foreign\…`), чтение
в этой сессии не разрешено. Так что «включено на сервере» — факт на 25.07, не на сегодня.

Отсюда и асимметрия, из которой растёт риск Р1: **на сервере механизм работает, на ПК спит**, а
шаги ПК-театра исполняет ПК. Пока флаг на ПК выключен, конфликта нет по построению.

## 7. Что решать владельцу

1. **Включать ли вообще** — и если да, то РАЗДЕЛЬНО: у флагов независимый откат, а профили риска
   разные. `STEP_SELFHEAL` дёшев (бьёт по провалам) и упирается в Р1. `PLAN_ADAPT` безопаснее по
   очереди, но дороже по лимитам (бьёт по каждому успеху) и даёт думателю право закрыть цепь
   досрочно.
2. **До включения `STEP_SELFHEAL` — закрыть Р1**: либо подтвердить, что цепей `Filipp-pc-dec` на
   полосе больше нет, либо добавить в `_maybe_selfheal :2486` вторую метку (одна строка, зеркало
   существующего гейта) и регресс-тест рядом с `:3721`.
3. **Три строки в баннер старта** (`selfheal=`, `plan_adapt=`, `local_dec=`) — чтобы факт подхвата
   рубильника читался из лога сразу, а не после первого срабатывания.
