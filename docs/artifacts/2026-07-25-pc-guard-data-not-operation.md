## 2. Сравнение гардов: почему список имён здесь врёт

Прямой diff имён даёт «на ПК нет 37 функций и 24 констант», но это **обманчивая цифра**: гарды —
две РАЗНЫЕ реализации одной доктрины, а не один файл с дельтой.

| | VPS | ПК |
|---|---|---|
| строк | 929 | 762 → 952 |
| точка входа | `classify` → `_analyze` → `_block_reason` | `decide` → `_decide_bash`/`_decide_write`/`_decide_read` |
| скан-текст | `_scan` → `_units` → `_split_segments` | `_scan_text` |

### Корень случая A — не тот, что казался

Класс-фикс «аргументы .py — данные» на ПК **уже был** (`f85bc76`). Он не срабатывал по другой
причине: `_RE_SHELL_SEP` — регулярка, кавычек она не знает. Текст записи
`"…убраны os.remove и rm -rf из признаков; демон 79694 active"` рвался по точке с запятой
**внутри строки**, кавычка в куске оставалась непарной, `shlex.split` падал,
`_strip_script_cli_args` честно возвращал сегмент как есть — и `rm -rf` оказывался в скан-тексте
рядом с путём репозитория. Отсюда и утренний отказ «Remove-Item on system path `D:\turbobaby-bot`
is blocked».

## 3. Что перенесено и что сохранено

Перенесены три поведения выше плюс их опоры (`_base`, `_cmd_index`, `_RE_ENV_ASSIGN`, `_WRAPPERS`,
`_SEARCH_CMDS`, `_PATTERN_FLAGS`, `_EXEC_IN_PATTERN`). Порядок внутри сегмента:
`git -m` → аргументы `.py` → шаблон поиска.

**Специфика ПК сохранена и дополнена:**

- в поисковые команды добавлены `Select-String` / `sls` / `findstr` — здесь основной шелл
  PowerShell, ищут обычно ими;
- **`&` разделителем не считается**: в PowerShell это оператор вызова (`& "C:\…\claude.EXE"`), а не
  связка команд. Дыры нет — не разрезанный кусок сканируется целиком;
- `_base()` снимает `.exe`, чтобы `grep.exe` опознавался как `grep`;
- `_mask` работает по **тексту** сегмента, а не по переклеенным токенам: на Windows `shlex` ест
  обратные слэши в путях, и склейка ослабила бы скан.

**Осознанно НЕ переносил:** `_subst_inners` (тела `$(…)` отдельными единицами скана),
`_dedup_*`, `RED_TOKENS`, жёсткий блок по `_PROTECTED_PROCS`. Они не участвуют ни в одном из
измеренных расхождений, а на ПК их роль закрыта другими механизмами (`_RE_ARG_EXEC` держит
подстановки красными — случай F зелёным не стал). Тащить чужую архитектуру целиком ради полноты
списка — не порт, а переписывание.

## 6. Живая проверка — краснеет, но НЕ гардом репозитория

Результат честный и не такой, какого ждали. Попытка записать в журнал строку, где рядом стоят
`os.remove`, `rm -rf` и `Remove-Item`, **по-прежнему отбивается**:

```
Remove-Item on system path 'D:\turbobaby-bot' is blocked. This path is protected from removal.
```

Но отбивает её **не** `pretool_guard.py`. На той же самой строке репозиторный гард даёт зелёное:

```
decide      -> ('defer', '', '')
scan-текст  -> cd D:\turbobaby-bot;python cowork_log_append.py
```

То есть починка сделала ровно то, что должна, а сверху работает **второй, внешний слой защиты**,
живущий не в репозитории (в `.claude/settings.json` из хуков только `dispatch_notify` и наш
`pretool_guard`). Замеры внешнего слоя тремя пробами:

| проба (аргумент no-op команды) | результат |
|---|---|
| `Remove-Item` в тексте | прошла |
| `rm -rf` и `os.remove` в тексте | прошла |
| `текст записи; Remove-Item дальше по строке` | прошла |
| все три слова вместе в одной строке записи | **заблокирована** |

Смена интерпретатора (`python` → полный путь к `venv`) на вердикт не влияет — реагирует именно
текст. Правило внешнего слоя, стало быть, уже, чем «любое красное слово», но его логика нам не
видна и в репозитории не лежит.

**Практический вывод для владельца:** в журнальных строках боевые токены лучше называть словами
(«деструктивные вызовы файловой системы»), а не цитировать буквально — ровно так и записаны
`ARTIFACT`/`DONE` этой задачи. Подбирать формулировки, чтобы протащить буквальные токены сквозь
внешний слой, я намеренно не стал: это был бы обход защиты, а не её починка.

## Остатки

1. На VPS не перенесены ПК-находки обратного направления (`Select-String`/`findstr` там не нужны,
   но `.exe`-срезка и «`&` — оператор вызова» — чисто ПК-вещи, обратный порт не требуется).
2. Прежние: пункт 4 слоёв в `_manual_card` на VPS; переавторизация Claude CLI →
   `SPLINTER_LLM_VIA_CLI=1`; три потерянные записи `-60` в кассе.
