## 3. Зацепка проверена первой: воронка 286 → 2

**ПОДТВЕРДИЛАСЬ — и число воспроизведено точно, до единицы.**

```
userbot.log, маркер «→ IPC (bot-режим)» : вхождений 286, СТРОК 286, различных id 286, дублей 0
userbot.log, маркер «заявка intake #»   : 2
moderation_ipc.db: drafts 458 → intake 2
```

Но у левого числа есть две поправки, и обе нужны, чтобы им дальше пользоваться:

**Поправка 1. 286 — это число строк ЖУРНАЛА, а не число продукта.** Источник истины называет
**458**. Разрыв не угадан, а разобран поимённо: строка журнала несёт id строки базы
(`SUGGEST: черновик #{did} → IPC`), поэтому множества сравнимы.

```
ЕСТЬ В ЖУРНАЛЕ, НЕТ В БАЗЕ: 0        ← журнал не выдумывает
ЕСТЬ В БАЗЕ,  НЕТ В ЖУРНАЛЕ: 172     ← 458 − 286
пропущенные id: 13…287, НЕ сплошным блоком ; статусы пропущенных: {'posted': 172}
по суткам: 04.07 — 79 из 82, 05.07 — 92 из 94, 14.07 — 1 из 6 ; остальные 28 суток — БЕЗ пропусков
```

Механизм потери 172 строк этим заходом **не установлен** (ротационных хвостов у `userbot.log` нет,
дыра лежит в середине, а не префиксом) — и к вопросу захода не относится, записано в остатки.

**Поправка 2. Окно «09.06–15.08» — это окно ФАЙЛА, а не окно этих строк.** Прикладные строки
userbot'а **даты не несут вовсе**: `userbot_listen.py:65-70` ставит формат `"%(message)s"`.
Замер: 64 090 строк файла, из них с ISO-датой **1 585 (2.5%)**, у всех 286 маркеров ведущей даты
**0**. Датировка по позиции (привязка к ближайшей дате выше по файлу) даёт окно **03.07–13.08,
31 сутки** — то есть ровно диапазон `drafts`, а не 09.06–15.08.

**Что из зацепки следует для вопроса захода.** Премиса владельца верна: состояние «продукт шага 1
есть, шаг 2 дальше не ушёл» встречается **сотнями** — 458 черновиков против 2 заявок. Материала
для суждения о состоянии (1) в избытке.

## 5. Почему ответ здесь ДРУГОЙ, чем на шаге «приход» — место записи

Это ядро вердикта. У «прихода» строка рождается ПОСЛЕ продукта, поэтому провал не оставляет
ничего. У «брони» строка рождается **в момент сборки, ДО всякой отправки**, и остаётся навсегда.

```
moderation_ipc.save_intake_candidate (moderation_ipc.py:157-168)
    INSERT INTO intake (text, status, …) VALUES (?, 'draft', …)
                                                     ↑ строка РОЖДАЕТСЯ уже в состоянии (2)
```

Полный конвейер и кто чем двигает состояние:

| шаг | код | статус после |
|---|---|---|
| менеджер жмёт «📋 Бронь» | `moderation_bot.py:491-492` | — |
| сборка карточки | `booking_draft.make_booking_and_intake` (`moderation_bot.py:223-224`) | — |
| **запись кандидата** | `save_intake_candidate` (`moderation_bot.py:235`) | **`draft`** |
| менеджер жмёт «✅ В CRM» | `confirm_intake` (`moderation_ipc.py:171-179`) | **`pending`** |
| userbot забирает (виток 3 с, `userbot_listen.py:224,227`) | `fetch_pending_intake` (`suggest.py:6939`) | `pending` |
| итог поста | `mark_intake` (`suggest.py:6950/6956/6964/6968`) | `posted` \| `failed` \| `skipped` |

### Вопрос 3: сколько выходов стои́т между сборкой карточки и записью

Считано по AST тем же способом, что для «прихода»:

```
moderation_bot._post_booking_card: строки 204–241
  СБОРКА make_booking_and_intake : строка 224      ЗАПИСЬ save_intake_candidate : строка 235
  все return: [213, 218, 229] ; все raise: []
  ДО сборки            (return < 224) : 2   [213 — не approver, 218 — нет транскрипта]
  МЕЖДУ сборкой и записью (224<r<235) : 1   [229]        ← ИСКОМОЕ ЧИСЛО
  ПОСЛЕ записи         (return > 235) : 0
ДЛЯ СРАВНЕНИЯ, шаг «приход» (задача 32): 7 выходов return None
```

**1 против 7 — и этот один даже не считается в минус.** Выход 229 стои́т в `except` самой сборки:
он срабатывает, когда сборка УПАЛА, то есть карточки нет вовсе — это состояние (1) по определению,
а не спрятанное (2). Выходов, способных оставить СОБРАННУЮ карточку без строки, — **ноль**.

Внутри сборки — два `return None` (`booking_draft.build_intake:511` жёсткий блок HONDA CLICK 125,
`:577` валидных полей нет). Оба тоже рождают состояние (1): карточка не собралась.

### Вопрос 2: какие поля меняются при (2)→(3) и есть ли отметка ПОПЫТКИ

Переход (2)→(3) делает один `UPDATE` (`moderation_ipc.py:193-196`) и меняет **4 поля**:
`status`, `posted_msg_id`, `reason`, `updated_ts`. Внутренний переход (2)-`draft`→(2)-`pending`
меняет 2 поля: `status`, `updated_ts`.

**Отдельной отметки ПОПЫТКИ отправки — НЕТ, есть только отметки ИТОГА.** Между взятием строки
(`suggest.py:6939`) и отметкой итога записей в `intake` не делается ни одной; из четырёх точек
`mark_intake` две стоя́т ДО всякой отправки (6950 `skipped` — внутренний аккаунт, 6956 `failed` —
не тот префикс), одна на успехе (6964) и одна на исключении (6968). Следствие называю прямо:
**если пост ушёл (6960/6962), а процесс умер до 6964, сообщение стоит в группе, а строка осталась
`pending` — источник покажет (2) там, где на деле (3).** Ложный отрицательный без единой отметки.
Исторически не встречался: маркеров падения поста в журнале 0.

## 6. Исторический пример: чем (2) доказано на живых строках

Состояния (2) в остатке нет ни одной строки — и всё же **обе исторические строки прожили его
измеримо**, потому что родились в нём:

```
id | status | posted_msg_id | client_id | len(text) | created_ts → updated_ts            | Δ сек
1  | posted | есть          | NULL      | 209       | 08.07 05:36:24.358 → 05:37:28.258 | 63.900
2  | posted | есть          | NULL      | 188       | 08.07 06:37:27.182 → 06:37:34.695 |  7.513
updated_ts > created_ts: 2 из 2 ; updated_ts == created_ts: 0
```

`created_ts` ставится при INSERT со статусом `draft`, `updated_ts` — при `mark_intake('posted')`.
Значит строка №1 была наблюдаема в состоянии (2) **63.9 секунды**, строка №2 — **7.5 секунды**
(виток поллера 3 с + тап человека). Читатель источника в эти окна увидел бы ровно «собрана, не
ушла», и никакая другая ветка кода этого вида ему бы не подсунула.

**Честно о силе этой демонстрации.** Поле `status` за всю историю приняло РОВНО ОДНО значение
(`posted`) — дисперсия по данным нулевая, и на одних агрегатах различение не показать. Показывают
его три меры вместе: (а) литерал `'draft'` в INSERT — состояние (2) есть состояние РОЖДЕНИЯ строки,
а не редкая аварийная ветка; (б) `updated_ts > created_ts` на 2 из 2 — переход состоялся и
датирован; (в) отдельный индекс `idx_intake_status` — схема спроектирована спрашивать по статусу.
Это доказательство «код + данные», и я не выдаю его за чисто числовое.

## 7. Что различитель НЕ покрывает (это НЕ СУДИМО, а не «в порядке»)

1. **Состояние (1) неразложимо.** «Кнопку не жали» и «жали, но карточка не собралась»
   (`build_intake` → None) дают одинаковый источник — строки нет. Числа нажатий кнопки в контуре
   не пишет никто: `moderation_bot.log` логирует только исключения, и их **0** («booking card #» = 0,
   «intake candidate #» = 0). Поэтому «458 → 2» **нельзя** читать как «456 сборок провалилось»:
   верное чтение — «успешных сборок за всю историю ровно 2, число попыток неизмеримо».
2. **Собранная, но не записанная карточка невидима.** Если `save_intake_candidate` бросит
   исключение (`moderation_bot.py:238-239`), карточка всё равно уйдёт менеджеру — уже без кнопки —
   а строки не будет. Исторически не случалось ни разу (0 в журнале), но ветка живая.
3. **`pending` двузначен** — см. §5: «ещё не забрали» и «запостили, но не отметили» неразличимы.
4. **Вход в сборку ограничен транскриптом.** Черновиков без транскрипта **184 из 458**: на них
   кнопка обрывается на `moderation_bot.py:215-218` ДО сборки. Первый черновик с транскриптом —
   05.07 20:17:58; 184 пустых — это до-миграционные строки 03–05.07.
5. **«Бронь заведена» этим источником не судится вовсе** — `intake` фиксирует, что ТЕКСТ ушёл во
   внутреннюю группу, а не что бронь есть в CRM. Обратной связи из CRM контур не читает
   (опись задачи 10, §6). Здесь ничего не изменилось.

## 8. Вердикт

**НАЙДЕН.** Различитель — таблица **`intake`**, поле **`status`**; подкрепляющие — `posted_msg_id`
(заполнен 2 из 2, ложных зелёных 0) и `reason` (причина неотправки). Три состояния шага «бронь»
отображаются на три непересекающихся предиката, и отображение держится не на удаче, а на **месте
записи**: строка рождается в момент сборки со статусом `'draft'`, до всякой отправки, и не
удаляется никогда (`sqlite_sequence = count = 2`, удалений 0). Выходов, способных оставить
собранную карточку без строки, между сборкой и записью — **0** (против 7 у «прихода»).

**Что это значит для экзамена.** Клиентский цикл как полигон **не отменяется** — в отличие от
шага «приход», шаг «бронь» судим в принципе. Но годен он сегодня плохо, и по причине, к
различителю отношения не имеющей: **весь корпус — 2 строки за один час одного дня (08.07,
05:36–06:37), обе с одинаковым исходом.** Отрицательных примеров (`draft`/`pending`/`failed`/
`skipped`) в истории нет ни одного, поэтому прибор, построенный на этом поле, проверить на
КРАСНОТУ живыми данными нельзя — только синтетикой. Это вывод о материале, а не о приборе.

## 9. Что НЕ проверено

- **Механизм потери 172 строк журнала** (04–05.07) — ротационных хвостов нет, дыра в середине.
  Вопрос к `log_setup`, не к источнику истины; в остатки.
- **Числа нажатий «📋 Бронь»** — не логируются вовсе (см. §7.1). Чтобы (1) стало разложимым,
  нужен след попытки сборки; правку здесь НЕ делаю, заход был на один вопрос.
