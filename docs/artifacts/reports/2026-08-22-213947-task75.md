## П.4 — принимает ли вердикт, снятый на снимке? Ответ кодом

**Ворота не различают пин и живьё ВООБЩЕ — ни поля, ни ветки.**

```
grep -n -i "pin\b|живьём|live"  client_contour.py   → 0 совпадений
grep -n "runner"                client_contour.py   → 0 совпадений
```

Замер полей по живой записи:

```
в записи    : cases cases_total checks_passed checks_total clean commit corpus corpus_sha failed result runner ts when   (14)
сверяются   : cases cases_total checks_passed checks_total clean commit corpus_sha result runs                          (9)
НЕ сверяются: corpus  failed  runner  ts  when                                                                          (5)
```

Отсюда точный ответ: **ворота живого прогона не ТРЕБУЮТ и отличить его от пинованного не МОГУТ.** «Живьём» держится не проверкой, а устройством канала (п.3): у единственного писателя пина нет. Следствие, которое надо знать: зелёная запись, положенная в файл пинованным прогоном, воротами была бы **принята** — ровно поэтому замок стои́т на писателе, и ровно поэтому запись такой строки руками была бы подделкой ворот, а не «оформлением результата». Побочно: непрочитанные `ts`/`when` означают, что у зелёного вердикта **нет срока годности**.

## П.5 — требуется ли рука ВЛАДЕЛЬЦА? Нет, ни одним условием

Ворота различают не РУКУ, а **ФАЙЛ-ИСТОЧНИК основания**. Второй ключ об авторе прогона не спрашивает ни строкой (см. п.4: поле `runner` не читается). Первый ключ — тоже:

```python
def approve(commit, who="owner", path=None, now=None):
    ...
    ap[c] = {"who": who, "ts": time.time() if now is None else now}     # who ЗАПИСЫВАЕТСЯ
...
def owner_approved(commit, path=None):
    c = short(commit)
    if not c:
        return False
    ap = _load(path or RELEASE_FILE).get("approved")
    return isinstance(ap, dict) and c in ap                              # who НЕ ЧИТАЕТСЯ
```

`who` в `client_contour.py` встречается 4 раза, и ни разу — на чтении из реестра. То есть «да владельца» удостоверяется тем, что строка легла в `pc_orchestrator.client_release.json`, а положить её может только рычаг `_exec_release_client` (`pc_orchestrator.py:2394-2409`), который дёргает команда владельца. Полномочие защищено ДОСТУПОМ К РЫЧАГУ, а не проверкой подписи.

Прогон исполнителя годится полностью — и это прямой замысел, записанный в коде (`client_contour.py:441-443`): «держать его выключенным значило бы **оставить владельца единственным ключом**».

**Условие 3 «есть зелёная запись».** Зачем: «ворота файлу НЕ ВЕРЯТ НА СЛОВО — кто может писать этот файл, тот открывает клиентский контур в обход „да“ владельца» (`client_contour.py:382-384`). ## П.8 — да, это архитектурная развилка, и вот она

**Говорю прямо: зелёное на снимке воротами не принимается в принципе** — но не запретом, а отсутствием дороги (п.3, п.4). Это не недоделка предыдущих заходов: замок поставлен сознательно и описан в коде. Значит решать владельцу, а не исполнителю.

**Вариант А — оставить как есть: второй ключ = ТОЛЬКО живой прогон.**
Цена: ключа не будет, пока флапает живая голова, — а флап этим заходом и предыдущими не устранён. Пин остаётся диагностическим прибором (воспроизводимым, чувствительным к порче кода: 12/12 → 7/12), но ключом не становится никогда. Выкатка держится на «да» владельца — то есть владелец **остаётся единственным ключом**, ровно то, чего второе основание должно было избежать. Дети продолжают жить на коде прежнего дня.

**Вариант Б — признать пинованное зелёное вторым ключом.**
Что потребуется: явная ветка в `trainer_verdict` и новое поле записи «на чём снят» (иначе ворота примут пин молча — сегодня они не различают). Цена: вердикт удостоверяет **КОД, а не ПРОДУКТ** — дрейф живой головы и живой сети уходит из-под ворот целиком; появляется новый незакрытый вопрос «кто и когда снимает свежий снимок» (устаревший снимок = ворота удостоверяют вчерашний мир, и у вердикта, напомню, сегодня нет срока годности); и тот, кто может снять снимок, получает влияние на ворота. Взамен — ключ становится достижимым СЕГОДНЯ: 12 из 12, покейсно одинаково в трёх прогонах и на +1/+7/+30/+365 суток.
