## Итог в пяти строках

1. **Дата 2099 — не решение, а ЗАМЕНА.** Журнал полосы дословно хранит задуманную команду
   `schtasks /Create /TN pc_orchestrator … /SC ONSTART /RL HIGHEST /RU mxfill1 /F` и рядом отчёт
   «watchdog(5мин)+**ONCE-target** зарегистрированы (**ONSTART нужна admin у Филиппа**)». То есть

   ТОЛЬКО вотчдог, второго экземпляра не будет».
2. **Но 2099 — не причина простоя, и правка одной этой даты не даст ничего.** Все пять наших
   задач имеют `LogonType = InteractiveToken`; такая задача **не запускается без интерактивной
   сессии независимо от триггера**. Живое доказательство: у вотчдога триггер — время + повтор
   каждые 5 минут бессрочно, за окно простоя пришлось **122 назначенных срабатывания и ноль
   исполненных**, а `NumberOfMissedRuns` при этом **0** — Планировщик их даже не считает
   пропущенными.
3. **Пароль для подъёма по старту системы НЕ обязателен.** На этой машине УЖЕ живёт задача,
   поднимающая наш `venv\Scripts\python.exe` из этого репо по триггеру загрузки, — наблюдатель
   ожиданий `TurboBabyExpectPC` под **SYSTEM**, заведённый 11.08 (журнал: «пароль не вводился,
   plaintext не хранится»). Пароль нужен ровно в одном варианте: если исполнять от `mxfill1` без
   входа.
4. **Автологон, выбранный владельцем 06–07.08 как решение, так и НЕ ВООРУЖЁН**: `AutoAdminLogon = 0`,

5. **Класс подтверждён замером своей полосы:** за 21.6 суток (28.07–18.08) — три эпизода «контура

## 2. История: когда заведена, когда правилась, есть ли запись про 2099

### Когда

```
pc_orchestrator            created=2026-07-04 23:24:44  modified=2026-07-04 23:24:44
pc_orchestrator_watchdog   created=2026-07-04 23:23:58  modified=2026-07-04 23:23:58
```

(`Get-Item C:\Windows\System32\Tasks\<имя>`; `RegistrationInfo/Date` в XML совпадает посекундно.)

**Создание и последняя правка совпадают посекундно у обеих задач.** Значит `2099-01-01` стоит там
**с момента заведения, 04.07.2026 23:24:44, и с тех пор не трогалось ни разу.** Вотчдог заведён на
**46 секунд раньше** демона — то есть сначала подъёмник, потом мишень: это порядок человека,
который сознательно строит связку «мишень + подъёмник», а не оговорка.

### Журнал событий Планировщика — его НЕТ, и это не «не нашёл»

```

Get-WinEvent -LogName 'Microsoft-Windows-TaskScheduler/Operational'

### Журнал полосы — по ПОЛНЫМ телам, и он ответ ДАЁТ

### Что это значит — вывод по забору

Задумана была задача с триггером **старта системы** и повышенными правами. `ONSTART` + `/RL HIGHEST`
+ `/RU mxfill1` требовали и админа, и (без `/IT`) пароля учётки — ни того, ни другого у сессии не
было. Вместо этого зарегистрировали «**ONCE-target**»: задачу-мишень с датой, которая не наступит,
чтобы её звал `schtasks /Run` из вотчдога. Настоящий `ONSTART` записали **в остатки** — и остаток
живёт незакрытым **45 суток**.

**Забор, таким образом, двойной, и половинки надо разделить:**

- **Половина «мишень для `/Run`» — живая и нужная.** Убрать её нельзя: `MultipleInstancesPolicy =
  IgnoreNew` + единственная точка подъёма — это то, чем контур не плодит вторых демонов. Вотчдог
  зовёт мишень буквально: `pc_orchestrator.py` → `_schtasks_run` → `["schtasks","/Run","/TN",TASK_NAME]`.
- **Половина «дата 2099» — временный протез под нехватку прав, а не проектное решение.** Трогать её
  не страшно; страшно трогать её ОДНУ (см. §3 и §8).

Подтверждающая мина в нашем же коде — шапка `pc_orchestrator.py:22` до сих пор утверждает:

```
Автозапуск: schtasks (ONSTART) + watchdog (--watchdog): …
```

Документация описывает **задуманное**, а не поставленное. Грепающий по шапке получит ложное
«ONSTART настроен».

## 3. Нужен ли сохранённый пароль для подъёма по триггеру старта системы

**Ответ: НЕТ, не обязателен — и это доказано живым фактом ЭТОЙ машины.** Но у ответа три ветки, и
путать их дорого.

### Живое доказательство «без пароля можно»

На машине уже есть задача, которая по триггеру **загрузки** запускает наш `venv\Scripts\python.exe`
из этого репо и переживает выход пользователя — наблюдатель ожиданий. Журнал полосы, 10.08.2026:

DONE Dispatch 06:37: наблюдатель ожиданий ПК заведён в Планировщике — задача TurboBabyExpectPC
под SYSTEM (пароль не вводился, plaintext не хранится), триггеры boot + повтор 10 мин …;
LastRunTime 11.08 06:34:29, LastRes[ult…]
```

**Задача существует прямо сейчас, хотя ни `Get-ScheduledTask`, ни COM-перепись её не показывают.**
Обе переписи дали по 204 задачи и обе слепы одинаково — потому что сессия не повышена. Контроль
(та же проба на трёх именах, файловая система и COM Планировщика раздельно):

```
=== файловая система ===
ZZZ_ne_sushestvuet_12345   -> ItemNotFoundException | Cannot find path … because it does not exist.
TurboBabyExpectPC          -> UnauthorizedAccessException | Access is denied
pc_orchestrator            -> ЧИТАЕТСЯ  created=2026-07-04 23:24:44

=== COM Schedule.Service.GetFolder('\').GetTask(name) ===
ZZZ_ne_sushestvuet_12345   -> The system cannot find the file specified. (0x80070002)
TurboBabyExpectPC          -> Access is denied. (0x80070005 E_ACCESSDENIED)
pc_orchestrator            -> ЕСТЬ, State=4 LastRun=18.08.2026 14:13:03 NextRun=01.01.2099
```

Несуществующее имя даёт «файла нет», `TurboBabyExpectPC` даёт «доступ запрещён» — **разные отказы,
и разница и есть доказательство существования.** Тот же контроль независимо снят 14.08 и лежит в
журнале. И задача **работает**: `tmp/expect_pc/state.json` живой (17:44:39 в день замера), а два
эпизода О2/О3 были открыты **04:22:14 и 04:24:29** — то есть через ~20 минут после перезагрузки,
когда в систему ещё никто не входил.

**Мина на будущее:** `Get-ScheduledTask` о невидимой задаче **молчит**, а не жалуется. Вывод «такой
задачи нет», сделанный из неповышенной сессии, — born-false. Правильная проба — контроль на паре
имён, как выше.

### Три ветки ответа

| принципал | пароль? | откуда это следует | цена |
|---|---|---|---|
| **SYSTEM** (`S-1-5-18`) | **НЕ нужен** | живой `TurboBabyExpectPC` на этой машине + журнал 10.08 «пароль не вводился». На машине ещё 16 системных задач с `BootTrigger` под `ServiceAccount`/СИСТЕМА | нужен **админ** для регистрации. Для демона — ломает `claude -p`, см. §8 |

### Чем именно поднимается вотчдог, поднявший демона — и поправка к диагностике 18.08

Диагностика 18.08 (`docs/artifacts/2026-08-18-task43-stuck-diagnosis.md`, §Итог п.3) говорит:
«Демона поднимает вотчдог, **живущий в userbot**». **Это неверно.** Вотчдогов два, и это разные
сущности:

1. **Тот, что поднял ДЕМОНА, — отдельная задача Планировщика `\pc_orchestrator_watchdog`**,
   исполняющая `pc_orchestrator.py --watchdog` коротким процессом каждые 5 минут. Три
   независимых доказательства:
   - `grep -n "watchdog\|вотчдог\|schtasks" userbot_listen.py` → **единственное совпадение —
     комментарий** в строке 486, ни одной исполняемой строки;
   - такт лога совпадает с расписанием задачи посекундно. `StartBoundary 23:23:00` + `PT5M` даёт
     минуты `…:03, :08, :13, :18, :23, :28, :33, :38…`, и живые строки ложатся ровно в них:
     `03:08:02, 03:13:02, 03:18:02, 03:23:02, 03:58:02, 14:13:03, 14:18:03, 14:23:02, 14:28:02,
     14:33:02, 14:38:02`;
   - `NextRunTime = 18.08.2026 17:48:00` при `LastRunTime = 17:43:01` — тот же такт живьём.
   Поднимает он через `_schtasks_run` → `schtasks /Run /TN pc_orchestrator`.
2. **Тот, что поднял `moderation_bot`, — не процесс, а функция `client_watchdog_tick` ВНУТРИ
   `poll_once` самого демона** (`pc_orchestrator.py:8631`, троттлинг 5 мин). Своей задачи
   Планировщика у него нет вовсе.

**Что поднимает сам вотчдог-задачу: ничего. Её «поднимает» вход пользователя** — до появления
интерактивной сессии Планировщик её триггер не отрабатывает. Дословный замер окна простоя,
`pc_orchestrator.log`:

```
2026-08-18 03:58:02,524 INFO watchdog: продукту 277с, но идёт объявленный заход (92с из 4500с) …
2026-08-18 14:13:03,241 WARNING watchdog: продукта нет … и процессов демона НЕТ — поднимаю через schtasks
```

Между ними — **ни одной строки**. Счёт строк лога по часам 18.08:
`00:18 · 01:6 · 02:14 · 03:14 · (04…13 отсутствуют полностью) · 14:29 · 15:10 · 17:3`.

От первого назначенного срабатывания после загрузки (04:03:00) до последнего перед входом
(14:08:00) укладывается **122 срабатывания. Исполнено ноль.** И `NumberOfMissedRuns = 0` —
Планировщик не считает их пропусками, потому что попытки запуска не было ни одной: условие
принципала не выполнялось. Это самый чистый факт разбора: **не «триггер не тот», а «принципал не
тот»**.

## 5. Moderation_bot: зависит ли его подъём от того же условия входа

**Да — и жёстче остальных: у него ТРИ последовательных условия, а не одно.**

Цепочка (`pc_orchestrator.py` → `_client_watch_specs` → `_raise_client_bot("moderbot")` →
`pc_agent.ModerbotProcess().start()`):

```
вход пользователя
  → задача \pc_orchestrator_watchdog отрабатывает свой 5-минутный такт   [условие 1: вход]
  → schtasks /Run /TN pc_orchestrator → демон стартует                    [условие 2: жив демон]
  → poll_once → maybe_client_watchdog → client_watchdog_tick              [условие 3: виток ДОШЁЛ]
  → _raise_client_bot("moderbot") → pc_agent.ModerbotProcess().start()
```

Живой замер 18.08 показывает цену третьего условия:

```
14:13:05  ДЕМОН СТАРТ
14:13:56  CLAIM id=44 in_progress        ← poll_once ушёл в синхронный claude -p
14:38:51  COMPLETE id=44 status=done
14:38:55  moderation_bot запущен агентом, PID 15760
14:39:07  контур-вотчдог: moderation_bot МЁРТВ (лежал 43812с, смерть 1/3) → подъём ok=True, PID после=[15760]
```

`43812 с` = **12 ч 10 м 12 с** — совпадает с числом из постановки. Демон поднялся в 14:13:05, а
модербот — только в **14:38:55, через 25 м 50 с**, потому что `poll_once` всё это время
синхронно исполнял задачу 44. Задача имеет право молотить до 45 минут (`timeout=2700s`, две
попытки), значит **штатная задержка подъёма модербота после подъёма демона — до ~45 минут, и это
не сбой, а устройство**.

Итого разница в простоях честно раскладывается: демон — 10 ч 19 м (от heartbeat 03:53:25),
модербот — 12 ч 10 м, и лишние 1 ч 51 м это не «модербот умер раньше», а сумма «его лог замолчал
раньше (02:28:55) + подъём ждал конца задачи 44».

**Отдельная мина, которая тут же и живёт:** у модербота есть `skip` — «нет `MODERBOT_TOKEN` →
это не смерть, а штатный простой». Под SYSTEM или в session 0 окружение другое, и `skip`
превратил бы реальную смерть в вечное «штатный простой» **молча**. К сегодняшнему состоянию это
не относится, но любой перенос принципала обязан это проверить.

## 6. Что будет при следующей перезагрузке, если ничего не менять

**Одной строкой:** контур встанет от момента перезагрузки до первого входа владельца — по
единственному измеренному случаю этого класса это **10 ч 07 м**, а по окну, в котором Windows
вообще имеет право перезагружаться (`ActiveHoursStart = 8`, `ActiveHoursEnd = 2` → окно
**02:00–08:00**, целиком ночное), ожидаемая вилка **6–20 часов**.

Обоснование числами:

```
RebootRequired(WU) = False ; RebootPending(CBS) = False        (прямо сейчас перезагрузка не висит)
ActiveHoursStart = 8 ; ActiveHoursEnd = 2 ; SmartActiveHoursState = 0
```

Перепись `System`-лога за 21.6 суток (28.07–18.08):

| эпизод | что было | машина | контура нет |
|---|---|---|---|
| 29.07 19:18:43 → 30.07 01:17:17 | аварийный обрыв (`6008`), затем две перезагрузки на обновления | **выключена** 5 ч 56 м | 5 ч 58 м |
| 06.08 00:05:33 → 06.08 19:38:27 | аварийный обрыв (`6008`) | **выключена** 19 ч 32 м | **19 ч 33 м** — худший |
| 18.08 04:00:05 → 18.08 14:08:50 | две перезагрузки на обновления (`MoUsoCoreWorker`, затем `TrustedInstaller`) | **ВКЛЮЧЕНА** | **10 ч 07 м** |

**Три эпизода за 21.6 суток** — совпадает с реплеем из постановки. Но их надо разделять: только
третий — «здоровая включённая машина без контура», и только его лечит автостарт. Первые два лечит
BIOS `Restore after AC Power Loss` и ИБП, и они остаются открытыми независимо.

Два уточнения, каждое — готовый ложный вывод, если его не назвать:

- **Класс «перезагрузка на обновления» сработал ДВАЖДЫ, а не впервые 18.08:** 30.07 в 01:15 и
  01:16 машину так же перезагрузил `TrustedInstaller`. Он ничего не стоил только потому, что
  владелец вошёл через **24 секунды** после загрузки — то есть случайно не спал. Считать 18.08
  редкостью нельзя.
- **Рычаг «отодвинуть окно перезагрузок» уже выбран до упора.** `8 → 2` — это ровно 18 часов, а
  18 часов и есть максимум активных часов, разрешённый Windows (документация Microsoft; замером
  своей полосы не подтверждал). Расширять нечего: окно 02:00–08:00 неустранимо.
- `AutoReboot = 0` по-прежнему: при BSOD машина не перезагрузится сама вовсе. Отдельный сценарий,
  открыт с 06.08.

## 7. Варианты подъёма — что можно было бы сделать (НИЧЕГО НЕ ВЫПОЛНЕНО)

Все шесть перечислены с ценой и риском; ни один не применён, ни одна настройка не тронута.

### А. Вооружить автологон — **доводка уже принятого решения, а не новая развилка**

- **Что:** владелец один раз запускает `autologon_arm.ps1` в **обычном** окне PowerShell (не в
  сессии Claude). Скрипт лежит в корне репо с 07.08, проверен на разбор (0 ошибок) и компиляцию.
- **Требует от владельца:** ввести пароль учётки `mxfill1` вслепую. Если пароль пуст — скрипт
  откажет (`СТОП: введён пустой пароль`), и надо сначала задать непустой.
- **Даёт:** контур целиком, **включая RC**, без единой правки задач: сессия создаётся сама, все
  пять задач отрабатывают как при живом человеке. `\tb_lock_on_logon` запирает экран через 5 с.
  Полная перекличка по хронометражу — **~6 минут после загрузки**.
- **Риск:** пароль лежит на машине в LSA Secrets — физический доступ к машине даёт к нему доступ
  (машина стоит в чужой квартире). Смена пароля учётки ломает автологон **молча**. Блокировка на
  `+5 с` наступает раньше подъёма RC-консоли (`+18 с`) — не измерено, ручка `Delay` → `PT60S`.
- **Замер сегодня:** `AutoAdminLogon = 0`, `DefaultPassword` отсутствует,
  `DevicePasswordLessBuildVersion = 2` — **не вооружён**, как и 07.08.

### Б. Перевести вотчдога под SYSTEM с триггером загрузки (зеркало `TurboBabyExpectPC`)

- **Требует:** админ у владельца (`schtasks /Create … /RU SYSTEM`). **Пароля НЕ требует.**
- **Риск — молчаливый и высокий:** вотчдог под SYSTEM позовёт `schtasks /Run /TN pc_orchestrator`,
  а МИШЕНЬ останется под `mxfill1/InteractiveToken` и без входа не стартует. Получим вечный
  «ТИХИЙ СБОЙ ПРЕДОТВРАЩЁН» и алярм владельцу вместо подъёма. **Сам по себе вариант Б не работает** —
  он требует и В.

### В. Перевести и мишень `\pc_orchestrator` под SYSTEM

- **Требует:** админ. **Пароля НЕ требует.**
- **Риск:** это и есть §8. Демон поднимется, а `claude -p` не найдёт авторизацию — см. ниже.

### Г. `LogonType = Password` для вотчдога и мишени («вне зависимости от входа», от `mxfill1`)

- **Требует:** админ + **пароль в Планировщике** + право «Вход в качестве пакетного задания».
- **Даёт:** профиль пользователя, DPAPI разворачивается, `~/.claude/.credentials.json` доступен.
- **Риск:** session 0 без рабочего стола — **RC мёртв заведомо** (`rc_remote_control.vbs` прямо
  пишет, что интерактивной сессии нужен живой TTY). При пустом пароле вариант отпадает физически
  (`LimitBlankPasswordUse = 1`).

### Д. Не менять подъём, сжать простой сигналом

- **Требует:** ничего в репо. Нужен настроенный пароль неконтролируемого доступа AnyDesk.
- **Даёт:** О2/О3 уже открывают эпизоды через **~20 минут** после остановки (18.08: 04:22:14 и
  04:24:29 — и это работало во время простоя, потому что наблюдатель под SYSTEM). AnyDesk и
  Tailscale — службы `LocalSystem`/`Auto`, живут до входа → владелец входит удалённо и поднимает.
- **Риск:** простой не исчезает, а становится равен времени реакции человека. Не решение, а жгут.

### Е. Отодвинуть окно перезагрузок Windows

- **Нерабочий.** Активные часы уже 18 из 18 возможных. Запаса ноль.

**Что бы я рекомендовал владельцу:** **А**. Не потому, что она «лучшая по бумаге», а потому, что
решение по ней уже принято 07.08, инструмент написан и проверен, и это **единственный вариант,

одиночку (Б), либо упираются в §8 (В), либо убивают RC (Г).

## 8. Предсмертный взгляд — как провалится будущая починка

**Одной строкой:** починку сделают самым лёгким способом — переведут задачу под **SYSTEM** с
триггером загрузки (пароля не просит, регистрируется в одну строку, живой пример `TurboBabyExpectPC`
рядом), убедятся по heartbeat, что «демон поднялся сам», — и не заметят, что `claude -p` ищет
авторизацию в `C:\Users\mxfill1\.claude\.credentials.json`, которого у профиля SYSTEM нет, так что
демон будет исправно брать задачи и **валить их все подряд**, а О2, О4 и вотчдог промолчат, потому
что оборот `poll_once` идёт и heartbeat свеж — они мерят ОБОРОТ, а не УСПЕХ.

Подпорка под этот прогноз — замером, а не рассуждением:

```
ЕСТЬ  C:/Users/mxfill1/.claude/.credentials.json  (3768 байт, mtime 2026-08-18 14:09:02 +0700)
ЕСТЬ  C:/Users/mxfill1/.local/bin/claude.EXE      (263931552 байт)
лог демона: claude=C:\Users\mxfill1\.local\bin\claude.EXE
```

Обе точки — **в профиле пользователя**. У SYSTEM `%USERPROFILE%` = `C:\Windows\System32\config\systemprofile`.
Плюс: у ПК-исполнителя **ветки фолбэка нет вовсе** (`--fallback-model` есть только у думателя), то
есть отказ головы = провал задачи, а не деградация. И `MODERBOT_TOKEN`-skip превратит смерть
модербота в «штатный простой» молча.

**Дешёвый замок против ровно этого:** любая проверка починки обязана быть не «демон поднялся», а
«демон **сдал задачу** `done` после перезагрузки без входа человека» — то есть одна короткая
read-only задача в очередь и её итоговый статус. Заход, проверенный по heartbeat, проверенным не
считается.
