остановился и не начал третью единицу поштучно.

**Что сделал вместо третьей единицы:** сменил не объём, а ЦЕНУ единицы. Ряды считаны ОДНИМ
пакетным проходом (одна команда `awk` по логу даёт окно `CLAIM→парковка` каждого ряда, один
цикл `git log --since/--until` — продукт внутри окна, один `find -newermt` — продукт на диске).

## 5. Что делает код в точке приговора (пункт 5) — СЛОВАМИ

**Маркер бьёт продукт ВСЕГДА. Адрес результата перед объявлением `needs_approval` не
спрашивается ни одной веткой.**

Порядок в `pc_orchestrator.py` дословный:

1. `_run_task_impl` (строки 2640–2669): сразу после возврата `run_claude` читается файл-маркер
   гарда, затем
   ```python
   card = _detect_needs_approval(out, marker_content, run_token)
   if card is not None:
       log.info("id=%s NEEDS_APPROVAL (карточка ГАРДА, маркер нашего запуска)", tid)
       return "needs_approval", card
   ```
   Этот `return` стои́т **ПЕРЕД** проверкой кода возврата `rc`, перед разбором пустого stdout,
   перед всеми ветками провала. Ничего, кроме маркера и токена запуска, в решении не участвует.
2. `process_new` (строки 4069–4110): опорный снимок по названному адресу снимается ДО захода
   (`done_base = done_judge_pc.baseline(text)`), а СУДЬЯ адреса зовётся строкой 4110 —
   `status, result = _judge_done(...)` — **внутри ветки `if status == "done"`**. Ряд, ушедший в
   `needs_approval`, до этой строки не доходит вовсе: ветка `if status == "needs_approval"`
   (строка 4077) заканчивается `set_needs_approval` и уходом под надзор.

То есть на полосе ЕСТЬ читатель адреса — `done_judge_pc` + `content_product_verifier`, и он даже
снял базовый снимок по адресу перед заходом, — но включён он ТОЛЬКО на закрытии «сделано».
Маркер гарда стои́т на дороге раньше и уводит ряд мимо судьи. Спросить «а продукт по адресу уже
лежит?» некому: такой ветки в коде нет.

Это разведка, кода не тронуто ни строки: `git diff --stat` по `pc_orchestrator.py` пуст.

## 7. Предел разведки (пункт 7)

Что посчитать не удалось и почему — по-честному, без округления в свою пользу:

1. **Дословный АДРЕС РЕЗУЛЬТАТА восстановлен только у 2 рядов из 43** — у #239
   (`03-informing.0904`) и #72 (`00-lesson-migrate-book.0906`): их ключ задания демон печатает в
   лог строкой `ящик Штаба: взято 1 (#N ключ=…)`. У остальных 41 ряда текста ТЗ в логе нет
   ВООБЩЕ: ящик Штаба заведён недавно, а задачи владельца и автозадачи попадают в очередь без
   следа текста. Поэтому у 41 ряда исход считан не по дословной строке адреса, а по
   КАНОНИЧЕСКОЙ ФОРМЕ продукта полосы (файл в `docs/artifacts` или собственный коммит захода).
   Строгий счёт «адрес назван дословно и сверен» дал бы **2 зелёных / 0 красных / 41
   неизвестный** — и он бесполезен; измеренное число 40/3/0 честнее по смыслу, но опирается на
   форму адреса, а не на его букву. Разницу называю прямо, чтобы её не приняли за твёрдость.
2. **Текст ТЗ из очереди не поднять.** Номера очереди переиспользованы (см. §2), ряды августа в
   живой очереди не лежат, а черновики докладов `tmp/pc_report/task<id>-…` заведены только с
   04.09 — из 43 рядов ими покрыты 2. Читать историю очереди через мост я не стал: это сеть ради
   данных, которых по августу там уже нет.
3. **Узлы мозга как адрес результата не проверялись ни у одного ряда.** Часть заданий полосы
