## 2. Схема решателя и правил

**Действия** (`topic_decider.py`, модель возвращает ровно один JSON-объект):

| действие | поля | что делает в тени |
|---|---|---|
| `записать` | `что` (пробег / работа), `км`, `источник` = mid сообщения-основания | правила → дверь-пометка: `_odo_confirmed` или «кнопка Пыма» |
| `спросить` | `вопрос`, `ждём_что`, `от_кого` | правило второго вопроса |
| `ответить` | `текст` | — |
| `позвать` | `кого` ∈ {Пым, владелец}, `зачем` | — |
| `ничего` | `почему` | — |

**Разбор** (`parse`): принимается только JSON-объект (допустима обёртка ```json). Пусто, проза, JSON
внутри прозы, два объекта, список, чужое действие, нет обязательного поля, `кого` вне двух ролей →
`{"действие":"ничего","почему":"не понял"}`. Догадок нет: число из прозы не выдёргивается.

**Правила кодом** (`rules`; порядок = приоритет; модель о них не знает и не решает):

| правило | условие | итог |
|---|---|---|
| `без_mid` | `записать` без `источник`, или mid не равен входящему и не встречается в ленте темы | `ничего`: запись отклонена |
| `нет_числа` | `записать` пробег без числа | `ничего` |
| `убывание` | км < последнего записанного (событие `record` ленты, иначе `_LAST_RECORDED_KM`) | `позвать` Пыма |
| `потолок` | `odo_ceiling.verdict(км, текущий, ODO_CEILING_KM)` = ask (текущий — `_odo_current` моста, иначе записанный) | `позвать` Пыма |
| `доверие` | основание — сообщение не доверенного автора (входящее: `_act_trusted`; из ленты: роль pym/owner) | `записать`, но дверь «кнопка Пыма» |
| (без правила) | основание от Пыма/владельца, пробег | `записать`, дверь `_odo_confirmed` |
| (E2b) | `записать` работу ТО (не пробег) | дверь «кнопка Пыма» всегда, кто бы ни назвал |
| `второй_вопрос` | `спросить`, когда открыт вопрос того же вида (вид: пробег / работы / иначе слово) | `ничего`: «вопрос вида … уже открыт (#id)» |

Открытые вопросы по видам (`decider_open_kinds`): файл вопроса о пробеге из 0088 (`_MILEAGE_Q`, с id
сообщения-вопроса) и словари памяти `_PENDING_MILEAGE`, `_SOFT_ODO_PENDING`, `_ODO_LOWER_PENDING`,
`_BATCH_ODO_PENDING`, `_PENDING_CORRECTION`, `_PENDING_WORKS` (всё это вид «пробег»), плюс
`_ACT_GATE_PENDING` (вид «подтверждение»).

**Как идёт одно решение:**
1. Вход (`decider_shadow`). Флаг выключен → `None` сразу, ни одного вызова.
2. Снимок СИНХРОННО, до перехватов (`decider_snapshot`): `topic_context` без моста, факты для правил
   (mid, роль, `_act_trusted`, mid→роль событий ленты, записанный пробег, порог потолка, открытые
   виды). Цена — чтение одного файла ленты.
3. Фоновая задача (`decider_run`, `create_task`; прежний путь её не ждёт). В потоке: ТО-заявка
   (`_sp_open`) и текущий пробег (`_odo_current`) — только чтение моста. Потом модель `claude.quick`
   (`max_tokens=400`, `tag="decider"`, `expect_json=True`; модель — `TOPIC_DECIDER_MODEL` или
   умолчание клиента). Дальше разбор, правила, строка журнала и событие ленты.
4. Строка журнала — только действие, числа, id и имя правила, без текста людей и модели:
   `🧠 решатель (тень): #12401 → позвать · Пым · правило убывание (модель: записать)`.
5. Событие ленты `kind=decision`: `on` (mid входящего), `input_kind`, `model` (как ответила модель),
   `final` (итог правил), `rule`, `door`, `parsed`. `topic_feed.read` такие события по умолчанию
   ПРОПУСКАЕТ (`SHADOW_KINDS`). Поэтому контекст мозга и окно «последних 30» с тенью и без неё
   одинаковы. Видеть их — `read(..., shadow=True)`.

## 6. Что нужно для экзамена на архиве chatlog/servicing

Чистая часть (`topic_decider.py` + `odo_ceiling.py`) импортируется на ПК без splinter, поэтому экзамен
можно гонять там, где лежит архив. Нужно:

1. **Перевод строк архива в события ленты.** Поля есть: `mid, ts, topic_id, reply_to, text, media,
   bot`. Не хватает роли: автор в архиве — псевдоним `p`+12 hex (`chatlog_store.py:159–170`). Надо
   вычислить псевдонимы Пыма и владельца той же солью на ПК и сопоставить им `pym`/`owner`; имена в
   артефакты не выносить. `bot: true` → `bot_ask`, если есть «?», иначе `bot_msg`; фото → `photo`.
2. **Разбор фото.** В архиве лежат файлы снимков (233), но не разбор. Варианты: строки журнала
   `разбор mileage=… conf=…` из `splinter.log` по теме и времени (без модели) или повторное зрение
   (233 вызова модели).
3. **Что легло в учёт.** Событий `record` в архиве нет. Их дают строки `splinter.log`
   `→ одометр <байк> = N (подтверждено человеком)` и записи ТО по «да», привязанные по байку и времени.
4. **Открытые вопросы на каждый момент.** Их нужно восстановить из `bot_ask` вида L («Вижу N км…») и
   ответов на них: срок 3 ч, ответ реплаем засчитывается в любом возрасте (0088).
5. **Разметка истины.** Ожидаемое действие на каждое сообщение размечают владелец или Штаб.
   Обязательный минимум: 24 вопроса L за 14 суток, из них 4 протухших, и случай 8952. Исход по журналу
   годится как черновик разметки, но не как истина.
6. **Прогон с живой моделью.** ≈354 сообщения = ≈354 вызова `quick` (плюс зрение, если п.2 через
   модель). Это живой вызов модели, в этом задании запрещён. Нужен отдельный допуск и бюджет.
7. **Пороги допуска** (SPLAGENTMAP0110 §5): 0 записей мимо гейта (по правилам — проверяемо счётом
   `rule`/`door`); 0 вопросов при открытом таком же; доля правильного действия ≥ 90 % на темах с
   вопросами о пробеге.
8. **Окно архива** 18.09–30.09 11:23. Реплай 8952 (01.10 06:08) в него не входит; есть ли он в сборе
   01.10 09:09 UTC — НЕИЗВЕСТНО, не проверял.

Альтернатива без перевода архива — неделя тени в проде: события `decision` лягут в ленту с тем же
`topic_context`, что видит мозг, и сверяются с тем, что сделал прежний код.
