# Правила бота под git: один файл взят, второй недостижим без красной операции

**Дата:** 2026-08-17 (задача помечена 2026-08-16) · **Коммит правил:** `95077e4` · **Основание:**
[`2026-08-16-regression-probe10.md`](2026-08-16-regression-probe10.md) (коммит `164cea9`)

**Повод.** У набора правил бота нет ни истории, ни отката: прогон регрессии однажды их изменит,
и вернуть будет нечем. 16.08 обошлось случайно — оба sha256 совпали до и после прогона.

## Итог одной таблицей

| файл | sha256 (основание) | взят под git | почему |
|---|---|---|---|
| `trainer_rules.json` | `bee2d75f…94e4` | **ДА**, коммит `95077e4` | ничто не мешало: `.gitignore:64`, снято `git add -f` |
| `manager-bot/docs/playbook.md` | `88e73178…c6dd` | **НЕТ** | путь за границей ВЛОЖЕННОГО репозитория; обойти можно только удалением `manager-bot/.git` — красная операция и решение владельца |

Оба sha256 на диске совпали с основанием **до** любых действий — основание живо, замер не протух.

## Замок A. Содержимое не изменилось

Проверено не обещанием, а тремя числами для `trainer_rules.json`:

| замер | значение |
|---|---|
| sha256 на диске ДО `git add` | `bee2d75f81b916ab83796442a70b7350cf348e498865a2fdbe5a09d68a1494e4` |
| sha256 на диске ПОСЛЕ `git add` | тот же, `bee2d75f…94e4` |
| sha256 кругового рейса (`checkout-index`, тот же фильтр, что у отката) | тот же, `bee2d75f…94e4`; `cmp` молчит |

**Риск здесь был настоящий, а не теоретический.** В репозитории `core.autocrlf=true`, а файл несёт
7 CRLF и **не имеет завершающего перевода строки** (последний байт — `}`). Git хранит блоб в
**1901 байт** против **1908** на диске: семь `CRLF` свёрнуты в `LF`. То есть **наивная сверка «sha
блоба против sha диска» показала бы порчу там, где её нет** — и наоборот, отсутствие такой сверки
скрыло бы настоящую порчу при смешанных концах строк. Поэтому замок снят кругом «add → checkout
через штатный фильтр → `cmp` с живым», а не сравнением блоба.

`playbook.md` в этот замок не входит: он не добавлялся вовсе (см. ниже), его sha256 на диске
остался `88e73178…c6dd`.

## Замок B. Секретов внутри нет — но у `playbook.md` есть НАЗВАННОЕ место под них

Скан обоих файлов на `token|password|secret|api_key|bearer|private_key|ssh-rsa|AKIA|sk-…|xox…|ghp_|AIza`
и на длинные случайные строки (`[A-Za-z0-9_+/-]{24,}`):

| файл | совпадений на ключи/токены/пароли | длинных случайных строк |
|---|---|---|
| `manager-bot/docs/playbook.md` | **0** | **0** |
| `trainer_rules.json` | **0** | **0** |

Содержимое по существу: `trainer_rules.json` — 6 выученных уроков (тексты правил формулировки,
происхождение `тренажёр`); `playbook.md` — стиль общения, запреты и 9 выученных правил. Ни имён
клиентов, ни телефонов, ни реквизитов.

**Но честный ответ шире «секретов нет».** В `playbook.md` есть раздел, отведённый под них прямо:

```
## Факты (кошельки/контакты)
- (реквизиты оплаты/контакты — по мере необходимости; пока пусто)
```

Это ровно то «место для секретов», о котором спрашивала постановка. Сегодня оно **пусто**, поэтому
запрет на добавление из него НЕ следует. Важно, кто его наполняет: **автоматика туда не пишет** —
все три писателя книги (`suggest.append_playbook_rule` / `replace_playbook_rule` /
`remove_playbook_rule`) работают только по секции `_LEARNED_HEADER = "## Выученные правила"`, а
`remove_playbook_rule` про остальное говорит прямо: «прочее (стиль/факты) не трогаем». Значит
реквизиты в этот раздел кладёт **человек руками**, и это происходит редко и осознанно.

**Следствие для владельца:** если `playbook.md` когда-нибудь возьмут под git, в тот же день надо
решить судьбу этого раздела — попавший в историю реквизит из неё не вынимается. Сегодня он пуст,
и решать нечего.

## Почему `playbook.md` взять не удалось — четыре измеренных факта

1. **`manager-bot/` — отдельный репозиторий.** `git -C manager-bot rev-parse --show-toplevel` →
   `D:/turbobaby-bot/manager-bot`, у него **свои 2 коммита** и **свой remote**
   `https://github.com/mxfill77/turbobaby-manager-bot.git`.
2. **`git add -f manager-bot/docs/playbook.md` делает НИЧЕГО при `exit=0`.** Пустой вывод, пустой
   индекс, код возврата ноль — **молчаливый ложный успех**. Сессия, доверившаяся коду возврата,
   отрапортовала бы «файл добавлен», не добавив ничего. Это готовый ложный диагноз, и он проверен
   здесь `git diff --cached --name-only` (пусто) после попытки.
3. **Добавление каталогом отката НЕ даёт.** `git add -n -f manager-bot/` предупреждает сам:
   `warning: adding embedded git repository` … `Clones of the outer repository will not contain the
   contents of the embedded repository`. Это gitlink — указатель на коммит, содержимого файла он не
   хранит; «взято под git» было бы враньём именно там, где нужен откат.
4. **Во внутреннем репо файла тоже нет.** `git -C manager-bot status --short -- docs/playbook.md` →
   `?? docs/playbook.md`. То есть истории у книги правил нет **нигде**, и повод задачи для неё верен
   вдвойне.

Единственный путь положить файл под git по ЖИВОМУ пути — снять границу вложенного репозитория,
то есть **удалить `manager-bot/.git`**. Это удаление (класс `delete`), оно рвёт связь июньского
снимка со своим remote и уничтожает его 2 коммита. Автономно не делалось и обходов не искалось.

### Развилка владельцу (одну строку выбрать)

| вариант | что даёт | чем платим |
|---|---|---|
| **оставить как есть** | ничего | у книги правил по-прежнему нет отката; регрессия однажды её перепишет |
| **снять `manager-bot/.git`** (красная, руками) | `playbook.md` встаёт под git по живому пути | теряется история и remote июньского снимка |
| **коммитить книгу во ВНУТРЕННЕМ репо** | откат появляется, путь живой, удалять нечего | правила уезжают в ДРУГОЙ GitHub-репозиторий (`turbobaby-manager-bot`) — вместе с разделом под реквизиты |

Рекомендация: третий вариант **не** брать вслепую именно из-за раздела «кошельки/контакты» —
чужой remote и место под реквизиты в одном файле сочетаются плохо.

## Замок C. Откат появился

Прежнее состояние восстанавливается **одной командой**:

```
git checkout HEAD -- trainer_rules.json
```

Проверено дважды, живыми числами:

| проверка | результат |
|---|---|
| извлечение **из коммита `95077e4`** во временный индекс + `checkout-index` в `_scratch_rulesgit_0816/fromcommit/` | sha256 `bee2d75f…94e4`, `cmp` с живым файлом молчит |
| **настоящая** команда отката на живом пути | `exit=0`, sha256 после — `bee2d75f…94e4` |

Вторая проверка была безопасна не по вере: побайтное равенство доказано ПЕРВОЙ, поэтому команда
заведомо была no-op по байтам. Порядок обратный («сначала выполним, потом посмотрим») был бы
ставкой на живом наборе правил.

Замечание: строка `trainer_rules.json` в `.gitignore:64` **оставлена как есть** и ничему не мешает —
`.gitignore` управляет только неотслеживаемыми файлами, а этот теперь отслеживается, и его правки
будут видны в `git status` штатно. Убирать строку значило бы менять чужое поведение сверх границы
задачи.

## Границы

Тронут ровно один файл дерева — `trainer_rules.json` (добавлен, не изменён). Правила не менялись,
бот не запускался, регрессия не трогалась, ничего не удалялось. Временное — в
`_scratch_rulesgit_0816/` (оставлен). `.env` и конфиги не читались.
