# Splinter на VPS переведён на новый ключ Anthropic (02.09.2026)

Продолжение [сверки по отпечаткам](2026-09-02-ключ-на-сервере-сверка-хешей.md), где вердикт
был **ОТСУТСТВУЕТ**. Здесь — сам перенос.

**Значение ключа не всплыло нигде.** Оно прошло ровно один путь: строка из
`D:\turbobaby-bot\.env` → `stdin` процесса `ssh` → переменная удалённой оболочки → тело
временного файла. Ни на одном шаге оно не попадало в stdout, в аргументы процесса (а значит,
и в `ps`), в историю shell, в лог и в этот файл. Проба ключа тоже сделана без argv: заголовок
`x-api-key` подан curl'у конфигом со stdin (`-K -`), а не флагом `-H`.

## Отпечатки до/после (sha256, первые 12 hex)

| файл | до | после | mtime после (UTC) |
|---|---|---|---|
| `D:\turbobaby-bot\.env` (ПК, эталон) | `586c9bba1738` | не менялся | 2026-09-01 14:45:07 |
| `/root/turbobaby-manager-bot/.env` (VPS) | `7e14f78031a5` | **`586c9bba1738`** | 2026-09-02 07:09:36 |
| `D:\turbobaby-bot\manager-bot\.env` (ПК) | `7e14f78031a5` | не трогали | 2026-05-28 09:54:48 |

Премиса проверена первым действием: перед правкой серверный отпечаток был всё ещё
`7e14f78031a5`, то есть не равен ПК — работа имела смысл.

## Как заменено

Резерв (создан 02.09 05:49:00 UTC, `644 root:root`, содержимое = состояние до правки):

```
/root/turbobaby-manager-bot/.env.bak-20260902-054900
```

Замена атомарная: `mktemp` рядом в том же каталоге → `chmod --reference` и
`chown --reference` с исходного файла → сборка `head -n 2` + новая строка + `tail -n +4` →
`mv -f` поверх (rename в пределах одной ФС). Тронута ровно строка **N=3**, имя ключа
(`ANTHROPIC_API_KEY`, без префикса `export`) сохранено как было.

Проверки после записи:

- строк в файле **74** — как до;
- права и владелец **`644 root:root`** — как до;
- `diff` файла и резерва **с вырезанной строкой 3** → различий нет: прочие 73 строки
  байт-в-байт прежние;
- временных остатков `.env.new.*` — **0**.

## Загрузил ли работающий Splinter новое значение

Судим по результату, а не по PID:

| проверка | значение |
|---|---|
| `mtime` файла | 2026-09-02 **07:09:36** UTC |
| `ActiveEnterTimestamp` до рестарта | 2026-09-02 06:34:42 UTC (MainPID 1798064) |
| `ActiveEnterTimestamp` после | 2026-09-02 **07:10:57** UTC (MainPID 1799139) — **моложе mtime на 1 мин 21 с** |
| `is-active` / `SubState` | `active` / `running` |
| `NRestarts` | 0 — в цикл падений не ушёл |
| хвост `splinter.log` (20 строк), совпадений `traceback\|error\|401\|authentication` | 0 |
| минимальный запрос к `api.anthropic.com/v1/messages` ключом из файла | **HTTP 200** |

Повторная проверка в 07:12:32 UTC (через 1 мин 35 с): тот же `MainPID 1799139`, `NRestarts` по-прежнему 0, совпадений `traceback|401|authentication_error` в 40 строках лога — 0, контрольный отпечаток файла — снова `586c9bba1738`.

Процесс поднялся **после** правки файла, а `bot.py:47 load_dotenv()` отрабатывает при импорте —
значит в память легло новое значение. **Исход: НАЙДЕНО.**

## Побочный факт, усиливающий вчерашний вывод

До нашего рестарта `ActiveEnterTimestamp` был **06:34:42 сегодня**, а не 30.08, как при вчерашнем
замере: Splinter успел перезапуститься сам в промежутке — и это **не помогло**, потому что
файл оставался старым. Перезапуск лечит только исход «в памяти старое»; здесь болезнь была в
файле, что вчерашний артефакт и утверждал.

## Поправка к вчерашнему артефакту

Длина значения — **108** символов, а не 107: `wc -c` считался уже после `tr -d '\n'`, и я
вычел лишнюю единицу. Отпечатки от этой описки не зависят (считались от того же потока), но
guard `-eq 107` в первом заходе на ней честно споткнулся и остановил запись — файл тогда не
пострадал, упали до подмены. Цифра во вчерашнем файле исправлена.

## Что осталось незакрытым

`orchestrator-daemon.service` читает **тот же** `.env` своим `load_dotenv` и с 02.09 07:09
держит в памяти старое значение: его не перезапускали — разрешение этого блока касалось
только `splinter.service`. Прикладной эффект зависит от того, пользуется ли демон платным
ключом сам (в его коде ключ из окружения детей вырезается: `orchestrator_daemon.py:1472`,
`:2001`), — не проверялось.

`manager-bot\.env` на ПК по-прежнему несёт старый `7e14f78031a5` — по условию не трогали.
