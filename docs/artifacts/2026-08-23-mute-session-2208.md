## 6. Сколько задача может числиться «в работе», ничего не делая

**Пять минут — это про СЕССИЮ (`MUTE_AFTER=300`), а не про задачу.** Для задачи чисел два, и оба
длиннее:

| порог | чей | когда сработал бы для 60 |
|---|---|---|
| `PC_ORPHAN_STALE = 300` с (5 мин) | реапер одиночек, «ДОКАЗАННАЯ сирота» | **не применился**: короткий порог берётся только при вердикте `alive is False`; вердикт спрашивает, мог ли реестр процессов застать старт ребёнка (`_executor_verdict(tid, since=…)`), а после перезагрузки реестр моложе `since` → «не знаю» → берётся длинная мерка |
| `PC_SINGLE_STALE = 5400` с (**90 мин**) | тот же реапер, мерка молчания | ≈ **01:01:55** (от `updated` 23:31:55) |
| `EXPECT_PC_RUN_MIN = 100` мин (О1·`in_progress`) | наблюдатель ВНЕ демона, тик 10 мин | ≈ **01:11:55**, плюс до 10 мин на тик |
| `TASK_TIMEOUT = 2700` с (45 мин) | сам прогон | **не применим**: прогон умер вместе с демоном, таймер умер с ним |

**Живой факт на момент разбора (00:40, через 1 ч 08 мин после claim): не сказал НИКТО.** В логе
демона после 23:39:01 нет ни одной строки про id=60 — следующая запись это `CLAIM id=61` в
00:26:59. В состоянии наблюдателя ожиданий `tmp/expect_pc/state.json` поля `"open": {}` и
`"waits": {}` пусты.

**Ответ: владелец узнаёт через 90 минут (реапер, `PC_SINGLE_STALE`), а при его молчании — через
100–110 минут (О1·`in_progress` плюс тик наблюдателя). Пятиминутного порога у задач нет ни
одного, а тот, что есть (`PC_ORPHAN_STALE=300`), перезагрузка отключает по устройству: после
перезагрузки доказать смерть исполнителя нечем.** Это и есть дыра класса: перезагрузка — ровно
тот случай, когда исполнитель заведомо мёртв, и ровно тот, когда короткий порог не берётся.

По убыванию отношения «польза / риск». Ни одно не применено — это разведка.

1. **Вывести управляющую сессию RC-среды из области детектора.** Признак — не имя и не
   `entrypoint`, а форма запуска: в командной строке есть `--sdk-url` и нет `-p`. Такая сессия
   дежурная, транскрипт ей не положен. Цена ошибки в другую сторону мала: настоящий отказ RC
   ловится не этим прибором, а `rc_supervisor` (`channel_alive`, пороги 3600/43200 с). Ожидаемый
   эффект по корпусу — **7 карточек из 7 не выписываются**, ни одна настоящая немота не теряется,
   потому что ни одной настоящей в корпусе нет.
2. **Дать классу настоящий предмет: немота ИСПОЛНИТЕЛЯ ОЧЕРЕДИ.** Заказчик известен машинно —
   `task_started.json` хранит `child`; сессия с этим PID обязана дать транскрипт за 300 с.
   Это тот же порог 5 минут, но приложенный туда, где он что-то значит.
3. **Починить короткий порог сиротства для перезагрузки.** В `task_started.json` уже лежит
   `proc: "13576-1787382114"` — подпись демона с меткой времени. Если подпись принадлежит
   процессу, которого нет, И система загружена ПОЗЖЕ `at` задачи — исполнитель мёртв **доказанно**,
   и ждать 90 минут не за чем. Это снимает 85 минут слепоты ровно в том случае, где сегодня
   слепота максимальна.
4. **Перевезти детектор немоты на наблюдателя вне демона** (`TurboBabyExpectPC`) — иначе класс
   «жив, но не работает» продолжит наблюдаться прибором, который сам подвержен ровно этой болезни.
5. **Починить лог прибора** (`session_watch.py:111-122`): запасной `FileHandler` должен ставиться
   и когда `rotating_handler` вернул `None`, а не только при исключении. Сегодня семь
   срабатываний не оставили в `session_watch.log` ни строки.
6. **Не смешивать в карточке сторожа два числа.** «лежал» для модербота обязано печатать оба:
   отсутствие процесса и молчание продукта. 22.08 разница между ними была 93 минуты.
