## 2. Попытка перевода на файл учётных данных — ОТКАЧЕНА АВТОМАТИЧЕСКИ

Сделано: создан `/root/.git-credentials` (`600 root:root`), в него перенесена 1 запись,
`credential.helper` = `store --file=/root/.git-credentials`, все три адреса очищены от токена.

Проверка не прошла — одинаково для всех трёх:

```
адрес: https://github.com/mxfill77/turbobaby-manager-bot.git
токен в адресе: НЕТ
ls-remote rc=128: fatal: could not read Username for 'https://github.com': terminal prompts disabled
!!! ЧТЕНИЕ НЕ ПРОШЛО — возвращаю прежний адрес
```

Скрипт откатил все три адреса к прежнему виду. **Доступ не потерян**, регрессии нет.
`git push --dry-run origin main` (уже на восстановленном адресе): гейт
`✅ ГЕЙТ (полный): 130 тестов зелёные (47.0с) — прод-операция «push» разрешена.` → `Everything up-to-date`, `rc=0`.

### Рабочая гипотеза причины

Сообщение «could not read **Username**» означает, что помощник вернул **пусто** — запись не
подошла. Наиболее вероятно: исходный адрес содержит токен **без имени пользователя**
(`https://<токен>@github.com/…` — обычная форма PAT). Мой перенос сохранил структуру как есть,
и в файле получилось `https://<токен>@host` — то есть **логин без пароля**, чего помощнику мало.

**Лечение (одна строка):** записывать пару явно — `https://x-access-token:<токен>@github.com`
(GitHub принимает PAT как пароль при любом логине).

**Диагностический шаг, не печатающий значений:**
```
printf 'protocol=https\nhost=github.com\n\n' | git credential-store --file=/root/.git-credentials get | sed -E 's/=.*/=<скрыто>/'
```
Покажет, какие поля помощник вообще отдаёт (`username=`, `password=`), без самих значений.

### ПРИЧИНА ПОДТВЕРЖДЕНА ЗАМЕРОМ 25.07 02:49

Ошибка одинакова для всех трёх репозиториев (проба чистым адресом, конфиг не менялся):

```
fatal: could not read Username for 'https://github.com': terminal prompts disabled
```

Диагностика помощника (значения не печатались):

```
структура записи: строка 1: элементов до @ — ОДИН (двоеточия НЕТ → пароля нет)
                  хост после @: github.com
git credential-store --file=… get   → (пусто = помощник не нашёл подходящей записи)
git credential fill                 → fatal: could not read Username …
git version 2.53.0
```

**Гипотеза подтверждена.** Исходный адрес несёт токен **без имени пользователя**
(`https://<токен>@github.com/…`), мой перенос сохранил структуру — и в файл легла запись
«логин без пароля». `git-credential-store` отдаёт только **полную пару**; при отсутствии пароля
он не возвращает вообще ничего (проба показала пустой ответ), git идёт спрашивать логин, а
подсказки отключены → та самая ошибка. Дело не в правах, не в пути и не в версии git.

### Что подойдёт (не применялось)

1. **Тот же `store --file=`, но запись ПАРОЙ:** `https://x-access-token:<токен>@github.com`.
   GitHub принимает PAT как **пароль** при произвольном логине; `x-access-token` — канон
   (так делает GitHub Actions), годится и `mxfill77`. Права файла уже `600 root:root`.
   Порядок безопасного повтора (значение нигде не печатается):
   ```
   U=$(git -C /root/turbobaby-manager-bot config --get remote.origin.url)
   T=${U#https://}; T=${T%%@*}
   umask 077; printf 'https://x-access-token:%s@github.com\n' "$T" > /root/.git-credentials
   chmod 600 /root/.git-credentials
   # затем очистить три адреса и проверить ls-remote; при провале — вернуть адреса
   ```
2. `~/.netrc` (`machine github.com login x-access-token password <токен>`, `600`) — по защите
   эквивалентно, требование пары то же самое.
3. **Стойче всего — уйти с HTTPS+токен на ключ развёртывания GitHub:** тогда токена в файловой
   системе нет вообще. Требует действия на стороне GitHub (добавить публичный ключ в репозиторий),
   с VPS в одиночку не делается.
4. `credential.helper cache` **не подходит**: держит секрет в памяти с TTL, а хук `pre-push` и
   демон отгружают без интерактива и переживают перезагрузку.

⚠️ Пока фикс не применён, `/root/.git-credentials` содержит **нерабочую** запись — копию секрета,
которая ничего не даёт. Либо починить парой, либо удалить файл и снять `credential.helper`.

### Текущее состояние — что изменилось по итогу

- Токен по-прежнему в трёх `.git/config` (как и был, **экспозиция не выросла**).
- Появилась **дополнительная копия** в `/root/.git-credentials`, права `600 root:root` —
  строже, чем у `.git/config` (права `.git/config` не измерял).
- `credential.helper` настроен глобально и сейчас безвреден (просто не находит запись).

Если повтор не планируется — файл и настройку стоит убрать, чтобы не плодить копии секрета.

## 3. Ключ удалённого доступа — оценка (ничего не менялось)

### Сторона VPS

```
/root/.ssh                 700 root:root
/root/.ssh/authorized_keys 600 root:root   ключей: 1
    тип=ssh-ed25519  комментарий=turbobaby_pc_to_vps
приватных ключей на VPS НЕТ
```

Посадка демона:
```
permitrootlogin yes
passwordauthentication yes
pubkeyauthentication yes
kbdinteractiveauthentication no
permitemptypasswords no
```

### Сторона ПК

```
C:\Users\mxfill1\.ssh\turbobaby_vps   411 байт
ACL: NT AUTHORITY\СИСТЕМА:(I)(F) · BUILTIN\Администраторы:(I)(F) · mxfillpc\mxfill1:(I)(F)
парольная фраза: НЕТ (пустая подходит)
256 SHA256:mDGGVQx0DwkInQkSe5kiGCEIA6J7EhMhZHVPJXtbPes turbobaby_pc_to_vps (ED25519)
агент: не запущен
```

Отпечаток и комментарий совпадают с единственным ключом в `authorized_keys` — лишних доступов нет.

### Оценка риска

**Хорошо:** современный ED25519; ровно один авторизованный ключ; каталог и файл на VPS с
правильными правами; **приватных ключей на VPS нет** — компрометация сервера не даёт прыжка
дальше; ACL на ПК не открывает файл группе «Все».

**Риск 1 — ключ без парольной фразы (главный).** Файл лежит в профиле пользователя. Любой, кто
получит файл — кража/утеря ноутбука, вредонос под этой учёткой, попадание профиля в облачную
синхронизацию или бэкап — получает **root на VPS немедленно**, без дополнительных условий.

**Риск 2 — вход по паролю разрешён (`passwordauthentication yes` + `permitrootlogin yes`).**
Root по паролю доступен из интернета: постоянная брутфорс-поверхность. При работающем ключе
пароль не даёт ничего, кроме риска. Не зависит от риска 1.

**Риск 3 — мелкий.** ACL наследуемый: полный доступ у `Администраторы` и `СИСТЕМА`. Для строгих
проверок OpenSSH на Windows это лишнее.

### План защиты — НЕ ПРИМЕНЯЛСЯ, нужен ваш выбор

1. **Парольная фраза на существующий ключ, без перевыпуска:** `ssh-keygen -p -f <ключ>` —
   меняется только шифрование файла на диске; публичная часть и `authorized_keys` не трогаются,
   на VPS ничего не ломается.
   ⚠️ **Порядок важен:** автоматика (задача Планировщика `TurboBabyRC`, headless-сессии) ходит
   этим же ключом. Сначала поднять агент Windows и загрузить в него ключ
   (`Set-Service ssh-agent -StartupType Automatic`, `Start-Service ssh-agent`, `ssh-add <ключ>`),
   **потом** ставить фразу, **потом** проверить автоматический заход. Иначе автоматика встанет.
2. **Ужать ACL до владельца:** `icacls <ключ> /inheritance:r /grant:r "%USERNAME%:R"`.
3. **Закрыть вход по паролю на VPS:** `PasswordAuthentication no`,
   `PermitRootLogin prohibit-password`, затем `sshd -t && systemctl reload sshd`.
   ⚠️ Делать **только** при открытой второй сессии или доступной консоли провайдера — иначе
   есть шанс запереть себя снаружи.
4. **Отдельный ключ для автоматики**, не тот, которым ходит человек: компрометация одного не
   отдаёт второй, и отзыв не ломает вторую полосу.
5. Плановая ротация ключа и токена GitHub раз в N месяцев.

Пункт 3 самый дешёвый и самый выгодный по соотношению риск/усилие; пункт 1 самый ценный, но
требует аккуратного порядка из-за автоматики.
