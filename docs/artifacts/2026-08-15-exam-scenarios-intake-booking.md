## 2. Сценарии поломки + отрицательный тест наблюдения

Правило прибора: у каждого сценария есть состояние **«признак выглядит правильным, результата
нет»**. Прибор, который на этом состоянии зелён, к экзамену не допускается.

### Шаг 1

**S1 · Источник недоступен: парк не получен** (`PARK_NONE` — Bridge отдал 404 И снимка
`park_list.md` нет, `suggest.py:126-132`).
*Правильно:* черновик не собирается, строки в `drafts` НЕТ, менеджеру уходит «⚠️ Черновик НЕ собран
… проверьте мост», в `userbot.log` — warning.
*Отрицательный тест (корневой):* `drafts` пусты, heartbeat модербота свеж. Прибор, считающий приходы
как `COUNT(drafts)`, скажет «приходов не было» — то есть **приход был, продукт не родился, а источник
истины неотличим от тишины**. Тест обязан падать, пока прибор не различает эти два состояния.
Сегодня различитель один — процессный `userbot.log` (ротация ~20 МБ), в источнике истины следа нет.

**S2 · Источник недоступен: IPC мёртв на enqueue** (`suggest.py:7112` → деградация в reply-режим).
*Правильно:* клиенту ничего; черновик уходит в группу; строки в `drafts` нет **по построению**.
*Отрицательный тест:* менеджер видит карточку черновика в группе (признак «конвейер жив»), в
источнике истины ноль. Карточка в группе НЕ засчитывается за шаг 1 — исход «не судим», не «пройден».

**S3 · Результат пуст: LLM отдал пустое** (`suggest.py:7070`) — плюс два соседних пути без строки:
сбой генератора (`:7066`) и брак гвард-модели (`:7091`).
*Правильно:* строки нет, менеджер уведомлён именованной причиной, клиенту ничего.
*Отрицательный тест:* **три разные причины дают один и тот же наблюдаемый ноль** (S1, S2, S3).
Прибор обязан требовать ПРИЧИНУ, а не отсутствие строки; «нет строки» само по себе зелёным
или красным не является.

**S4 · Исполнитель умер: лёг модербот.**
*Правильно:* `drafts` копятся в `new`; `is_bot_alive` (порог 15 с) объявляет мёртвым
(`moderation_ipc.py:282-293`).
*Отрицательный тест:* heartbeat свежий, а `card_msg_id` не появляется ни у одной строки — heartbeat
пишется веткой, отдельной от постинга карточек. Судить по **продукту** (переход `new→posted`), а не
по признаку жизни — правило полосы (О3, `2026-08-12-watchdog-judges-product.md`).

### Шаг 2

**S5 · Источник недоступен: IPC мёртв/таймаут на тапе «✅ В CRM»** (`INTAKE_ENQUEUE_TIMEOUT=10`,
`moderation_bot.py:255-269`).
*Правильно:* строка остаётся `draft`, кнопка НЕ снимается (ретрай возможен), менеджеру —
«⚠️ Не удалось поставить заявку в очередь (IPC недоступен) — НЕ отправлено».
*Отрицательный тест:* строка `intake` есть, текст правильный (признак «заявка оформлена»), но
`updated_ts == created_ts` и постинга не будет никогда. Шаг 2 засчитывается ТОЛЬКО по
`posted`+`posted_msg_id`, не по наличию строки.

**S6 · Источник недоступен: IPC мёртв в поллере userbot** (`suggest.py:6938-6942` → `return 0`).
*Правильно:* ноль постов, ноль изменённых статусов, ошибка видна наружу.
*Отрицательный тест:* поллер вернул `0` — и это **тот же ноль**, что «нечего постить». Обе ветки
возвращают `0`, различия нет нигде, кроме строки лога. Прибор, меряющий «обработано n», обязан
различать нули; сегодня контракт нарушен.

**S7 · Брони нет: `build_intake → None`** (нет валидных полей `:576`, либо HONDA CLICK 125 `:510`).
*Правильно:* кандидат не сохраняется, кнопки «✅ В CRM» нет (`kb=None`), карточка менеджеру уходит.
*Отрицательный тест:* ровно та же картинка — карточка без кнопки — выходит при **падении
`save_intake_candidate`** (`moderation_bot.py:236-239`: `except` → `kb=None`, карточка всё равно
шлётся). «Кнопки нет по делу» и «кнопки нет из-за сбоя БД» на карточке неразличимы. Тест обязан
падать, пока карточка не несёт причину.

**S8 · Брони нет: тап по устаревшей/повторной кнопке.**
*Правильно:* `confirm_intake` возвращает `False` (`UPDATE … WHERE status='draft'` → rowcount 0),
менеджеру «⚠️ Заявка уже отправлена или устарела — пропускаю», второй записи не появляется.
*Отрицательный тест:* два тапа подряд → в `intake` ровно одна строка и ровно один `posted_msg_id`.
Признак «бот ответил менеджеру» зелёный в обоих исходах; судить по `rowcount`/числу строк, а не
по тексту ответа.

**S9 · Неполный результат превращается в честный нуль** (главный по рамке).
*Правильно:* пост без дат / модели / депозита обязан нести явную пометку неполноты по КАЖДОМУ
непопавшему полю экстракции.
*Отрицательный тест:* фикстура-транскрипт, где извлеклись только `Клиент` и `Контакт`. Наступает
`status='posted'`, `posted_msg_id` есть — прибор зелён, а наружу ушла трёхстрочная карточка,
выглядящая как честная бронь. Ожидание: `posted` без пометки неполноты **недопустим**.
Сегодня допустим — это провал E2.6, а не тест-баг.

**S10 · Ложный зелёный на самом переходе** (`suggest.py:6963-6964`):
```
6963:                mid = getattr(sent, "id", None)
6964:            moderation_ipc.mark_intake(r["id"], "posted", posted_msg_id=mid)
```
*Правильно:* `posted` ставится только при полученном id сообщения; нет id → `failed`+`reason`.
*Отрицательный тест:* poster вернул объект без `id` → строка получает `status='posted'` при
`posted_msg_id IS NULL`. Признак идеально зелёный, продукта нет. **Тестов на это нет**:
`grep posted_msg_id test_*.py` → 3 попадания, все на непустой id. Это ветка кода, а не гипотеза.

**S11 · Исполнитель умер: лёг userbot после подтверждения.**
*Правильно:* строки остаются `pending` и поднимаются при возврате исполнителя (это выполняется —
у `fetch_pending_intake` нет TTL), но **отсутствие исполнителя обязано быть видно**.
*Факт:* возрастного сторожа у `intake` нет ни одного — `grep -c 'created_ts|updated_ts'` по
`suggest.py` и `moderation_bot.py` → **0** и **0**. Строка может лежать `pending` сутками молча,
при том что менеджеру уже сказано «⏳ Отправляю во Входящие брони».
*Отрицательный тест:* `status='pending'` (признак «принято в работу») при мёртвом исполнителе.
Эпизод обязан объявляться по ВОЗРАСТУ `updated_ts`, а не по статусу; порог мерить по своей полосе
(поллер 3 с ⇒ законная задержка — секунды, не часы).

**S12 · Красное останавливает цепочку** — три стопа, все до внешнего эффекта:
CLICK 125 → `None` (`booking_draft.py:379-387, 510`); текст без префикса → `failed`+reason
(`suggest.py:6959-6961`); внутренний аккаунт команды → `skipped`+reason (слой 2, `:6947-6952`).
*Правильно:* пост не уходит, исход именован, цепочка дальше не идёт.
*Отрицательный тест:* подсунуть текст, который начинается с `🆕 БРОНЬ`, но собран НЕ `build_intake`
(обрезан до одного заголовка). Признак-префикс зелёный, полей нет — сегодня такой текст будет
запощен. Признак = префикс, продукт = содержательные поля; проверять надо второе.

**S13 · После сбоя система знает: что сделано, что нет, что неизвестно** (фото паспорта,
`suggest.py:6975-6990`).
*Правильно:* пересылка фото — best-effort ПОСЛЕ `mark posted`; её сбой НЕ трогает статус заявки.
Это сознательное «неизвестно», и оно обязано быть названо.
*Отрицательный тест:* `status='posted'`, `posted_msg_id` есть, фото не доехало. Прибор обязан
ответить «карточка — да, фото — неизвестно», а не «шаг 2 пройден целиком». Третий исход
обязателен (правило слоя ожиданий, п. 3). Сегодня в источнике истины следа о фото нет вовсе —
ни поля, ни статуса; слово «неизвестно» живёт только в тексте карточки (`booking_draft.py:593-595`).
