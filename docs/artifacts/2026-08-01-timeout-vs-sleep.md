# Таймаут против сна: чем на самом деле упали 158 и 160 (01.08.2026)

Задача 161. Шаг 1 — замер read-only, шаг 2 — правка, шаг 3 — ручное закрытие 160.
Время в файле ЛОКАЛЬНОЕ (UTC+7), как в `pc_orchestrator.log`; UTC даётся отдельно.

## 0. Главное: сна не было ни в одном из двух окон

Премисса задания («в окне 160 детектор сна зафиксировал скачок 2845 с при пороге 2760») верна
как факт лога и неверна как диагноз: **скачок — это сама задача, а не сон**. Три независимых
опровержения:

1. **Суммарный сон с загрузки — 8,97 ч, и весь он приходится на 30.07.** Замер этого ПК
   01.08 15:47 (ctypes, read-only):

   | часы | значение | что значат |
   |---|---|---|
   | `GetTickCount64` (= `time.monotonic()` на Windows) | 224673,5 c = 62,41 ч | время с загрузки, **сон включён** |
   | `QueryUnbiasedInterruptTime` | 192388,9 c = 53,44 ч | то же **без сна** |
   | разница | **32284,6 c = 8,97 ч** | всё проспанное за эту загрузку |

   Загрузка ≈ 30.07 01:2x, и 8,97 ч — это ровно известный эпизод 30.07 03:43→12:41 (скачок
   32381 с в логе в 12:42:20). На 01.08 не остаётся **ни секунды** сна.
2. **`pretool_guard.log` пишет сквозь оба окна.** 158 (13:15–14:00): записи в 13:15, 13:16, …,
   13:47, 13:56; максимальный разрыв **9 мин**. 160 (14:34–15:19): 14:34 … 15:09, 15:17, 15:18,
   15:19; максимальный разрыв **9 мин**. Спящая машина инструментов не вызывает.
3. **Оба скачка раскладываются на работу без остатка:** 2845 = 2700 (таймаут 160) + 145 накладных
   витка; 3103 = 2700 (таймаут 158) + 403.

Обе задачи **честно выбрали весь бюджет работой**. У 160 последний коммит `3a1ba41` в 15:19:12 —
за **14 секунд** до обрыва: её убили на финальном шаге, а не в зависании.

## 1. Чем мерился таймаут (место в коде)

`pc_orchestrator.py` → `run_claude` → `subprocess.run(argv, …, timeout=timeout)`; дальше CPython:
`subprocess.run` → `Popen.communicate(timeout)` → `Popen._remaining_time` → `_time()` =
**`time.monotonic`**. На Windows `time.monotonic` — это `GetTickCount64` (проверено замером выше:
две величины совпали до 2 с), а `GetTickCount64` — **смещённое** время, проспанное в нём есть.

Значит **до правки таймаут считался по настенным часам, включая сон**: уснувшая посреди задачи
машина тратила её 45 минут, ничего не делая. Для 158/160 это не сработало (спать было нечему),
но класс — живой: 30.07 сон длиной 8,97 ч убил бы любую задачу трижды.

## 3. Правка (коммит `38932bf`)

Одна механика — два исправления:

* **`awake_monotonic()`** — часы бодрствования (`QueryUnbiasedInterruptTime`, Win7+). Не Windows
  или сбой вызова → `time.monotonic()`, то есть прежнее поведение байт-в-байт (fail-open).
* **`_wait_awake(proc, timeout, …)`** — ожидание кусками по 60 с. В бюджет уходит **меньшая** из
  двух дельт (настенной и бодрствования): проснулись — счётчик продолжает с места остановки.
  `communicate(timeout=…)` при превышении вывод не теряет (контракт CPython), поэтому цикл
  безопасен. `run_claude` переведён с `subprocess.run` на `Popen` — иначе бюджет не переоценить
  по ходу; зависший **бодрый** прогон по-прежнему убивается и отдаёт `TimeoutError`.
* **`report_long_sleep(gap, slept=…)`** — карточка «ПК спал» теперь судит по **измеренному** сну
  (скачок минус прирост бодрствования), а не по скачку. Замера нет (`slept=None`) → прежний
  разбор по скачку: потерянный сигнал о настоящем сне хуже ложного.

**Регресс:** новый файл `test_pc_awake_clock.py`, 15 голденов. До правки — **15/15 красных**
(`AttributeError: module 'pc_orchestrator' has no attribute '_wait_awake'`), после — зелёные.
Ключевые: сон 45 мин посреди задачи → таймаута нет, потрачено 900 с из 2700; сон 9 ч (живое
число 30.07) переживается; **бодрый зависший прогон рвётся ровно по бюджету** (обе половины
регресса в одном файле); три живых ложняка 01.08 (3988/3103/2845 при `slept=0`) молчат; настоящие
сны 30.07 и 26.07 сигналят.

**Полный гейт: 2746 OK** (было 2731, из них 15 новых). Правились два существующих голдена
`TestEncoding` — спавн переехал на `Popen`, контракты кодировки и argv в них сохранены.

## 5. Остатки владельцу

1. **158 не закрыта.** Задание просило закрыть только 160. По следам 158 (13:15:21–14:00:21)
   коммитов нет, но её работа не пропала: 160 прямо сказано «в дереве лежит НЕЗАКОММИЧЕННАЯ правка
   захода 158 (+223/+167)» — 160 её доделала и закоммитила. Формально 158 висит `failed`.
2. **Думатель (`_thinker_exec`) остался на `subprocess.run(timeout=…)`** — тот же класс, но цена
   ниже (сбой думателя = fail-safe `None`, а не провал задачи). Точка касания: `pc_orchestrator.py`
   → `_thinker_exec`.
3. **VPS-полоса не тронута** (запрет «на сервер не ходить»). Там `orchestrator_daemon` мерит бюджет
   тем же `subprocess.run(timeout=…)`; на Linux `CLOCK_MONOTONIC` сон **не** считает, поэтому класс
   зеркалится только в части детектора сна, не бюджета. Проверять на сервере.
4. **Настоящая причина обоих таймаутов — объём задания, а не машина.** 45 минут выбираются
   заданиями такого размера целиком; у 160 последний коммит лёг за 14 с до обрыва. Ручки: размер
   задания либо `PC_TASK_TIMEOUT`.
