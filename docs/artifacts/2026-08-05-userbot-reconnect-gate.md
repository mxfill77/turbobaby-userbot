## 1. Что чинилось

Необработанный `ConnectionError` Telethon (`mtprotosender.py:266` после `connection_retries`),
вход — `userbot_listen.py:485 → await client.start()`. Пять смертей за сутки 04–05.08, причина
внешняя (переезд ПК между Wi-Fi `Samgold 7` ↔ `Bless_house_2.4GHz`, коды локального стека
Windows 121/1236/1231, DNS ложился целиком), один простой — 370 минут. Ошибок прикладного кода
среди пяти падений нет ни одной.

Класс не новый: у `pc_agent` он закрыт давно (ФИКС 1, «сетевые сбои НЕ должны ронять процесс
агента»). userbot оставался единственным долгоживущим процессом контура без такой обработки.

## 2. Что изменено — три точки, `userbot_listen.py` +157/−61

| точка | было | стало |
|---|---|---|
| `serve_forever` (новая) | `await client.start()` … `run_until_disconnected()` в теле `main`, любой сетевой отказ уходил наружу и убивал процесс | вход → слушаем → **обрыв не роняет**: пауза 5с, далее ×2 до потолка 300с, вход снова. Возврат из функции = ШТАТНАЯ остановка (Ctrl+C/disconnect), тогда цикла нет |
| `_startup_once` (новая) | пост-стартовый блок жил в `main` инлайном | тот же текст, вынесен дословно + два замка: `_moderation_hooked` (второй `on_moderation` = двойная модерация) и `_ipc_poller` (второй поллер = **двойная отправка клиенту**) |
| `_suggest_ipc_poller` | долбил сеть и лил `ConnectionError` в лог каждые 3с всё время простоя | `if not client.is_connected(): sleep(3); continue` — очередь дождётся подъёма. Внутренний авто-реконнект Telethon сюда не попадает (`_user_connected` там остаётся True), короткие просадки обрабатываются как раньше |

**Форма — штатная для Telethon, не самодельная.** Повторный `client.start()` на ТОМ ЖЕ объекте
допустим по устройству библиотеки (сверено по коду 1.43.2, а не по памяти):
`SQLiteSession.close()` только обнуляет `_conn`, `_cursor()` переоткрывает лениво;
`connect()` заново поднимает send/recv/update/keepalive-циклы и свежий `_disconnected`-future;
`run_until_disconnected()` заново шлёт `GetState`, то есть снова просит апдейты.
`self.session = None` (единственное, что ломает переиспользование клиента) ставится ТОЛЬКО в
`log_out()` — userbot его не зовёт никогда.

Внутренний авто-реконнект Telethon (`connection_retries=5`, ~30с) **не трогали**: он остаётся
первой ступенью, новый цикл включается ровно там, где сдался он.

## 3. Границы соблюдены

* **экземпляр один** — клиент и `userbot.lock` берутся один раз на жизнь процесса, переподключение
  идёт на том же объекте; голден `test_klient_i_lok_odni_na_ves_prostoy` меряет это через `main()`;
* **вотчдог не заглушен и не обойдён** — `pc_orchestrator` не тронут ни строкой, второй слой на месте;
* **`SUGGEST_TEST_MODE` не тронут**, формулировки/прайс/логика общения — ни строки;
* ловится ТОЛЬКО сетевой класс (`OSError` и потомки + `asyncio.TimeoutError`). Баг кода, отозванная
  сессия, `RPCError` роняют процесс **как раньше** — вечный цикл, глотающий настоящий дефект, хуже
  падения. `CancelledError`/`KeyboardInterrupt` — `BaseException`, остановку не глушат.

## 7. Остатки — назвать вслух

1. **Файл на диске уже новый.** Если бот умрёт по другой причине и его поднимет контур-вотчдог,
   новый код применится сам — отдельного «да» вотчдог не спрашивает. Ровно этот сценарий правка и
   отменяет (падений от сети больше быть не должно), но факт назван: молчаливого применения не
   бывает только у выключенного вотчдога.
2. **«Жив, но глухой» вотчдог не видит.** `_client_watch_step` действует только когда процесса НЕТ
   (сверено по коду): раньше сеть убивала процесс и это поднимало карточку, теперь процесс живёт.
   Затяжной простой виден ТОЛЬКО строкой ERROR в `userbot.log` — автоматического крика в Telegram
   на это нет ни у кого. Если такой крик нужен, это отдельная задача по `pc_orchestrator`
   (клиентский контур она не задевает).
3. **Корень не в коде.** Пока ПК ходит через флапающую пару точек, обрывы продолжатся — правка
   делает их безопасными, но не отменяет. Развилка владельца из разбора (кабель / одна точка)
   остаётся открытой.
