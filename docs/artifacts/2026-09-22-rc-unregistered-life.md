## ЧТО СДЕЛАНО

**A. `rc_auth_detect.py`** — счётчики жизни в состоянии детектора и ответ `registered(state)`.
- Счётчики: `life_lines`/`life_parsed` (строк за жизнь, осмотрено/опознано), `bridge` (строк
  `[bridge:`), `registered`, `rotations`, `last_unread`.
- Маркеры регистрации — три живых строки разного рода: `[bridge:init] Registered`,
  `[bridge:work] Starting poll loop`, `/work/poll`.
- **Ротацию лога самим CLI счётчики переживают.** Живой `rc_server_debug.log.1` (10 МБ, 12.09 18:43)
  отрезан посреди жизни, начатой 09.09. Сброс там сделал бы здоровый сервер «незарегистрированным».
  Пара контракта `seen`/`parsed` сбрасывается как раньше.
- Исходов три: **True** / **False** / **None**. None — это «не знаю»: состояния нет, оно старого
  образца, лог жизни пуст, формат не опознан, последнее чтение сорвалось. По False сторож гасит
  процесс, поэтому незнание приговором не бывает. Состояние старого образца счётчиков посреди жизни
  не получает: счёт с середины превратил бы «не знаю, что было до» в «не было».
- `life_stage(state)` — стадия с числами для строки журнала и карточки: «до [bridge:init] — ни одной
  строки моста (строк лога 11, строк моста 0)» или «мост начат, регистрации нет (…)».

**B. `rc_supervisor.py`**, только ветка `auth_watch` (rc-server).
- **Ранний снос.** Условия: грейс прошёл, `registered` = False (не None), ESTABLISHED = 0 (именно ноль,
  число известно) `LIVENESS_STRIKES` проверок подряд. Тогда строка `БЕЗ РЕГИСТРАЦИИ: жизнь ≈270с, грейс
  180с позади, <стадия>; соединений 0 3 проверок подряд — гашу pid=…`. Слова ЗОМБИ в ней нет:
  реплеи отличат новый снос от старого.
- **Вердикт каждой жизни.** Перед вердиктом — последний проход по логу. Итог уходит строкой
  `итог жизни pid=… (≈…с, вышла сама|погашена сторожем): <вердикт>; <стадия> — серия без регистрации N из K`.
- **Серия.** Растёт только от жизни, которую погасил сторож и в которой регистрации нет. Жизнь с
  регистрацией рвёт серию и снова взводит карточку. «Не знаю» серию не растит и не рвёт. Серия живёт в
  памяти потока ветки, между жизнями.
- **Карточка.** На K-й жизни серии — одна карточка через `notify_owner` → `dispatch_notify --critical`
  → `deliver(declared=True)` → инбокс 1160. В ней:
  - стадия с числом строк лога;
  - бинарь и его mtime;
  - учётка детей словами рычага 70w (`child_env`);
  - следующая пауза и потолок;
  - «После починки перезапусти TurboBabyRC»;
  - ссылка на разбор.

  Не ушла (исключение или `False` от отправителя) — повтор на следующей жизни серии.
- **Backoff.** `unreg_pause`: K-я жизнь → 3600 с, дальше ×2, потолок 21600 с. Пауза не меньше
  `RESTART_DELAY`: ноль в ручке не делает тугой цикл.
- **Ручки** (связываются на импорте, как все прочие):

  | ручка | по умолчанию |
  |---|---|
  | `RC_UNREG` | `1`; клапан, `0` = поведение до 22.09 |
  | `RC_UNREG_LIVES` | `3` |
  | `RC_UNREG_BACKOFF` | `3600` с |
  | `RC_UNREG_BACKOFF_MAX` | `21600` с |

  Стартовая строка называет их числами: `жизни без регистрации (rc-server): RC_UNREG=1 RC_UNREG_LIVES=3
  RC_UNREG_BACKOFF=3600с RC_UNREG_BACKOFF_MAX=21600с`.
- **Не тронуто:** пороги 24.07/30.07, `channel_alive`, страйки старого пути, `established_conns`.
  Ветка канала не судится вовсе: вопроса у неё нет, детектор её лог не читает. `RC_LIVENESS=0`
  выключает и ранний снос: это клапан «рестарт лишь по выходу». `RC_AUTH_WATCH=0` выключает рестарт
  по кредам, но не вопрос о регистрации. Читатель лога у них общий, а клапаны разные.
- Двойник детектора без `registered`, на котором стоят все прежние тесты ветки, даёт прежнее
  поведение байт-в-байт.

## ОДНО ОТСТУПЛЕНИЕ ОТ ТЗ (решение исполнителя, откат в одну строку)

ТЗ считает в серию каждую жизнь без регистрации. Здесь в серию идут только жизни, которые **погасил
сторож** (ранний снос, старый ЗОМБИ, креды). Жизнь, которая **вышла сама** без регистрации, получает
вердикт в журнал («регистрации НЕТ, но процесс вышел сам — в серию не идёт»), но серию не растит и не
рвёт. Причины:
1. Класс задачи — молчаливое зависание, а выход громкий: у него код в журнале.
2. На классе 18–22.09 выходов 0 из 91, поэтому вклад выходов в поимку этого класса — ноль.
3. Единственный живой случай серийных выходов (05.08) — сетевой отказ, прошедший сам. Буква ТЗ дала
   бы на нём 2 ложные карточки «почини и перезапусти» и 57,4 мин лишнего простоя устройства.

**Вернуть букву ТЗ:** в `rc_supervisor._close_life` строка `counts = verdict is False and ended ==
"killed"` → `counts = verdict is False`. Тесты `test_self_exited_unregistered_life_is_not_a_hang` и
`test_exit_loop_alone_never_backs_off` тогда покраснеют: мутация M1 это проверила, и их придётся
переписать.

## ОСТАТОК, ЧЕСТНО

1. **Не применено.** Константы связываются на импорте, а супервизор 19924 держит старый код. Нужен
   рестарт `TurboBabyRC` — красная операция, только с «да» владельца. Правка лежит на ветке worktree,
   не в `main`. Попадёт в рабочее дерево `D:\turbobaby-bot` — применится на следующем же старте задачи,
   в том числе при входе в Windows (`LogonTrigger`). **Признак применения** — стартовая строка с
   `жизни без регистрации (rc-server): RC_UNREG=1 …` и строки `итог жизни` на каждом конце жизни rc-server.
2. **Вечная петля выходов карточки не даёт.** Её цена — отступление выше. Сегодня такая петля
   рестартует раз в ~45 с и видна только в журнале. Это отдельный класс (порог по времени, а не по числу
   жизней), здесь не сделан.
3. **Серия не переживает рестарт супервизора** — на каждый старт своя карточка (3 на окне 18–22.09).
   Сохранять её на диск ТЗ не просило.
4. **Путь карточки проверен по argv, а не живой доставкой:** тесты в сеть не ходят. Что `--critical`
   уходит в 1160 — код `dispatch_notify.deliver`, не наблюдение этой сессии.
5. **Сорванный netstat даёт 0 соединений** (`established_conns` не тронут по ТЗ). Для раннего сноса
   это значимо только в паре с твёрдым `registered = False`.
6. **`diag_rc_liveness_replay.py` строку `БЕЗ РЕГИСТРАЦИИ` не знает.** Такие жизни он увидит
   неоконченными; не правился.
7. **Именованный канал `turbobaby-pc` висит и на основном профиле** (остаток №2 разбора). Эта правка
   его не судит по ТЗ.
