## 3. Был ли откат выполнен — ВЫПОЛНЕН, и вот чем это доказано

Исход не «неизвестно»: у отката есть **независимое от расписки** подтверждение.

| улика | что показывает |
|---|---|
| `step7c_deploy.txt`, 06:38:41–06:41:32 | `✅ Откат выполнен: Redeployed AKfycbxNC9gCM7-a…` — **расписка** инструмента |
| **`step8_after_rollback.txt`, 06:42:24** | живое чтение: «прод обслуживает версию: **79**», при том что версия **@83 уже существовала** (создана 06:40:54). Это не расписка, а наблюдение мира |
| `step10a_deploy_v83.txt`, 06:49:01–06:49:08 | `Redeployed … @83`, exit 0 — откат перекрыт вторым ходом |

**Откат сделала АВТОМАТИКА, а не сохранённая команда.** Ветка `_do_rollback` в
`bridge_deploy.py` зовёт `clasp redeploy PROD_ID -V 79` сама, когда падает смок.

**Сохранённая команда отката НЕ выполнялась.** Единственное её вхождение во всех 11 скриптах
захода — `echo` в `step34.sh:14`, то есть печать команды в отчёт:

```
step34.sh:14: echo "ssh -i ~/.ssh/turbobaby_vps root@… 'cd … && clasp redeploy … -V 79'"
```

**Мина истории оболочки — назвать обязательно.** `/root/.bash_history` последний раз изменён
**2026-07-20**, и все 26 совпадений `clasp/redeploy` в нём — июльские. Это **не** значит, что
сегодня clasp не звали: команды шли неинтерактивным `ssh`, а он в `.bash_history` не пишет
ВООБЩЕ. По этому файлу судить о сегодняшнем дне нельзя ни в одну сторону; доказательство даёт
журнал захода и живое чтение, а не история.

Автоматики, способной двинуть деплой после 06:49, нет: в `/etc/systemd/system/` ни одного юнита
с упоминанием `bridge_deploy`/`clasp`.

Проверка, которая не сошлась, — вторая половина смока. Дословно из кода
(`bridge_deploy.py::_smoke_ok`, строки 155–167):

```python
"""Read-only смок: ping alive + delivery_zones_get непустой. Возвращает (ok, detail)."""
        z = c.delivery_zones_get()
        if not z.get("ok"):
            return False, f"delivery_zones_get не ok: {z.get('error', str(z))}"
        zones = z.get("data", {}).get("zones", [])

```

То есть маршрут ответил **`ok`**, но список зон пришёл **пустым** — сработала ветка `if not
zones`, а не ветка «маршрут не ok». `ping` при этом прошёл: до второй проверки дело дошло.

Ранее (06:44 UTC) замерено, что тот же `delivery_zones_get` отдаёт `ok=true` и **0 зон на
нетронутом @79 тоже, 3 пробы из 3** — то есть проверка краснит по состоянию мира, а не по
выложенному коду.

## 5. Пульс как файл — строка ЦЕЛАЯ, а не оборванная

Прочитан документ целиком (`read_doc name=pulse`), не длина через ping:

| поле | значение |
|---|---|
| прочитан | `ok` |
| символов | **37** |
| строк | **1** |
| заканчивается переводом строки | нет |
| последние кодовые точки | `… 0x432 0x44b 0x43f 0x43e 0x43b 0x43d 0x435 0x43d` = «выполнен» |
| совпадает с форматом писателя **дословно** | **да** |

Формат писателя в коде: `pulse=f"🟡 bridge_deploy: откат к @{prev_ver} выполнен"`. Подстановка
`prev_ver=79` даёт строку длиной **ровно 37** символов — столько в документе и лежит. Строка
обрывается не на полуслове, а на последней букве последнего слова, и посимвольно равна
эталону. **Запись не рвалась. Отдельной находки «оборванная запись» здесь НЕТ.**

**Настоящая находка другая — пульс НЕ УСТАРЕЛ, а НЕ БЫЛ ПЕРЕЗАПИСАН, и это класс.** Пульс
пишется РОВНО одним путём — `bridge_deploy.py::_log_cc(..., pulse=…)`. Второй ход (06:49) шёл
прямым `clasp redeploy … -V 83`, минуя этот скрипт, а прямой вызов clasp пульса не пишет ни
строкой. Итог: у прода **два** способа сдвинуться, а у пульса — покрытие только одного.
Пульс замер на 06:41 и с тех пор описывает состояние, которого больше нет.

Отсюда и расхождение, ради которого затевалось чтение: **и пульс, и журнал говорили правду —
про разные моменты.** Пульс правдив на 06:41, журнал — на 06:49 и далее. Спор решается не
выбором источника, а чтением живого прода, и живой прод отвечает **@83**.

## 8. Что осталось незакрытым (не чинилось — заход читающий)

   отменённое состояние как текущее — ровно то, что и случилось.
