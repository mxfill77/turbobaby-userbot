зарегистрированы в реестре. Штаб больше не носит эти правила в промпте — читает их отсюда.

## 2. Чем это сделано — канал и правки кода

Запись в мозг с ПК идёт только через доверенного писателя `brain_writer.py` (класс 328: секреты
Bridge читает сам писатель, вызывающий их не видит). Создание дока в этом канале **было, но не
имело выхода наружу** — `create_plain()` существовала без CLI-ключа, и позвать её можно было
только скриптом-однодневкой, то есть ровно тем, что класс 328 и запрещает. Правка закрывает дыру
и две смежные:

| правка | зачем |
|---|---|
| `brain_writer.py` → CLI `--name KB_имя --create ключ` | создание дока стало операцией канала, а не поводом писать скрипт-однодневку; «`-`» вместо ключа = создать без регистрации |
| `create_plain()` → **ОБРАТНОЕ ЧТЕНИЕ** (дословно + длина), `get`-транспорт, поля `verified/chars_back/fffd` | «мост ответил ok» фактом записи не является — у `apply()` сверка была, у создания её не было. Каждый отказ теперь НАЗЫВАЕТ id уже созданного файла: создание НЕидемпотентно, Drive держит одноимённые файлы спокойно, и слепой повтор дал бы ДУБЛЬ в папке Brain |
| `create_plain()` → **гард мохибейка на ВХОДЕ** (`U+FFFD` в тексте → отказ, код 1) | обратное чтение сверяет отправленное с легшим и честно подтвердит побитый текст, если он приехал побитым уже к писателю. Единственное место, где мусор ещё можно не пустить в мозг, — до отправки |
| `brain_writer.py` → `_stdin_text()`: stdin декодируется ЯВНО как UTF-8 | на Windows `sys.stdin` берёт локаль (cp1251), и многострочный кириллический блок приехал бы в мозг мусором — тем самым U+FFFD, который мы потом ищем. Это класс 29–30.07 (мохибейк вывода), закрытый на входе теми же средствами, что `_out()` — на выходе |
| `brain_writer.py` → `--probe` печатает длину, число строк и счётчик U+FFFD | доказательство «прочитал назад» стало числом, а не словами |
| `test_brain_writer.py` → мок `create_brain_plain` приведён к ЖИВОМУ формату (`ok/name/key(null)/id/chars`), добавлен `lie_on_create` | правило-класс «мок обязан копировать живой формат»; без `lie_on_create` лживое создание нечем было проверить |

Тесты: **33/33 зелёные** (`test_brain_writer`, было 26 — семь новых: обратное чтение создания,
отказ с id в тексте, гард мохибейка на входе, отказ чтения после создания, нормализация хвостового
перевода строки, блокировка живого Brain в тест-контексте без ОБОИХ моков, UTF-8-декод stdin).
Смежные своды зелёные тем же прогоном: `test_utf8_output_guard`, `test_pretool_guard` — **339/339**.

## 2а. Брак журнала, найденный этой же задачей (закрыт)

Финальная строка ритуала ушла в мозг **пустой**: вызов `cowork_log_append.py - <<EOF …EOF` —
привычка от `brain_writer`, где «`-`» это сентинел stdin, — у писателя журнала сентинелом НЕ был.
Код брал `argv` ЛИБО stdin (`raw = " ".join(sys.argv[1:]) if len(sys.argv) > 1 else read_stdin_text()`),
поэтому записал литерал «`-`», а тело heredoc выбросил молча. В журнале это две строки

```
DONE 2026-07-31 22:24 UTC: -
DONE 2026-07-31 22:24 UTC: -
```

Класс тот же, что у мохибейка stdin (29.07): **ни один гард этого не видит** — строка непустая,
длина растёт, обратное чтение совпадает с записанным. Ловится только глазами.

- **Правка:** «`-`» в argv стал сентинелом stdin (`cowork_log_append.py` → `main`); обычный
  argv-вызов stdin по-прежнему не трогает (detached-спавн из `dispatch_notify` его не имеет).
- **Тесты:** `test_cowork_log_append` **53/53** (три новых в `TestArgvStdinSentinel`).
- **Две пустые строки в журнале оставлены как есть** — вычистить их значило бы переписать
  существующий Brain-док с усыханием, что этой задачей запрещено. Рядом стоит строка `NOTE`,
  объясняющая происхождение, чтобы читатель журнала не гадал.

## 3. Что владельцу стоит знать

1. **Соседство с ключом `rules`.** В реестре уже есть `rules` (`1AnBAniKQtrpJQevVWlzxVrdb1n51aj1G`,
   16 736 симв.) — это «KB_RULES — СВОД ПРАВИЛ РАБОТЫ», по описи 30.07 док СМЕШАННОЙ роли
   (инструкция + карта колонок таблицы «Байки») и **в коде его не читает никто**
   (`docs/artifacts/2026-07-30-brain-inventory.md:51`). Пересечение по теме возможно: часть
   парковых правил может дублироваться там. Ревизия `rules` этой задачей НЕ делалась — правка
   существующих доков была запрещена условием. Остаток: сверить `rules` и `business_rules`,
   решить, что где живёт.
2. **Читателя в коде у нового дока пока нет.** `business_rules` сейчас читается только ритуально
   (штаб зовёт по имени). Боевой клиентский `suggest.py` берёт FAQ из ключей `faq/turbobaby_faq`,
   про новый ключ он не знает. Если правила должны влиять на ответы клиенту — это отдельная
   задача с правкой `suggest.py`.
3. **Док — plain-text, а не Google-Doc.** Так создаёт единственный канал создания
   (`createBrainPlain_` → `folder.createFile(name, text, 'text/plain')`). Для чтения это
   безразлично (`brainTextRead_` ветвит по MIME), для будущей дозаписи — тоже: `write_doc` умеет
   оба типа, а plain ещё и не изнашивает структуру DocumentApp.

читает отсюда. Клиентский и внутренний контуры обращаются сюда же.

- HONDA CLICK 125 в аренду не сдаётся никогда.
- Клиентам называть только модели реального парка (Лист1 файла
  «байки»). Модели с пометкой «нет в парке» не показывать.
- Депозит = деньги ИЛИ паспорт, никогда оба сразу.
- Доставка только по Пхукету.

ПАРТНЁРЫ

- Бот сам клиента партнёру НЕ передаёт.

ОДОМЕТР
- OCR — подсказка, запись только по подтверждённому числу.
- Убывание пробега: до 500 км механик решает сам; больше 500 или

КАССА

- Механик внутреннего контура — Earth. Финконтроль — Пым.

- Ger в TurboBaby не работает.

ЗАПРЕТ БЕЗОПАСНОСТИ (не бизнес-правило, снимает только владелец)

## 5. Как повторить/дописать

```
# создать новый док в папке Brain и сразу зарегистрировать
venv/Scripts/python.exe brain_writer.py --name KB_имя --create ключ < текст.txt

# дозаписать строку в существующий (канал дозаписи доки не создаёт)
venv/Scripts/python.exe brain_writer.py --name ключ "строка"

# прочитать назад: длина, строки, U+FFFD, голова
venv/Scripts/python.exe brain_writer.py --probe --name ключ
```
