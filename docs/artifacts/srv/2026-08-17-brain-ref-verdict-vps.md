## 0. Короткий ответ

Причин НЕ одна и НЕ та, что названа в живом журнале. Их **три, и они складываются**, а самая
тяжёлая в журнале не названа вовсе:

1. **К мосту не ходим** — литерал `brain=False` в `orchestrator_daemon.py:5692`. Это и есть
   строка «к мосту не ходили» из живого файла счёта.
2. **Руки СЛОМАНЫ, а не выключены** — `result_judge_facts.py:167` зовёт
   `BridgeClient().read_doc(...)`, **метода `read_doc` у клиента НЕТ** (живая проверка:
   `hasattr → False`). Все живые читатели мозга ходят через `._call("read_doc", name=…)`.
   Снять запрет п.1 — значит получить `AttributeError`, который широкий `except` на строке 168
   выдаст за «мост не отвечает». То есть **вердикт не изменится ни на слово**.
3. **Прежней длины узла (`len_before`) не пишет никто** — и без неё `_judge_brain`
   (`result_judge.py:257-260`) отвечает НЕИЗВЕСТНО даже при прочитанном узле и найденной
   подстроке. Производителя нет ни одного.

Цена чтения, которой оправдан п.1, **измерена и оказалась мала**: одно живое чтение узла
`business_rules` — **2.42 с** (14 588 code points, `ok:True`). Комментарий демона ссылается на
543 с — это верхняя оценка `cc_log`, а не цена этого узла.

**Живой счёт:** из 5 цепочек, вошедших в счёт с момента включения правила, **3 оборвались, и все
три — по адресу вида `brain`**; обе цепочки с адресом вида `file` устояли («доказан»).
100 % обрывов живой серии сегодня даёт этот один вид адреса.

## 3. Может ли процесс судьи технически дойти до моста

**Клиент есть.** `orchestrator_daemon.py:39` — `from bridge_client import BridgeClient, …`;
`result_judge_facts.py:166` импортирует мост лениво, внутри функции. Настройки в процессе демона
загружены (`bridge_client` сам их не грузит — грузит вызывающий).

**Запрета по флагу НЕТ ВОВСЕ.** `brain=False` — не переменная окружения, а **литеральный
аргумент** в `orchestrator_daemon.py:5692`. Ручек, которые могли бы его перевернуть, не
существует: `SHADOW_RULE` (:5669) и `RULE_ON_COUNT` (:5521) умеют только **погасить** ветку
целиком. Включить чтение узла сегодня нечем — только правкой кода.

**И даже сняв запрет, судья до узла не дойдёт.** Живая проверка класса клиента (сеть не
трогается):

```
метод read_doc у клиента есть: False
методы клиента со словом doc: ['register_brain_doc', 'write_doc']
```

А руки зовут именно метод:

```
167	        reply = bridge_client.BridgeClient().read_doc(name=key)
168	    except Exception as e:                       # noqa: BLE001 — мост может отсутствовать вовсе
169	        return {"read": False, "text": "", "len": 0, "len_before": before,
170	                "why": "мост не отвечает (%s)" % type(e).__name__}
```

Все ЖИВЫЕ читатели мозга ходят иначе — через общий `_call`:
`brain_sync.py:62`, `cclog.py:211`, `health.py:344`, `expectations_run.py:258`, `devbot.py:2079`
(`BridgeClient()._call("read_doc", name=…)`); `brain_sync.py:60-61` прямо оговаривает: «своего
метода-обёртки нет». Значит `brain_fact` при `brain=True` вернёт `read: False` с причиной
**«мост не отвечает (AttributeError)»** — отказ СВОЕГО кода прикинется молчанием моста.

**Почему это не поймал гейт.** `brain_fact` не зовёт **ни один тест** (0 вхождений в `tests/`).
Все проверки вида `brain` кормят рукотворные словари фактов
(`tests/test_result_judge.py:128-141, 200`), а единственный вызов настоящих рук стоит с
`brain=False` (:138) — то есть до тела `brain_fact` не доходит. Ровно класс §8 `ENV_PLAYBOOK`:
«мок, переставший задевать ветку, хуже отсутствующего».

**Цена одного живого чтения — замерена (одно чтение, узел из живого случая):**

```

методы клиента со словом doc: ['register_brain_doc', 'write_doc']
одно живое чтение узла business_rules: 2.42 c
ok: True | ключи ответа: ['id', 'name', 'ok', 'text']

```

Довод, которым оправдан `brain=False` (`orchestrator_daemon.py:5650`: «чтение узла доходило до
543 с»), — это верхняя оценка **`cc_log`** из замера О5, а не цена узла, который называют живые
адреса. Узел из живого случая читается за **2.42 с**, и он существует (адрес разрешается).

## 4. Чего не хватает для ДОКАЗАН — поимённо

Не одного, а **трёх**, и первые два ничего не стоят без третьего.

**(а) Ожидаемая подстрока в САМОМ адресе.** `result_judge.py:167-172`. Из шести живых адресов
её не назвал один (цепочка 37, `KB_trainer_log`) — этот случай не лечится ни мостом, ни длиной,
только дисциплиной того, кто пишет ТЗ.

**(б) Само чтение.** Двойной затор: литерал `brain=False` (`orchestrator_daemon.py:5692`) **и**
несуществующий метод (`result_judge_facts.py:167`). Снятие ОДНОГО из двух не покупает ничего.

**(в) `len_before` — прежняя длина узла. Её не пишет НИКТО.** Без неё судья отвечает
НЕИЗВЕСТНО даже на прочитанном узле с найденной подстрокой:

```
257	    before = b.get("len_before")
258	    if before is None:
259	        return _v(UNKNOWN, "узел «%s» содержит названное, но длину не с чем сравнить — «уже "
260	                           "было» отсюда неотличимо" % parts["key"])
```

Поимённо, где эта величина обязана появиться:
* `result_judge_facts.gather(refs, before=None, brain=True)` — параметр `before`, :179;
* `result_judge_facts.brain_fact(key, before=None)` — :158, поле факта `len_before` :176;
* читатель — `result_judge.py:257`.

**Производителей — ноль.** `gather` зовётся из боевого кода **ровно один раз**
(`orchestrator_daemon.py:5692`) и `before` не передаёт; сам `brain_fact` в своём докстринге
(:161-164) это состояние и признаёт.

**Кто должен был бы писать.** Тот, кто **СОЗДАЁТ** запись с адресом, — потому что «прежняя
длина» существует только до шага:
* дверь `bridge_client.enqueue_task(..., result_ref=…)` (`bridge_client.py:858`) — сегодня у неё
  **ноль боевых вызовов** (проверено: единственное вхождение `result_ref=` в живом коде — сама
  сигнатура). Адреса приезжают ТЕКСТОМ ТЗ, который пишет Штаб/владелец, и разбираются
  `result_ref.of_task`;
* либо рука «при рождении» в демоне по образцу `chain_cards.note` (журнал рождения карточек).
  Сегодня демон записывает `refs` **только в ТЕРМИНАЛЕ** (`_series_rule_note`, :5563-5567) —
  в момент, когда прежней длины узла уже не существует нигде.

Отсюда честный вывод: **`brain` — единственный из пяти видов, которому нужен снимок мира ДО шага.**
`file`, `commit`, `row`, `service_start` доказываются одним взглядом после; `brain` — разностью
двух взглядов, и второго взгляда система не делает по построению.

## 6. Предсмертный взгляд — как провалится будущий фикс

**Одной строкой:** фикс перевернёт `brain=False` → `True`, гейт останется зелёным (ни один тест не
зовёт `brain_fact`, все кормят рукотворные факты), а в проде каждая `brain`-цепочка начнёт платить
чтение узла в терминале и получит **ТО ЖЕ «неизвестно»** — сперва потому, что метода `read_doc` у
клиента нет и `AttributeError` выдаст себя за «мост не отвечает», а после его починки — потому что
`len_before` по-прежнему не пишет никто; обрывы не исчезнут, исчезнет только их честная причина.

Второй, более тихий способ провалиться: «починить» вид `brain`, ослабив `_judge_brain` — убрать
требование роста и засчитывать одно лишь «содержит». Тогда ДОКАЗАН начнёт выдавать узел, в котором
названное лежало **и до шага**, и правило зелёного перестанет мерить работу — это ложное зелёное,
против которого замок и поставлен (`result_judge.py:244-249`).
