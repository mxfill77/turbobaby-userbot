## 2. Читает ли ЖИВОЙ процесс правило (`.env` не открывался ни разу)

**Судим по коду, который флаг читает, и по поведению — как и требует задание.**

Код (`orchestrator_daemon.py`, строки 5334–5336 и 5339–5349):

```python
def _rule_on_count():
    """RULE_ON_COUNT в .env: по умолчанию ВКЛЮЧЕНО, «0» гасит ветку ДО чтения фактов. …"""
    return (os.environ.get("RULE_ON_COUNT") or "1").strip() != "0"


def _rule_since(state):
    """Момент включения правила в счёте | '' (правило выключено). …"""
    if not _rule_on_count():
        return ""
    r = state.get("rule") or {}
    since = str(r.get("since") or "")
    if since:
        return since
    since = time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime())
    state["rule"] = {"since": since, "definition": RULE_ON_NOTE,
                     "before": dict(state.get("derived") or {})}
```

возвращает `""` ДО всякой записи, и тогда в состоянии НЕ ПОЯВЛЯЕТСЯ ни ключа `rule`, ни поля
`rule_since` в `derived`, ни хвоста в строке `line`. Все три появились:

Хронология сходится посекундно: артефакт снял состояние (63 цепочки) → в 18:51:33 родилась цепочка

прочитан как «ремонт руками», поэтому обрыва он не дал; в снимок 18:54:50 эта единица ещё не попала,
отсюда вес 32/64 вместо 33/64.

### это записанное поведение, а не сюрприз

Артефакт `2026-08-16-rule-on-count.md` предупредил о ровно этом классе заранее (там же он поправил
числа ЕЩЁ более раннего задания — «42 чистых из 46, лучшая 15»):

> «Код сохраняет ФАКТИЧЕСКОЕ содержимое файла, а не число из текста задания, — поэтому в `rule.before`
> уедет то, что будет лежать в момент включения, каким бы оно ни было.»

**ЧТЕНИЕ ПУНКТА 4: старые числа НЕ ПОТЕРЯНЫ.** Числа задания живут посимвольно в снимке на диске;
`rule.before` держит факт на момент включения — на одну закрытую цепочку моложе. Отказом это не
является: правило сохраняет не число из текста, а состояние мира; расхождение +1/+1/+1 объяснено
поимённо и укладывается в 3 мин 17 с между снимком и включением. Обрывы (4, все «ремонт») совпали в
обоих местах.

## 5. По какому определению счёт идёт СЕЙЧАС

**По НОВОМУ.** Определено по коду и по содержимому файла, флаг как «намерение» в расчёт не брался.

По файлу — четыре независимых следа: `derived.rule_since` = `2026-08-16T18:54:56` (непусто);
хвост в `line` («правило зелёного с …») — его печатает `chain_series.render` ТОЛЬКО при непустом
`rule_since`; `before_rule` = **64** — все прежние цепочки объявлены не входящими в счёт;
`best_ever` = **0** — рекорд прежнего определения вперёд НЕ унаследован.

По коду (`_series_derive`, строки 5749–5757):

```python

    # ПЕРВЫЙ ПЕРЕСЧЁТ ПОД ПРАВИЛОМ: счёт начинается С НУЛЯ. Рекорд и последний обрыв ПРЕЖНЕГО
```

`since` непустой → `fresh` сработал на первом пересчёте (отсюда нули и `best_ever` = 0), и дальше
`since` уходит и в вердикт каждой цепочки, и в свод серии.

**ЧЕСТНАЯ ГРАНИЦА, ЧТОБЫ НЕ ЗАВЫСИТЬ ГОТОВНОСТЬ:** новое определение ДЕЙСТВУЕТ, но ещё НИ РАЗУ НЕ
ПРИМЕНЯЛОСЬ к цепочке — с момента включения ни одна не закрылась, вердиктов правила в файле ноль.
Правильное слово о состоянии — «включено и ждёт первой цепочки», а не «работает и меряет».
