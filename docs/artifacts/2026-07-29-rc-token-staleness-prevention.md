# Протухшая авторизация rc-server: два варианта профилактики (развилка, 29.07.2026)

Повтор инцидента 28.07 (`docs/artifacts/2026-07-28-rc-server-revoked-token.md`) ровно через
сутки. Лечение то же — снять rc-server, сторож поднимет новый. Здесь — **варианты, чтобы
третьего раза не было**. НЕ ПРИМЕНЕНО: решение за владельцем.

> **✅ СТАТУС НА 31.07.2026: РАЗВИЛКА ЗАКРЫТА, ВАРИАНТ (а) ПРИМЕНЁН. Не делай второй раз.**
> В репозитории живёт модуль `rc_auth_detect.py`, проведённый в сторожа (`rc_supervisor.py`).
> Включён по умолчанию: `ENABLED = os.getenv("RC_AUTH_WATCH", "1") != "0"`, то есть работает
> без всякого ключа в окружении; выключается только явным `RC_AUTH_WATCH=0`.
> Ложный диагноз, который снимает эта пометка: «детектора нет, надо писать» — и следующая
> сессия дублирует существующий модуль.

Время в логах CLI — UTC, местное = UTC+7.

## Что уточнил живой повтор (важнее самого рестарта)

**1. Сервер чинит СВОЙ токен, но детям отдаёт протухший.** Собственный API-слой моста
умеет рефрешить:

```
05:03:46.478Z [bridge:api] StopWork: 401 received, attempting token refresh
05:03:46.489Z [bridge:api] StopWork: Token refreshed, retrying request
05:03:47.362Z [bridge:api] POST .../work/cse_01VL18wK.../stop -> 200
```

А вот СВЕЖЕ ПОРОЖДЁННЫЙ воркер умирает за 2–3 с:

```
05:03:43.393Z [bridge:session] Spawning sessionId=… accessToken=[REDACTED]
05:03:43.827Z [code-session] Get session_01VL18wKrkBWsKVwmifPHQ7c failed 401: OAuth access token has been revoked.
05:03:45.978Z [bridge:session] sessionId=… failed exit_code=1 pid=11272
05:03:46.068Z [bridge:session] … workId=cse_01VL18wK… exited status=failed duration=2s
```

**2. Уже открытая сессия при этом продолжает работать** — серверу приходит обновлённый токен
вместе с work и он проталкивает его в живого воркера:

```
00:09:06.084Z [bridge:work] Updated access token for existing sessionId=… workId=cse_01M7Ptr…
```

После этой строки сессия `cse_01M7Ptr…` отработала **84 хода** (00:13Z→04:24Z, `Session
completed`) — УЖЕ ПОСЛЕ того, как креды были переписаны в 05:10:10 местного.

Отсюда ловушка диагностики: «после перелогина в логе есть успешная работа ⇒ токен живой» —
**неверно**. Умирают только НОВЫЕ спауны. Поэтому симптом владельца — «новая сессия висит в
Connecting», а не «всё встало»: старая сессия могла идти как ни в чём не бывало.

**3. Проба сторожа зелена по определению.** Процесс жив, лог свеж, соединения есть
(замер 10×3 с: ESTABLISHED у сервера в 4/10 — короткие поллы; у воркера 10/10). Ни один
предикат живости этот отказ не видит.

**4. Голый греп по `401` — мусор.** В логе 28→29.07 подстрока `401|revoked|Unauthorized`
дала **18 совпадений, из которых настоящих 4**: остальные — `401` внутри JSON (`estimated_tokens`,
uuid, доли секунды `…:23.401Z`). Ложных 78 %. Любой детектор обязан цепляться за дословную
строку, а не за число.

## Вариант (а): детектор протухшей авторизации в стороже/вотчере

Сторож (или отдельный вотчер) читает хвост `rc_server_debug.log` и рестартует ветку
`rc-server` при обнаружении отказа авторизации.

**Минусы:**
- **Реактивен**: ловит только ПОСЛЕ первого отказа — одна сессия владельца всё равно умрёт
  (правда, за 2–3 с, а не «висит вечно»).
- **Риск ложного рестарта** на разовом сетевом/серверном 401. Каждый лишний рестарт — это
  НОВЫЙ `environmentId`, то есть видимая владельцу возня с выбором Environment на телефоне.
- Лог обнуляется при рестарте (`rc_supervisor.py:352`) — детектор обязан держать смещение и
  переживать усечение файла, иначе перечитает старое и рестартанёт по мёртвой улике.

**Как минусы снимаются (если брать этот вариант):**
- Признак — **дословная** строка `failed 401: OAuth access token has been revoked`, а не `401`
  (см. п.4: иначе 78 % ложных).
- Судить **по действию, а не по подстроке** (правило среды №5): рестарт только когда за
  строкой 401 следует `exited status=failed` с `duration` в единицы секунд. Тогда разовый
  сетевой 401, который мост пережил рефрешем (как `StopWork` выше), детектор не тронет.
- Две неудачи подряд вместо одной — цена ещё одна умершая сессия, зато ложный рестарт
  практически исключён.

## Вариант (б): авто-рестарт rc-server при смене mtime `.credentials.json`

Вотчер следит за `C:\Users\mxfill1\.claude\.credentials.json` и рестартует rc-server, как
только файл переписан.

**Минусы:**
- **Проактивен, но бьёт вслепую**: перелогин может случиться в СЕРЕДИНЕ работы — рестарт
  оборвёт активные rc-сессии (а они, как показал п.2, продолжают работать нормально).
  Нужен дебаунс/грейс.
- **mtime меняется не только от логина.** Сегодня `CreationTime == LastWriteTime == 05:10:10` —
  файл переписан целиком, но так же выглядит и обычный автоматический рефреш токена любым
  процессом `claude` на машине (а их тут одновременно с десяток). Триггер будет срабатывать
  регулярно и вхолостую — и каждый холостой ход снова меняет `environmentId`.
- Чтобы отличить логин от рефреша, надо смотреть В СОДЕРЖИМОЕ (identity токена/`expiresAt`) —
  то есть тянуть секреты в агентский код, чего правило репо прямо не хочет. Максимум
  безопасного — хеш файла, но хеш меняется и от рефреша тоже, то есть не помогает.

**Как минусы снимаются (если брать этот вариант):** рестарт только когда сервер ПРОСТАИВАЕТ
(нет живых детей-воркеров) + грейс 60–120 с. Обрыв работы уходит; холостые рестарты и смена
Environment — остаются.

## Рекомендация

**Брать (а)** — с дословным признаком и правилом «строка 401 + сессия упала за секунды»,
плюс, по желанию, порог в две неудачи подряд.

Почему не (б): его единственное преимущество — проактивность — стоит регулярных холостых
рестартов (mtime меняется от рефреша, а не только от логина), а каждый рестарт видим
владельцу сменой Environment. (а) же срабатывает ровно на том событии, которое и есть поломка,
и не требует ни одной догадки о происхождении файла кредов.

Цена (а) честно называется: **первая сессия после перелогина всё равно умрёт**. Но умрёт за
2–3 с с внятной причиной, а следующая поднимется сама — вместо сегодняшнего сценария, где
владелец час стучится в «Connecting», а потом человек лезет читать логи.

Гибрид (детектор (а) + пассивный намёк из (б) как приоритет проверки) возможен, но выигрыш
над чистым (а) — только эти 2–3 секунды. Усложнение не окупается.
