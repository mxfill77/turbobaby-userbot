### Как снималось: HEAD НЕ ДВИГАЛСЯ ни разу

Ветка собрана сантехникой, без `checkout -b` и без переключения веток:

```
git add -- <4 пути>
TREE=$(git write-tree)                      # b629c7bfbacfeeb226ee858e4d66b2b39ef4f659
CM=$(git commit-tree $TREE -p HEAD -m "…")  # ed674cd…
git branch wip-works-buffer-50-56-20260822 $CM
git reset -q -- <4 пути>                    # разстейдж; рабочего дерева не касается
git checkout -- invariants_check.py service_receipt.py splinter.py
```

Это сделано намеренно. Обычный путь (`checkout -b` → commit → `checkout main`) заставил бы git
**удалить `works_ledger.py` с диска** — файла нет в `main`, и переключение снесло бы его.
Запрет «НИЧЕГО НЕ УДАЛЯТЬ — ни файлов» это запрещает, поэтому HEAD остался на `main`,
а `works_ledger.py` так и лежит на диске нетронутым (см. ниже).

## Замок, который сработал ложно (говорю прямо)

Первая попытка записи **встала на замке 4** («исполнитель не идёт») и не сделала НИ ОДНОЙ
правки: `git status` и индекс после отказа были ровно теми же. Причина — моя ошибка, а не
состояние сервера: проверка `pgrep -f "claude -p"` нашла **сама себя**, потому что строка
успеха в том же скрипте содержала литерал `claude -p`, и он попал в командную строку
собственного процесса. Замок переписан на якорь по началу cmdline, повтор прошёл чисто.
Отказ был fail-closed: остановка до записи, а не частичное состояние.
