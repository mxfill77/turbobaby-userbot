## Короткий ответ

Ревизор **помнит** отказы — механизм есть, читается каждый прогон и работает. Но **заполняется
он только руками**, через CLI. Ни одна строка кода не превращает «нет» владельца в вердикт.
За всё время существования реестра глушение не сработало **ни разу**: `hits=0` у всех шести
записей, раздел счёта выбывших проверок **пуст**.

А сама находка ложна потому, что в паттерне дефицита стои́т отдельный сверхширокий токен
`разбира\w+`, который ловит обычную фразу поддержки «уже разбираемся».

## 1. Чек «нет утверждений о наличии»: почему «разбираемся» — утверждение о наличии

Чек живёт в `suggest._smoke_checks` (`suggest.py:7352-7360`) — **тот же код**, что гоняет e2e-смоук;
ревизор зовёт его пост-релизным проходом `_revizor_postrelease_findings` (`pc_orchestrator.py:8350`).

```python

    viol = availability_violations(client, avail=None)
    checks.append({
        "name": "нет утверждений о наличии",
        "ok": not viol,
        "expected": "наличие/дефицит/особые условия без данных не утверждаются",
        "fact": ("клеймы наличия: " + "; ".join(c["raw"] for c in viol) if viol
                 else "клеймов наличия нет"),
    })
```

Слово ловится **не** паттерном наличия, а паттерном ДЕФИЦИТА — `suggest._AV_SCARCITY_RE`
(`suggest.py:6809-6813`). Условие дословно, виновная альтернатива выделена:

```python

    r"послед\w+\s+(?:байк\w*|штук\w*|шт\b|один|одна|экземпляр\w*)|остал\w+\s+(?:один|одна|1\b)|"
    r"осталось\s+\d|мало\s+остал\w+|почти\s+(?:всё|все)\s+разобрал\w*|разбира\w+|успевай\w*|"
    r"успей\w*|спеши\w+|торопи\w+|только\s+сегодня\b|"
    r"last\s+one|only\s+\d+\s+left|almost\s+gone|selling\s+fast|hurry|going\s+fast|only\s+today", re.I)
```

Дальше приговор безусловен — `_av_unsupported` (`suggest.py:6872-6882`):

```python
        if c["kind"] == "avail_pos" and state is True:
            continue
        if c["kind"] == "avail_neg" and state is False:
            continue
        bad.append(c)          # scarcity/special — данных-источника нет → ВСЕГДА нарушение
```

`avail=None` (Bridge про дефицит не спрашивают вовсе), `kind='scarcity'` → ветки помилования нет.

**Живой прогон (`probe.py`, блок A–C):**

```

availability_violations('разбираемся')  = [{'kind': 'scarcity', 'raw': 'разбираемся'}]
availability_state(None)     = None  (данных Bridge нет)

какая альтернатива какого паттерна ловит слово:
  _AV_SCARCITY_RE  → альтернатива 'разбира\\w+'

  'Уже разбираемся с вашим вопросом, вернусь с ответом.' → ['разбираемся/scarcity']
  'Разбираемся по датам и вернусь.'                    → ['Разбираемся/scarcity']
  'Мы не разбираемся в этом вопросе.'                  → чисто
  'Сейчас уточним и вернёмся.'                         → чисто

  чек «нет утверждений о наличии» ok=False
     факт: клеймы наличия: разбираемся
```

Факт воспроизводится дословно тем, что стои́т в карточках 58 и 4.

**Это рецидив уже закрытого класса — и признание стои́т строкой выше в том же файле.**
`suggest.py:6841-6845` описывает ровно такой ложняк соседнего токена:

> вместе с чересчур широким токеном «успева\w+» это дало живой ложняк id=360 (окно 45349667):
> «раньше ночи НЕ успеваем» — про время подачи, а не про дефицит… Срочность несут повелительные
> формы («успевайте», «успей»), они и остались в паттерне.

`успева\w+` тогда сузили до `успевай\w*|успей\w*`. Соседний `разбира\w+` **оставили широким**,
хотя идиому дефицита несёт стоящая рядом альтернатива `почти\s+(?:всё|все)\s+разобрал\w*`.
Отрицание он снимает (`не разбираемся` → чисто, `suggest.py:6846-6848`), а обычную речь поддержки —
нет.

## 2. Помнит ли ревизор отказы владельца

**Место есть. Читается. Пустое по этому чеку. И заполняется только руками.**

- Хранилище: `pc_orchestrator.revizor_verdicts.json`, ключ **`класс|окно|предмет`**
  (`_revizor_verdict_key`, `pc_orchestrator.py:7392`) + отдельный отпечаток существа (улика,
  `_revizor_finding_gist`). Три исхода: `ложная` / `законная` / `не разобрана`.
- Читается **каждый прогон**, до доставки: `reg, chk = _revizor_registry_read()`
  (`pc_orchestrator.py:8529`), затем `_revizor_apply_verdicts` и `_revizor_apply_bench`.
  Механизм исправен — это не сломанный фильтр.
- **Пишется ровно из одного места — CLI `--revizor-verdict` (`pc_orchestrator.py:9344-9358`).**
  Проба, блок I: вызовов `revizor_set_verdict(` в демоне — **2** (определение + один вызов),
  и этот единственный вызов стои́т в ветке разбора `sys.argv`.

**Ключевой ответ: отказ владельца в реестр не попадает никогда — такого кода нет.**
Отказ живёт своей жизнью: devbot финализирует задачу как `failed` с префиксом
`отклонено Филиппом` (`_REJECT_PREFIX`, `pc_orchestrator.py:4383`). Его читают три потребителя —
`NO_HEAL_PREFIXES` (запрет самопочинки), `card_terminal_log.py`, `queue_snapshot_pc.py`.
**Ревизора среди них нет.** В логе демона отказ не оставляет даже строки: там пишется только
`APPROVED id=N`.

Единственная межпрогонная память ревизора о находке — **память о ДОСТАВКЕ, а не о РЕШЕНИИ**,
и она умирает вместе с карточкой. `_revizor_find_owner_card` (`pc_orchestrator.py:8230`):


находка пишется заново как первая. Это ровно тот класс, который в коде **уже описан** на
`pc_orchestrator.py:7339-7344` — по находке про депозит 08–09.08. Замок от него (реестр) построили,

## 4. Как делятся «спросить владельца» и «в ленту»

Признак — **поле `action` находки**, и больше ничего (`_revizor_route`, `pc_orchestrator.py:8480-8503`):
`task` → зелёная задача, `owner` → карточка, всё прочее → `noise`, только лог. Поверх — три
поправки: ворота деплоя и **ворота входа в клиентский контур** (`task`→`owner`, если правка задевает
`suggest.py`), затем вердикт `ложная` → лента, затем порог пользы проверки → лента.

**Почему эта находка попала к владельцу:** потому что у детерминированного прохода `action`
не вычисляется вовсе — он **зашит константой**. `_revizor_postrelease_findings`
(`pc_orchestrator.py:8371`):

```python

```

То же в `_revizor_ipc_findings` (`:8428`). Ни одна ветка не спрашивает, важна ли находка:
любой провал чека #92 — карточка владельцу. Оценку `task/owner/noise` даёт только LLM-думатель

**Про «семь соседних, ушедших в ленту» — премиса не подтвердилась, и это важно.**

## 5. Видит ли ревизор записанные бизнес-правила

**Нет. Ни думатель, ни детерминированные чеки.**

Думатель запускается через `_thinker_exec` с `--max-turns 1`, **`--allowed-tools ""`** и
**cwd = tempdir, не репо**. Он физически не может открыть ни файла, ни мозга. Весь его мир —
преамбула (**3418 символов**, проба блок I) плюс текст пакета окна. Преамбула = роль +
`docs/revizor_checklist.md` + контракт вывода. В чек-листе **59 строк**, из них тело — семь
классов а–ж про форму ответа (переспрос, чужая модель, утечка маркеров, ложная ✅…).
**Ни одного бизнес-правила там нет** — ни депозитов, ни цен, ни сроков. Проба: слово «депозит»
в чек-листе встречается (в описании класса «а» — «цена/депозит/скидка, которых НЕТ во входных
данных»), а ступени сумм (3000/5000/7000) — **нет**.

Детерминированный чек депозита правил не читает тем более. `suggest._smoke_deposit_conflict`:

```python
    deps = sorted({int(m.group(1).replace(" ", "")) for m in _SMOKE_DEP_AMOUNT_RE.finditer(s)})
    if len(deps) > 1:
        return "разные суммы депозита: " + ", ".join(f"{v} ฿" for v in deps)
```

Две разные суммы в тексте = противоречие. Никакой таблицы классов техники у него нет.

**Пересчёт ступеней своим проходом (поправка к постановке).** Лестница депозитов живёт
в `suggest.CRITICAL_FACTS` (`suggest.py:276-290`) — 20 моделей, но **различных ступеней шесть**,
а не семь: 3000 · 5000 · 7000 · 15000 · 20000 · 25000. Ровно эти шесть и стоят уликой во всех
шести записях реестра. Бот печатает прайс-блок целиком — чек видит шесть сумм и зовёт лестницу
противоречием.

Депозиты, записанные в мозг 19.08, ревизор не видит: у него нет доступа к мозгу ни одной дорогой,
а лестница, по которой он мог бы свериться, лежит в 14 строках `suggest.py`, куда он тоже не
заглядывает.

## 6. Что минимально нужно, чтобы отказ имел силу на следующем прогоне

Не строил — называю. Механизм глушения уже готов и исправен; недостаёт **одного провода и одной
поправки ключа**.

1. **Провод «отказ → вердикт».** На финализации карточки отказом (`answer_card(tid, False)` /
   приход `failed` с префиксом `отклонено Филиппом`) разобрать строки `• [класс X] окно cid: улика`
   отвеченной карточки обратно в ключ + существо и позвать по каждой
   `revizor_set_verdict(key, "ложная", gist=улика, why=f"отказ владельца, карточка {tid}")`.
   Строки карточки для этого достаточны: класс и окно стоят в ней явно, имя чека #92/#93 —
   первым словом улики («чек «…»: …»). Сегодня это единственное недостающее звено: реестр
   читается, ключ считается, глушение работает — просто никто не пишет.
2. **Разделить, за что «нет».** Карточка сводная: одна кнопка отвечает сразу за N строк.
   Пока отказ не привязан к строке, любой провод либо глушит лишнее, либо не глушит ничего.
   Минимум — сохранять при доставке соответствие «карточка tid → список ключей», которого сейчас
   не существует нигде.
3. **Ключ детерминированных чеков — без окна.** `класс|окно|предмет` привязывает решение
   к диалогу; новое окно рождает новый ключ, и та же ложная находка приезжает снова (пункт 3
   выше: депозит, шесть вердиктов, седьмое окно — доставлено). Для #92/#93 предмет и есть
   проверка, окно тут лишнее. Либо это, либо порог `REVIZOR_BENCH_MIN_DECIDED=20` недостижим:
   за 12 суток набралось 6 разобранных, и чек остаётся «В ПОТОКЕ».
4. **Корень — отдельно.** Пункты 1–3 глушат следствие. Ложную находку рождает
   `разбира\w+` в `_AV_SCARCITY_RE`; пока токен широкий, чек будет ловить речь поддержки
   на каждом новом окне.

## 7. Предсмертный взгляд

Починку сделают проводом «отказ → вердикт», она сработает на дословной улике и на том же окне —
и провалится на следующем тике, когда регулярка поймает **другое** слово («успевайте», «доступен»)
или другое окно: отпечаток существа не совпадёт, замок `pc_orchestrator.py:7535` честно скажет
«существо находки изменилось», и та же по сути ложная находка приедет владельцу как новая —
защита от слепоты сохранит шум, потому что глушили находку, а не причину.
