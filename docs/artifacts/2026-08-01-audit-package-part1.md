# ПАКЕТ ВНЕШНЕГО АУДИТА TurboBaby — ЧАСТЬ 1 из 2: КОНТЕКСТ И ОГРАНИЧЕНИЯ

Версия 01.08.2026. Часть 2 (опись мозга, сверка документов с кодом, дорожная карта) придёт
отдельным сообщением. Всё ниже — состояние на 01.08.2026; числа сняты с живого репозитория
и живого мозга, не по памяти.

## 1. КТО МЫ И ЧТО СТРОИМ

TurboBaby — аренда мотоциклов на Пхукете. Владелец один, тайская команда работает на земле
(сервис, развозка техники), клиенты пишут в личку Telegram. Софт разделён на два контура:
клиентский (переписка с клиентом, RU+EN) и внутренний (учёт техники, работ и денег, RU+TH).
Разделение не организационное, а машинное — см. §3.

Сверх-цель одна: **владелец рулит бизнесом с телефона**. Финал — клиентский слушатель на
Raspberry Pi, домашний ПК выключен. Ось всей разработки — **оркестратор-дирижёр**: очередь
задач лежит в мозге, демон берёт ОДНУ задачу (поллинг ~60с, жёсткий таймаут 45 мин),
исполняет её headless-агентом прямо в репозитории под трёхцветным гардом; «красное» действие
демон не исполняет сам — задача уходит в NEEDS_APPROVAL, владельцу летит карточка в Telegram,
без «да» шаг не повторяется (отказ или 30 мин молчания → failed). Всё новое сверяется одним
вопросом: как это двигает оркестратор? Метрика прогресса — число карточек, НЕ дошедших до
владельца, и число цепочек, пройденных дирижёром без вмешательства человека.

Масштаб, числами. Полос две: ПК (`turbobaby-userbot`) и VPS (`turbobaby-manager-bot`), у
каждой свой репозиторий и свой демон. ПК-репозиторий: 89 py-файлов под git, 69 181 строка,
39 тестовых модулей, 419 коммитов (142 из них за последние 7 дней), 149 разборов в
`docs/artifacts/`. Память системы — документы Google Docs через собственный мост (Bridge на
Apps Script), реестр 33 ключа; слои: KB_PULSE (статус), KB_MASTER (карта), cc_log (история
VPS), cowork_log (история ПК, 212 тыс. символов), KB_business_rules, KB_trainer_log. Голова
обеих полос — `claude-opus-5`, запасная `claude-opus-4-8`.

## 2. КАРТА СРЕД (кто что может и чего не может)

- **ШТАБ** — Claude на сайте, у владельца в браузере. Думает, проектирует, ревьюит, пишет ТЗ,
  читает мозг. **Кода не выполняет и живых фактов не производит вовсе**: любая его гипотеза
  проверяется командой на полосе, а не спором. Termux исключён навсегда, новых сред не заводим.
- **328 devbot** — постановка задач с телефона: владелец пишет в тему 328 Telegram-форума
  `тз: …` (очередь VPS) или `пк: тз: …` (очередь ПК). Аварии контура и карточки сессий — в
  тему 1160. Не может: править реестр моста, трогать живые таблицы, деньги, удалять.
- **DISPATCH** — интерактивный Claude Code на ПК (терминал у владельца). Полные права полосы
  ПК под гардом, умеет clasp и Apps Script (правку самого моста).
- **RC-сессии** — тот же Claude Code на ПК, но управляемый с телефона (Remote Control, задача
  Планировщика `TurboBabyRC`). Живучесть держит сторож: тик 30с, льгота свежему процессу 180с,
  порог протухания именованной ветки 43 200с, гасит только после 3 неудачных проб подряд.
  Каждая RC-сессия ОБЯЗАНА финальным шагом записать итог в мозг — иначе для Штаба её не было.
- **pc_agent** — единственная дверь для команд владельца с телефона к боевому процессу
  клиентского слушателя. Отдельный бот, фиксированный белый список из пяти команд (обнови /
  статус / стоп / старт / сводка), проверка chat_id + темы 205 + одного user id. Произвольного
  shell нет по построению.
- **SSH ПК→VPS** — обязательно с таймаутами. **Команды по SSH идут мимо гарда** — это
  единственный канал без трёхцветной защиты, поэтому серверный заход не дробится: бэкап →
  правка → тесты → гейт → коммит → откат при любом красном, всё внутри одного вызова.

## 3. ДВА КОНТУРА И ПОЧЕМУ ИЗОЛЯЦИЯ АБСОЛЮТНА

**ВНУТРЕННИЙ** (учёт, RU+TH): агент Splinter на VPS, Bridge, memory.db. Здесь работает тайская
команда; русские тексты уходят к ней машинным переводом RU→TH.
**КЛИЕНТСКИЙ** (RU+EN, без тайского): userbot-слушатель и бот модерации на ПК, подсказчик
ответов. Память контуров раздельная.

Изоляция абсолютна не по декларации, а по коду. Ворота выкатки: коммит, задевающий
**транзитивное import-замыкание клиентских процессов**, автоматически не применяется.
Замыкание считается по факту с диска разбором AST от двух входных точек (слушатель и
модерация), включая импорты внутри функций, и дополняется не-.py файлами, чьи имена лежат
строковыми литералами в модулях замыкания (промпты, json-правила меняют поведение бота без
рестарта). Списка имён нет сознательно: новый модуль становится клиентским В ТОТ ЖЕ МОМЕНТ,
когда бот его импортирует. **Fail-closed**: граф не построился — «клиентским» считается всё.
Пропуск через ворота даёт только «да» владельца либо зелёный тренажёр.

Ворота заведены после живого инцидента: 30.07 в 01:48–01:53 авто-реконсайл рестартнул обоих
боевых ботов на коммит `4528917` за 17 минут до того, как владелец успел остановить цепочку.
От живого клиента текст удержал только тестовый режим подсказчика — везение второго слоя, а не
ворота.

## 4. ОГРАНИЧЕНИЯ, КОТОРЫХ ТЫ НЕ ЗНАЕШЬ (читать до первой идеи)

1. **Два контура — жёсткая граница.** Любое предложение вида «общий модуль», «одна память на
   всё», «один бот и там и там» упирается в ворота §3 и будет отклонено не обсуждая.
2. **Клиентский слушатель привязан к домашнему IP Пхукета** (Telegram-сессия
   пользовательского аккаунта). Поэтому клиентский контур переносится ПОСЛЕДНИМ и никогда
   целиком. Идеи «вынести всё в облако / контейнеры / вторую площадку сейчас» нерабочие: они
   ломают привязку, а не улучшают её.
3. **Тренажёр — единственный автоматический вердикт для ворот клиентского контура.** Зелёный
   засчитывается только целиком: 12 кейсов, 222 чека из 222, тот же 40-символьный коммит, sha
   корпуса, два прогона из двух, без грязи. Частичный прогон, ручное «я проверил, работает» и
   зелёные юниты воротами не считаются. Файлу вердикта ворота не верят на слово — запись
   обязана доказать себя целиком, иначе её мог бы подделать любой писатель.
4. **Тайская команда не общается с клиентами.** Она целиком внутри внутреннего контура; её
   тексты идут через машинный перевод. Схемы вида «пусть механик ответит клиенту в чате» вне
   модели бизнеса.
5. **done = живой факт.** Расписка моста, `ok` от API, карточка, отчёт агента и любая сводка —
   нарратив, не факт. Фактом считается: хеш в `git log`, PID живого процесса, чтение назад
   ДРУГИМ процессом. Свежий класс 01.08: код ответа описывает доставку расписки, а не судьбу
   мутации. Если твоё предложение проверяется только чьим-то рапортом — оно не проверяется.
6. **Клиентский контур сейчас ЗАМОРОЖЕН,** вместе с черновиками, тренажёром, формулировками
   для клиентов и бизнес-данными. Работа идёт по базе разработки и внутреннему контуру.
   Находки по замороженному попадают в список, а не в работу; исключение даёт только владелец,
   поимённо и однократно.
7. **Сред больше не заводим.** Этот пакет владелец вставляет руками — ноль новых интеграций,
   ноль доступов. Твой доступ к мозгу обсуждается только после того, как ты дашь то, чего у
   нас нет.

## 5. ПРАВИЛА, ПО КОТОРЫМ МЫ РАБОТАЕМ (сжатая рамка проекта)

- **Память по слоям:** статус — KB_PULSE, карта — KB_MASTER, история VPS — cc_log, история ПК —
  cowork_log. «Проверь» = сначала пульс, затем ОБА журнала. Коннектор отстаёт: «та же версия»
  значит «возможен лаг», никогда — «ничего не происходит».
- **Журнал = индекс:** тело длиннее 600 символов уходит в артефакт, в журнал — итог и путь.
- **FACT-культура (закон):** сводка агента — гипотеза, при расхождении с сырыми числами верить
  числам; гипотеза Штаба — тоже гипотеза, проверяется командой, не спором; окно с коммитом ≠
  авторство работы; проверка обязана повторять живой формат запуска; фикс класса применяется
  к ОБЕИМ полосам сразу; каждая сессия финальным шагом пишет итог в журнал; одна задача — один
  вызов, серверную работу не дробить.
- **Доктрина подтверждений:** судить по ДЕЙСТВИЮ, а не по совпадению слов. Высшая карточка
  (живые таблицы, деньги, клиентский контур, выкатка прода, удаление вне временного каталога,
  снос процессов) требует ответа с названным объектом; нет числа или имени — карточки быть не
  должно; одна карточка — одна операция; перезапуск живого процесса — отдельное разрешение;
  карточка не устаревает сама; **отказ владельца терминален**, режим «разрешить всё» не включаем.
- **Правила Штаба:** KB_MASTER — точка входа №1; задачи выдаются блоком кода; завершение
  никогда не объявляется по слову агента; досыл к задаче = новая задача; перед повтором упавшей
  задачи — сначала статус очереди; паузы не предлагать; один заход — одна цель.
- **Экономия кругов:** второй случай одного класса — это разведка списком, а не третья заплата;
  фикс не идёт в среду, чей дефект он чинит; Штаб называет симптом и живой факт, место
  исполнитель находит сам; в каждом ТЗ стандартный блок запретов (ничего не удалять, включая
  уборку за собой; место для временного назвать явно; конфиги и секреты не читать — читать код,
  который их читает; боевых записей нет; процессы не трогать без отдельного разрешения);
  догадка Штаба проверяется ДО постановки задачи.

Что мы хотим от тебя по существу: идеи и возражения, которых у нас нет. Ступень 1 — ты оппонент
без доступа. По итогу мы замерим ровно одно: дал ли ты то, чего у нас не было, или пересказал
наше. Канал с доступом к мозгу обсуждается только после положительного замера.

У тебя нет доступа к живой системе. Ты можешь давать идеи, спорить с планом и указывать на дыры
в рассуждении. Ты НЕ можешь утверждать факты о состоянии системы — любое такое утверждение будет
проверено командой и, скорее всего, опровергнуто. Если чего-то не знаешь — спрашивай, не
достраивай.
