## 6. Почему повод БУДЕТ подниматься и дальше (свойство сигнала, не полосы)

`recon_auto_run.repeat_signals` читает ряды со статусом `failed` (`CLOSED_STATUSES = ("failed",)`)
и считает **вхождения маркера**. У этого счёта нет:

* **окна по времени** — ряд 04.09 весит столько же, сколько ряд сегодняшний;
* **дедупа по заданию** — досылка #208 считается вторым эпизодом, хотя это первое, посланное дважды;
* **убывания** — ряд `failed` в очереди не переписывается, маркер в нём вечен.

Следствие, названное числом: счётчик будет показывать **ровно 3** на каждом обороте разведки,
пока эти ряды видны мосту, — независимо от того, что прибор починен, а класс не повторяется.

Единственное, что этот счёт гасит, — **собственный продукт разведки**:

```
python _scratch_v0_recon_0905/probe_dedup.py
   slug   = вердикт-v0-при-закрытии-неизвестно-продукт-по-ад
   ключ   = f7ea6afd9bb2
   метка дедупа = разведка-вердикт-v0-при-закрытии-неизвестно-продукт-по-ад
   метка ВХОДИТ в имя адреса: True
дедуп ПОСЛЕ появления файла: analysed -> {'f7ea6afd9bb2'}
повод переживает дедуп (пустой список = повод снят): []
```

Ключ совпал с ключом задания дословно (`f7ea6afd9bb2`). **Этот файл и есть замок:**
`recon_auto.analysed` снимет повод по метке в имени, и разведка по нему больше не встанет.

  номер задачи (`done_judge_pc.note`: `rows[str(tid)] = entry`), поэтому повторный суд НАД ТОЙ ЖЕ
  задачей затирает прежний. **Отсюда честная граница числа «новых эпизодов после #210 — ноль»:**
  оно верно для задач, судившихся один раз, и слепо к задаче, которую сначала осудили
