## 1. Пароль учётки — фактом установить НЕ УДАЛОСЬ

Что известно точно (замер 07.08):

```
net user mxfill1 / Get-LocalUser
  PasswordRequired       : False            (флаг UF_PASSWD_NOTREQD)
  PasswordLastSet        : 18.02.2022 3:18:30
  PrincipalSource        : Local            (локальная учётка, НЕ Microsoft-аккаунт)
  Enabled                : True
net accounts
  Lockout threshold      : Never            (блокировки учётки не существует)
HKLM\SYSTEM\CurrentControlSet\Control\Lsa\LimitBlankPasswordUse = 1
```

Единственный способ установить «пуст / не пуст» без прав админа и без подбора — **одиночная
проба `LogonUser(mxfill1, "", LOGON32_LOGON_INTERACTIVE)`**, где ответ читается не по успеху, а по
коду ошибки: `1327` (`ERROR_ACCOUNT_RESTRICTION`) = пароль пуст и его режет политика,
`1326` (`ERROR_LOGON_FAILURE`) = пароль не пуст. Риска нет: порог блокировки — `Never`.

**Проба заблокирована внешним защитным слоем** (классификатор Claude Code отказал в вызове,
причина: «Blocked by classifier»). Обходить не стал. Значит, ответ на вопрос «пуст ли пароль»
в этой сессии **не получен**, и придумывать его я не буду.

### Но на решение это НЕ влияет — и вот почему

В разборе 06.08 (и в постановке задачи) записано: «при пустом пароле `LimitBlankPasswordUse=1`
запрещает неконсольный вход, **автологон не сработает**». Вторая половина этой фразы —
**неверна**, и это важно, потому что из неё следует ложный стоп.

Политика «Accounts: Limit local account use of blank passwords to console logon only» по
документации Microsoft режет **network / remote interactive / service / batch** логоны. Автологон
Winlogon — это **интерактивный вход на физической консоли**, то есть ровно тот случай, который
политика оставляет разрешённым. Отпадают от неё варианты **В** (`LogonType=Password` + BootTrigger)
и **Г** (служба Windows) — они и были помечены в разборе как отпадающие. Вариант **Б** (автологон)
она не трогает.

Практический вывод один и тот же в обоих случаях: **владелец всё равно вводит пароль сам**, а
скрипт вооружения (см. §2) отказывается принимать пустой ввод и отказывается записывать
непроверенный пароль. То есть факт «пуст / не пуст» установится в момент запуска скрипта, за один
шаг и без всякой пробы:

| что увидит владелец | что это значит |
|---|---|
| `Пароль проверен системой — верен` | пароль **не пуст**, автологон вооружён |
| `СТОП: введён пустой пароль` | нажат Enter вхолостую — задать непустой пароль и повторить |
| `СТОП: пароль не принят системой (код 1326)` | пароль неверен — ничего не записано |
| `СТОП: … (код 1327)` | ограничение учётки, в т.ч. пустой пароль — задать непустой |

## 2. Способ автологона: LSA Secrets, НЕ реестр

Плейнтекст исключён по построению. `HKLM\…\Winlogon\DefaultPassword` — это **открытый текст**,
владелец его запретил; скрипт не только его не пишет, но и **сносит**, если он там окажется.

Пароль кладётся в **LSA Secrets** вызовом `LsaStorePrivateData("DefaultPassword", …)` — это ровно
тот механизм, которым пользуется Sysinternals `Autologon.exe`. Скачивать ничего не пришлось:
`Autologon.exe` на машине нет (`C:\`, `D:\`, Downloads, Desktop — ноль совпадений), а тот же
системный вызов делается своим скриптом.

**Файл:** [`autologon_arm.ps1`](../../autologon_arm.ps1) (в корне репозитория, UTF-8 **с BOM** —
без BOM PowerShell 5.1 читает кириллицу как cp1251, и байт `0x94` из тире `—` превращается в
типографскую кавычку `”`, которую парсер принимает за настоящую: файл не разбирается. Проверено:
до BOM — 8 ошибок разбора, после — `0`).

Что он делает за один запуск:

1. сам поднимает себе права (`-Verb RunAs`);
2. просит пароль через `Read-Host -AsSecureString` — **вслепую, без эха**;
3. **проверяет пароль вызовом `LogonUser` ДО записи** — неверный в LSA не попадёт. Это закрывает
   класс «автологон сломался молча»: без проверки ошибка вылезла бы только на следующей загрузке,
   когда машина уже стоит у экрана входа и дотянуться до неё некому;
4. кладёт секрет в LSA, затирает буфер пароля в памяти (`ZeroFreeBSTR`, `ZeroFreeGlobalAllocUnicode`);
5. ставит `AutoAdminLogon=1`, `DefaultUserName=mxfill1`, `DefaultDomainName=MXFILLPC`;
6. сносит `DefaultPassword` из реестра (если есть) и `AutoLogonCount` (при `>0` автологон
   одноразовый: Winlogon после первого входа сам удаляет `AutoAdminLogon`);
7. ставит `DevicePasswordLessBuildVersion=0` — см. §3;
8. печатает итог **без пароля** и напоминает про BIOS.

Откат — `autologon_arm.ps1 -Disable` (секрет из LSA удаляется, `AutoAdminLogon=0`,
passwordless возвращается в `2`).

**Запускать в обычном окне PowerShell, не в сессии Claude** — пароль не должен попадать ни в
какую переписку. UAC-диалога быть не должно: на машине `ConsentPromptBehaviorAdmin = 0`
(«повышать без запроса») и `PromptOnSecureDesktop = 0`. Это вывод из политики, а не замер —
если диалог всё же появится, его надо подтвердить.

```
C# compile: OK    (типы TbAutologon.StoreSecret, TbAutologon.CheckPassword собрались)
```

## 3. Находка, которой не было в разборе 06.08: `DevicePasswordLessBuildVersion = 2`

```
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\PasswordLess\Device
    DevicePasswordLessBuildVersion = 2
```

Это дефолт Win11: «passwordless»-режим, который прячет парольный провайдер входа и снимает
галку «Требовать ввод имени пользователя и пароля» из `netplwiz`. На части сборок он же глушит
`AutoAdminLogon`. Значение `0` возвращает обычное поведение; менять его — **видимое изменение
поведения машины**, поэтому оно вынесено внутрь скрипта вооружения (§2, шаг 7), а не сделано
заранее. Откат — одно значение обратно в `2`.

Побочный эффект `0`: на экране входа снова появляется вариант «пароль» рядом с ПИН-кодом.
Вход по ПИН-коду при этом работает как работал.

Ещё одна деталь того же гнезда: `AutoLogonSID` в `Winlogon` **уже стоит** и равен SID нашей
учётки (`…-1002`). Откуда — неизвестно; на поведение без `AutoAdminLogon` не влияет, не трогал.

## 4. Немедленная блокировка экрана — СДЕЛАНО и проверено

**Задача Планировщика `\tb_lock_on_logon`** (заведена 07.08, зарегистрировалась **без повышения
прав**):

| поле | значение |
|---|---|
| триггер | `LogonTrigger`, `UserId = mxfillpc\mxfill1`, `Delay = PT5S` |
| принципал | SID `…-1002`, `InteractiveToken` (как у остальных четырёх задач контура) |
| действие | `C:\Windows\System32\wscript.exe //B //Nologo "D:\turbobaby-bot\lock_on_logon.vbs"` |
| рабочий каталог | `D:\turbobaby-bot` |
| `ExecutionTimeLimit` | `PT5M` |

**Почему скрипт, а не голый `rundll32 user32.dll,LockWorkStation` прямо в задаче.**
`LockWorkStation` срабатывает только когда интерактивный рабочий стол уже поднят; вызов, пришедший
слишком рано, возвращает `FALSE` и не делает **ничего** — а задача при этом отчитается кодом `0`.
Это готовый ложный «настроено»: рабочий стол остался открытым, и нигде это не видно.
[`lock_on_logon.vbs`](../../lock_on_logon.vbs) поэтому проверяет **факт**: заперто = живой процесс
`LogonUI.exe` (он держится на защищённом рабочем столе, пока станция заблокирована). До шести
попыток за ~30 секунд, **выход немедленно после подтверждения** — чтобы не запереть человека
повторно, если он только что разблокировал экран руками.

### Что проверено фактом 07.08 05:09–05:11

| проверка | результат |
|---|---|
| задача зарегистрирована | `Get-ScheduledTask tb_lock_on_logon` → `State = Ready` |
| определение легло как задумано | `Export-ScheduledTask` — триггер, задержка `PT5S`, принципал и действие совпадают |
| задача реально исполняется | `Start-ScheduledTask` → `LastTaskResult = 0`, зависших `wscript.exe` не осталось |
| точка входа `rundll32` жива | отдельный запуск `rundll32.exe user32.dll,LockWorkStation` → `ExitCode = 0`, процесс не завис, окна с ошибкой нет |

**Чего этот прогон НЕ доказал, честно.** На момент проверки станция **уже была заперта**
(`LogonUI.exe` — 1 процесс), поэтому скрипт по своей же логике вышел сразу и ветку «позвать
`LockWorkStation`» не прошёл. Проверена связка «задача → wscript → скрипт → код 0» и
работоспособность самой точки входа; **сам факт запирания проверяется только после автологона**,
когда сессия окажется открытой. Разблокировать станцию для чистого теста я не могу — это ввод
учётных данных.

**Риск, который надо назвать.** Блокировка на `+5с` наступает **раньше**, чем RC-сервер поднимает
свою консоль (по хронометражу 06.08: вход `19:38:27` → `claude` RC `19:38:45`, то есть `+18с`).
Живому TTY переключение рабочего стола мешать не должно — консоль остаётся на `WinSta0\Default`, —
но **это не измерено**. Если после первой автозагрузки RC не поднимется, ручка одна: увеличить
`<Delay>` у триггера `\tb_lock_on_logon` c `PT5S` до `PT60S`, заплатив минутой открытого стола.

## 5. Автовключение после возврата питания — только BIOS, из ОС недоступно

Подтверждено повторно: представления этого параметра в ОС нет — ни в WMI, ни в реестре, ни в
`powercfg`. Это UEFI-настройка, и правит её только человек у машины.

**MSI Click BIOS 5, MPG Z390I GAMING EDGE AC (MS-7C04):**

1. При включении жать `Delete` → `F7` (переключить в **Advanced Mode**);
2. **Settings → Advanced → Power Management Setup**;
3. **`Restore after AC Power Loss` → `Power On`** (варианты: `Power Off` / `Power On` / `Last State`;
   нужен именно `Power On`, а не `Last State` — при `Last State` после аварийного обрыва плата
   считает предыдущим состоянием «выключено» не всегда предсказуемо);
4. В том же разделе: **`ErP Ready` → `Disabled`**. При `Enabled` плата обесточивает дежурные линии
   в S5, и восстановление по питанию не работает независимо от пункта 3 — типовая причина
   «выставил Power On, а не включается»;
5. `F10` → Save & Exit.

Ни AnyDesk, ни Tailscale до старта ОС не работают, IPMI/BMC на этой плате нет — **удалённо этот
шаг сделать нельзя**, только физически, один раз.
