### Фикс — одобрение ПО ЗАДАЧЕ × ПО КЛАССУ, двумя каналами

* гард дописывает в **файл-маркер** строку `Класс операции: <вид>` (`pretool_guard.py:1659`);
  текст интерактивной карточки не изменился ни на байт;
* карточка вместе с классом сохраняется в очередь (`set_needs_approval`) и **возвращается** с
  approved-задачей → `pc_orchestrator._approved_kinds` (`:800`) читает класс оттуда же
  (`pretool_guard.kinds_from_card`, 3 слоя: строка класса → `op=` от модели → фраза карточки).
  Локального состояния нет — одобрение переживает рестарт демона;
* демон штампует ребёнку `PRETOOL_APPROVED_KINDS=<виды>` + `PRETOOL_APPROVED_TASK=<id>` и
  добавляет абзац `APPROVED_CLAUSE` **после** преамбулы (последнее слово теперь за одобрением);
* гард отвечает третьим решением `approved` (`pretool_guard.py:1445`) — не карточка, но и не
  тишина: строка в логе есть;
* преамбула требует от модели класс: `NEEDS_APPROVAL: op=<класс> | <карточка>`.

**Границы (что послабление НЕ открывает):** другой класс — карточка как была; маркер разбирается
всё-или-ничего (постороннее слово → одобрения нет вовсе); сбой разбора самого гарда идёт мимо
`decide_for_role` (except-ветка `main`) → карточка всегда; вне ре-рана одобренной задачи маркера
не существует; `op=other` = «класс не назван» → прежнее поведение.

## ДЕФЕКТ 2 — карточка на проверке НАЛИЧИЯ файла

### Почему `Test-Path .env` краснел

`_decide_bash` искал секрет одним подстрочным признаком:

```python
_RE_ENV = re.compile(r"(?i)(\.env(\b|['\"\s]|$)|\.session\b)")   # pretool_guard.py:214
...
if _RE_ENV.search(scan):
    return ("ask", "env", "")                                     # было: любое УПОМИНАНИЕ пути
```

Признак не различал «читаю содержимое» и «проверяю, есть ли файл», а вид `env` стоит в
`_HARD_CARD` — правило «нет объекта → журнал» его не гасит. Поэтому карточку рождала команда,
в которой дословно написано «not reading contents». В той же команде вторым источником был
`Write-Output "=== .env exists ==="` — имя секрета в **подписи к выводу**, то есть в данных.

### Развод по ДЕЙСТВИЮ

| Действие | Было | Стало |
|---|---|---|
| `Test-Path .env`, `Get-Item`, `ls -la`, `dir`, `stat`, `test -f`, `[ -f … ]` | карточка | тихо (`defer`, вид `env_probe` в логе) |
| `os.path.exists/isfile/isdir/getsize`, `os.stat`, `Path(...).exists()` | карточка | тихо |
| имя секрета в тексте `echo`/`Write-Output`/`printf` | карточка | тихо |
| `cat`, `type`, `head`, `tail`, `Get-Content`, `gc`, `grep`, `findstr`, `Select-String` | карточка | **карточка (hard-блок)** |
| `open().read()`, `read_text()`, `load_dotenv`, `os.environ`, `subprocess`, `exec` | карточка | **карточка** |
| `Get-Item .env \| Get-Content`, `ls .env \| xargs cat` | карточка | **карточка** (труба из пробы = красное) |
| `ls > .env`, `echo TOKEN=1 >> .env` | карточка | **карточка** (перенаправление в сегменте пробы) |
| `$p = '.env'; Get-Content $p` | карточка | **карточка** (путь через переменную) |
| `Test-Path .env; python -c "os.rename('.env','x')"` | карточка | **карточка** (мутация файла) |
| `Read`/`Edit` инструментом по `.env` | карточка | **карточка** (`read_secret`/`edit_secret`) |
| **`Select-String -Path .env -Pattern TOKEN`** | **тихо (дыра!)** | **карточка** |

Последняя строка — **дыра, найденная по ходу и закрытая**: значение `-Path` считалось поисковым
шаблоном и вырезалось из скан-текста вместе с путём к секрету, поэтому ЧТЕНИЕ `.env`
PowerShell-формой проезжало зелёным. Проверено на HEAD до правки: `('defer', '', '')`.

Признак пробы **не обрывает разбор**: `Test-Path .env; rm -rf a b c` по-прежнему даёт карточку
`delete`, а тело скрипта судится отдельно от текста команды (`Test-Path .env; python evil.py`,
где `.env` читает `evil.py`, остаётся красным).

## ОСТАТКИ (с точками касания) — решение владельца

1. **Зеркало временных зон на python-полосе.** Шелловое удаление во временных зонах карточки не
   стоит (`_delete_targets_all_temp`), а `os.remove` того же файла из python-кода — стоит: цель
   внутри кода не разрешается без анализа потока данных, и «не смогли доказать зону → красное»
   выбрано сознательно. Точки касания: `pretool_guard._stays_red` (ветка `py_write`),
   `_RED_PY_TOKENS`, `_is_temp_zone`. Цена: ~1 карточка в сутки.
2. **Тело heredoc сообщения коммита.** `_strip_git_msg` вырезает payload `-m/--message`, но
   `git commit -F - <<'EOF' … EOF` подаёт текст через stdin, и слова из сообщения попадают в
   скан-текст (а `_split_segments` ещё и режет тело по `;`). Точки касания:
   `pretool_guard._strip_git_msg`, `_split_segments`, `_scan_text`. Правка требует heredoc-aware
   сегментации — это ядро разбора, отдельным заходом.
3. **Класс-фикс на ВТОРУЮ полосу (CLAUDE.md п.9).** На VPS (`orchestrator_daemon.py:3090`
   `_convert_other_approved`) одобрение в гард НЕ прокидывается принципиально — петля рвётся
   терминальной ручной картой (слои 1–2, `:858`). Тот же per-task маркер там не заведён. Точки
   касания: `orchestrator_daemon._convert_other_approved` / `process_approved`,
   `pretool_guard.py` полосы сервера. Требует решения владельца — репозиторий чужой (боевой
   сервер), правка не в этом заходе.
4. **`op=other` сжигает «да».** Если модель не назвала класс, привязать одобрение не к чему —
   ре-ран снова упрётся. Диагноз теперь честный: `✋ … [класс операции в карточке не назван
   (op=other)]`. Лечится только качеством формулировки в преамбуле; наблюдать по логу.
