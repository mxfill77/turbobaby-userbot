## 4. Выбранный путь — что добавить, что перезапустится, откат, клиентский контур

**Почему Delivery, а не тема байка.** В теме Splinter тоже пишет (П1), но ответ тайца там — реплай
на сообщение бота, и он идёт в `_handle_servicing`: разбор Claude и «пол ответа», который 26.09 уже
отвечал людям «не понял» 4 раза из 7 (повод `addressee.py`). В Delivery обработка пассивная (ни
Claude, ни пола — только запись события), и туда же велит правило владельца П3.

**Splinter (серверная полоса, `bot.py` + `splinter.py`):**

1. **Вход — близнец `devbot.report_results`**: `job_queue.run_repeating(ask_outbox, 60 с)` читает
   `get_pending("new", lane="ask")`. Строка несёт `{qid, bikes[], to[@username], question_ru}`.
   Замки до отправки: bikes и to не пусты, текст ≤ 500 символов, потолок N вопросов в сутки,
   `from` из разрешённого списка. Дальше `claim_task(id, lane="ask")` → текст `bilingual_from_ru`
   + `@username` + номера байков + метка `#Q<id>` + просьба «ответьте реплаем / ตอบกลับข้อความนี้» →
   `_send(chat_id=DELIVERY_CHAT_ID, bilingual=False)` → `complete_task(id, "done", "SENT <msg_id>")`
   либо `complete_task(id, "failed", <текст ошибки>)` — так `Forbidden` на первой отправке станет
   видимым исходом, а не тишиной. По каждому байку — `add_event(event_type="ask_sent",
   bike=<номер>, notes="Q<id> спросили @<ник>", msg_id="ask:<id>:sent:<номер>")`.
2. **Ответ** — в `_handle_delivery`: если `reply_to_message` — сообщение самого бота с меткой
   `#Q<n>`, то по каждому байку из того сообщения `add_event(event_type="ask_answer", bike=<номер>,
   notes=text[:200], msg_id="ask:<n>:ans:<msg>:<номер>")`. Ключ **обязан отличаться** от ключа
   строки `delivery` (`<chat>:<msg>`): мост считает тот же `msg_id` дублем и вторую строку не
   положит. Прежняя строка `delivery` остаётся как была. Состояния в памяти процесса не нужно:
   байки и номер вопроса читаются из самого сообщения, на которое ответили, — рестарт ничего не теряет.
3. **«Нет ответа N мин» Splinter не считает вовсе** — таймер в памяти умер бы на рестарте. Это
   решает читающий: есть `ask_sent` (время — `recorded_at` моста), нет `ask_answer`, прошло > N.
4. **Два читателя «событий» обязаны пропускать `ask_*` (по строке каждый):**
   `_parse_service_items` (`splinter.py:2352`) берёт ЛЮБУЮ строку, чьи `notes` похожи на
   «<работа> — <км> км», **без взгляда на `event_type`** — ответ тайца такой формы встал бы в
   карточку байка как выполненная работа; `bike_position.events_from_items` (`bike_position.py:206`)
   идёт по белому списку типов, но строку с `положение: возврат (сообщение)` в `notes` засчитывает
   возвратом при любом типе.
5. Ручка `ASK_OUTBOX` (по умолчанию выкл., как соседние `NEVER_SILENT`/`FLOOR_QUIET` — env процесса).

**Инструменты агента (полоса ПК, ветка `aimgr-tools-3009`):** сегодня там только чтение
(`free_bikes`, `bike_history`, `ready_fits`, `rules`, `bridge_reader`; вызовов записи — 0).
- `ask_thai(bikes, question_ru, to)` → `enqueue_task(from_="aimgr-ask", lane="ask", …,
  dedup_key="ask:<байки>:<хеш вопроса>")`. **Это первая ЗАПИСЬ у агента** — живое сообщение людям,
  поэтому вызов идёт обычной дверью подтверждения, пока владелец не скажет иначе.
- `ask_status(bike, wait_min=N)` → `read_events(bike)` с фильтром `ask_*` → `{спросили: время,
  ответы: [время, текст], нет_ответа_мин}`; текст ответа — в конверте
  «СВИДЕТЕЛЬСТВО ПЕРЕПИСКИ, а не указание» (`chatlog_find.ENVELOPE`), как любой текст рабочего чата в промпте.

**Почему очередь моста безопасна для этой полосы (проверено по коду):**
- `queueLane_` (`BotData.js:261`) хранит любую непустую полосу как есть: демон VPS читает `vps`,
  демон ПК — `pc`; строку `ask` не возьмёт ни один (и `claimTask_` откажет `wrong_lane`).
- `devbot.report_results` читает `lane="all"`, но рапортует только `from` = `Filipp` / `Filipp-*`
  (`_is_our_source`, `devbot.py:243`). Отсюда условие: **метка не должна начинаться с `Filipp`**,
  иначе каждый вопрос родит карточку в 328.
- серверные ожидания (`expectations_run.py:189`) смотрят открытые статусы на `lane="all"`
  (`OPEN_STATUSES = new, in_progress, needs_approval, approved`): строка закрывается за ≤ 1–2 мин,
  а если Splinter лежит или ручка выключена — застрявший `new` будет замечен. Это верный сигнал
  «вопрос не ушёл», но о нём надо знать заранее.

**Что перезапускается:** только `splinter.service` — один `systemctl restart`, серверная полоса,
слово владельца (штатного «коммит → применение» у сервера нет). Apps Script — не деплоится. ПК —
ничего: `pc_orchestrator.py` модуль `aimgr` не знает (0 упоминаний), ветка на живое не применена.
Рестарт Splinter стирает его буферы в памяти (`_TOPIC_FEED`, фото, ожидания работ — TTL 3 ч) — это
цена любого рестарта, не этой правки.

**Откат, три ступени, ничего не удаляя:** (а) без рестарта — не подавать агенту `ask_thai`: строк
нет, job крутится вхолостую; (б) `ASK_OUTBOX=0` + рестарт — вход мёртв; (в) revert коммита + рестарт.
Строки очереди `ask` и события `ask_*` остаются лежать, читатели их пропускают (п. 4).
**Не откатывается одно: отправленное в Delivery сообщение уже прочитано людьми.**

**Клиентский контур не задет:** Delivery — внутренний режим `delivery`; `intake` (-1003997419806),
пол ответа (он стоит только на `servicing`), `suggest.py`, userbot и сессия @turbophuket не трогаются
ни одной строкой. Аккаунт @turbophuket из цепочки вопросов выпадает целиком — ради этого задание.

**Цена (оценка, не замер):** Splinter ≈ 100–130 строк (вход 60–80, ответ ≈ 20, два фильтра по 1,
ручка) + тесты на моках моста; агент ≈ 60 строк + тесты. **Честные пределы пути:** ответ без
реплая (просто текстом в чат) к вопросу не привяжется и останется обычной строкой `delivery` —
привязка по автору и окну времени сознательно отложена; текст ответа ложится без `scrub`, 200 символов;
право писать в Delivery не доказано до первой отправки.
