# Чтение очереди ПК не переживало отказ второго плеча моста (07.08.2026)

**Итог одной строкой.** Мост ИСПРАВЕН, токен и деплой ни при чём. Второе плечо Apps Script
(`echo`) отказывает примерно в четверти чтений, а у читателя очереди — единственного из трёх
клиентов моста — не было повтора запроса целиком. Один отскок ослеплял виток демона.
Повтор идемпотентного GET перенесён в САМ транспорт (`bridge_http`), где им пользуются все трое.

Адреса здесь маскированы сознательно (правило `_leg_error`): полный `/exec` несёт id деплоя.

---

## 1. Что ИМЕННО отвечает мост на чтение очереди

Снято живой пробой 07.08 ~06:40–07:10 (`get_pending`, `lane=pc`, только чтение, ни одной записи).

### Первое плечо — всегда одинаково

```
GET  https://script.google.com/macros/s/<id деплоя>/exec?action=get_pending&token=…&status=new&lane=pc
→ 302
   Content-Type:  application/binary
   Server:        ESF
   Cache-Control: no-cache, no-store, max-age=0, must-revalidate
   Location:      https://script.googleusercontent.com/macros/echo?user_content_key=…[len≈375-386]&lib=…[len33]
   тело:          пустое (0 симв.)
```

### Второе плечо — три разных ответа

**(а) Норма (30 из 40 проб).**

```
GET  <echo, ключ расписки>
→ 200
   Content-Type: application/json; charset=utf-8
   Server:       ESF
   тело (123 симв.):
   {"action":"get_pending","ok":true,"items":[],"statuses":["new"],"lane":"pc","_status":200}
```

**(б) ОТСКОК — 7 из 40 (17,5%). Это то, что видит демон.**

```
GET  <echo, ключ расписки>
→ 302
   Content-Type: application/binary
   Server:       ESF
   Location:     https://script.google.com/macros/s/<id деплоя>/exec?action=get_pending&token=…&status=in_progress&lane=pc
   тело:         пустое
```

**(в) 404 — 3 из 40 (7,5%).** Второе плечо отдаёт HTML-страницу Google Docs (в тайской локали),
а не JSON. Одноразовый ключ протух.

**Итог замера: 30 OK / 7 отскоков / 3 ответа 404 = 25% одиночных чтений падало.** Отказы шли
**пачками** (#5–#7, #35–#38 подряд), а не поодиночке.

### Важная поправка к тексту отказа в логе

Демон печатает: «туда придёт голый GET **без тела и без токена**». Для ЧТЕНИЯ это неверно:
`Location` отскока несёт **полный исходный query, токен в нём цел** (видно выше). Формулировка
верна для ЗАПИСИ — у POST query нет и быть не может. Отсюда и весь класс: запрет писался по
инциденту записи и был применён к обоим методам.

## 2. То же плечо, что `ab5106d`? — ДА, то же. Почему запись пережила, а чтение нет

Плечо одно (`echo`), ветка одна (`_BOUNCE_TEXT` в `bridge_http._fetch_receipt`), правка одна.
Разница — **не в мосте, а в том, кто и чем страховался**:

| клиент | повтор запроса ЦЕЛИКОМ | спул | итог при отскоке |
|---|---|---|---|
| журнальный писатель (`cowork_log_append`) | `with_retry`, 2 попытки | **есть** | строка не теряется |
| писатель мозга (`brain_writer`) | `_retry_read`, 3 попытки | нет, но есть обратное чтение | чтение вытягивается |
| **читатель очереди (`pc_orchestrator.Bridge._call`)** | **НЕТ ВООБЩЕ** | **невозможен** | **виток слеп** |

`ab5106d` дал всем трём durable-**транспорт** (ручной обход редиректа) — и это сработало: POST
перестал превращаться в голый GET. Но лекарство от МЁРТВОГО КЛЮЧА («переспросить целиком»)
легло тогда не в транспорт, а в личные обёртки двух писателей. Лекарство даже названо дословно
в `cowork_log_append.transient`: «лечится не повтором мёртвого ключа, а НОВЫМ запросом целиком
(форма VPS `retry_full=True` для read-only GET)» — но у третьего клиента обёртки нет, и он этой
фразы не получил.

Почему повтор второго плеча не помогает: `user_content_key` **одноразовый и выдаётся первым
плечом**. Переспрашивать тот же адрес echo бессмысленно — ключ мёртв навсегда. Новый ключ
рождается только вместе с новым 302, то есть с новым запросом целиком.

## 3. Простой числом и цена

* **Окно:** 02:46 → 06:18 07.08 = **3 ч 32 мин**.
* **Отказов чтения в `pc_orchestrator.log` за окно: 43** — 28 `get_pending(in_progress)` +
  15 `get_pending(new)`, все `BridgeTransportError` с текстом про отскок.
* **Задач НЕ взято: 0.** Перепись очереди ПК-полосы на момент разбора: `new` 0, `in_progress` 0,
  `needs_approval` 0, `approved` 0. Демон (PID 13880) жив и опрашивал мост всё окно.
  Полоса была пуста — слепота обошлась без потерь задач, но любая поставленная задача
  задерживалась бы на случайное число витков.

Честная поправка к постановке: чтение падало **не непрерывно, а примерно в четверти витков**.
«Мост лежит» — неверный диагноз; лежал клиентский путь чтения при живом мосте.

## 4. Что исправлено (клиент, не мост)

`bridge_http.py`:

1. **`exchange` переспрашивает идемпотентный GET ЦЕЛИКОМ** — `READ_TRIES=3`, пауза
   `READ_PAUSE=1.2` с удвоением. Повтор включается **только если первое плечо уже ответило**
   (флаг `answered` из нового `_walk`): «связи нет» и отказ моста по существу доходят до
   вызывающего немедленно, чтобы `error_kind` не назвал их с опозданием на три паузы.
2. **Мутация не переспрашивается никогда** — для не-GET число попыток жёстко `1`, это не ручка.
   Инвариант `ab5106d` («POST уходит ровно один раз») закреплён отдельным тестом на всех трёх
   видах отказа плеча.
3. **Отскок на чтении больше не жжёт попытки по мёртвому ключу** — `_fetch_receipt` отдаёт отказ
   сразу (экономия ~1,8 с пауз на попытку). Для POST поведение прежнее: внешнего повтора у него
   нет и не будет, так что переспросить всё же стоит.
4. `_read_retryable` — что считается «стоит переспросить»: `BridgeReceiptLost` никогда (проверка
   первой, он наследник `BridgeTransportError`); `HTTPError` — только временные коды второго
   плеча; сетевые типы — да.

`pc_orchestrator.py` **не тронут**: починка живёт в транспорте, поэтому её получают все три
клиента, а не один.

### Фикстура: найдена и исправлена собственная ложь

Первая редакция считала отскоки **глобальным счётчиком**, и старый код её «проходил» —
повтор по тому же адресу echo «вылечивал» мёртвый ключ, чего вживую не бывает. Счёт переведён
**на ключи**: мёртвый ключ мёртв навсегда, сколько ни переспрашивай. Только после этого тест
стал красным на старом коде, то есть начал описывать настоящий дефект.
(Правило-класс «мок обязан копировать живой формат».)

## Остаток (не делалось здесь)

* **Текст отказа в логе врёт про чтение** — «без тела и без токена» верно только для записи
  (§1). Правка текста `_BOUNCE_TEXT` затрагивает голдены — отдельной задачей.
* **Первое плечо не повторяется** — 1 таймаут из 40 живых чтений проходит насквозь. Лечится
  внешним рубежом у вызывающего; у читателя очереди его по-прежнему нет.
* **Точка касания VPS.** На своей полосе `bridge_client._exchange` идёт по ЛЮБОМУ `Location`
  и отпечаток `doGet` разбирает как обычный `unauthorized`. Отскок там не опознаётся вовсе —
  класс открыт, полоса не наша (правило «зеркало обязано сверить посылку»: посылку VPS здесь
  не мерили).
