## 2. Разговорный мозг в теме обслуживания

**Где зовётся.** Только на ветке «к боту обращаются»: `bot.py:888` `_owner_addresses_bot` →
`manager_reply(... bilingual=True, force_bike=<байк из названия темы>, force_mileage=<последний пробег с фото>)`
(`bot.py:975`). Фото с подписью — `bot.py:1389`. До мозга сообщение проходит шесть перехватов
(`bot.py:839–878`, по порядку): `expire_stale_mileage_question` → `handle_service_result` (ТО фаза 2)
→ `handle_correction_confirm` → `handle_mileage_confirm` (пробег / понижение / партия) →
`handle_oil_backdated_service` → `handle_mileage_correction` → `handle_post_close_ack`. Первый
взявший сообщение — последний, кто его видит.

**Кто вообще доходит до мозга.** `_addresses_bot` (`bot.py:446–473`): автор ∈ владелец ∪ Пым И
(тег бота ИЛИ реплай на бота ИЛИ открытое окно `_AWAITING_REPLY` 10 мин). Механик до мозга не
доходит никогда; его сообщения идут в `splinter.handle` (учёт по шаблонам). За 14 суток строк
«→ мозг» из тем обслуживания — 6.

**Какой контекст получает** (`bot.py:905–968` + `manager_reply` `bot.py:536–567`):

| часть | откуда | предел |
|---|---|---|
| история | `memory.get_context_for_claude(chat, 12, topic)` → таблица `conversations` | 12 строк И не старше 48 ч; только диалог «владелец/Пым ↔ мозг» |
| байк | `bike_from_topic` (название темы, `memory.db.topic_bike`) | — |
| последний пробег | `last_mileage_in_topic` из `_RECENT_PHOTOS` | память процесса, 3 ч |

**Какие инструменты пишут** (`claude_client.py`, список `BRIDGE_TOOLS` :119–286): `set_service`,

**Чья проверка стоит перед записью.**
- `set_service` в теме обслуживания **заблокирован кодом** (E2b, `claude_client.py:485–513`): при
  заданном `_force_bike` запись не идёт, работа ставится в `pending_service_confirm`, а `bot.py`

  Записывает только кнопка «да» доверенного (`ТО фаза2 запись по «да»`). Байк модели подменяется
  байком темы.
- пробег пишет не мозг, а перехваты: `_odo_confirmed` (`splinter.py:3471`) — единая точка для
  текста, кнопки `svc:mok` и `svc:sodo`; перед ней: «да» только от доверенного (`_act_trusted`,
  `splinter.py:4893`), мягкий гейт убывания (Пым/владелец, :4930–4966), сторож B, верхняя граница
  (`odo_ceiling`), замок повторов подсказок (`hint_dedup`).
- `flag_important` / `close_important` охраняет только промпт («спроси подтверждение»), не код.

Вывод для п.5: **гейты записи уже кодом и уже вне мозга** — это главное, что делает агента
безопасным. Дыра не в записи, а во входе: мозг решает почти вслепую и не на каждом сообщении.

## 3. История тем: что есть у Splinter и что лежит на ПК

## 5. Предложение: агентный контур тем обслуживания (одна страница)

**Цель для бизнеса.** В теме обслуживания Splinter на каждое сообщение отвечает как менеджер,
который помнит тему: что прислали, что он сам спросил, что ещё открыто, кто ответил и на что.
Записи в таблицы при этом остаются под теми же замками, что сегодня.

**Устройство — четыре части; гейты записи не трогаем.**

1. **Память темы на сервере** (`topic_feed`, новая таблица в `memory.db` рядом с `conversations`).
   Строка на событие: `chat, topic, mid, ts, who` (роль: механик / Пым / владелец / бот), `kind`
   (текст / фото / кнопка / вопрос бота / запись), `reply_to`, краткое `text`, для фото — разбор
   зрения (пробег, уверенность), для вопроса бота — `ask_id`. Пишут: вход `bot.py` (каждое
   сообщение группы обслуживания, ДО перехватов), `_send`/`_hint_send` (вопросы бота с `mid`),
   `_odo_confirmed` и запись ТО (что легло). Плюс **открытые ожидания на диске**: таблица
   `open_ask` (`ask_id, topic, kind, ждём_что, от_кого, mid_вопроса, ts, срок, статус`). Ей
   заменяются семь словарей-вопросов из п.1 (`_PENDING_MILEAGE`, `_SOFT_ODO_PENDING`,
   `_ODO_LOWER_PENDING`, `_BATCH_ODO_PENDING`, `_PENDING_CORRECTION`, `_AWAITING_REPLY`,
   `_ACT_GATE_PENDING`). Срок становится полем, перезапуск ничего не стирает; ветка
   `splinter-odo-reply-0110` (a7f81c3) — первый шаг этой части для одного вида вопроса.
2. **Сборка контекста перед решением** (одна функция `topic_context(chat, topic)`): байк темы;
   последние ~30 событий ленты за 7 суток; открытые `open_ask`; ТО-заявка из таблицы; последний
   подтверждённый пробег и интервалы ТО; на что сообщение — реплай. Объём ~2–4 тыс. токенов.
3. **Решатель с коротким набором действий.** На каждое входящее в теме (не только от
   владельца/Пыма) модель возвращает JSON ровно одного действия:
   `записать{что, км, источник=mid}` · `спросить{один вопрос, ждём_что, от_кого}` ·
   `ответить{текст}` · `позвать{Пым|владелец, зачем}` · `ничего{почему}`.
   Решатель **ничего не пишет сам**: `записать` идёт в существующие двери (`_odo_confirmed`,
   ТО-заявка → кнопка Пыма), и там стоят прежние гейты. Шесть перехватов `bot.py:839–878`
   на первом этапе остаются ПЕРЕД решателем как предохранитель и снимаются по одному после
   экзамена.
4. **Правила кодом** (модель о них не решает):
   - кто подтверждает: «да» и числа пробега — только `_act_trusted` (владелец/Пым), как сейчас;
     механик может назвать число, но запись ждёт кнопку Пыма;
   - диапазоны: пробег не ниже последнего записанного (сторож B, мягкий гейт), не выше
     `odo_ceiling`; прирост вне нормы → `позвать`, а не `записать`;
   - источник и время: у каждой записи `mid` сообщения-основания и `ts`; без `mid` — отказ;
   - один вопрос на тему: `спросить`, когда по теме уже открыт `open_ask` того же вида, —
     отказ кодом (закрывает «переспросы подряд» и logic_error «повторяет свой же вопрос»);
   - откат: каждая запись — акт `undo_last` с кнопкой отмены (механизм уже есть, `_SVC_UNDO`),
     плюс выключатель решателя флагом без кода (поведение возвращается к сегодняшнему).

**Экзамен до живого.** Источник — ПК-архив `chatlog/servicing` (354 сообщения, 21 тема,
18.09–30.09, фото файлами, реплаи и свои вопросы бота есть, п.3) плюс журнал `splinter.log`
за то же окно как «что сделал бот». Прогон офлайн: для каждого сообщения собрать контекст
только из предыдущих, получить действие, сверить с разметкой владельца/Штаба. Пороги допуска:
0 записей мимо гейта; 0 вопросов при открытом таком же; доля «правильное действие» ≥ 90 %
на темах с вопросами о пробеге (их в окне 24, из них 4 протухших — обязательные случаи).
**Обязательный случай — NMAX 155 BLACK 8952, 30.09–01.10:** фото 30.09 11:19–11:20 UTC (9 шт.,
зрение 38872, conf=high) → вопрос L 11:23 → перезапуск 18:23 → реплай Пыма 01.10 06:08 с
числом 38972. Ожидаемое действие: `записать{odo=38972, основание=mid ответа, вопрос=ask_id
30.09}` через дверь подтверждения пробега, **без переспроса**. Сегодня было: мозг, переспрос
(АУДИТ logic_error 06:08:20), блок E2b, карточка, запись в 06:10:57 — три шага вместо одного.
Пока архив снимается раз в 12 ч и только на ПК, экзамен гоняется на ПК, а в прод решатель идёт
сначала **в тень**: решает и пишет решение в журнал, а действует прежний код. Сверка тени за
неделю — затем включение по темам.

**Чего это стоит и что нельзя.** Нельзя: дать модели писать в таблицы напрямую (E2b это уже
запрещает и должен запрещать); полагаться на ПК-архив как на живую память (до 12 ч задержки,
сервер его не видит). Цена: вызов модели на каждое сообщение темы (~350 сообщений за 13 суток,
≈ 27 в сутки, по ПК-архиву) против сегодняшних 6 вызовов мозга за 14 суток — нагрузка мала.
Порядок работ: (1) `topic_feed` + `open_ask` на диске (без смены поведения) → (2) сборка
контекста + решатель в тени → (3) экзамен на архиве и тени → (4) включение по слову владельца,
с откатом флагом.

  только `/root/splinter_agent_0110_tmp/log14.txt`; на ПК — только `tmp/splinter_agent_0110/`
