## 1. Постановка: поправка владельца принята

Исходная формулировка («признак не должен опираться на лог») уточнена владельцем: предикат
`channel_alive` **уже составной** — мёртв только когда лог протух **И** соединений ноль. Дело не в
плече лога, а в **ПОРОГЕ для ветки канала**. Класс лечили 24.07, но только серверу:

```python
SERVER_LIVENESS_MAX_AGE = int(os.getenv("RC_SERVER_LIVENESS_MAX_LOG_AGE", "3600") or "3600")
SERVER_SPEC = {..., "max_age": SERVER_LIVENESS_MAX_AGE, "auth_watch": True}
NAMED_SPEC  = {"label": "named-channel", ..., "log": NAMED_LOG}      # ← своего порога НЕТ
```

Ветка канала молча наследовала общий `LIVENESS_MAX_AGE=1200`. Комментарий 24.07 даже
проговаривал это как осознанное решение — и был **неверен**: «Именованный канал остаётся на общем
LIVENESS_MAX_AGE (его соединения тают ~за 15 мин — 1200с ему достаточно)».

## 2. Признак живости: ЧТО у канала есть, а чего нет (замер, а не рассуждение)

Живой канал pid 13464 (старт 20:41:34.623), замер 20:45:47.960:

| Величина | Значение |
|---|---|
| последняя запись в `--debug-file` | **20:41:35.814** (+1,19 с от старта) |
| строк в файле | **70**, все метки внутри — `13:41:34.891Z … 13:41:35.795Z` (**904 мс**) |
| возраст лога | **252,1 с** |
| возраст процесса | **253,3 с** |
| разница | **постоянная 1,2 с** |
| ESTABLISHED соединений | **5** (у сервера pid 4872 в тот же миг — **1**) |
| CPU, потоки, хендлы | 1,47 с · 19 · 266 |

**Вывод фактом:** у ветки канала «свежесть лога» — не heartbeat, а **одноразовая отметка старта**.
Поэтому `log_age(t) ≡ возраст процесса − 1,2 с`, и порог 1200 с пересекается **всегда**, у любого
канала, включая абсолютно здоровый. Второе плечо (`established > 0`) в простое тоже гаснет — это
доказано не спот-замером, а **самими гашениями**: каждое требует 0 соединений на 3 проверках
подряд, и таких за окно 358.

Побочно опровергнут тезис артефакта-корня «0 соединений у канала — норма»: в рабочей фазе канал
держит **5** соединений против 1 у сервера. Ноль появляется только в простое.

## 3. Порог числами САМОЙ ветки (не копия серверного)

Так как `log_age ≡ возраст процесса`, возраст лога в момент гашения **равен длительности жизни из
журнала** — реплей точен без реконструкции mtime. Замер по боевому `rc_remote_control.log`
(`diag_rc_liveness_replay.py`, окно 24.07 16:50 – 30.07 20:41, **6,16 суток**):

```
named-channel  жизней  359  из них ЗОМБИ  358  самовыход   1
rc-server      жизней    8  из них ЗОМБИ    6  самовыход   2
последние сутки: named-channel ЗОМБИ 29,  rc-server ЗОМБИ 1
длительность жизней канала: min=1200  медиана=1290  max=33245
топ повторов: 1290с×333, 1230с×12, 1260с×5
```

- **1290 с = 1200 + 3×30** — смерть наступала **детерминированно**: 333 жизни из 359 длились ровно
  столько. Это не «иногда ложное срабатывание», это расписание.
- Самый долгий молчок **ЖИВОГО** канала: **33 245 с = 9,23 ч** (30.07 03:28:27→12:42:32) — жизнь
  пережила сон ПК и была срублена уже на пробуждении. Вторая: **12 410 с = 3,45 ч**
  (26.07 09:49:15→13:16:05). Обе без exit-строки, т.е. процесс всё это время был жив.

**Порог 43200 с (12 ч)** = запас ~30 % над 33 245 с; перекрывает ночной простой и типовой сон ПК
(класс #171). Серверный 3600 с сюда не годится: он выведен из разрыва **вех поллинга** (~10 мин),
которых у канала нет вообще. Пороги обязаны отличаться — на это есть тест
`test_named_threshold_is_not_a_copy_of_server`.

## 4. Реплей: было 29 → стало 0

```
страйки=3, интервал=30с ⇒ гашение при возрасте лога >= порог + 90с
БЫЛО  (общий 1200с)    порог=  1200с  рубеж=  1290с  гашений за окно:  336/359   за сутки: 28
СТАЛО (ветка канала)   порог= 43200с  рубеж= 43290с  гашений за окно:    0/359   за сутки: 0
```

**Честная оговорка о 336 против 358.** Идеализированное правило (`age ≥ порог + страйки×интервал`)
объясняет 336 фактических гашений из 358; остальные 22 сработали на 1230–1263 с, то есть на
27–60 с РАНЬШЕ рубежа — дрожание 30-секундного цикла (сетевой опрос netstat крадёт доли тика).
Для вывода это ничего не меняет: максимум наблюдённой жизни 33 245 с лежит на 10 045 с (2 ч 47 м)
**ниже** нового рубежа 43 290 с, поэтому при 43200 не срабатывает ни одна из 359.

**Откуда 29 против 27 в задании.** Проверено по журналу: за календарный день 30.07 — **29**
гашений, за скользящие 24 ч от последней строки — тоже **29**. Расхождение не в окне: артефакт-корень
писался в 19:59, последним снос 19:57:44 был 27-м; после него ветку погасили ещё дважды — в 20:19 и
20:41:18. То есть за время разбора класс успел сработать ещё два раза.

## 5. Настоящий мёртвый канал по-прежнему гасится — доказательство

Гашение по **выходу процесса** (`proc.poll() != None`) — отдельная ветка монитора, её правка не
касается: ловится за ≤30 с. Зависший-но-живой канал ловится порогом. Прогон предиката:

```
OK  труп: молчит порог+90с, соединений 0                 age= 43290 est=0 → МЁРТВ (ожидание: МЁРТВ)
OK  труп: молчит сутки, соединений 0                     age= 86400 est=0 → МЁРТВ (ожидание: МЁРТВ)
OK  труп: лога нет вообще, соединений 0                  age=  None est=0 → МЁРТВ (ожидание: МЁРТВ)
OK  здоровый: молчит 21,5 мин (старый ложняк), 0 conns   age=  1290 est=0 → ЖИВ (ожидание: ЖИВ)
OK  здоровый: молчит 9ч14м (сон ПК), 0 conns             age= 33240 est=0 → ЖИВ (ожидание: ЖИВ)
OK  здоровый: молчит сутки, НО есть соединение           age= 86400 est=1 → ЖИВ (ожидание: ЖИВ)
```

Плюс два голдена через **весь цикл монитора**: `test_really_dead_channel_still_killed_with_numbers`
(труп на 43290 с → ровно 1 kill) и `test_idle_channel_survives_full_monitor_loop` (здоровый на
1290 с → 0 kill за 6 проверок). Предикат сам не менялся:
`test_predicate_itself_unchanged` держит «соединение спасает канал при сколь угодно старом логе».

## 7. ТРЕТЬЕЙ ветки нет — и замок, чтобы не забыть снова

Проверено по всему репозиторию: `channel_alive` / `probe_alive` / `LIVENESS_MAX_AGE` вне
`rc_supervisor.py` и его тестов **не вызывает никто** (единственное совпадение —
`session_watch.py:14`, где имя предиката упомянуто в шапке как контекст; импорта `rc_supervisor`
там нет, в списке импортов только stdlib). Веток ровно две: `BRANCHES = (SERVER_SPEC, NAMED_SPEC)`.

Замок на будущее — `test_no_branch_rides_the_shared_default`: у **каждой** ветки в `BRANCHES`
порог обязан быть задан явно. Новая третья ветка без своего `max_age` уронит тест, а не унаследует
молча общие 1200 с и повторит класс в третий раз.
