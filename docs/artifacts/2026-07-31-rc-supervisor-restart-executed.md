## §3 Почему авто-рестарта не случилось (замер, а не рассуждение)

Ожидание 00:04:25 → 00:07:46, опрос каждые 10с, **200с = 3+ интервала PT1M**: супервизор не
появился ни разу. Состояние задачи после сноса:

```
State             : Ready          ← не Running: экземпляр завершён
LastTaskResult    : 4294967295 (0xFFFFFFFF = -1)   ← код от Stop-Process -Force
NumberOfMissedRuns: 0
NextRunTime       :                ← пусто
RestartCount      : 3   RestartInterval: PT1M      ← настройка НА МЕСТЕ
MultipleInstances : IgnoreNew
Triggers          : MSFT_TaskLogonTrigger          ← единственный
```

Вывод, стоящий отдельной строки: **`RestartOnFailure` на внешнее убийство не отвечает.**
Ненулевой код действия (-1) Планировщик записал в `LastTaskResult`, но перезапуск не завёл —
рестарт привязан к *сбою запуска задачи*, а не к коду выхода действия. Триггер один,
`LogonTrigger` ⇒ до следующего входа в систему задача не стартует сама **никогда**.
Это опровергает надежду «сторож поднимет сам» из карточки отката (`_ROLLBACK["kill"]`).

## §5 Что осталось владельцу: РОВНО одна команда

```powershell
Start-ScheduledTask -TaskName TurboBabyRC
```

(равнозначно `schtasks /Run /TN TurboBabyRC`). Предварительных условий нет: имя устройства
свободно, экземпляр задачи завершён (`State: Ready`), `IgnoreNew` не помешает.

## §6 Как проверить, что порог В ПАМЯТИ (сразу, без ожидания 22 минут)

Первая же строка нового супервизора в `rc_remote_control.log` обязана назвать пороги:

```
супервизор стартовал (pid=<новый>, ветки=['rc-server:порог 3600с', 'named-channel:порог 43200с'], cwd=D:\turbobaby-bot)
```

Это **отчёт процесса о собственной памяти**: список строится из `spec["max_age"]` тех самых
объектов, по которым потом судит монитор. Чтение файла с диска (`python -c "import
rc_supervisor…"`) доказательством НЕ является — константы связываются один раз на импорте,
hot-reload в CPython нет; ровно на этом разрыве класс и прожил 20 часов.

Поведенческое подтверждение — **через ~22 минуты** после старта (1290с + тик 30с): канал
обязан пережить 1290-ю секунду. Полная тишина ветки `named-channel` в логе за это окно = фикс
в силе. Если снос всё же случится — новая строка НАЗОВЁТ порог числом (`> порога 43200с`), и
это тоже отчёт о памяти.

## §7 ОСТАТОК: дыра в гарде — контроль Планировщика мимо признака (точки касания)

Найдено при сухом прогоне `decide_for_role` перед действием:

```
'schtasks /Run /TN TurboBabyRC'            -> ('ask',   'schtasks', '')   ← красное, верно
'Start-ScheduledTask -TaskName TurboBabyRC'-> ('defer', 'unknown',  '')   ← ПРОПУСК
```

Причина: `pretool_guard.py:170` ловит `\bschtasks\b`, а PowerShell-командлеты пишутся
`*-ScheduledTask` — подстроки `schtasks` в них нет. Мимо признака идут `Start-`, `Stop-`,
`Register-`, `Unregister-`, `Enable-`, `Disable-`, `Set-ScheduledTask`. На ПК, где основная
оболочка — PowerShell, это широкий обход: headless-сессия может поднять/снять/перерегистрировать
любую задачу Планировщика без «да» владельца. Я этой дырой **не воспользовался** — операция
класса `schtasks` в одобрении не стоит, и пропуск гарда одобрением не является.

Точки касания фикса: `pretool_guard.py:170` (признак), `_stays_red` ветка `schtasks`
(`:1807-1808`) — карвинг чтения должен зеркалить `_RE_SCHTASKS_QUERY`: `Get-ScheduledTask*`
зелёное (чтение), глаголы действия красные. Тесты — `test_pretool_guard.py`. Правило-класс
репозитория: судить по ДЕЙСТВИЮ, а не по подстроке (те же разводы 30.07: `sqlite3` как имя
модуля, `.env` как упоминание пути).
