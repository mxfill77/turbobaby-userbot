## 3. ЗАГРУЗКА (п.2) — `trainer_photo.download`

* Скачивает **тем же сеансом, которым бот и так работает**: `msg.download_media(file=…)` ходит
  через клиента, которому принадлежит сообщение. Второй Telethon-сессии не заводится ни одной,
  боевой `userbot.lock` не трогается.
* **Место для временного названо явно:** `tmp/trainer_photos/` в корне репозитория (константа
  `trainer_photo.PHOTO_DIR`, проверяется тестом). Имя файла — `trn_<chat_id>_<msg_id>.<ext>`.
  Ничего отсюда не удаляется: уборки за собой нет.
* Тип определяется **по сигнатуре первых байтов**, а не по имени: jpeg/png/gif/bmp/webp. Имя
  файла — это ровно то, что врёт в отрицательном тесте.
* Сорванная загрузка исключения не выпускает: она обязана дать третий исход, а не уронить турн.

## 4. РАСПОЗНАВАНИЕ (п.3) — три исхода, и они разные

`trainer_photo.describe(path)` зовёт голову ТЕМ ЖЕ `claude` CLI и по ТОЙ ЖЕ подписке, что
клиентский `suggest._cli_llm` (ANTHROPIC_API_KEY вычищается из env). Отличий ровно два, оба
вынужденные: `--allowed-tools "Read"` (без него файл не открыть) и свой таймаут 300 с — при
замеренных 88 с бюджет в 30 с давал бы гарантированное ложное «не смог».

| исход | когда | что в продукте |
|---|---|---|
| **РАСПОЗНАНО** | прочитаны непустые строки | содержимое едет в транскрипт, ответ строится по нему |
| **НЕ РАСПОЗНАНО** | байты есть, содержимого нет: не изображение · голова отказалась · голова молчит · **голова недоступна** | человеческие слова «Фото пришло, но прочитать его я не смог. Пришлите, пожалуйста, те же данные текстом.» Содержимое в этой ветке **ВСЕГДА пусто** |
| **НЕ СКАЧАЛОСЬ** | байтов нет вовсе | свои слова: «Фото не скачалось — до меня дошло только уведомление о вложении…» |

Второй и третий исход различаются по существу: там читать было ЧТО и не вышло, здесь читать
было НЕЧЕГО. Тест `test_not_downloaded_is_a_third_outcome` держит это различие явно.

**Замок против выдумки — машинный, а не обещание в промпте:** при исходе НЕ РАСПОЗНАНО поле
`text` затирается в пустое, а на не-изображении голова **не зовётся вообще** (незваная голова не
может выдумать ничего). Оба свойства проверяются тестами.

## 5. ОТРИЦАТЕЛЬНЫЕ ТЕСТЫ (п.4) — оба, без них не принимается

**№1 — непригодный файл под видом снимка.** Две формы, обе закрыты:

* *не изображение вовсе* (текст/архив с расширением `.jpg`): сигнатура не опознана → исход
  **НЕ РАСПОЗНАНО**, голова **не звана ни разу** (тест считает вызовы: `called == []`), строк 0;
* *сигнатура верная, тело битое* — проба на **ЖИВОЙ голове**:

```
[2] файл=probe_broken.jpg  байт=4100  тип=jpeg  исход=НЕ РАСПОЗНАНО  строк=0  за 71.3 с
    причина: голова сказала, что прочитать не смогла
    слова человеку: Фото пришло, но прочитать его я не смог. Пришлите, пожалуйста,
                    те же данные текстом.
```

Выдуманных строк о содержимом — **0**. Живая голова честно отказалась, и её отказ стал ИСХОДОМ,
а не содержимым снимка.

**№2 — голова недоступна.**

```
[3] файл=probe_grid.png  байт=9699  тип=png  исход=НЕ РАСПОЗНАНО  строк=0  за 0.0 с
    причина: голова недоступна: RuntimeError: claude CLI не найден
    слова человеку: Фото пришло, но прочитать его я не смог. …
```

Исход — **НЕ РАСПОЗНАНО**, а не пустой ответ: исключение наружу не выпускается, молчания нет ни
в одной ветке. Тот же результат даёт таймаут CLI (он приходит в `describe` пустой строкой).

## 6. ЖИВОЕ ДОКАЗАТЕЛЬСТВО (п.5) — НЕ СДЕЛАНО, и вот почему

**Наружу за этот заход не ушло НИ ОДНОГО сообщения.** Номера отправленного сообщения нет —
сообщения нет.

Причина названа честно, а не смягчена. Чтобы бот ответил по снимку, уже лежащему в группе,
нужны две вещи, и обе запрещены этому заходу:

1. **врезка в `userbot_listen.py`** — только там живут объект сообщения и клиент Telethon
   (`_trainer_group_message`, строки 428–433). Запрет захода: `userbot` и `moderation_bot` не
   трогать;
2. **рестарт боевого `userbot_listen.py` (PID 10892)** — Python не перечитывает модуль на лету,
   поэтому даже применённая правка не ожила бы без перезапуска. Запрет задания: процессы не
   трогать и не перезапускать без отдельного разрешения.

Обходить это второй Telethon-сессией на том же файле `turbobaby_session.session` заход отказался
СОЗНАТЕЛЬНО: второй ключ авторизации на живой сессии — риск уронить боевого слушателя, а живых
чатов задание касаться запрещает.

### Что владельцу сделать, чтобы снимок пошёл в продукт (правка НЕ применена, текст готов)

В `userbot_listen.py` — импорт `trainer_photo` рядом с `import trainer`, и в
`_trainer_group_message` вместо двух строк:

```python
    has_photo = getattr(msg, "photo", None) is not None
    body = trainer.client_body(text, has_photo=has_photo, geo_marker=gm)
```

поставить:

```python
    has_photo = getattr(msg, "photo", None) is not None
    note = None
    if has_photo:
        trainer.bump_seq()                       # чтение снимка длится ~90 с: гасим ответ,
                                                 # запланированный на подпись (дебаунс 8 с)
        got = await trainer_photo.download(msg, chat_id=chat_id)
        if got["ok"]:
            desc = await asyncio.to_thread(trainer_photo.describe, got["path"])
        else:
            desc = {"outcome": trainer_photo.NOT_DOWNLOADED, "text": "", "lines": 0}
        note = trainer_photo.transcript_body(desc)
        words = trainer_photo.human_note(desc)
        if words:
            await _trainer_send(event.client, chat_id, words)
    body = trainer.client_body(text, has_photo=has_photo, geo_marker=gm, photo_note=note)
```

и перезапустить `userbot_listen.py`.

**Зачем `bump_seq()` первой строкой — это не украшение.** Подпись и снимок приходят РАЗНЫМИ
апдейтами (доказано следом 18:10), дебаунс ответа — 8 с, а чтение снимка головой заняло 88.3 с.
Без гашения токена бот ответил бы на одну подпись за 8 с, то есть ровно тем же «пришлите фото»,
и снимок опоздал бы к собственному ответу.
