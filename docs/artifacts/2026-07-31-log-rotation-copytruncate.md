## 1. Что было снято замером, а не пересказом

Проход 1 записал в §6: «Переименовать не вышло бы: файл занят тремя процессами». Первая
половина верна, вторая — нет. Проверено:

```
before: 23302269 bytes
RENAME:    FAIL PermissionError [WinError 32] 'pricing.log' -> 'pricing.2026-07-22.log'
COPY:      OK -> pricing.2026-07-22.log (23302269 bytes)
TRUNCATE:  OK, pricing.log = 0 bytes
```

**Почему `rename` нельзя, а усечение можно.** Python открывает лог через `_wopen`/`_SH_DENYNO`:
соседям отдаётся `FILE_SHARE_READ|FILE_SHARE_WRITE`, но **не** `FILE_SHARE_DELETE`.
Переименование требует у файла права DELETE — его нет, отсюда WinError 32. Чтение и усечение
просят ровно то, что соседи разрешили, и проходят. Это не трюк, а штатный режим `copytruncate`
у `logrotate` — заведённый ровно под этот случай.

## 2. Почему это ЛЕЧИТ, а не «просто уменьшает файл»

Ключ: чужой хендлер держит свой поток в режиме `"a"`. После усечения его `shouldRollover`
меряет `seek(0,2)` → 0 < порога → **перекат больше не запрашивается**, и запись ложится.
Стенд на ШТАТНОМ `RotatingFileHandler` (именно он крутится в трёх боевых процессах — они
стартовали до починки):

```
до усечения:    PermissionError WinError 32 → handleError → Message: 'quote before truncate'
                строка ПОТЕРЯНА, бэкап .1 не создан
после усечения: size=22, 'quote AFTER truncate' в файле — строка ЛЕГЛА
```

То есть внешний copytruncate **поднимает застрявшего соседа без его рестарта**. Это и было
нужно: рестарт трёх процессов — красный класс `kill`, он не одобрен.

## 3. Что изменено в коде

| место | было | стало |
|---|---|---|
| `_copytruncate` | — | новая вторая ступень переката (copy2 + truncate(0)) |
| `_rotate` (писатели без logging: гард) | `os.replace` упал → отказ | упал → пробуем copytruncate → успех |
| `SafeRotatingFileHandler.doRollover` | отказ → громко, файл растёт вечно | отказ → copytruncate → перекат ПРОШЁЛ; громко только если сорвались ОБЕ ступени |
| файл-сигнал | только `ROTATE-FAIL` | плюс `ROTATE-NOTE` — обходной путь не прячем |

**Петля разорвана явно:** `_report_rotate_failure` ротирует сам файл-сигнал, а `_rotate` при
copytruncate зовёт `_report_rotate_note` — тот дописывает через `_signal_append`, который
**не ротирует**. Иначе `_rotate → _report_* → _rotate` замкнулись бы.

**Размен назван вслух:** между `copy2` и `truncate` есть окно в миллисекунды; строки, попавшие
в него, не попадут ни в архив, ни в новый файл. Терять миллисекунду раз в 5 МБ несопоставимо
дешевле, чем терять ВСЕ записи вечно, как было девять суток.

## 4. Чего проход 1 не мог закрыть в принципе

Разведение по владельцу лечит только тех, кого можно развести. **Один и тот же входной скрипт,
запущенный дважды, получает ту же кличку и снова спорит за канон** — хуки `dispatch_notify.py`
бегут по нескольку разом. Именем это не чинится никогда; чинится второй ступенью. Записано в
докстринг модуля, чтобы вывод «разведение = достаточно» больше не рождался.

`rename`, а такой перекат теперь ПРОХОДИТ. Красить их обратно подгонкой было бы враньём.

  `ROTATE-FAIL`. Третий тест — живой инцидент целиком на штатном хендлере (см. §2).

## 6. Ложный красный, который стоит знать

Полный прогон **в этой сессии** дал 14 красных в `test_pretool_guard`/`test_pc_orchestrator`.
Причина не в коде: сессия headless-задачи несёт в окружении `PRETOOL_APPROVED_KINDS=delete`,
`PRETOOL_ASK_MARKER`, `PRETOOL_APPROVED_TASK=77`, а эти тесты читают **живой** `os.environ` —
и видят настоящее «да» владельца на удаление. Гасится снятием переменных:

```
env -u PRETOOL_ASK_MARKER -u PRETOOL_APPROVED_KINDS -u PRETOOL_APPROVED_TASK \
    -u PRETOOL_MARKER_TOKEN  python -m unittest discover  →  2471 OK
```

**Это та же болезнь 2, что лечил `log_setup` для логов** («тесты читают боевое окружение»),
только в гарде: одобрение класса, выданное сессии, молча меняет вердикт её же тестов. Не
чинил — `pretool_guard.py`/`test_pretool_guard.py` лежали изменёнными до начала сессии, это
чужая работа. **Записано в остатки с точкой касания** (`pretool_guard.py:1879`
`APPROVED_KINDS_ENV`): признак «идёт тест» там же, где он уже есть у логов.
