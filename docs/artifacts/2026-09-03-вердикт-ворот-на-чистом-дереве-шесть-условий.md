# Вердикт ворот на ЧИСТОМ дереве: шесть условий кода — все шесть выполнены

**Исход в одной строке.** Четыре текстовых файла, державшие дерево грязным, закоммичены
(`4a7fd42`, кода в коммите **0 байт**); клиентское замыкание между прежним кандидатом `1454db0` и
новым `4a7fd42` **не изменилось ни на байт**; вердикт переснят полным набором в двух кругах —
**16/16 кейсов, 300/300 чеков, красных 0, «неизвестно» 0, 32 единицы из 32**, дерево чистое,
вершина не двигалась. По правилу КОДА ворот (`client_contour.trainer_verdict`) **выполнены ВСЕ ШЕСТЬ
условий**, и `build_verdict` собрал запись `result = "green"` — впервые с 26.08.

**Ворота при этом НЕ открыты и открыться не могли: в реестр
`pc_orchestrator.client_trainer_green.json` не записано НИЧЕГО.** Живая проба после прогона:
`trainer_verdict('4a7fd42…')` → `False, «вердикта на этот коммит нет (последний зелёный — на
74be777)»`, `release_reason` → `None`. Запись в реестр и ЕСТЬ открытие — это движение владельца, не

`run_gate.py` не зовёт `trainer_run.write_verdict` ни одной веткой, `summary.json` несёт поле
`written_to_gate: false`. Проба состояния ПОСЛЕ прогона:

```

                                              (последний зелёный — на 74be777)»)
client_contour.release_reason('4a7fd42…')  → None
client_contour.owner_approved('4a7fd42…')  → False
```

Реестр ворот не менялся ни на строку: зелёная запись по-прежнему **одна** и она на `74be777`
(26.08, ещё 12-кейсовый корпус); красных **четыре** — `6478a39` (30.07, 10/12), `55aad22` (31.07,
10/12), `91d244e` (25.08, 11/12), `298a387` (02.09, 6/12). Одобрений владельца в

Почему записать зелёное нельзя: зелёная запись в `pc_orchestrator.client_trainer_green.json` и ЕСТЬ
открытие. `release_reason` вернёт `'trainer'`, `_client_block` не удержит тик, и
`reconcile_children_tick` перезапустит детей САМ — следующим тиком реконсиляции, без карточки и без
«да». Открытие делает демон по карточке владельцу; «да» за владельца никто не говорит.

**СТРОКА ДЛЯ ВЛАДЕЛЬЦА — ОБЪЁМ ПРЫЖКА: при открытии ворот дети получат РАЗОМ 140 коммитов

`price_source.json` (2 коммита), `model_name.py` (1 коммит, файл НОВЫЙ).**

|---|---|
| коммитов разом | **140** (было 138 на прошлом замере; +2 = артефакт и этот коммит текстов) |
| путей тронуто | **216** |
| из них **клиентских** | **3** |
| неклиентских | **187** (доки, тесты, `pc_orchestrator.py`, хуки) |

База детей измерена, а не взята из прошлого артефакта: живые процессы — userbot **PID 13284** с

## 10. Что НЕ делалось

Кода не правилось ни байта: в коммит `4a7fd42` вошли 4 `.md`-файла, файлов кода среди staged **0**.
Ворота руками не открывались, реестр вердиктов и реестр одобрений не менялись, дети не
перезапускались, процессы не трогались (только чтение `Win32_Process`). Корпус кейсов не менялся —
`corpus_sha` тот же `6d5d78f0d83acdca`. Живых чатов, боевой базы и рабочих таблиц не касались:
`trainer_run.isolate_ipc()` уводит `moderation_ipc.db` в temp, логи — в temp
(`TURBOBABY_TEST_LOGS=1`). Клиентам не писали. `.env` и конфиги не читались. Ничего не удалялось,
включая **32 накопленные единицы прошлого прогона** — они остались в `units.jsonl` рядом с новыми
32. Временное — только `_scratch_gate_verdict/`, в коммит не входит.

## 11. Что осталось НЕИЗВЕСТНО

- **Вердикт стареет от коммита ЭТОГО артефакта.** Ворота судят коммит целиком, и коммит артефакта
  двигает вершину с `4a7fd42` на новый хеш. Клиентское СОДЕРЖИМОЕ при этом не меняется ни на байт
  (артефакт — файл в `docs/artifacts/`), и `closure_check.py` это докажет на любой паре, но
  ЗЕЛЁНЫЙ ВЕРДИКТ ПРИНАДЛЕЖИТ `4a7fd42`, а не наследнику. Обойти нельзя: «артефакт последним».
  Практический вывод для владельца: **одобрять или открывать надо ровно `4a7fd42`** — на вершину
  после этого коммита вердикта нет и не будет без нового прогона.
- **Дерево чисто было на момент замера, а не навсегда.** Контур ревью пишет в лоток по своему
  расписанию; между этим артефактом и решением владельца новый файл может появиться. Проверка
  «чисто» стоит одну команду и обязана повторяться перед записью вердикта, а не наследоваться.
- **Устойчивость 300/300 — это два круга, а не двадцать.** Два прогона (прошлый на `1454db0` и этот
  на `4a7fd42`) дали посимвольно одинаковую раскладку по кейсам — это 64 единицы подряд без
  единого красного чека, что сильнее каждого замера по отдельности. Но генератор недетерминирован,
  и доверительного интервала на редкий провал здесь не считалось.
- **Прыжок мерился по КЛИЕНТСКОМУ замыканию, а не по поведению.** «Три файла» — ответ на вопрос
  «что доедет до живого клиента», а не «насколько изменится ответ клиенту». Регрессия поведения
  между `6cbdd15` и `4a7fd42` этим прогоном не мерилась: тренажёр судил ТОЛЬКО кандидата.
- **Модербот на прыжке отдельно не проверялся.** `moderation_core.py`/`moderation_bot.py` в дифф
  прыжка не попали — значит менять им в этих 140 коммитах нечего, но и вердикта о них у нас нет.
