## 2. Виток демона по частям, с числами за сутки (п.3)

Состав витка — это тело `while` в `pc_orchestrator.py:13132–13200`, и «виток» здесь именно
тело цикла, а не `poll_once` (так сказано комментарием на стр. 13137). Порядок вызовов:
`poll_once` → вотчдог детей → сессия → ревизор → ступень A → ступень B → ступень D →
ступень E → **ящик Штаба** → ступень F → сводка контура → витрина → ступень G → докоммит
урока → git ff-pull → реконсиляция детей → self-update → **сон POLL_SEC=60 с**.

|---|---|---|---|---|---|
| **исполнение задания** (CLAIM→COMPLETE) | 23 | **1145.5 с** | **2703.5 с** | 31904.5 с (8.9 ч) | строки `CLAIM`/`COMPLETE` |
| ↳ из них чистая голова (`METRICS lane=pc dur_s`) | 24 | 1308.5 с | 2700.7 с | 33387.3 с | строки `METRICS` |

| **сводка контура + витрина** | 65 | **17.7 с** | 118.5 с | 1699.4 с | зазор «ступень F → витрина» |

**Что в журнал НЕ пишется и потому названо неизвестным, а не нулём:**

- длительность витков **короче 300 с** — порог `PC_LOOP_GAP_NOTE_SEC = 300`
  (`pc_orchestrator.py:9535`); распределение витка в таблице **цензурировано снизу** и медиана
  879 с относится только к длинным виткам;
- собственная цена `poll_once` (чтение очереди, claim, реапер, слепок) отдельной строкой не
  пишется ни разу — она видна только целиком, внутри длины витка;
- цена ступеней B, D, G и ревизора: строки у них есть не каждый виток, соседних пар для
  зазора набирается меньше пяти — **неизвестно**;
- цена собственно сводки контура (раз в 4 ч) внутри строки «ступень F → витрина» не отделена
  от витрины — **неизвестно порознь**, известно только вместе.

**Слой ожиданий О — не часть витка, и это ФАКТ по коду, а не «не нашли».** В теле цикла его
вызова нет; во всём `pc_orchestrator.py` имя `expectations_pc` встречается **3 раза**, и все
три — список зависимостей self-update (стр. 7451, 7455) и комментарий (стр. 13382). Слой живёт
отдельной задачей Планировщика `TurboBabyExpectPC` раз в 10 минут (своё состояние —
`tmp/expect_pc/state.json`). Вклад в длину витка — **ноль секунд**.

**Главное число части:** исполнение задания даёт **31904 с из 36434 с** суммарной длины длинных
витков, то есть **87.6 %**. Виток полосы ПК — это почти целиком синхронный заход головы.

## 3. Чем ограничена частота ящика (п.4) — ответ по коду, числом

**Опрашивается ли ровно раз за виток — ДА.** `maybe_shtab_box()` зовётся один раз,
`pc_orchestrator.py:13179`; второго вызова в файле нет.

**Стои́т ли собственная отсрочка — ДА, и она названа.** `SHTAB_BOX_MIN_SEC = 600 с`
(`pc_orchestrator.py:11639`, ручка env с тем же именем). Проверка в `maybe_shtab_box`
(стр. 11763–11769): `if (now - prev) < SHTAB_BOX_MIN_SEC: return None`. Сверх неё —
`SHTAB_BOX_LIMIT = 1` (стр. 11647): **не больше ОДНОГО задания за оборот**, сколько бы ни
ждало.

**Кто из двух связывает — зависит от того, занята полоса или нет, и обе ветки измерены:**

- **полоса пуста** → связывает пол 600 с. Живой замер ночного окна 09-11 05:29–07:55 местного:
  взгляды в 05:29:50 · 05:40:55 · 05:52:18 · 06:03:29 · 06:14:38 · 06:26:07 · 06:37:34 ·
  06:48:44 · 07:00:06 · 07:12:15 — шаг **11.1–11.4 мин** = 600 с пола + 20–70 с самого взгляда
  + доли `POLL_SEC`. Медиана по всем 85 промежуткам суток — **11.8 мин**;
- **полоса занята** → связывает ДЛИНА ВИТКА, потому что заход головы исполняется СИНХРОННО
  внутри `poll_once`, и пока он идёт, до `maybe_shtab_box` тело цикла не доходит вовсе.
  Улика: ряд #7 взят в работу 09:28:08Z, сдан 09:54:24Z — между взглядами ящика 09:25:14Z и
  09:57:18Z **32 минуты без единого оборота ящика**, при поле паузы 10 минут.

**Показ числом, что частота есть следствие длины витка.** Промежутки между ВЗЯТИЯМИ
(30.7 … 63.5 мин, медиана 38.5) сравниваются с длиной длинного витка (медиана 879 с = 14.7 мин,
max 3034 с = 50.6 мин) и с временем исполнения задания (медиана 1145.5 с = 19.1 мин,
max 2703.5 с = 45.1 мин). Взятие возможно только в обороте, а оборот — только между заходами;
поэтому промежуток между взятиями = длина витка с заданием + один-два холостых взгляда.
Живая цепочка взятий 09-11: 13:09:26Z → 13:53:22Z → 14:34:22Z → 15:17:12Z → 16:18:20Z →
16:51:17Z → 17:27:24Z → 18:02:38Z, шаги **43.9 · 41.0 · 42.8 · 61.1 · 33.0 · 36.1 · 35.2 мин** —
и каждому соответствует ровно один заход головы из таблицы выше.

**Вывод:** «раз в полчаса-час» — это НЕ настройка ящика. Ящик настроен на 10 минут и в
простое их держит. Полчаса-час получаются потому, что полоса однопоточная и берёт следующее
задание не раньше, чем сдаст текущее.

## 4. Слепота снимка — причина названа адресом (п.5)

### Разведение вариантов, которые предложил Штаб

| вариант | вердикт | чем доказано |
|---|---|---|
| очередь пересоздавалась | **НЕТ, но номера ПЕРЕИСПОЛЬЗУЮТСЯ** — и это включающее условие | сам демон говорит это словами: «отметка старта id=7 … номер переиспользован очередью, отметку ставлю заново» (лог 09-12 01:05:22 мест.). За сутки номера 1–6 прошли по 3 круга |
| снимок читает собственный кэш, а не живую очередь | **ДА, ровно наполовину** | открытая половина читается живой (`read_open`, `queue_snapshot_pc.py:572`), а **закрытая половина — местный накопитель** `st["closed"]` в `queue_snapshot_pc.state.json`; из очереди она перечитывается только для `failed` и один раз на жизнь для `done` (`seed_done`, стр. 617) |
| ряды отфильтрованы датой или иным условием | **дата — НЕТ** (окно суток режет только старое, стр. 372), **иное условие — ДА, и оно и есть причина** | см. ниже |
| ряды есть, но снимок берёт их из другого места | **ДА**, см. строку про кэш | — |

### Причина А — потеря закрытий. `queue_snapshot_pc.py`, `merge_closed`, строки 374–380

```python
for tid, item in prev_open.items():
    if str(tid) in now_open:
        continue
    if str(tid) in closed:      # ← ЗДЕСЬ
        continue
    closed[str(tid)] = {...}
```

Реестр закрытых ключуется **НОМЕРОМ РЯДА**, а номер очередь переиспользует. Ряд #4 закрылся
09-11 16:36:58Z — но в реестре уже лежала запись «#4, закрыт 09-10 19:41:30Z, ключ
23-a-kopiya-ramki», подрезкой суток ещё не снятая. Условие `str(tid) in closed` истинно →
`continue` → **новое закрытие отбрасывается молча**, старая запись остаётся со своим `at`,
своей целью и своим исходом. То же для #1, #3, #5, #6. Номер #2 записи не получил вовсе:
старая уехала по окну уже ПОСЛЕ того, как новая была отброшена.

Это не филтр по дате и не усечение: **это дедуп по номеру, принятый за дедуп по личности**.
Тот же класс полоса уже переписывала 11.09 — `docs/artifacts/2026-09-11-ПЕРЕПИСЬ-ryad-ne-lichnost-1109.md`.

Соседние ветки живут тем же ключом и потому тоже участвуют:
`apply_failed` (стр. 443–456) по номеру **перезаписывает** — поэтому упавшие ряды видны, а
сданные нет; `seed_done` (стр. 632–633) по номеру **пропускает**, но зовётся один раз на жизнь
состояния и суточной картины не портит.

### Причина Б — порядок показа. `queue_snapshot_pc.py`, `_closed_key`, строки 307–311

```python
def _closed_key(pair):
    return (0, -int(pair[0]))
```

Реестр показывается **по убыванию НОМЕРА**, а не по времени закрытия. Поэтому «последним
закрытым» читатель видит #12 даже тогда, когда позже него закрылись #1…#6. Причина Б
самостоятельно давала бы ту же картинку и после починки причины А, поэтому чинить надо обе.

### Витрина врёт НА ТОМ ЖЕ ОСНОВАНИИ — своей ошибки у неё нет

`vitrina_pc_run.idle_facts` (стр. 283–296) берёт «с какого времени пусто» как `max(at)` по
`snapshot["closed"]` — то есть по ТОМУ ЖЕ замороженному реестру. Её докстринг рассуждает верно
(«последним событием очереди было именно закрытие»), но опирается на посылку «реестр знает про
КАЖДОЕ закрытие», а реестр её не выполняет. Отсюда «пусто ≥ 4.0 ч с 13:47Z» и ложная ТРЕВОГА.

Вторая строка витрины — своя, но того же рода. `vitrina_pc_run.shtab_last_facts`
(стр. 319–339) берёт **ключ задания** из `item["goal"]` реестра, а **время** — из живых отметок
claim по номеру: `at, kind = (claims or {}).get(rid), "claim"` (стр. 328). Час получается
правильный, ключ — от чужого ряда с тем же номером. Отсюда «#6 … ключ=25-a, взято 17:29 UTC».

Третий след того же корня — строка ОСЕЙ: витрина печатает «строк очереди закрылось за сутки:
6», тогда как по журналу за UTC-сутки 09-11 закрылось **15**. Точное окно счёта
(`closed_since`) в этом заходе не разбиралось, поэтому число 6 названо согласующимся с причиной
А, но не доказанным ею отдельно.

### Сколько раз за сутки витрина сказала «очередь пуста», пока полоса работала

Правок витрины за сутки — **90** (строка «витрина: правка (сообщение 9212)»). История тел не
хранится: витрина правит ОДНО сообщение на месте, в состоянии лежит только последнее. Поэтому
счёт восстановлен по пересечению времени правок с живым состоянием очереди из журнала:

- правок **после заморозки реестра (13:47:36Z) при ПУСТОЙ очереди — 10**;
- из них простой назван **завышенно — 9**, худшее завышение **+252 мин** (4.2 ч);
- из них **ТРЕВОГА «пусто ≥ 4 ч» при истинном простое меньше 4 ч — 1** (та самая, что лежит в
  состоянии на 18:02Z);
- правок, где витрина назвала бы пустой ЗАНЯТУЮ очередь, — **0**: признак `busy` читается
  живой открытой половиной и не врёт ни разу.

Момент, когда Штаб КЛАДЁТ документ в папку, полосе не виден ни одним прибором — виден только
момент, когда ящик увидел прирост числа документов. Поэтому число ниже — **НИЖНЯЯ оценка**.

За сутки ящик заметил **11 приходов** (суммарно 14 новых документов: три раза приходило по два)
и сделал **24 взятия**. Задержка «увиден ящиком → взят полосой»:

- **n = 14 · медиана 18.2 мин · максимум 377.9 мин · сумма 891.7 мин (14.9 ч)**;
- в среднем на задание — **63.7 мин**;
- к каждому числу добавляется **до одной паузы взгляда** (медиана 11.8 мин), потому что
  документ, положенный сразу после взгляда, ждёт следующего.

Максимум 377.9 мин — это ночной документ, замеченный 09-11 04:54Z и взятый 08:18Z–08:52Z:
холостых оборотов ящика в этом окне было 18, и ни один ничего не взял. Разбор причины этого
конкретного окна в задание не входил.

Второе слагаемое цены — **очередь ждала работы сама**: 22 окна простоя за сутки, сумма
**893.3 мин**, среднее **40.6 мин**, медиана 16.7 мин. Два окна из 22 (383.8 и 211.3 мин)
дают больше половины суммы — без них среднее падает до 14.9 мин.

### Во что обходится слепота прибора

Прибор молчит не про «сколько-то», а про **половину суток**:

- закрытий рядов за сутки по журналу — **23**; попало в реестр — **11**;
  **потеряно 12, то есть 52 %**;
- из шести закрытий после 13:47:36Z потеряно **6 из 6 (100 %)**;
- решений, которые прибор мог увести в сторону, — **10 показов витрины** (из них 9 с завышенным
  простоем и 1 с ложной ТРЕВОГОЙ) **плюс каждое чтение самого снимка** внешним читателем:
  снимок — док мозга `queue_state_pc`, его читает Штаб, и его шапка при этом честно говорит
  «снято: 17:24Z», то есть предъявляет СВЕЖЕСТЬ на устаревшем содержимом. Это худший род
  ошибки: не молчание, а свежая на вид ложь;
- отдельная строка сверх заказанного: слепота **подталкивает к поступку**. Строка ТРЕВОГИ
  прямо зовёт «будить Штаб по пустой очереди» в ту минуту, когда очередь работала непрерывно
  и в ней уже лежали три невзятых задания (`census.waiting = 3`).

## 6. Цена правки — по каждой причине (п.7). Решение чинить принимает Штаб

### Правка 1 — ключ реестра закрытых должен нести ЛИЧНОСТЬ, а не номер

- **что:** ключевать `closed` парой «номер + отличитель» (метка `[от Штаба … ключ=…]` из цели
  либо время claim), а не `str(id)`;
- **где:** `queue_snapshot_pc.py` — `merge_closed` (366–381), `apply_failed` (440–461),
  `seed_done` (617–636), `_closed_key` (307–311, сломается на составном ключе),
  `render_body` (223–297, печатает `#tid`), `signature` (354–363);
  `vitrina_pc_run.py` — `shtab_last_facts` (319–339, иначе час и ключ снова разъедутся);
- **сколько:** 2 файла, 7 мест, **ориентировочно 30–45 строк**;
- **чем проверить:** голден в `test_queue_snapshot_pc.py` (в файле 41 теста): «номер 4
  закрылся дважды за сутки с разными целями» → в реестре ждём ДВЕ записи, а не одну;
  второй голден — «после починки `signature` меняется на втором закрытии» (иначе слепок не
  перезапишется). Живая проверка без моста: прогнать `merge_closed` на выгрузке нынешнего
  `queue_snapshot_pc.state.json` плюс шесть потерянных закрытий из журнала и получить 17
  записей вместо 11.

### Правка 2 — «последний закрытый» должен считаться по ВРЕМЕНИ

- **что:** сортировать `closed` по `-at`, а не по `-int(id)`;
- **где:** `queue_snapshot_pc.py` → `_closed_key` (307–311);
- **сколько:** 1 файл, 1 место, **3–5 строк**;
- **чем проверить:** голден с двумя закрытиями, где МЕНЬШИЙ номер закрылся ПОЗЖЕ, — он обязан
  встать первым. Правка дешёвая, но **сама по себе слепоту не снимает**: без правки 1 сортировать
  по времени будет нечего.

### Правка 3 — витрина не должна склеивать живой час с чужим ключом

- **что:** брать ключ и час из ОДНОЙ записи; не нашлось пары — говорить «неизвестно», а не
  подставлять ключ по номеру;
- **где:** `vitrina_pc_run.py` → `shtab_last_facts` (319–339);
- **сколько:** 1 файл, 1 место, **8–12 строк**;
- **чем проверить:** голден в `test_vitrina_pc.py` (в файле 119 тестов): реестр с записью
  «#6 → ключ A» и живой claim «#6 в 17:29Z» от задания с ключом B → строка обязана сказать
  «неизвестно», а не «ключ A в 17:29Z». После правки 1 нужда в правке 3 частично отпадает, но
  не полностью: пара «claim без записи в реестре» останется возможной.

### Правка 4 — частота ящика. Дефекта нет, выбор есть

Чинить нечего: 600 с — измеренное число (обоснование при константе, `pc_orchestrator.py`
стр. 11615–11638), а полчаса-час дают синхронные заходы головы. Если Штаб хочет чаще, цена
такая:

- **дешёвый путь, 0 строк кода:** `SHTAB_BOX_LIMIT` > 1 — ящик берёт несколько заданий за
  оборот, и они стоя́т в очереди рядами `new`, пока полоса жуёт первое. Задержка приёма падает,
  длина витка не меняется. Риск назван прямо: суточный потолок 40 выбирается быстрее, и
  сигнальная остановка получает больше материала за раз;
- **дорогой путь:** вынести оборот ящика из синхронного тела витка (отдельный процесс, как у
  слоя ожиданий). Это **новая задача Планировщика** (красная операция), плюс развод замка с
  демоном, плюс пересмотр О2, который сегодня оправдывает тишину объявленным заходом. Порядок —
  не правка, а отдельное задание.
