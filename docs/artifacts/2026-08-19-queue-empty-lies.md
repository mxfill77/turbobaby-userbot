## 1. Где считается строка «очередь пуста» и что она берёт в расчёт

Строка рождается в `_announce_idle` — `tmp/srv_e2e_20260814/devbot.py:1633-1653`:

```python
async def _announce_idle(context, by):
    """Переход «работа была → всё закрыто» → РОВНО одно сообщение в 328. Пока очередь пуста и
    ничего нового не приходило, сообщение не повторяется; новая задача взводит сигнал заново."""
    global _queue_busy, _closed_since_busy
    if _queue_open_count(by):
        _queue_busy = True
        return
    if _queue_busy:                     # было занято, стало пусто — это и есть переход
        ids = sorted(set(_closed_since_busy))
        tail = ("\nЗакрыто: " + ", ".join(str(i) for i in ids)) if ids else ""
        msg = f"🟢 Очередь пуста — в работе 0, ждёт тебя 0, в очереди 0 (обе полосы).{tail}"
```

**Первое, что надо знать про эту строку: три числа в ней — не числа, а буквы.** «в работе 0,
ждёт тебя 0, в очереди 0» — литеральный текст f-строки, туда ничего не подставляется. Никакой
разбивки по корзинам за ними нет; есть **один булев вентиль** `_queue_open_count(by)`.

Сам счёт — `devbot.py:1616-1630`:

```python
def _queue_open_count(by):
    """Сколько задач наших меток ещё живо в снимке. by=None сюда не доходит: без данных очереди
    о пустоте не заявляем НИКОГДА (тот же fail-safe, что у плашки «состояние недоступно»)."""
    n = 0
    for st in _OPEN_STATUSES:
        for it in by.get(st, []) or []:
            if str(it.get("from") or "") not in QUEUE_FROMS:
                continue
            if st == "needs_approval" and _revizor_silenced.get(str(it.get("id"))) == _gen(it):
                continue
            n += 1
    return n
```

### Слагаемые поимённо — их ровно четыре, и все из одного снимка

`_OPEN_STATUSES` — `devbot.py:1611`:
```python
_OPEN_STATUSES = ("new", "in_progress", "needs_approval", "approved")
```

| № | слагаемое | источник | что считает |
|---|---|---|---|
| 1 | `by["new"]` | снимок Bridge | строки в статусе `new` |
| 2 | `by["in_progress"]` | снимок Bridge | строки в работе |
| 3 | `by["needs_approval"]` **минус** `_revizor_silenced` | снимок Bridge + словарь в памяти процесса | конверты владельцу, кроме уехавших лентой карточек ревизора |
| 4 | `by["approved"]` | снимок Bridge | одобренные |

Все четыре — из **одного** объекта `by`, собранного `_poll_queue_sync` (`devbot.py:92-119`)
одним вызовом `get_pending_multi(_REPORT_STATUSES, lane="all")`. Оба фильтра по метке
(`devbot.py:117` и `devbot.py:1622`) отсеивают всё, чей `from` не входит в `QUEUE_FROMS`
(`devbot.py:169-170`): `Filipp-328`, `Filipp-328-dev`, `Filipp-328-dec`, **`Filipp-curator`**,
`Filipp`, плюс шесть ПК-меток. Метка куратора в список входит — значит его строки видны.

### Что НЕ берётся в расчёт

* **`done` и `failed`.** Они едут в том же снимке (`_REPORT_STATUSES`, `devbot.py:71`), но в
  `_OPEN_STATUSES` их нет. Именно их читает срез целей — счётчик не смотрит туда никогда.
* **Хвост `Закрыто:`** (`devbot.py:1641-1642`) — это НЕ окно суток и вообще не часы. Это список
  `_closed_since_busy` (`devbot.py:1613`), пополняемый одной строкой `devbot.py:1940` на каждую
  отрапортованную done/failed-карточку и **обнуляемый самим `_announce_idle`** на каждом пустом
  тике (`devbot.py:1653`). «Закрыто: 24, 25» значит «за только что кончившийся занятый отрезок
  отрапортованы карточки 24 и 25» — и ничего про сутки.
* **Состояние в памяти процесса.** `_queue_busy` и `_closed_since_busy` — глобалы, **файла
  состояния нет** (в отличие от соседнего ревизора с `/tmp/cc_revizor_frozen.json`,
  `devbot.py:1669`). Рестарт `splinter` стирает и то и другое.
* **Сеть.** `_announce_idle` и `_queue_open_count` не делают **ни одного** вызова Bridge — они
  чистые функции над уже полученным `by`.

## 2. Видит ли она незакрытые цели куратора — НЕТ. Это ключевой ответ

**Не видит ни одной строкой.** Полный путь данных до ветки:

`report_results` (`devbot.py:1810`) → `by = await asyncio.to_thread(_poll_queue_sync, pb)`
(`devbot.py:1821`) → … → `await _announce_idle(context, by)` (`devbot.py:2009`) →
`_queue_open_count(by)` (`devbot.py:1637`).

`_queue_open_count` трогает ровно эти имена: `_OPEN_STATUSES`, `it["from"]`, `QUEUE_FROMS`,
`it["id"]`, `_gen(it)`, `_revizor_silenced`. Ни `_curator_goals`, ни `_CURATOR_GOAL_RE`, ни
`_curator_pending` в этом пути не упомянуты.

**И вот что делает это дефектом, а не решением: в ТОМ ЖЕ файле есть вторая правда о пустоте,
которая цели СМОТРИТ.** Плашка карточки — `devbot.py:2426-2432`:

```python
    # Проверить кураторские цели через готовый снимок (без Bridge-вызовов)
    flat = [it for lst in by.values() for it in lst]
    goals = _curator_goals(None, flat) or {}
    if any(g["active"] or g["wait"] or g["owner"] for g in goals.values()):
        return "⏳ Работа продолжается: 0 задач (🧭 куратор активен)"

    return "✅ ВСЁ ЗАВЕРШЕНО — очередь пуста, кураторских целей нет. Это была последняя задача"
```

Комментарий над сигналом (`devbot.py:1607-1610`) прямо обещает, что разойтись они не могут:

> «Считается из ТОГО ЖЕ снимка, что и плашка карточки (_build_banner), чтобы две правды не
> разошлись.»

Обещание выполнено наполовину: **снимок общий, предикат — разный.** У плашки есть оговорка про
цели, у сигнала её нет. Это и есть место дефекта.

## 3. Есть ли уже место, где число незакрытых целей доступно, и чего оно стоит

**Хранилища целей нет вовсе.** Ни Brain-док, ни JSON, ни вкладка листа: поиск по
`open_goals|goals_open|active_goals|goal_count|GOALS_FILE|goals\.json` по всему снимку — **0
совпадений**. Цель существует ТОЛЬКО как текстовый маркер в колонке `task_text` очереди:
`_CURATOR_GOAL_RE = re.compile(r"\[куратор цели (\d+), шаг (\d+)\]")` (`devbot.py:2144`),
маркер ставит демон при постановке продолжения (`orchestrator_daemon.py:3009`).

**Читатель — `_curator_goals` (`devbot.py:2183-2222`), и он стоит РОВНО ТОГО ЖЕ вызова**, потому
что вызова не делает вовсе, если снимок уже есть:

```python
    if items is _UNSET:
        items = _queue_snapshot(pb)
```

При `_curator_goals(None, flat)` аргумент `pb` равен `None` и не трогается ни разу. Плашка так
и зовёт его (`devbot.py:2427`), с комментарием «без Bridge-вызовов». Сводка «статус» считает по
нему настоящее число открытых целей — `devbot.py:2660-2661`:

```python
    cur_work = sum(1 for g in goals.values()
                   if not (g["owner"] or g["wait"]) and g["active"])
```

**Итого: цена доступа к числу незакрытых целей внутри тика — ноль вызовов, ноль сети.**

Цена отдельного вызова, если бы он понадобился (не понадобится): `get_pending_multi(..., lane="all")`,
клиент опроса с `POLL_TIMEOUT = 15` (`devbot.py:70`), `retry_attempts` 3 (`bridge_client.py:325-343`),
до 6 хопов редиректа. Живая латентность этого вызова записана в `CLAUDE.md` (О5): **медиана 3.2 с,
p95 46.3, p99 228.5, max 417**. То есть отдельный вызов стоил бы в худшем случае дороже всего тика
(45 с) — и брать его незачем.

### Но именно здесь лежит главная находка разведки

**В момент, когда экран соврал, `_curator_goals` вернул бы `{}` — и был бы прав.** Порядок работы
демона, две соседние строки `orchestrator_daemon.py:4886` и `:4895`:

```python

        log.info("COMPLETE id=%s status=%s bridge_ok=%s", tid, status, cm.get("ok"))
        ...
        _maybe_curator_single(task.get("from"), tid, text, result, status=status)   # куратор цели (CURATOR=1)
```

Задача становится `done` в очереди **СНАЧАЛА**. Только потом синхронно запускается куратор —
`_thinker_exec(prompt, CURATOR_TIMEOUT, "curator")` (`orchestrator_daemon.py:2720`) с
`CURATOR_TIMEOUT = 180` (`orchestrator_daemon.py:2366`), и лишь после вердикта ставятся
продолжения (`orchestrator_daemon.py:3009`).

**Между этими двумя строками есть окно до 180 секунд, в котором:**
* закрытая задача уже `done` — в открытые не считается;
* продолжение ещё не существует — строки в очереди нет;
* цель открыта, и знать об этом неоткуда **ни счётчику, ни срезу целей**.

Единственный живой признак этого окна лежит в памяти devbot — `devbot.py:195`:

```python

```

Он непуст ровно тогда, когда карточка показывает `🧭 Куратор оценивает итог — вердикт через ~10с`
(`devbot.py:206`), и держится до `_CURATOR_WAIT_MAX = 240` (`devbot.py:207`). **Это единственное
место, где «цель ещё судится» доступно в момент лжи, и стоит оно ноль.**

## 4. Разрыв по времени: сколько длится окно лжи

**Окно ограничено КОДОМ, а не статистикой, и это сильнее замера.** Верхняя граница —
`CURATOR_TIMEOUT = 180` с (3 мин) на размышление куратора, плюс постановка продолжений, плюс
тик devbot `interval=45` (`bot.py:1484-1491`). Живой случай 19.08: закрытие 11:56 → задача 27
видна в 11:59 = **3 минуты**, то есть ровно у потолка `CURATOR_TIMEOUT`. Число сходится с кодом,
а не с догадкой.

**Замер по журналу — честная оговорка: он мерит ДРУГУЮ популяцию.** Куратора на полосе ПК нет
вовсе (`grep -ci 'curator|куратор' pc_orchestrator.py` → **0**), и сам срез целей отбрасывает
ПК-строки (`devbot.py:2200-2201`, «куратор живёт только на vps»). Поэтому мой проход по
`pc_orchestrator.log` за окно суток (18.08 12:00 → 19.08 12:04, n=21 пары «COMPLETE → следующий
CLAIM») измеряет темп подачи задач владельцем, а не продолжения куратора:

```
медиана = 5.62 мин   min = 1.27   max = 361.03
1.27 1.78 1.83 1.85 1.95 2.03 2.08 2.57 3.07 3.55 5.62 | 14.27 16.13 21.72 22.37 27.57 28.15 49.35 127.52 176.85 361.03
```

Распределение **двугорбое**, и разрыв между горбами чистый (5.62 → 14.27): быстрый горб n=11,
медиана **2.03 мин**, потолок 5.62; медленный n=10, медиана 27.9, потолок **361 мин (6.0 ч)** —
это простои, а не продолжения. Живые 3 минуты попадают в быстрый горб.

**Вывод для развилки «ждать или говорить сразу» — говорить сразу.** Слепое ожидание пришлось бы
держать ≥180 с (потолок куратора), и оно: (а) задержало бы КАЖДЫЙ честный доклад о пустоте на три
минуты; (б) всё равно не отличило бы «куратор думает» от «работы правда нет», потому что в этом
окне очередь пуста ОДИНАКОВО в обоих случаях; (в) упёрлось бы в медленный горб — 6-часовой простой
ожиданием не лечится. Признак же (`_curator_pending`) доступен мгновенно и стоит ноль.

        return f"⏳ Работа продолжается: {total} (🎭 {' · '.join(parts)}){ids}"

Форма подтверждена собственным артефактом снимка
(`tmp/srv_e2e_20260814/docs/artifacts/2026-08-05-feed-noise-cut.md:83-90`) — там та же пара строк
с номером 331 вместо 27.

**Почему они оказались рядом с «пусто» и не помешали ему — три причины, каждая проверяемая:**

1. **Это ДВА РАЗНЫХ сообщения, а не одно.** Слова о продолжении шлёт `report_results` внутри цикла
   по завершённым (`send_message`, `devbot.py:1920`) либо дописывает `_check_curator_pending`
   правкой (`edit_message_text`, `devbot.py:1506`). «Очередь пуста» шлёт `_announce_idle` отдельным
   `send_message` (`devbot.py:1646`), один раз в самом конце тика (`devbot.py:2009`), в жёстко
   заданную тему 328 и без кнопок. Ни одна из функций не читает вывод другой.

2. **Слова о продолжении приходят в СТАРОЕ сообщение ПРАВКОЙ.** Карточка сначала уходит с надписью
   `🧭 Куратор оценивает итог — вердикт через ~10с`, номер сообщения запоминается в
   `_curator_pending` (`devbot.py:1936`), и вердикт вписывается туда позже через
   `edit_message_text`. **Правка не двигает сообщение**: карточка остаётся выше «пусто» навсегда,
   какой бы поздней ни была вписанная в неё правда. Владелец читает сверху вниз «цель не закрыта»
   → «очередь пуста» и видит одновременность там, где её не было.

3. **В тик, когда «пусто» ушло, продолжения ещё не существовало — и это доказывает сам хвост
   сообщения.** «Закрыто: 24, 25» означает, что сигнал ушёл в тике сразу после закрытия задачи 25,
   пока куратор ещё думал (§3, окно ≤180 с). Обратное невозможно арифметически: демон ставит
   продолжения ДО завершения карточки-маркера (`orchestrator_daemon.py:3602-3603` — «Карточка-маркер
   дедупа встаёт ПЕРВОЙ, продолжения ставятся МЕЖДУ её enqueue и complete»), поэтому в тике, где
   devbot уже видит вердикт, строка 27 в снимке ЕСТЬ, `_queue_open_count ≥ 1`, и `_announce_idle`
   выходит на `devbot.py:1638` не сказав ничего. Значит наблюдённая пара строк — это два РАЗНЫХ
   тика (≥45 с), склеенных правкой в одну картинку.

**Прецедент, что так бывает не везде: на полосе ПК тот же экран цели УЖЕ смотрит.**
`pc_orchestrator._contour_status` (`pc_orchestrator.py:2260-2270`) говорит «🟢 ТИХО» только если
`_loc_active_chains(snap)` пуст, то есть нет ни незакрытого шага, ни живого родителя
(`pc_orchestrator.py:4757-4775`); при `snap is None` он сознательно отказывается говорить ТИХО.
Это поведение прибито тестами `test_pc_orchestrator.py:3540-3615`. Считается всё из того же
снимка — `_loc_fetch_items()` (`pc_orchestrator.py:4702-4715`, 6 вызовов `get_pending`, таймаут 90 с
каждый), лишних вызовов ноль. То есть нужная форма на полосе ПК уже написана и работает —
но соседний ПК-прибор `queue_snapshot_pc.py` цепей НЕ смотрит (`grep 'active_chains|цепь|chain'`
→ **0**) и печатает «очередь пуста» ровно так же слепо, как VPS.

**Починка научит `_announce_idle` звать `_curator_goals` — тесты позеленеют (в них у цели ЕСТЬ

## Сводка

1. Строка «очередь пуста» — не сводка, а **один булев вентиль** `_queue_open_count` над четырьмя
   статусами очереди (`new`/`in_progress`/`needs_approval`/`approved`); три числа в тексте

   плашка `_build_banner` их смотрит, из того же снимка. Комментарий обещает общую правду; общий
   у них снимок, а предикат разный.
3. Число открытых целей доступно **за ноль вызовов** (`_curator_goals(None, flat)`), но в момент
   самой лжи оно всё равно вернуло бы `{}`: демон закрывает задачу ДО консультации куратора
   (`orchestrator_daemon.py:4886` против `:4895`), и продолжения ещё нет в очереди.
4. Окно лжи ограничено кодом: `CURATOR_TIMEOUT = 180 с` + тик 45 с; живой случай 19.08 дал

   мерит другую популяцию — куратора на полосе ПК нет вовсе. Ждать не надо: ожидание задержит
   каждый честный доклад и всё равно не различит случаи.
5. Читателей пустоты — **16**, из них сообщение потребляет только сам devbot, остальные
   пересчитывают её заново; двое (`result_judge_pc`, тесты гейта) прибиты к ДОСЛОВНЫМ фразам, и
   переименование сломает их молча.
6. Слова о продолжении в экране **уже есть** и не мешают «пусто» по трём причинам: это разные
