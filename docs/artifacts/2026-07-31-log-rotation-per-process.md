никогда, и `RotatingFileHandler` молча выбрасывал КАЖДУЮ строку. Разведение файла по

## 1. Диагноз, снятый живьём (не пересказ)

| замер | значение |
|---|---|
| `pricing.log` | 23 302 269 байт, mtime **22.07.2026 21:39:37** — при пороге 5 МБ |
| хвост файла | `2026-07-22 21:39:37,324 | quote ok bike=ADV 350CC UNIT-4 …` |
| проба захвата (`FileShare.None`) | `pricing.log` — **LOCKED**, `delivery.log` — **LOCKED**, `dispatch_notify.log` — free, `pretool_guard.log` — free |
| живые процессы | PID 1656 `userbot_listen.py`, 9988 `moderation_bot.py`, 13852 `pc_orchestrator.py` (все три тянут `suggest` → `pricing`) |

**Механика.** `RotatingFileHandler.emit` → `shouldRollover` (23 МБ > 5 МБ, всегда True) →
`doRollover` → `os.rename` открытого другим процессом файла → `PermissionError [WinError 32]`
→ `except` → `Handler.handleError` → **строка потеряна**. У демона без stderr `handleError`
не печатает ничего. То есть замерший mtime — не «лог затих», а **девять суток немоты
диагностики котировок**, и выглядело это как здоровье: файл ведь перестал расти.

Тот же WinError 32 уже ловили руками 30.07 — комментарий в `trainer_run.py:83-87` («первый же
прогон полез ротировать `pricing.log` … и утонул в PermissionError WinError 32»); лечили тогда
частный случай прогона, а не класс.

## 3. Способ разведения и почему такой

**Файл разводится по КЛИЧКЕ ПРОЦЕССА — имени входного скрипта**, не по PID:

```
pricing.log →  pricing.userbot_listen.log
               pricing.moderation_bot.log
               pricing.pc_orchestrator.log
```

* **PID отвергнут:** новый файл на каждый рестарт, за неделю каталог нечитаем, бэкапы
  множатся на каждый PID, «покажи лог котировок» перестаёт иметь ответ.
* **Кличка процесса** стабильна между рестартами, сразу отвечает «чей это лог», и число
  файлов равно числу процессов.

**Канон достаётся хозяину.** `pc_agent.log` пишет `pc_agent`, `pc_orchestrator.log` — демон,
`userbot.log` — `userbot_listen` (имя не совпадает, объявлено в `LOG_OWNERS`), то же для
`rc_remote_control.log` → `rc_supervisor`. Все существующие читатели логов, документация и
память остаются верны. Суффикс получает только **чужой** процесс, импортировавший модуль.
У `pricing.log`/`delivery.log` хозяина нет вовсе (процесса `pricing` не существует) — канон
не занимает никто, и спорить за `rename` больше некому.

**Разводится только `handler_path`, а не `log_path` — и это не мелочь.** Файл держит (и мешает
`rename`) лишь тот, кто открыл его надолго, то есть хендлер. Писатели в режиме
open→write→close — гард (`pretool_guard._log` → `open(p,'a')`) и дозапись метрик
(`dispatch_notify._write_session_metrics` → `pc_orchestrator.log`) — ротации не мешают, и
разводить их **нельзя**: единая лента аудита гарда рассыпалась бы на файл-на-процесс без
всякой пользы. Голден на это есть.

## 4. Отказ переката больше не проглатывается (пункт 3 задания)

`SafeRotatingFileHandler` при сорвавшемся перекате:

1. **запись всё равно ложится в файл** — растущий лог лучше немого (прежде строка терялась);
2. строка `ROTATE-FAIL …` уходит в **три** места: общий файл-сигнал `log_rotation_errors.log`,
   `stderr`, и — один раз за эпизод — в сам лог; плюс `log_setup.rotation_failures()` в памяти
   процесса;
3. следующая попытка откладывается на `LOG_ROLLOVER_RETRY_SEC` (300 с) — иначе `rename`
   дёргался бы на КАЖДОЙ строке.

`rotate_if_needed` (писатели без `logging`) — тот же сигнал; возврат оставлен прежним
(`False` и «не пора», и «не смогли»), чтобы не ломать вызывающих: смотреть надо сигнал.

**Размен назван вслух:** при неустранимом отказе файл будет РАСТИ сверх порога. Это
осознанно — тихая потеря диагностики хуже видимого роста, а видимый рост чинится по сигналу.

> **Поправка прохода 2 (31.07):** «неустранимый отказ» оказался устранимым. У переката теперь
> ВТОРАЯ ступень — `_copytruncate`; рост сверх порога остаётся только если сорвались обе, что
> на порядок реже. См. [`2026-07-31-log-rotation-copytruncate.md`](2026-07-31-log-rotation-copytruncate.md).

## 6. Что с живым `pricing.log` — не удалён

> **ВЕРДИКТ НИЖЕ СНЯТ ЗАМЕРОМ 31.07 (проход 2), вторая его половина неверна.** `rename`

> Класс ошибки: «не смог я» записано как «невозможно».

**Оставлен как есть, 23 302 269 байт.** Переименовать не вышло бы: файл занят тремя
процессами — ровно та причина, из-за которой не проходил и перекат. После рестарта процессов
он перестанет быть адресатом (каждый уйдёт в свой `pricing.<владелец>.log`) и останется
историей за 15–22.07; тогда его можно будет перекатить или убрать одним движением.
