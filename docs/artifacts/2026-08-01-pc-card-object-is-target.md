# Объект карточки — ЦЕЛЬ операции, а не её имя

Дата: 2026-08-01. Задача 137, продолжение задач 134/135.
Основание — остаток, названный своими словами в отчёте `80d5cb4` и в
[`docs/artifacts/2026-08-01-pc-kind-stamp-origin.md`](2026-08-01-pc-kind-stamp-origin.md) §«Границы

## Что было не закрыто и чем это отличалось от остатка

Остаток `80d5cb4` был про **чтение** объекта (подделка `\nОбъект: X\n` внутри объекта, сегодня
fail-closed). Задача 137 — про **содержание** объекта, и это другая половина того же поля.
Живой факт, карточка задачи 136 от 31.07 (лог гарда `2026-07-31 23:54:24`, пуш владельцу
`dispatch_notify.log:5856`):

```
⛔ ВЫСШАЯ ЦЕНА · НЕОБРАТИМО · подтверждение только с объектом: «да os.remove»
🔴 Хочу выполнить python с боевой записью (os.remove) — разрешить?
Объект: os.remove
Число: —
Откат: боевую запись Bridge снимает только обратная операция (void_last/…)
Команда: PYTHONIOENCODING=utf-8 venv/Scripts/python.exe tmp/probe_kind_stamp_origin.py 2>&1 | head -60
```

Два разрыва в одной карточке:

1. **Объект называл ДЕЙСТВИЕ.** Неизвестно, ЧТО именно удаляют. Хуже, чем просто неинформативно:
   `py_write` — вид ВЫСШИЙ, он подтверждается **переписыванием объекта** (пояс 31.07 против
   «трёх `live_sheet` подряд не читая»). Владелец переписывал имя функции — рука работала, глаз
   не работал, то есть пояс стоял, а защищаемого свойства не давал.
2. **Откат был про чужую операцию.** Команда — локальная проба в `tmp/`, Bridge не касается
   вовсе, а строка отката предлагала «обратную проводку Bridge».

## Проба на живом формате: КРАСНЫЙ до, ЗЕЛЁНЫЙ после

## Правка (`pretool_guard.py`)

Правило доктринальным блоком над `_RE_PY_LITERAL`: **в поле «Объект» стоит ЦЕЛЬ — путь, имя
сущности, номер, — а не имя функции или модуля.**

| часть | что сделано | где |
|---|---|---|
| **СЕМЬИ** | `_RED_PY_TOKENS` собран из двух списков: `_PY_BRIDGE_TOKENS` (деньги и парк) и `_PY_FS_TOKENS` (питон-родное разрушение файлов). Порядок склейки прежний — `_py_write_call` возвращает первый совпавший токен | `_PY_BRIDGE_TOKENS`, `_PY_FS_TOKENS` |
| **ЦЕЛЬ** | `_py_card_fields` собирает объект и число: файловая семья → путь + «N целей»; Bridge → сущность с идентификатором (`кошелёк cash`) + «сумма N». Вызовы разбираются по глубине скобок, запятые внутри кавычек разделителями не считаются | `_py_call_args`, `_first_arg`, `_py_literal_target`, `_py_card_fields` |
| **ПОДСТАНОВКА** | `_card_fields` меняет имя операции на цель ровно там, где объект пришёл ТОКЕНОМ (`o in _RED_PY_TOKENS` — то же условие, по которому вид держит красное). Деталь вроде «скрипт не прочитан» или «-m X» остаётся как была | `_card_fields` |
| **ОТКАТ** | `_rollback` получил третий параметр (сама операция): файл → «из git или бэкапа», Bridge → обратная операция, `void_last` → своя строка, неразобранное → «неизвестен» (честный прочерк вместо шаблона) | `_rollback`, `_ROLLBACK_PY*` |
| **КРУГ** | `card_object()` — объект, НАПЕЧАТАННЫЙ в карточке; `decide_for_role` сверяет «да» владельца именно с ним | `card_object`, `decide_for_role` |

**Цель обязана быть ЛИТЕРАЛОМ.** `os.remove(p)`, `rmtree(os.path.join(a, b))`,
`add_transaction(wallet=w)` цели не называют: `p`/`w` — имена переменных, а не файл и не
кошелёк. Назвать их объектом значило бы повторить ту же ошибку в новой форме — карточка
выглядела бы проверяемой, не будучи ею.

**Почему круг пришлось закрывать отдельно.** До правки объект разбора и объект карточки
совпадали случайно, и `approval_covers` сверяла ответ владельца с внутренним значением.
Как только карточка стала называть цель, «да tb_probe_136.txt» вернулось бы в гард сверкой с
`os.remove` — то есть НЕ вернулось бы никогда: операция ходила бы по кругу, а выглядело бы это
как «владелец подтвердил, а оно не работает». Пояс — та же привычка, что чинили 31.07, только
с другой стороны: служебное значение читается оттуда, куда его положил гард; здесь — оттуда,
откуда его читает глаз владельца. Fail-closed сохранён: пустой объект ключей не даёт.

## Развилка, которую пришлось решать: `void_last`

Строгое «нет цели — нет карточки» уперлось в границу владельца «деньги спрашивают ВСЕГДА»
(`_HARD_CARD`, зеркало `_ALWAYS_CARD` сервера): **отмена последней проводки зовётся без
аргументов ПО СВОЕЙ ПРИРОДЕ**, и запрет вместо вопроса сделал бы её неисполнимой. Решение
раздельное, по природе операции:

* **разрушение файла — НЕ деньги**, Bridge не касается: нет пути → карточки нет вовсе (`deny`),
  решение гарда прежнее (красное, операция не исполняется);
* **боевая запись Bridge — деньги**: объектом названа СУЩНОСТЬ, которую операция трогает
  (`void_last` → «последняя проводка», `add_transaction` → «проводка», `create_booking(1)` →
  «новая бронь 1»). Это не «назовём действие по-русски»: сущность — то, что меняется, и по ней
  владелец операцию узнаёт. Свойство «карточка родится у КАЖДОГО из восьми токенов Bridge даже
  без идентификатора» пиннится тестом.

## Регресс

Новый класс `TestObjectIsTheTargetNotTheAction` (9 тестов) в `test_pretool_guard.py`:
живая карточка 136 называет файл, а не функцию · без литерала карточки нет, а решение прежнее ·
деньги несут кошелёк и сумму · каждый токен Bridge даёт карточку и без цели · переменная целью
не является · несколько целей считаются · откат относится к своей операции · круг одобрения
замкнут (и чужой объект его не открывает) · у прочих видов объект не изменился.

**Переписаны два существующих теста, оба — по существу правки:**

* `test_four_lost_operations_card_again_with_empty_number` ждал в объекте `void_last`; теперь
  ждёт «последняя проводка». Проверяемое свойство — «операция без числа по природе всё равно
  рождает карточку с объектом» — не изменилось;
* `test_py_write_real_call_cards` держал файловую форму (`os.remove(chr(120))`) под девизом
  «деньги спрашивают всегда». Форма уехала в свой тест (`…file_destruction_needs_a_path`):
  разрушение файла деньгами не является. Девиз остался ровно на деньгах и получил СВОЙ пояс —
  тест по всем восьми токенам Bridge.

## Границы и остатки

* **Замок происхождения и оба рубежа не ослаблены**: `_detect_needs_approval`,
  `_executor_red_claim`, `scrub_kind_stamp`, `kinds_from_card` не тронуты; проба F1 подтверждает,
  что текст модели классом по-прежнему не становится.
* **Жёсткий блок и файл секретов спрашивают всегда**: `_HARD_CARD` не тронут; ни один вид из
  него не переехал в журнальную ветку. У `py_write` без цели карточка не выписывается через
  `deny` — решение СТРОЖЕ `ask`, новых разрешений не выдаёт.
* **Объектный гейт денег не тронут по логике**: `approval_covers`, `is_top_tier`,
  `reply_confirms_object`, `_obj_keys` — без правок. Изменилось только ЗНАЧЕНИЕ, которое в гейт
  подаётся: теперь это объект из карточки, а не из разбора.
* **Клиентский контур не тронут**, процессы не перезапускались.
* **Формат карточки не вырос**: живая карточка 136 после правки — 301 символ; самая длинная
  законная карточка по всем видам с предельными значениями — **1170** (`kill`) при пороге
  `MARKER_CARD_MAX = 1400`, то есть `py_write` перестал быть самой длинной. Порог пересчитывается
  тестом, а не комментарием.
* **Рестарт демона не нужен, и это ЗАМЕР, а не рассуждение.** Читатель кода `80d5cb4` (тот, что
  сейчас в памяти демона) прогнан по карточкам, собранным НОВЫМ гардом:
  `объект: tmp/tb_x.txt → ответ «да tb_x.txt» → сверка True, классы ['py_write']` и
  `объект: кошелёк cash → ответ «да кошелёк cash» → сверка True, классы ['py_write']`.
  Причина: демон читает карточку (`object_from_card`, `reply_confirms_object` — обе не менялись),
  а решает свежий процесс хука.
* **ОСТАТОК, точка касания названа**: `object_from_card` по-прежнему берёт **первое** совпадение
  `search` по всей карточке — то есть половина «чтения» остатка `80d5cb4` как была, fail-closed
  (подделка ведёт к несовпадению → высший вид вычёркнут). Здесь не закрыта сознательно: границы
  задачи запрещают трогать объектный гейт. Закрывать тем же приёмом: скраб `Объект:` из тела +
  чтение с места гарда.
* **ОСТАТОК второй, тот же класс в другом виде**: у `git_force` объект — тоже действие
  (`push --force origin main`), а не цель. Мягче, чем у `py_write` (цель внутри строки видна, и
  вид не высший — объектным гейтом не подтверждается), поэтому в границы задачи 137 не входил.
* **ОСТАТОК третий**: цель, лежащая в ТЕЛЕ скрипта (`python cleanup.py`, где путь внутри файла),
  в карточку не попадает — `_card_fields` видит только команду. Такая операция получает `deny` с
  обучающим текстом «назови объект В САМОЙ КОМАНДЕ». Сделано намеренно: объект, вытащенный из
  файла, которого владелец в карточке не видит, проверяемым всё равно не был бы.
