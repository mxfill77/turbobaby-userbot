## 3. Ход на ПК (руки ПК-сессии: RC или Dispatch; из облака не исполнялся)

Правило хода: **паузы в середине rebase не бывает.** Демон не видит застрявший rebase: авто-фетч на
detached HEAD молчит (`git_ff_pull_tick`, проверка ветки), а self-update, реконсиляция детей и
`_commit_lesson` работают с промежуточным HEAD. `git rebase --abort` — это жёсткий сброс
отслеживаемых файлов, а не «ничего не удаляет».

**Шаг 0 — когда.** Ни одной задачи в работе: нет живых tid в `pc_orchestrator.task_started.json`,
`PARALLEL_TASKS=2`, и сосед по второй руке пишет в тот же индекс. Каталогов `.git/rebase-merge`,
`.git/rebase-apply` и файла `.git/MERGE_HEAD` нет. Если есть — операцию ведёт кто-то другой: чужой
rebase не abort'ить, остановиться. До push с ПК ничего не сливать в GitHub `main`, включая эту ветку и
`tender-dijkstra`: иначе снова будет non-ff.

**Шаг 1 — только чтение (это ответ на п.1 фактом):**

```

git status --porcelain                          # отслеживаемых правок нет (?? не считаются)
git rev-parse main origin/main                  # origin/main = 66b16175…; сдвинулся — разобрать новые коммиты, иначе стоп
```

(`git show --stat` каждого); `merge-tree` предсказывает конфликт в любом `.py`.

**Шаг 2 — страховка:** `venv\Scripts\python.exe git_serial_pc.py -- git tag pc-main-pre-rebase-2509 main`.
Нужен именно тег, а не ветка: при `rebase.updateRefs=true` ветку, указывающую на переносимый коммит, rebase
переставит сам. Тег не удалять и не пушить. Записать `git rev-parse pc-main-pre-rebase-2509` как «до».

**Шаг 3 — rebase через замок полосы, с явным upstream:**

Единственный допустимый конфликт — `claude_profile_choice.txt`. Он возникает, если правка ПК тронула
прежнюю первую строку, вставила строку над ней, записала файл с BOM или CRLF в blob. Закрывать сразу,
заготовленным текстом, в том числе и в промежуточном коммите. Текст файла: 5 строк шапки origin

## 4. Что демон сделает сам после сведения (чтобы не принять за сбой)

- **Self-update и подъём агента запускает сам rebase, а не push.** Их запускает смена HEAD, меняющая
  отпечаток замыкания демона (`maybe_self_update`, `_dep_blobs`). Гейт тестов → `_selfupdate_restart_children`
  → `selfraise_agent` (pc_agent изменён; цель отката — `3a2f448`) → эстафета демона → строка
  `self-update: X→Y`. Сессия процессы не трогает: это штатный путь. После этого начнут работать слова
  «учётки»/«учётка N»/«учётки заведи».
- **Ворота клиентского контура (заморозка):** 2–4 строки `ворота клиентского контура: применение <хеш> …
  ОСТАНОВЛЕНО` в ленту — от реконсиляции, от self-update и от первого витка нового процесса. userbot и
  moderbot остаются на прежнем коде, пока нет поимённого «да». Оговорки: ленивые импорты `pc_orchestrator` в
  живых ботах читают новый код с диска, а подъём ребёнка мимо ворот (вотчдог, сон, перезагрузка) увезёт его на
  новый код. Так уже было в 10:24 (userbot) и в 10:32 (moderbot — в безопасный режим).
- WARNING `учётка строителей: реестра нет — решает прежний файл claude_profile_choice.txt …` на каждом
  спавне строителей — это мост, а не сбой. Снимается словом «учётки заведи».
