## 3. Почему не легла строка «снова чистое» (вероятная гонка писателей журнала)

Факты:
- `_autofetch_note` сначала пишет признак в файл, потом зовёт `_cowork(msg)` (`pc_orchestrator.py`, около 8771).
  Признак `ok` в 10:51:12 UTC есть (слова DONE 10:57), а строки нет;
- `_cowork` (около 1149) пускает `cowork_log_append.py` отдельным процессом по принципу «запустил и забыл»:
  вывод в DEVNULL, отказ не виден;
- `cowork_log_append.main` делает `read_doc` всего документа (~4 МБ), затем `write_doc` всего документа.
  Замка между писателями нет. Обратное чтение (`readback_landed`) проверяет только СВОЮ строку и только в
  момент чтения;
- следующая строка того же демона легла в 10:51:19 (`…/journal/2026-09-25-105119-note.md`), через 7 с. Пару
  чтение + запись 4 МБ через мост за 7 с не уложить.

Вывод (вероятно, не доказано): два писателя прочитали один и тот же текст. Каждый дописал свою строку и
увидел её при обратном чтении. Вторая запись целиком затёрла первую. Потеря молчаливая, и спул её не ловит,
потому что первый писатель считает запись успешной. Тем же классом можно объяснить и пропавшую строку ворот
«применение e7039239 … ОСТАНОВЛЕНО» 08:30–08:36, хотя реконсиляция пишет её на каждый новый HEAD.
Точки касания — `cowork_log_append.main` (read-modify-write без замка) и `pc_orchestrator._cowork`
(параллельные спавны).

## 4. Ход на случай повтора (класс не закрыт)

Любой неотправленный коммит сессии ПК при движении `origin/main` снова даёт non-ff. Демон пишет одну строку и
владельца не будит. Что сработало 25.09 и чего держаться:

1. Сводить, когда нет задачи в работе (`pc_orchestrator.task_started.json`, `PARALLEL_TASKS=2`, один индекс на
   двоих), нет `.git/rebase-merge`, `.git/rebase-apply`, `.git/MERGE_HEAD`, `CHERRY_PICK_HEAD`, `index.lock`.
   Дерево `main` чистое.
2. Перед ходом снять п.1 фактом: `git log --format="%H | %an <%ae> | %aI | %cI | %s" --name-status origin/main..main`,
   `git merge-base main origin/main`, `git rev-list --merges origin/main..main` (пусто),
   `git cherry -v origin/main main`.
3. Страховка: тег или ветка без переключения. Ветку `rebase.updateRefs=true` переставит сам — либо тег, либо
   `-c rebase.updateRefs=false`.
4. `git -c rebase.updateRefs=false -c core.editor=true rebase --no-autostash origin/main` с явным upstream. Не
   `pull --rebase` и не голый `rebase`, без опций дат. Замок `git_serial_pc.py` держится на ОДНУ команду:
   `add`/`--continue`/`--abort` в развилке идут мимо него. В Git Bash путь писать `venv/Scripts/python.exe`,
   обратные слэши там съедаются.
5. Конфликт в рычаге: каждый коммит закрывать СВОИМ содержимым (шапка origin + текст этого коммита), иначе
   git сочтёт следующий коммит «already upstream» и молча его выбросит. Итог — одна значимая строка, без BOM
   и маркеров. Маркеры искать поиском по `<<<<<<<`/`>>>>>>>`, а не `git diff --check`: тот ловит и хвостовые
   пробелы. `rebase --continue` pre-commit не запускает. `rebase --abort` — это жёсткий сброс отслеживаемых
   файлов: при чужих правках в дереве его не делать.
6. До push: `git range-diff <база>..<страховка> origin/main..main`, равное число коммитов, тесты
   (`test_accounts test_accounts_run test_rc_supervisor test_rc_choice_wiring test_profile_choice test_pc_agent
   test_vps_token_install`). Гейт self-update (`test_pc_orchestrator test_pc_local_dec`) демон гоняет сам на
   первом витке после rebase — ещё до push. Есть ли на ПК свой `.git/hooks/pre-push`, из облака не видно.
7. Push обычный. Отказ non-ff → fetch и повторный rebase уже от НОВОЙ базы: старый тег и прежний merge-base
   для повтора не годятся. Force — никогда. Отката после законченного rebase без красной операции нет
   (`reset --keep` на страховку — слово владельца).
8. Признак штата — набор, а не одна строка: `git status -sb` без ahead/behind (при настроенном upstream),
   `cond=ok` в `pc_orchestrator.autofetch.json`, строка «снова чистое». Эта строка одинакова для «равно» и для
   «впереди» и может потеряться (§3). Самое сильное — строка `fast-forward main → …` на следующем движении origin.
