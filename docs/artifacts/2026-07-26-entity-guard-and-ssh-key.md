# ЧАСТЬ 1 — защита по тестовым сущностям

## Поправка к постановке: функций в дереве НЕ БЫЛО

ТЗ говорило «функции определены, но не вызываются». По факту хуже: **их не было в дереве вообще** —
они лежали в `git stash@{1}` («vps-local-24.07»). Опорный артефакт это и фиксировал:

> Функции для этого **НАПИСАНЫ** (в `stash@{1}`), но **НИ РАЗУ НЕ ВЫЗЫВАЮТСЯ** … Даже в
> `stash@{1}` функции **определены, но не вызваны** … **Порт = не только скопировать функции,
> но и ВРЕЗАТЬ вызовы**

Проверка греп-ом подтвердила: в коде ни `_extract_first_entity`, ни `_is_test_entity`, ни
`_ENTITY_*` — только ожидания в голдене. Голден `tests/test_guard_тест_entity.py` стоял под
`setUpModule → SkipTest` с 24.07, чтобы 19 падающих проверок не блокировали несвязанные деплои.

## 2. Как подключено

Добавлен **чистый решатель**, чтобы врезка была тестируемой, а не спрятанной в `main`:

```python
def _entity_blocktype(hit, blob):
    entity = _extract_first_entity(hit, blob)
    if entity and not _is_test_entity(entity):
        return "hard"
    return None
```

В `pretool_guard.main` после сборки карточки:
```python
blocktype = _entity_blocktype(hit, blob)
_guard_write_marker(…, hit, card, blocktype=blocktype)
if blocktype == "hard":
    _guard_log(hit, cmd, why)
    _emit(decision("block", hit, why))      # block → deny: кнопки «да» здесь нет
```

⚠️ **Тонкость, которая решает всё:** эмитить надо `decision("block", …)`, а не `"red"`. Потому что
`can_approve` даёт `deny` только для `kind=="block"`, а `red` сам по себе превращается в `ask` —
то есть кнопка «да» осталась бы на месте, и правило снова не работало бы. На это стоит отдельный
тест `test_hard_decision_is_deny_not_ask`.

В `orchestrator_daemon.run_task`, где раньше был безусловный `needs_approval`:
```python
if _guard_is_hard(_gd):
    return "failed", "✋ ЖЁСТКИЙ БЛОК: запись в живые таблицы по ЖИВОЙ сущности…"
return "needs_approval", what[:RESULT_MAX]
```

# ЧАСТЬ 2 — ключ доступа

## 5. Что было

```
authorized_keys: строк 1, права 600
  тип=ssh-ed25519  комментарий=turbobaby_pc_to_vps
  опции: (опций нет — ключ без ограничений)
отпечаток: SHA256:mDGGVQx0DwkInQkSe5kiGCEIA6J7EhMhZHVPJXtbPes

sshd -T: permitrootlogin yes · pubkeyauthentication yes · passwordauthentication yes
         permittty yes · allowtcpforwarding yes · x11forwarding yes · forcecommand none
```

То есть файл ключа давал **полный root-доступ откуда угодно, с пробросом портов и X11**.

## Почему «только с одного адреса» сломало бы доступ

```
принятые входы по ключу за 14 дней (уникальные источники):
    644 171.6.241.83
    234 171.6.244.149
     98 171.6.237.190      ← текущая сессия
```

Адрес **динамический** — сменился минимум трижды за две недели, оставаясь внутри `171.6.0.0/16`.
Прописать `from="171.6.237.190"` значило бы потерять доступ при первой же смене IP, вероятно в
течение суток. Поэтому источник ограничен **диапазоном провайдера**, а не адресом.

## 6. Что применено

```
restrict,pty,from="171.6.0.0/16" ssh-ed25519 <КЛЮЧ-СКРЫТ> turbobaby_pc_to_vps
```

- `restrict` — запрещает всё сразу: проброс портов, agent-forwarding, X11, user-rc.
- `pty` — **возвращено намеренно**: владелец работает с телефона через tmux (`CLAUDE.md`,
  «РАБОТА С ТЕЛЕФОНА»), а `restrict` без `pty` эту работу бы убил.
- `from=` — диапазон, а не адрес (обоснование выше).

**Автооткат на время правки.** Перед изменением взведён `systemd-run --on-active=20min`,
возвращающий прежний файл: если бы новый вход не прошёл, доступ восстановился бы сам. Таймер снят
только после подтверждённого входа.

## ⚠️ Чего я НЕ трогал, хотя это больше дыра

```
passwordauthentication yes   +   permitrootlogin yes
ОТКАЗАННЫЕ попытки за 14 дней (фон атак): 287 782
```

Пароль для root включён, и по нему круглосуточно долбится перебор — **287 тысяч попыток за две
недели**. Ограничение ключа этого не закрывает вообще: атака идёт мимо ключа.

Не выключил намеренно, и это стоит решить отдельно. Сейчас пароль — **единственный запасной путь**
владельца: других пользователей с `authorized_keys` на машине нет, а ключ теперь ограничен по
диапазону. Выключить пароль без заведённого второго пути — значит поставить весь доступ на один
файл. Это решение владельца, а не моё.
