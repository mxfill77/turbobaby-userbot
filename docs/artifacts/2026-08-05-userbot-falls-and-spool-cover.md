## 2. ПАДЕНИЯ userbot — ЧЕМ ЧИНИТСЯ (не применено)

### Дефект — дословно

`userbot_listen.py:483` открывает `try:`, у которого есть **только `finally:`** (строка 542)
и **ни одного `except`**. Внутри — два места, откуда Telethon бросает `ConnectionError`:

* **строка 485** `await client.start()` — сеть недоступна на старте;
* **строка 541** `await client.run_until_disconnected()` — авто-переподключение выдохлось.

Исключение проходит `finally` (поэтому в логе есть `ОСТАНОВЛЕН`), выходит из `main()`, из
`asyncio.run(main())` (строка 550) — а там ловится **только `KeyboardInterrupt`**. Процесс
умирает. Трассы (в `logs/userbot_stderr.log`, куда `pc_agent` шлёт stderr ребёнка):

```
File "D:\turbobaby-bot\userbot_listen.py", line 485, in main
    await client.start()
ConnectionError: Connection to Telegram failed 5 time(s)
```

`TelegramClient(SESSION, API_ID, API_HASH)` (строка 465) создаётся без ручек —
`connection_retries=5` по умолчанию, отсюда «failed 5 time(s)».

### Вариант A — правка `userbot_listen.py` (КЛИЕНТСКИЙ файл)

Что добавить: `except (ConnectionError, OSError, asyncio.TimeoutError)` + петля перезапуска
вокруг `asyncio.run(main())` с экспоненциальной паузой; плюс `connection_retries`/`retry_delay`
в конструктор клиента (строка 465).

* **Строк:** ~14–16 боевых (2 константы паузы, +1 в строке 465, ~12 в блоке `__main__`).
* **Файлов:** **1** — `userbot_listen.py`.
* **Замыкание импортов задевает?** Общих модулей — НЕТ. Но сам файл — ВХОД замыкания:
  `client_contour.is_client("userbot_listen.py") = True`. Живое замыкание (замер этого захода,
  `client_contour.closure()`, ok=True) — **12 файлов**: `booking_draft, delivery, lesson_router,
  log_setup, moderation_bot, moderation_core, moderation_ipc, pricing, suggest, trainer,
  trainer_log, userbot_listen` + 5 файлов данных. Значит «ворота контура» остановят применение
  коммита к детям (`применение X к «userbot,moderbot» ОСТАНОВЛЕНО — клиентские файлы: …`), и
  выкатка требует основания `owner` или зелёного тренажёра.
* **Цена сверх строк:** голдены класть некуда — `test_userbot_listen.py` в репо НЕТ, а
  `if __name__ == "__main__"` не импортируется. Честная форма — вынести петлю в функцию и
  завести новый тест-файл (+40–60 строк).

### Вариант B — надзор СНАРУЖИ, без единого клиентского файла

**Надзор уже есть и уже работает.** `контур-вотчдог` (`pc_orchestrator.py:5322+`) каждые
`CLIENT_WATCH_SEC=300` с ищет `userbot_listen.py` через CIM и поднимает мёртвого механикой
`pc_agent`. В эту неделю он поднял бота 4 раза из 6.

**Дыра не в надзоре, а в его политике сдачи.** `_client_watch_step`
(`pc_orchestrator.py:5419`): после `CLIENT_MAX_DEATHS=3` смертей подряд ставится
`halted=True`, и дальше ветка возвращает `"halted"` **навсегда** — сбросить флаг может только
`alive`, а живым процесс без подъёма не станет. Состояние лежит в RAM демона; демон в тот
раз не перезапускался (PID 6376 весь простой).

**Что это стоило числом:** 04.08 18:58:44Z вотчдог сдался, и бот пролежал до 05.08 00:50:31Z,
пока его не поднял руками разовый скрипт `tmp/rc-userbot-20260804-1958/raise_userbot.py`.
**370.6 минут из 479.8 за неделю (77 %) — это окно после сдачи вотчдога.**

* Что править: дать `halted` срок жизни (`CLIENT_HALT_TTL`) — по истечении вернуться к
  попыткам с обнулённым счётчиком.
* **Строк:** ~8 боевых (1 константа + ~5 в `_client_watch_step` + прокидывание параметра
  в `client_watchdog_tick`), плюс голдены в `test_pc_orchestrator.py` (~25–40).
* **Файлов:** `pc_orchestrator.py`, `test_pc_orchestrator.py`.
* **Замыкание импортов задевает?** **НЕТ.** `client_contour.is_client("pc_orchestrator.py") =
  False`; более того, `pc_orchestrator.py` и `pc_agent.py` стоят в `FOREIGN_ENTRIES` — обход
  замыкания на них СРЕЗАЕТСЯ. Ворота контура не срабатывают, self-update выкатит сам за ≤60 с.
* **Чего B не делает:** не отменяет падений. Бот по-прежнему умирает на каждом обрыве, но
  лежит ≤ детект(5 мин)+кулдаун(15 мин), а не 6 часов. Ожидаемо ~480 → ~120–150 мин/неделю.

**Есть и ручка без кода:** `PC_CLIENT_MAX_DEATHS` (`pc_orchestrator.py:134`, дефолт 3) —
поднять её значит править конфиг. Это красная зона, здесь не сделано и делать нечего:
она отодвигает сдачу, но не отменяет её.

**Рекомендация:** B сначала (не заморожен, выкатывается сам, снимает 77 % простоя), A потом
под основание владельца — только A убирает сами падения.
