    """ОДИН черновик по ПОЛНОМУ накопленному транскрипту (боевой пайплайн: прайс/зоны/generate).
    collected_facts и доставка считаются по всему окну диалога, а не по одному событию."""

    hints = suggest.extract_booking_hints(transcript)

    allow = suggest.park_allowlist()

    return trainer.strip_thai(draft or "")

## 2. Почему прогон из сессии послать НЕЛЬЗЯ — причина кодом

Пять замков, каждый достаточен сам по себе.

**Замок 1. Точки входа нет вообще.**

```
$ grep -n "__main__\|^def main\|argparse\|sys.argv" trainer.py trainer_log.py lesson_router.py
(пусто)
```

697 строк чистых функций. Вызвать «прогон» нечем: нет ни CLI, ни `main()`, ни разбора аргументов.

**Замок 2. Единственный приёмник — Telethon-событие, и он режет всё, что не живой человек.**
`userbot_listen.py:375–398`:

```python
    sender = await event.get_sender()
    if not isinstance(sender, User) or sender.bot:
        return  # только живые люди; модербот/каналы — не клиентские реплики
    if (sender.username or "").lower() in OWN_USERNAMES:
        return
    ...
    if int(chat_id) != int(bound):
        return  # строгая ИЗОЛЯЦИЯ: другая группа — не тренажёр
```

Сессия — не `User` с Telegram-апдейтом. Обойти «через Telegram» тоже нельзя: писать в группу
пришлось бы боевым аккаунтом, а `OWN_USERNAMES = {"turbophuket", "turbophuket1"}`
(`userbot_listen.py:53`) свои сообщения отбрасывает.

**Замок 3. Singleton-лок: второго клиента на сессии не поднять.** `userbot_listen.py:111` +
`main()` 460–461:

```python
    if not acquire_lock():
        return
```

Комментарий там же (57–59): «Главная страховка от ДВУХ клиентов на одной session
turbobaby_session (двойной клиент = риск бана)». Лок держит PID 1656 — проверено.

**Замок 4. Ответ уходит НАРУЖУ, а не возвращается вызывающему.**
`_trainer_client_turn` заканчивается `asyncio.create_task(_trainer_debounced_reply(...))`
(`userbot_listen.py:292`), а сам `_trainer_debounced_reply` ничего не возвращает — результат
существует только как сообщение в Telegram, значения в meta и строка в `KB_trainer_log`.
Ни кода выхода, ни возвращаемого объекта, ни файла результата.

**Замок 5. Состояние одно.** Прогон из сессии затёр бы живой ТЕСТ-11 (см. дамп выше): любой
`trainer.reset()` инкрементит N и чистит транскрипт владельца, а `bump_seq` инвалидирует его
отложенный ответ.

## 3. Что отдаёт на выходе и чего не хватает до «зелено/красно»

**Отдаёт:**
- текст ответа в группу: `render_answer(n, k, draft)` = `[тренажёр | ТЕСТ-N | правил: K]` + черновик + подсказка;
- 9 ключей состояния в meta (последняя пара клиент/бот доступна кросс-процессно);
- построчный лог прогона в мозг: `TRN … | TEST-N | client|bot|btn|lesson | текст`;
- **гипотезы** «что улучшить» — 2–4 строки прозы от LLM (`trainer.py:201–211`);
- решение по уроку: `apply_lesson` → `dict(axis='behavior'|'code', status, card, n)`.

**Чего не хватает — пять дыр:**

1. **Нет ожидания.** Ни одна функция не хранит, каким ответ ДОЛЖЕН быть. Единственная оценка —
   гипотезы, а их промпт требует: «Назови от 2 до 4 КОРОТКИХ гипотез, что в ОТВЕТЕ можно улучшить»
   (`trainer.py:206–209`). То есть даже на идеальном ответе будет 2–4 замечания. Это **генератор
   замечаний, а не судья**: pass/fail из него не выводится ни при какой обработке.
2. **Нет корпуса.** Один глобальный ТЕСТ-N, диалог набивается руками. Файла кейсов в репо нет
   (`ls *corpus*` → `No such file or directory`).
3. **Нет привязки к коммиту.** Ворота решают по `short(commit)` (7 hex, `client_contour.py:296`).
   В `trainer.py`/`trainer_log.py` слова «commit»/git нет ни разу — тренажёр не знает, какой код он
   прогнал.
4. **Нет машинного результата.** Ворота ждут файл; его не существует:
   `ls pc_orchestrator.client_trainer_green.json` → `No such file or directory`.
5. **Нет повторяемости.** `generate_draft` — живой LLM. Один прогон ничего не доказывает; ровно
   поэтому `test_golden_llm.py` (10 кейсов на реальном CLI) по умолчанию **пропущен**.

**Ворота говорят это сами** (`client_contour.py:342–349`) — дословно:

```python
def trainer_green(commit, path=None, env=None):
    """ВТОРОЕ основание — зелёный прогон через тренажёр. СЕЙЧАС ЭТО ЗАГЛУШКА, и вот почему честно:
    тренажёр «Тренеровка» связан с этим контуром в ОДНУ сторону — НАДЗОР-урок дописывает класс в
    `docs/revizor_checklist.md` (вход ревизора). Обратной связи «прогон зелёный → можно выкатывать»
    в коде нет: ни trainer.py, ни trainer_log.py, ни lesson_router.py не пишут никакого реестра
    прогонов. Поэтому основание ВЫКЛЮЧЕНО по умолчанию: без PC_TRAINER_GREEN=1 всегда False.
    Интерфейс заложен — когда тренажёр научится отдавать вердикт, он кладёт в TRAINER_GREEN_FILE
    {"green": {"<commit7>": {...}}}, и ворота откроются без правки ворот."""
```

Флаг выключен по факту, а не только по замыслу: `grep -c PC_TRAINER_GREEN .env` → `0`,
`os.getenv('PC_TRAINER_GREEN')` → `None`.

Владельцу это видно в карточке (`client_contour.py:378–379`): «зелёный прогон через тренажёр —
**СЕЙЧАС НЕДОСТУПЕН** (тренажёр вердикта не выдаёт)».

**Важный контрпример рядом.** «Прогон с двоичным вердиктом» в репо УЖЕ есть — но не у тренажёра:
`suggest.runLiveSmoke` + `pc_orchestrator._exec_smoke_step()` (2485–2506) → `('done'|'failed', карточка)`,
запускается `run_chain_smoke.py` с кодом выхода 0/1. Он проверяет шесть инвариантов транспорта
(`suggest.py:6296–6304`). Использовать его как есть нельзя: он **сидит на `SUGGEST_TEST_MODE`**
(`suggest.py:6536–6538`, вне TEST_MODE → `skipped`) и шлёт пробу в тестовое окно Telegram — а
TEST_MODE у нас граница, его не трогаем. Но его **набор чеков** — готовый образец для вердикта.

## ЧАСТЬ 2 — предложение (не реализовано)

### 4. Два варианта

#### Вариант А — безголовый раннер по корпусу, ВНЕ живого процесса

Новый файл (напр. `trainer_run.py`) + корпус (`trainer_cases.json`). Раннер: держит **своё**
состояние через уже существующий шов инъекции (`get`/`set` параметры есть у всех функций
`trainer.py`; `test_trainer.py` этим шовом пользуется в 73 тестах), гоняет кейсы через тот же
`suggest.generate_draft`, проверяет чеки, печатает вердикт, пишет `{"green": {"<commit7>": {…}}}`.

Плюс, которого нет у Б: **новый файл НЕ попадает в клиентский контур** — замыкание считается от
`userbot_listen.py`/`moderation_bot.py`, а его никто не импортит. Значит раннер можно писать и
переписывать сколько нужно, **не упираясь в ворота**.

Минусы честно:
- **Дубль пайплайна.** `_trainer_generate` останется в userbot, раннер её скопирует — два
  экземпляра логики, которые разъедутся. Это ровно правило-класс «мок обязан копировать живой
  формат», только наизнанку: раннер зелёный, живой userbot уже другой. Лечится лишь выносом общей
  функции — а это правка `userbot_listen.py`, то есть клиентский контур и своя же карточка ворот.
- **LLM недетерминирован и платный.** 12 кейсов × `generate_draft` — минуты и токены на каждый
  коммит; вердикт может флапать. `test_golden_llm` по этой причине выключен по умолчанию.
- **Не проверяет доставку.** Рендер шапки, дебаунс, токен `seq`, кнопки модербота — вне покрытия.
  «Зелено» будет про черновик, а не про то, что владелец увидит в группе.
- **Корпуса нет** — заводить с нуля.
- **Новая власть у файла.** Кто может писать `pc_orchestrator.client_trainer_green.json`, тот
  открывает клиентские ворота в обход «да» владельца. Пока корпусу нет доверия, `PC_TRAINER_GREEN`
  обязан остаться выключенным.

#### Вариант Б — рычаг внутри живого процесса: команда «прогон» в группе

`parse_command` уже разбирает 4 команды (`trainer.py:102–125`); добавить пятую — «прогон». Она
гоняет корпус тем же `_trainer_generate` внутри userbot, постит таблицу результатов в группу и
пишет green-файл.

Плюс: проверяется **ровно тот код и тот процесс**, который отвечает клиентам, — никакого дубля.

Минусы честно:
- **Правка идёт ровно в клиентский контур.** `trainer.py` и `userbot_listen.py` — оба в замыкании
  (12 модулей на HEAD). Курица-яйцо: чтобы ворота умели открываться тренажёром, первую же такую
  правку придётся протащить через ворота вручную, по «да».
- **Прогон блокирует живой диалог.** `_TRAINER_LOCK` сериализует генерацию (`userbot_listen.py:234`):
  12 кейсов × 30–60 с держат лок, владелец в группе в это время не работает, а его отложенные
  ответы устареют по `seq`.
- **Риск для боевого процесса.** Ошибка в раннере падает внутрь процесса, который в том же
  `on_incoming` обслуживает **реальных** клиентов в ЛС.
- **Нужен отдельный namespace состояния.** Иначе прогон затрёт ТЕСТ-11 (seq=24).

**Рекомендация: А** — единственный вариант, который сам не упирается в ворота, которые он призван
открывать; риска для боевого процесса нет. Дубль пайплайна закрывать отдельной задачей (вынос
общей функции — уже по «да», один раз).

### 5. Что считать зелёным вердиктом

**Корпус: 12 кейсов, каждый — ДОСЛОВНАЯ фраза живого клиента** (правило-класс CLAUDE.md: голдены
детекта = реальные фразы). Источники в репо уже есть: `KB_trainer_log` (ТЕСТ-1…11 — живые прогоны
владельца), инцидент #51, проба `runLiveSmoke`, кейсы `test_golden_llm` A.2/A.3.

| # | Кейс | Что ловит |
|---|---|---|
| 1 | первый контакт, одна модель | приветствие ровно один раз |
| 2 | «Какие марки и модели… какие цены на аренду…» (дословно, #51) | прайс-интент «все модели» |
| 3 | модель + даты + гео-пин Раваи | доставка = 590, не `[уточнить]` |
| 4 | только про депозит | контрпример прайса (не вываливать прайс) |
| 5 | новичок + мощный байк (A.3) | нет СВОЕЙ оценки безопасности, уводит к менеджеру |
| 6 | опыт не упомянут (A.2) | мягкий вопрос про опыт |
| 7 | месяц+ | кап месячного тарифа |
| 8 | EN-клиент | язык ответа = язык клиента |
| 9 | фото паспорта маркером | засчитано трекером |
| 10 | один день | суточный тариф, не ошибка |
| 11 | «есть ли в наличии?» без данных Bridge | нет УТВЕРЖДЕНИЙ о наличии |
| 12 | тайский в выводе | `strip_thai` отработал, ฿ сохранён |

**Проверяется машинно** (инварианты уже сформулированы в `suggest.py:6299–6304` — берём их же):
строка столбца J дословно · доставка = цена зоны · год поколения 20xx не утёк в тело · нет
отписки «вернусь» при полных данных · нет утверждений о наличии без Bridge · депозит без
самопротиворечия · тайских букв нет · язык совпал · приветствие один раз.

**Зелёный = 12 из 12 прошли ВСЕ применимые чеки. Ноль провалов.** Не «11 из 12», не средний балл:
ворота двоичные, а частичный зелёный на клиентском контуре означает «выкатываем текст, про который
знаем, что один кейс красный». Плюс два условия честности:

- **тот же коммит:** `git rev-parse HEAD` на момент прогона обязан совпасть с `short(commit)` в
  green-файле — иначе зелень удостоверяет другой код;
- **flake-контроль:** генератор недетерминирован → кейс зачтён при **2 прогонах из 2**. Это удваивает
  цену — честная цена за право не спрашивать владельца.
- Провал любого чека → green-файл **не пишется** (fail-closed, как везде в воротах).

## Остатки / точки касания

- Дубль `_trainer_generate` (вариант А) — отдельная задача на вынос общей функции, идёт по «да».
- `PC_TRAINER_GREEN` держать выключенным до первого доверенного прогона на полном корпусе.
- `lesson_router.py` клиентский по графу, но в `_FILE_PROCESS_RULES` его нет (класс dae330a,
  записан в остатки артефакта `2026-07-30-client-contour-gates.md`) — на раннер не влияет.
