## 1. Место, где решается право на запись правила — дословно

Цепочка от кнопки до записи, три файла:

| шаг | место | что делает |
|---|---|---|
| кнопка | `moderation_bot.py:98` | `InlineKeyboardButton("📌 Запомнить как правило", callback_data="m:{id}:remember")` |
| маршрут | `moderation_bot.py:494` | `if action == "remember": dec = moderation_core.remember_rule(draft, username)` |
| **право** | **`moderation_core.py:489`** | **`if not suggest.is_approver(username): return {"decision": "denied", …}`** |
| запись | `suggest.py:742` `append_playbook_rule` | открывает `PLAYBOOK_FILE` на `"w"` и пишет — В ТОМ ЖЕ ВЫЗОВЕ |

Сама проверка права — `suggest.py:1719-1723`, дословно:

```python
def is_approver(username) -> bool:
    """Есть ли право approve/edit/reject. Пустой whitelist = можно любому."""
    if not APPROVER_USERNAMES:
        return True
    return (username or "").lstrip("@").lower() in APPROVER_USERNAMES
```

**Что она делает при пустом списке: возвращает `True` безусловно, до всякого сравнения с
именем.** Это не побочный эффект и не недосмотр — поведение объявлено в собственной строке
документации функции («Пустой whitelist = можно любому») и продублировано комментарием у
объявления списка, `suggest.py:90`: «Право approve/edit/reject. ПУСТОЙ список = любой участник
группы может approve». То есть fail-**open** заведён сознательно, вопрос только в том, какие
операции под него попали.

### Главное: гейт у «одобрить» и у «записать правило» — ОДИН И ТОТ ЖЕ

Не похожий, не аналогичный — тот же вызов той же функции по тому же списку:

| операция | место | гейт |
|---|---|---|
| approve / reject / send / more (кнопки) | `moderation_core.py:135` | `suggest.is_approver(username)` |
| свободная правка ответа реплаем | `moderation_core.py:232` | `suggest.is_approver(username)` |
| **запись правила в книгу** | **`moderation_core.py:489`** | **`suggest.is_approver(username)`** |

Никакой дополнительной проверки у третьей строки нет ни одной. Формулировка аудита «право
модерировать ответ автоматически даёт право учить бота» — **буквально верна**: это не следствие
и не вывод, это одна и та же строка кода в трёх местах.

### Асимметрия, которой аудит не заметил: писать книгу ЛЕГЧЕ, чем читать

В том же файле живёт вторая, СТРОГАЯ проверка `is_intake_approver` (`suggest.py:1726-1732`).
Ею закрыты:

| операция | место | гейт |
|---|---|---|
| посмотреть книгу `/rules` | `moderation_core.py:398` | `is_intake_approver` (строгий) |
| **удалить** правило из книги | `moderation_core.py:439` | `is_intake_approver` (строгий) |
| перехват реплая-правки/урока (intake) | `moderation_core.py:295` | `is_intake_approver` (строгий) |
| **добавить** правило в книгу | `moderation_core.py:489` | `is_approver` (**слабый**) |

Показать книгу и убрать из неё правило — строгое право; **дописать в неё — слабое.** Опечатка
эта или решение, из кода не следует, но следствие однозначно: набор людей, способных положить
правило, ШИРЕ набора, способного это правило увидеть и снять. Записавший может не иметь права
посмотреть, что записал.

### Почему подмена гейта на строгий НИЧЕГО не изменила бы живьём

`is_intake_approver` при пустом своём списке падает в фолбэк:

```python
if not INTAKE_APPROVERS:
    return is_approver(username)
```

а живой `INTAKE_APPROVERS` **пуст (0 записей, см. §3)**. Значит «строгая» проверка сегодня
тождественна слабой, и правка `is_approver` → `is_intake_approver` в `remember_rule` дала бы
ноль изменений поведения. Это ловушка минимальной правки, и она разобрана в §6.

## 2. Как мерилось живое состояние и почему голый импорт солгал бы

`suggest.py` читает списки через `os.getenv` НА ИМПОРТЕ (`_csv_set`, строки 84-97), но сам
`.env` **не загружает**. Загрузку делает точка входа — `moderation_bot.py:27-31`:

```python
from dotenv import load_dotenv
load_dotenv()
import suggest            # noqa: E402  (после load_dotenv — читает конфиг из окружения)
```

**Отсюда готовый ложный замер:** любой скрипт, который просто делает `import suggest` без
предварительного `load_dotenv()`, получит `APPROVER_USERNAMES == set()` — пустое множество — и
честно отрапортует «список пуст, дыра открыта». Это был бы вывод об окружении скрипта, а не о
проде. Проба повторяет живую последовательность дословно: `load_dotenv()` → `import suggest`.

Замерочный скрипт: `_scratch_live_rules_rights_0905/probe_rights.py` (временное живёт там и
больше нигде). Что в нём сделано ради безопасности:

* книга правил — **подставная**, `_scratch_live_rules_rights_0905/playbook_fake.md`;
* живая книга `manager-bot/docs/playbook.md` только **статится** (размер+mtime до и после) как
  доказательство нетронутости;
* списки прав подменяются **в памяти процесса**; `.env` не правится и не читается глазами —
  печатаются ТОЛЬКО «пуст/не пуст» и число записей, значения не выводятся ни разу;
* `TESTING=1` ставится ДО импорта — боевой IPC недоступен по построению;
* дистилляция инъектируется заглушкой → **ни одного вызова LLM и ни одного сетевого запроса**;
* ни одной карточки никуда не отправлено.

## 4. Премиса аудита — четыре пункта, три исхода каждый

### Пункт 1. «На карточке есть действие, записывающее правило в книгу без промежуточного кандидата» — **ПОДТВЕРЖДЕНО**

`remember_rule` (`moderation_core.py:485-511`) в одном вызове: проверяет право → дистиллирует
директиву → зовёт `appender`, по умолчанию `suggest.append_playbook_rule`. Тот открывает
`PLAYBOOK_FILE` на `"w"` и пишет (`suggest.py:782-785`). Между нажатием и файлом нет ни очереди,
ни кандидата, ни второго подтверждения, ни отката. Возвращаемые исходы —
`remembered | duplicate | not_saved | denied | no_directive`; «на рассмотрении» среди них нет.

Отдельно: правило попадает В КАЖДЫЙ последующий промпт — книга подмешивается в генерацию, и в
`append_playbook_rule` заведено FIFO-вытеснение по `PLAYBOOK_MAX_RULES` (100). То есть запись
не только мгновенна, но и **вытесняет** самые ранние правила при переполнении.

### Пункт 2. «Пустой список разрешённых трактуется как разрешено любому» — **ПОДТВЕРЖДЕНО как механизм, ОПРОВЕРГНУТО как текущее состояние**

Механизм — дословный `if not APPROVER_USERNAMES: return True` (§1), поведение показано числом
в §5, проба 1. Текущее состояние — список не пуст, 5 записей (§3). **Дыра латентна: она
открывается опустошением одной переменной окружения, а не изменением кода.** Опустошить её
может очистка/переименование ключа, выкладка без него, запуск из каталога без `.env` — во всех
трёх случаях книга становится общедоступной на запись МОЛЧА, без единой строки в логе.

### Пункт 3. «Атомарный claim_decision описан, но не подключён; старые карточки с живыми кнопками остаются» — **ПОДТВЕРЖДЕНО (обе половины)**

Первая половина. `claim_decision` существует и полноценен — `moderation_ipc.py:264-285`, UPDATE
с предусловием по статусу внутри СУБД, возвращает `(взял?, строка)`. Зовётся он ровно из одного
места: `moderation_card.py:439`. А `moderation_card.py` импортируется только `dialog_card.py` и
двумя тестами — **`moderation_bot.py` его не импортирует вовсе** (его импорты: `suggest`,
`moderation_core`, `moderation_ipc`, `booking_draft`, `trainer`, `trainer_log`, `proc_identity`).
Модуль сам это и объявляет в своей шапке: «он не постит карточку в Telegram и не рисует кнопки
— это работа `moderation_bot`, которого этот заход НЕ трогает». Итог: в боевом пути кнопки
атомарного захвата нет.

Вторая половина. В `remember_rule` **проверки статуса черновика нет ни одной** — ни `status`, ни
`decided_by`, ни возраста. Единственный отсев в `on_callback` — `if draft is None: return`, то
есть «строка ещё существует в базе». Показано числом в §5, проба 2.

Уточнение, важное для правки: `claim_decision` закрывает РЕШЕНИЕ по черновику
(`ready|test_held|rejected`) и правом на запись правила не распоряжается — он не является
готовым замком для этой кнопки (см. §6).

### Пункт 4. «Сейчас TEST_MODE включён и контур заморожен — поэтому ущерба ещё не было» — **ОПРОВЕРГНУТО В МЕХАНИЗМЕ** (вывод верен, причина названа неверно)

`SUGGEST_TEST_MODE=True` — да, замерено (§3). Но `test_mode` передаётся ТОЛЬКО в
`process_callback` (`moderation_bot.py:496-497`), а ветка «remember» зовётся строкой выше:

```python
if action == "remember":     # 📌 захват правки в playbook (Фаза 2) — approver-гейт внутри
    dec = moderation_core.remember_rule(draft, username)
else:
    dec = moderation_core.process_callback(draft, action, username, suggest.SUGGEST_TEST_MODE, …)
```

У `remember_rule` параметра `test_mode` нет в сигнатуре вовсе. **Заморозка контура запись
правил не сдерживает: TEST_MODE запрещает отправку КЛИЕНТУ, а книгу правил кнопка пишет
одинаково в любом режиме.** Значит «ущерба не было» держится не на заморозке, а исключительно
на непустом списке из 5 записей. Снимут заморозку — в защите не изменится ничего; опустеет
список при живой заморозке — защиты не останется никакой.

## 5. Отрицательные пробы — числом, а не мнением

Все четыре — на подставной книге и подставном списке прав, в одном процессе, LLM не вызывался.
«bullets» — число правил в секции «## Выученные правила» подставной книги.

| # | что нажимаем | список | исход | bullets |
|---|---|---|---|---|
| **0** | контроль: посторонний, список НЕ пуст (1 запись) | не пуст | `denied` «⛔ Нет прав на запись правил» | 0 |
| **1** | **ГЛАВНАЯ: посторонний, список ПУСТ** | **пуст** | **`remembered`** | **0 → 1** |
| **2** | СТАРАЯ карточка: `status=sent`, `decided_by` уже стоит | пуст | `remembered` | 0 → 1 |
| **3** | повторный клик по той же кнопке | пуст | 1-й `remembered`, 2-й `duplicate` | 1 → 1 |
| **4** | пустая директива | пуст | `no_directive` | 0 |

**Проба 0 (контроль) обязательна и не декоративна:** она показывает, что гейт РАБОТАЕТ, когда
список настроен, — то есть проба 1 меряет именно пустоту списка, а не сломанную функцию.

**Проба 1 — предмет задания.** Пользователя `postoronniy_0905` в списке нет и быть не может;
при пустом списке правило записалось в книгу: было 0 правил, стало 1, карточка ответила
«📌 Записано в правила: …». **Заявка аудита подтверждена числом.**

**Проба 2 — старая карточка.** Черновик со статусом `sent` и уже проставленным `decided_by`
(повод закрыт, ответ клиенту отправлен) записал правило так же успешно: 0 → 1. Ни статус, ни
факт закрытия карточку не гасят. Практический смысл: карточка недельной давности, пролистанная
в истории группы, остаётся рабочей кнопкой записи в книгу.

**Проба 3 — повторный клик: ОДНА запись, не две.** Второй клик вернул `duplicate`, число правил
осталось 1. Защита здесь есть, но лежит НЕ в правах и НЕ в статусе, а в дедупликации по
похожести текста внутри `append_playbook_rule` (`_rules_similar`). Из этого следует граница:
дедуп спасает от точного повтора и не спасает от двух РАЗНЫХ правил, записанных с одной старой
карточки, — а также, что важнее, вторая запись не отвергается по праву, она отвергается по
тексту.

**Проба 4** — пустая директива отсекается до записи (`no_directive`), книга не трогается.

**Живая книга не пострадала:** `(5045, 1784744786)` до и после — размер и mtime совпадают.

### Почему набор тестов это не ловил

`test_moderation.py:445` (класс фазы 2) в `setUp` делает **`suggest.APPROVER_USERNAMES = set()`**
— то есть весь класс гоняется с ПУСТЫМ списком, и `test_remember_approver_appends` ожидает
`remembered`. Тест на отказ `test_remember_nonapprover_denied` существует, но он сам ставит
список непустым. Итог: набор проверяет «непустой список → отказ постороннему» и «пустой список
→ запись», и **второе зафиксировано как ПРАВИЛЬНОЕ поведение**. Теста, который требовал бы
отказа при пустом списке, нет ни одного — поэтому дыра зелёная и переживёт любой рефакторинг.

## 6. Каким МИНИМАЛЬНЫМ изменением закрывается (названо, НЕ сделано)

Три правки, по убыванию отношения «эффект / риск». Ни одна здесь не выполнена — код клиентского
контура задание править запрещает.

**Правка A — «пустой список даёт отказ», локально в точке записи. Обязательная.**
В `remember_rule` (`moderation_core.py:489`) заменить проверку на fail-**closed**:
право на запись правила выдаётся, только если список НЕПУСТ и имя в нём.
Ключевое — **править надо `remember_rule`, а не `is_approver`**: у `is_approver` радиус
поражения — все кнопки approve/reject/send и правка ответа, и разворот его в fail-closed при
пустом списке обездвижит модерацию целиком. Правка в одной точке записи трогает одну операцию.
Оговорка из §1: замена `is_approver` → `is_intake_approver` **сама по себе не годится** — при
живом пустом `INTAKE_APPROVERS` (0 записей) она уходит в фолбэк на тот же `is_approver` и не
меняет ничего. Нужен явный отказ на пустоте, а не смена имени функции.

**Правка B — «правка ответа и кандидат правила — разные операции».**
Кнопка «Запомнить как правило» должна писать КАНДИДАТА, а перевод кандидата в книгу — отдельное
действие под строгим правом. Это же снимает и асимметрию §1 (писать легче, чем читать).

**Правка C — статус карточки как предусловие** (закрывает пробу 2): действие «remember»
разрешать только на незакрытой карточке.

### Пригодны ли уже подготовленные `lesson_store` и `claim_decision`

**`lesson_store` — ПРИГОДЕН, и он ровно то, чего не хватает правке B.** У него шесть
обязательных полей на запись (вопрос клиента, что ответил бот, как правильно, ПОЧЕМУ, кто
записал, когда), свой номер, состояние и `withdraw()` — то есть у каждой записи есть автор,
время, причина и штатный откат, а у строки в книге правил нет ничего, кроме текста и даты.
Публичный API готов: `add(question, bot_answer, correct, why, who, when=…)` → номер;
`active()`, `by_author()`, `by_day()`, `withdraw()`, `capacity()`, `integrity()`. Модуль
намеренно не подключён («бот сюда не ходит НИ ОДНОЙ веткой… шаг 1 строит хранилище, участие
бота это отдельный шаг»), и это не дефект, а объявленная граница. Оговорка: `add()` требует
непустого «почему» и бросает `LessonRejected` — у кнопки такого поля сейчас нет, его придётся
либо спрашивать, либо заполнять формулировкой модератора; это работа, а не переключатель.

**`claim_decision` — ПРИГОДЕН ПО ПРИЁМУ, НЕ ПРИГОДЕН КАК ЕСТЬ.** Его предмет — статус строки
`drafts` и захват РЕШЕНИЯ первым ответившим (`ready|test_held|rejected`); правом на запись
правила он не распоряжается и вызывать его из «remember» бессмысленно — «запомнить» не является
решением по черновику и не должно закрывать карточку. Ценен именно приём, названный в его же
комментарии: предусловие проверяет САМА СУБД внутри одного UPDATE, потому что проверка на
Python оставляет окно между «посмотрел статус» и «записал», а нажатие и гашение идут из разных
процессов. Для правки C нужен тот же приём (предусловие по статусу), а не этот вызов.
Побочно: подключение `moderation_card` в боевой путь — отдельная задача с иным радиусом, и
смешивать её с закрытием этой дыры не следует.

## 8. Тестов живого набора сверх своих не гонялось — учёт числом

Пункт 8 задания — ограничение, а не действие, и «мы его соблюли» на слово не принимается.
Ниже учёт по ВНЕШНЕМУ журналу, который ведёт гард, а не заход: `pretool_guard.log`.

**Что считалось своим.** `_scratch_live_rules_rights_0905/probe_rights.py` — **ровно 1 запуск**,
`05.09 14:40:37`, пять проб внутри одного процесса. Частью набора он не является: грепом по
файлу имена `unittest`/`pytest` дают **0 совпадений** — это скрипт с `print`, а не тест-кейс.

**Что было бы «полным набором полосы».** 90 файлов `test_*.py` в корне репозитория, **5964**
строки `def test_` (счёт статический, грепом; ни один файл набора не импортировался).

**Учёт по журналу гарда**, окно задания `14:37:33 → 14:56:33` (обе попытки дожима), 52 строки:

| что | число |
|---|---|
| запусков набора в окне (`pytest`, `unittest`, раннер) | **0** |
| строк окна, где слова `pytest`/`unittest` вообще встречаются | 7 — и все 7 это собственные `grep`/`ls` ПРО эти слова, а не вызовы |
| строк окна, упоминающих файлы набора | 3 — все три **чтение** (`sed`/`grep` по `test_moderation.py`), исполнения нет ни одного |
| фон: упоминаний набора за 05.09 по ВСЕЙ полосе, все заходы | 352 (запуски и чтения не разделены) |

Фоновая строка нужна, чтобы ноль не читался как «набор тут никто не гоняет»: полоса гоняет
его весь день, ноль в нашем окне — сдержанность этого захода.

**Следствие для §5, и это честная граница.** Абзац «Почему набор тестов это не ловил» получен
**чтением** `test_moderation.py` (две команды `sed` в 14:41:40 и 14:41:58 — строки 445-470 и
470-520), а НЕ прогоном. Утверждение «теста, который требовал бы отказа при пустом списке, нет
ни одного» держится на прочитанном исходнике, а не на зелёном/красном прогоне, и так и должно
читаться.

**Почему п.8 здесь не гигиена, а защита самого замера.** `TestRememberRule.setUp`
(`test_moderation.py:447-449`) делает `suggest.APPROVER_USERNAMES = set()` — обнуляет ровно тот
список, пустоту которого меряет это задание. `tearDown` его возвращает, и прод не страдает,
потому что набор идёт своим процессом. Но если бы замер прав жил в ОДНОМ процессе с этим
классом, §3 прочитал бы «пуст=True, записей=0», и заявка аудита подтвердилась бы **ложно** —
набор изготовил бы ту самую дыру, которую мы ищем. Поэтому проба вынесена в отдельный процесс и
списка не заимствует ни у одного теста.

**Отвергнутая улика — чтобы её не предъявил следующий заход.** Соблазн доказывать «не гонялось»
датами `__pycache__`: `test_moderation.cpython-312.pyc` = 31.08 03:34, «значит с 31.08 не
запускался». **Неверно:** mtime у `.pyc` — время КОМПИЛЯЦИИ (первый импорт после правки
исходника), а прогон по готовому кэшу его не двигает вовсе. Контрпример замерен здесь же:
`suggest.cpython-312.pyc` = 05.09 **14:16:37**, тогда как своя проба импортировала `suggest` в
**14:40:37** — штамп принадлежит ЧУЖОМУ заходу, не ей. Кэш не доказывает ни запуска, ни его
отсутствия; доказывает журнал гарда.

Итог пункта: **полный набор полосы не гнался ни разу**, живого набора сверх своей единственной
пробы не исполнялось, и выводы §1-§7 от этого не зависят — они получены чтением кода и одной
собственной пробой на подставных данных.
