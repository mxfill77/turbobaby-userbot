# Ложная тревога прибора оборота (О2) 17.08 19:15 UTC: прибор читает ЧУЖУЮ отметку вместо идущей работы

**Разведка read-only, 18.08.2026.** Кода не правили, процессов не трогали, ничего не удаляли,
гейт не гоняли, в мозг не писали. Временное — `_scratch_falsealarm_0818/` (`probe.py` … `probe4.py`).

## Итог в четырёх строках

1. О2 крикнула «демон ПК не даёт оборота» ровно в ту минуту, когда демон **синхронно исполнял
   задачу 40** (взята 18:58:01, сдана 19:37:26, 2365 с при потолке 2700 — штатно, `outcome=done`).
2. Молчание оборота обязан был оправдать штамп занятости. Прибор берёт из штампа **поле `at`**, а
   `at` для задачи 40 **не обновился**: ключ `"40"` уже лежал в реестре с 15.08 — **id очереди
   переиспользуются**, и `_task_started_mark` вернулся рано (`if key in st: return`).
3. Самой свежей отметкой `at` в реестре осталась задача **34, закрытая тремя часами раньше**
   (475 с, `done`, тело отчёта на диске). Её и назвали «идущим заходом, переросшим срок».
4. **Сторож самого демона в ту же минуту ответил верно** — потому что читает ТОТ ЖЕ ФАЙЛ по
   `st_mtime`, а не по полю `at`. Разрыв между двумя прочтениями одного файла на момент замера —
   **3.70 часа**.

Тревога не одна: реплей живым кодом даёт **4 таких тревоги за всю жизнь наблюдателя, ложных 4 из
4**. Пятая **предсказана заранее и сбылась в 20:24:29 UTC — во время этой самой разведки**, тем
самым ключом эпизода, который был напечатан за девять минут до события (§9). Верных тревог у О2
за всю её жизнь — **ноль**.

## 1. Что прибор считает оборотом и откуда берёт время последнего

**Оборот = один виток `poll_once`.** Предмет назван дословно в докстринге
`expectations_pc.turn_state` (`expectations_pc.py:507`):

> «Судит ПРОДУКТ демона — оборот `poll_once`, а не признак жизни.»

**Источник времени — файл `pc_orchestrator.heartbeat`**, и ничто другое:

* читает `expectations_pc_run.heartbeat_facts` (`expectations_pc_run.py:150-162`) —
  `open(HEARTBEAT_FILE).read().strip()`, где `HEARTBEAT_FILE = os.path.join(REPO,
  "pc_orchestrator.heartbeat")` (`expectations_pc_run.py:80`);
* разбирает `turn_state` (`expectations_pc.py:537`): `ts = parse_iso(hb.get("raw"))`;
* пишет ровно один писатель — `pc_orchestrator._write_heartbeat()` (`pc_orchestrator.py:966-971`),
  одной строкой ISO-времени, и зовётся он **ровно один раз и последней строкой `poll_once`**
  (`pc_orchestrator.py:3755`, единственный вызов во всём файле).

Живой файл на момент замера — 32 байта, одна строка:

```
2026-08-17T20:04:17.037191+00:00
```

Порог — `EXPECT_PC_TURN_MIN`, дефолт **20 минут** (`expectations_pc.py:301`).
Сравнивается **не** возраст файла, а НАКОПЛЕННАЯ тишина бодрствования
(`expectations_pc_run.update_silence`): сон ПК в счёт не идёт. В этом эпизоде сон = 0, поэтому
стенной возраст и тишина совпали.

## 2. Знает ли прибор, что идёт работа

**Формально знает — у него в руках БЫЛО ДВА живых признака работы, и он не посмотрел ни на один.**

### Признак, который он смотрит, но читает не тем полем

`turn_state` спрашивает штамп занятости ДО измеренной тишины (`expectations_pc.py:547-554`), и это
правильный порядок. Штамп собирает `expectations_pc_run.busy_facts` (`:295-319`), и его собственный
докстринг обещает «отметку CLAIM»:

```python
298	    Читаем реестр отметок CLAIM (`pc_orchestrator.task_started.json`) и берём САМУЮ СВЕЖУЮ.
...
310	    for tid, val in d.items():
311	        raw = val.get("at") if isinstance(val, dict) else val
312	        ts = ex.parse_iso(raw)
...
319	    return {"task": best_id, "since": best, "limit": ex.TASK_TIMEOUT_SEC}
```

`os.stat` здесь нет: файл открывается, читается как JSON, и «самая свежая» ищется **по полю `at`**.
А `at` для повторно взятого id не обновляется никогда — см. §5.

### Признак, который смотрит сторож ДЕМОНА на том же файле

`pc_orchestrator._wd_busy_age` (`pc_orchestrator.py:8853-8871`) — **тот же файл, один `os.stat`**:

```python

8866	    except Exception:
8867	        return None
8868	    if product_ts is not None and mt <= float(product_ts):
8869	        return None

```

Реестр переписывается **на КАЖДОМ спавне headless** — `_task_started_child` (`:1155-1169`) кладёт
PID ребёнка и зовёт `_task_started_write`. Поле `at` она сохраняет, а **mtime обновляет**. Замер,
разрыв 7 мс:

```

7149:2026-08-18 03:06:02,395 INFO RUN id=41 (timeout=2700s, попытка 1/2)

mtime реестра отметок:
2026-08-18 03:06:02.402896300 +0700  pc_orchestrator.task_started.json
```

**Чего стоит прочитать этот признак: ровно один `os.stat` на файле, который прибор УЖЕ открывает.**
Ни новой пробы процессов, ни второго источника, ни сети. Плюс одно условие честности, уже
написанное у соседа: отметка оправдывает молчание, **только если она позже последнего оборота**
(`:8868`) — иначе след давно закрытой задачи вечно выдавал бы стоящий демон за работающий.

Расхождение двух прочтений одного файла на момент замера (`probe.py`):

```

самая свежая ОТМЕТКА `at`: id=34 at=2026-08-17T16:24:16.926550+00:00
```

### Второй живой признак, лежавший в том же словаре фактов

`snapshot()` кладёт в `facts["queue"]` снимок открытых строк полосы (`expectations_pc_run.py:576`),
и на тик тревоги в нём была строка задачи 40 со статусом `in_progress`. `turn_state` **к
`facts["queue"]` не обращается ни одной строкой** — `_rows(facts)` (`expectations_pc.py:413-418`)
зовут только О1 и `closures`. То есть прибор держал в руке прямое «работа идёт» и не спросил его.

**Итог §2:** прибор не «не знал» — он спросил не то поле и не заглянул в соседний ключ фактов.

## 3. Отрицательный тест: есть, но мимо этого случая

Отрицательные тесты О2 в `test_expectations_pc.py` есть, и они прямо про «идёт долгая законная
работа» — например `TestO2Turn.test_declared_pass_answers_even_when_silence_is_not_measured`
(`:162-175`), чей докстринг ссылается на живой случай 11.08 с задачей 469.

**Но случай 17.08 они не покрывают, и вот три дыры, каждая названа прямо:**

1. **Ни одна фикстура не разводит «задача в штампе» и «задача в работе».** Во всех пяти фикстурах
   с `busy` (строки 158, 169, 180, 190, 779) штамп принадлежит ТОЙ ЖЕ задаче, которая якобы идёт, а
   очередь пуста (`facts(rows=None)` → `"rows": []`). Фикстуры «штамп задачи X, а исполняется Y»
   нет ни одной. Ровно её отсутствие и пропустило дефект.
2. **Тест `busy_facts()` ровно один, и в нём порядок «правильный».**
   `TestLiveFormat.test_busy_stamp_reads_the_live_registry_shape` (`:440-452`) кормит реестр из трёх
   записей, где самая свежая `at` принадлежит работающей задаче 469. Реестра с ПЕРЕВЁРНУТЫМ
   порядком — закрытая задача свежее работающей — нет.
3. **Сквозной путь заглушён.** `TestRunHands.setUp` (`:360-361`) делает
   `run_mod.busy_facts = lambda path=None: None`, то есть ни один интеграционный тест не гоняет
   связку «реестр → `busy_facts` → `busy_state` → `turn_state`» целиком.

Сверх того: **сама `busy_state` не имеет ни одного прямого теста** (грепа `busy_state` по тест-файлу
— ноль совпадений), а максимальный возраст захода, который где-либо утверждён как `TURN_OK`, —
**1900 с** (`:158`). Полоса 1900…3300 с не покрыта вовсе.

Наконец, ранний возврат `_task_started_mark` **закреплён тестом как правильное поведение** —
`test_pc_orchestrator.py:4429-4434 test_start_mark_not_overwritten` дважды клеймит id 8 в разные
даты и требует, чтобы отметка НЕ обновилась. Посылка теста («у одобренной задачи работа шла в
ПЕРВОМ прогоне») верна; неверно то, что она молча распространилась на **повторно выданный id**.

## 5. Что за счётчик даёт «34». Имя поля в коде

**Это НЕ номер headless-захода и НЕ счётчик прибора. Это id строки очереди — но не той, что идёт,
а той, чья отметка оказалась самой свежей в реестре.** Цепочка имён, снизу вверх:

| где | имя | что это |
|---|---|---|

### Одна запись — три разные реальности

Нагляднее всего это видно на отметке ТЕКУЩЕЙ задачи. Живой замер, обе записи из боевого файла:

```
41 -> {"at": "2026-08-15T17:47:01.757911+00:00", "pid": 21216, "proc": "21216-1786723500", "child": 22100}
34 -> {"at": "2026-08-17T16:24:16.926550+00:00", "pid": 5540, "proc": "5540-1786975731", "child": 15580}
```

Запись `"41"` — это **три разных момента времени в одном словаре**:

* `at` — 15.08, задача с этим номером, закрытая трое суток назад;
* `pid`/`proc` — `21216-1786723500`, экземпляр демона, которого в системе давно нет;
* `child` — **22100, ЖИВОЙ процесс, исполняющий эту самую разведку** (спавн 17.08 20:06:02 UTC,
  подтверждён пробой в §6).

`_task_started_child` переписала одно поле из четырёх и обновила mtime; три остальных остались от
15.08. **Прибор читает единственное поле, которое НЕ обновляется, — `at`.** Сторож демона читает
mtime, то есть ровно тот факт, который эта же запись и породила.

## 7. Почему не сработал собственный убийца по объявленному сроку

**В этом эпизоде — потому что убивать было некого.** Единственный настоящий заход, шедший в ту
минуту (задача 40), прожил 2365 с при потолке 2700 с и закрылся сам, `outcome=done`. Заход 34 к
тому моменту был закрыт почти три часа. Фраза «свой kill не сработал» — не второе наблюдение, а
**второе следствие той же ошибки**: она печатается автоматически всякий раз, когда штамп перерос
свой срок (`expectations_pc.py:1107-1112`), и о работе убийцы не спрашивает никого.

Устройство убийцы, чтобы его не искали не там:

* **Где живёт.** `pc_orchestrator.run_claude` (`:1586-1640`) — внутри демона, в том же синхронном
  стеке, что и `poll_once`. Ждёт `_wait_awake(p, timeout)` (`:1628`), на исчерпании бюджета
  ловит `TimeoutError` и делает `p.kill()` + `p.communicate(timeout=30)` (`:1629-1636`).
* **Чем меряет срок.** `timeout` = `TASK_TIMEOUT` = **2700 с**, и тратится он **только на
  бодрствование**: `_wait_awake` ждёт кусками и засчитывает МЕНЬШУЮ из дельт стенных и «бодрых»
  часов (`min(d_wall, d_awake)`), а разницу копит в `slept`. Сон машины в бюджет не идёт.
* **Когда не срабатывает.** Три случая, и все три делают фразу карточки ненадёжной по устройству:
  1. **захода нет вовсе** — этот эпизод;
  2. **демон встал** — убийца живёт ВНУТРИ него и себя не судит (закон полосы «наблюдатель не
     живёт на том, за чем следит»);
  3. **машина спала** — прибор считает возраст захода стенными часами (`now - since`,
     `expectations_pc.py:502`) и сравнивает с `allow = 2700 + 600` (`:503`), а убийца тратит
     бюджет бодрствованием. Заход, переживший сон, законно не убит — но по стенным часам выглядит
     просроченным. Это **вторая, независимая** дорога к той же ложной фразе, и она откроется на
     первом же длинном заходе через сон, даже когда отметки будут читаться правильно.

## 8. Предсмертный взгляд: как провалится будущая починка порога

**Починка провалится, если тронут ЧИСЛО, а не ПРЕДМЕТ: возраст чужой отметки — величина, растущая
сама по себе (замер: от 20.1 до 51.2 часа против allow 3300 с, перебор до 55×), поэтому любой
порог, который её переживёт, одновременно снимает О2 с дежурства — а «поднять `BUSY_GRACE`»
выглядит и дешевле, и убедительнее, чем признать, что читается не то поле.**

Три вида той же ловушки, которые стоит назвать заранее:

* **`allow` до суток** — тревоги пропадут вместе со способностью заметить настоящую остановку;
  замер порога 1800 с у сторожа демона стоял на 1005 паузах СВОЕЙ полосы, а тут порог подгонялся
  бы под артефакт чтения.
* **`EXPECT_PC_TURN_MIN` вверх** — не трогает механизм вообще: тревога рождается не из тишины
  (тишина была честной — 20 минут), а из того, что штамп её не оправдал. Порог лишь отодвинет
  тревогу на более длинные заходы, где она всё равно ложная.
* **«чистить реестр по завершении»** — уберёт этот случай и заведёт худший: пустой реестр
  обнуляет ветку «объявленный заход», и все 16 верных молчаний из §4 превратятся в тревоги
  (тот самый контрфакт «25 ложных заметок за 20 суток», ради которого ветку и заводили). Реестр
  читают ещё три места (`_executor_verdict`, окно работы в `fail_result`, `_task_started_covers`),
  и снос отметок бьёт по ним раньше, чем по О2.

Признак, что починка настоящая: **вердикт не меняется, если из реестра выкинуть ВСЕ поля `at`
закрытых задач** — потому что предметом стал факт «файл тронут после последнего оборота», а не
чьё-то поле.

## Побочные находки (не чинили, называем)

1. **`send_note` всегда возвращает `True`.** `dispatch_notify.deliver` отдаёт кортеж
   `(channel, ok)` (`dispatch_notify.py:222, 215, 227`), а `expectations_pc_run.py:599` делает
   `bool(...)` — непустой кортеж истинен всегда. Объявленная страховка «заметка не ушла → эпизод не
   помечаем, скажем на следующем прогоне» (`:50-51`, `:685-686`) не работает: непрошедшая заметка
   молча теряется навсегда.
2. **Наблюдатель уводит СВОИ логи в `%TEMP%` собственным флагом.** `TURBOBABY_TEST_LOGS=1`
   (`:325`) ставится ради одалживания клиента моста, но переживает импорт и уводит
   `dispatch_notify.log` в temp (§4). Следствие: тревоги прибора нельзя сосчитать по репозиторию
   вообще ничем — и это ровно то, обо что споткнулся пункт 4 задания.
3. **Столкновение id бьёт не только по О2.** Отметка используется как начало ОКНА РАБОТЫ в отчёте
   о провале (`since=_task_started_get(tid)`, `pc_orchestrator.py:3716, 3191, 3233, 3258` и др.).
   На повторном id окно начнётся на 20–51 час раньше — и в «улики задачи» попадут чужие коммиты
   и чужие строки журнала за двое суток.
4. **`_task_started_covers` не имеет ни одного теста** (грепа по `test_pc_orchestrator.py` — ноль),
   хотя на нём стои́т приговор «сирота».
