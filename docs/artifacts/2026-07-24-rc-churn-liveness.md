# Причина churn RC-сред: ложная зомби-проба серверной ветки (24.07.2026, read-only)

Факт: rc-server перезапускается каждые 20–76 мин, каждый раз регистрируя НОВУЮ среду →
накопилось 7 мёртвых. Ничего не менял. Ниже — доказательство, что это **ложное срабатывание
пробы живости супервизора**, а НЕ самовыход процесса.

consecutive empty polls)`, дальше тишина >20 мин, затем гашение.

## 2. Код пробы живости (rc_supervisor.py) — целиком по сути

Пороги (общие, из env): `CHECK_INTERVAL=30с`, `LIVENESS_MAX_AGE=1200с (20 мин)`,
`GRACE_SECONDS=180с`, `LIVENESS_ENABLED=1`.

```python
def channel_alive(age_sec, established, max_age=None):
    _max = LIVENESS_MAX_AGE if max_age is None else max_age
    log_fresh = age_sec is not None and age_sec <= _max
    return bool(log_fresh or (established or 0) > 0)   # МЁРТВ ⟺ лог протух И 0 соединений
```
Монитор (`supervise_branch`) каждые 30с: если `proc.poll()!=None` → «процесс вышел»; иначе, после
грейса, если `not probe_alive(...)` → лог «ЗОМБИ», `_kill(proc)` (terminate), рестарт.

**Логика ОДИНАКОВА для обеих веток.** Единственное отличие — какой `--debug-file` проверяется
(`spec["log"]`: rc_server_debug.log vs rc_session_debug.log). Ни порога, ни условия отдельно для
серверной ветки НЕТ.

## 3. Гипотеза подтверждена числами

- Веховая запись сервера — раз в 100 поллов: poll#1 20:26:05 → poll#100 20:35:28 = **9м23с**
  (≈5.6с/полл). После #100 частота поллинга падает (backoff) → следующая веха >20 мин.
- Живой факт по убитому PID 15112: poll#100 в **20:05:38**, следующей строки НЕТ до гашения в
  **20:25:45** → разрыв **20м07с** > 1200с ⇒ «лог протух».
- Соединения: сервер держит 1 established к api (:443), НО оно кратко рвётся между long-poll
  (замер сейчас: PID 13120 = 1 conn; в момент реконнекта = 0). Проба 30с ловит миг «0 conns».
- Совпадение обоих (лог >1200с И мгновенный 0 conns) на одном 30-с тике ⇒ `channel_alive=False`
  ⇒ ЗОМБИ ⇒ гашение здорового простаивающего сервера. **Ложное срабатывание. Подтверждено.**
- Текущий PID 13120: poll#100 в 20:35:28; порог 1200с он пересечёт ~20:55:28 — до следующей вехи;
  ожидаемое ложное гашение ~20:55–21:10 (проверяемо), если conns совпадут с 0.

## 4. Кто инициатор — сторож, не процесс

**Инициатор — сторож (проба живости).** Все 5 перезапусков rc-server — строки
`[rc-server] ЗОМБИ: … гашу pid=…` (супервизор зовёт `_kill`/terminate). Строк
`[rc-server] процесс вышел (exit=…)` за сутки — **НОЛЬ**. Процесс сам не падает; его гасит сторож.

## 5. Предложенная правка ДЛЯ СЕРВЕРНОЙ ветки (НЕ применена)

Причина ложняка двойная: (а) веховый лог сервера редкий (разрыв >20 мин в простое), (б) 0 conns —
мгновенный артефакт реконнекта. Поэтому две меры (можно любую, лучше обе):

**A. Пер-branch порог свежести.** Вынести `max_age` в spec: серверу — с запасом над реальным
разрывом вех (напр. 3600с / env `RC_SERVER_LIVENESS_MAX_LOG_AGE`), named оставить 1200с.
```python
SERVER_SPEC = {"label":"rc-server", "mode":("rc",), "log":SERVER_LOG,
               "max_age": int(os.getenv("RC_SERVER_LIVENESS_MAX_LOG_AGE","3600") or "3600")}
# в probe_alive(...): est/age → channel_alive(age, est, max_age=spec.get("max_age"))
```

**B. Счётчик страйков (главное — бьёт по мгновенному 0 conns).** Гасить только если предикат
смерти держится N ПОДРЯД проверок, а не на одном тике:
```python
STRIKES = int(os.getenv("RC_LIVENESS_STRIKES","3") or "3")   # 3×30с = ~90с непрерывно
strikes = 0
...
if LIVENESS_ENABLED and c > _grace and not _alive(spec, proc.pid, max_age=spec.get("max_age")):
    strikes += 1
    if strikes >= STRIKES:
        log.info("[%s] ЗОМБИ (подтверждён %s×): гашу pid=%s", spec["label"], strikes, proc.pid)
        if proc.poll() is None: _kill(proc)
        break
else:
    strikes = 0
```
Здоровый сервер восстановит соединение за секунды → strikes сбросится, гашения не будет; реальный
зомби (стабильно стар+0conn) ловится за ~90с после порога. Отдельно стоит починить и named-канал
(та же проба), но задача про серверную ветку.

> Применение требует РЕСТАРТА супервизора (правка не подхватится на лету) — это отдельный красный
> шаг, здесь только предложение.
