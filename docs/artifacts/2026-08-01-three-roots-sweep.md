## §1. КОРЕНЬ А, ЛИЦО ШЕСТОЕ (живое): смягчение и обвинение читают РАЗНЫЕ тексты

Найдено чтением кода, подтверждено тремя строками живого лога.

```python
# pretool_guard.py:2191-2194  — обвинитель читает scan, смягчитель читает СЫРУЮ команду
scan = _scan_text(cmd)                       # ← шаблон поиска ВЫРЕЗАН как данные
reach = _env_reach(cmd) if _RE_ENV.search(scan) else None   # ← cmd, шаблон НА МЕСТЕ
```

`_env_reach` (`:2099-2151`) идёт по сегментам сырой команды и требует, чтобы команда сегмента
стояла в белом списке `_EXISTS_CMDS`/`_PRINT_CMDS`. Сегмент `grep -iE "^\.env|…"` в списках не
стоит → `return None` → смягчения нет → `_decide_bash_body:2304` красит команду в `env`.
При этом ТОТ ЖЕ шаблон обвинителем уже признан данными (`_strip_search_pattern:1615`).

**Цена: листинг каталога становится «обращением к секретам».** Два живых срабатывания за сутки,
оба доехали до владельца отдельными задачами:

| 01.08 02:46:27 | `ls -a /d/turbobaby-bot/tmp/srv \| grep -iE "^\.env\|^\.claude" ; echo "--- .env present? ---"; test -f …/tmp/srv/.env && echo YES` | `ask \| env` | первый блок карточки → **задача #144** |

**Закрытие — одна строка:** смягчитель и обвинитель обязаны читать ОДИН текст

### 4.2 Механика ПК: три способа склейки

**В-1. Склейка ПО ПРОГОНУ (главная).** `_write_marker:3269-3272` ДОПИСЫВАЕТ блок в
`pc_ask_<tid>.marker`; дедуп — только по полностью совпавшему блоку. `_detect_needs_approval`
(`pc_orchestrator.py:804-820`) читает файл ЦЕЛИКОМ и склеивает все блоки в ОДНУ карточку.
`needs_approval` выставляется один раз — когда прогон КОНЧИЛСЯ. Между первой красной операцией и
карточкой владельцу проходит весь остаток прогона.

**В-2. Склейка ПО КОМАНДЕ.** `_decide_bash_body:2254-2295` возвращает на ПЕРВОМ совпавшем правиле
`_RED_CMD`; `_scan_python` (единственный источник `py_write`/`sqlite`/`live_sheet` из тела) стоит
НИЖЕ (`:2323`). Значит `rm -rf tmp/x; python -c "…create_booking…"` даёт карточку про `delete`, а
боевая запись Bridge в той же строке не названа НИГДЕ. После «да» исполняется вся строка.
Сама команда в карточке обрезана до 200 символов (`_card:3101`).

**В-3. Склейка ПО КЛАССУ во времени.** `_run_task_impl:1259` `env[APPROVED_KINDS_ENV] =
",".join(kinds)`; `approval_covers:2637` — `if not is_top_tier(kind): return True`. Ни счётчика
использований, ни однократности, ни TTL внутри прогона нет. Одно «да» на обычный вид открывает
СКОЛЬКО УГОДНО операций этого вида, по ЛЮБЫМ объектам, на оба headless-захода (`:1269`).

## §6. КАК ЗАКРЫТЬ КАЖДЫЙ КОРЕНЬ ОДНИМ ПРАВИЛОМ

### Правило А: «У значения одно место и один текст — и то же самое у его смягчения»

Формулировка второго захода («признак засчитывается только на своём месте») верна, но
недостаточна: лицо 6 родилось не из места, а из **двух РАЗНЫХ ТЕКСТОВ** — обвинитель судил
`scan`, смягчитель `cmd`. Правило в рабочей форме:

> Любая пара «признак + его смягчение» обязана получать ОДИН И ТОТ ЖЕ разобранный вход и
> возвращаться ОДНИМ разборщиком. `_decide_*` отдаёт структуру `Op(kind, obj, num, rollback,
> mitigations)`; повторно грепать `raw_cmd`/`scan`/`result` запрещено всем — и `_card_fields`,
> и `_rollback`, и `_env_reach`.

Механический сторож (без него найдётся двадцать первое место): тест, который вычитывает исходники
гарда и демона и краснеет на `re.search(...)` по `cmd|scan|raw_cmd|result|task_text|out` вне
белого списка. Образец такого сторожа в репо уже есть — `test_free_signs_declare_action_check`
(`pretool_guard.py:305`), он ловит новый `_RE_*` мимо таблицы; расширить его с «признаков» на
«чтения служебных значений».

### Правило Б: «Проба объявляется происхождением процесса, и боевой выход один»

Порт `a739ee9` дословно: единый предикат `is_probe`, латч в `main()` ДО первой записи, глушение
ОБОИХ каналов. Плюс два уточнения, которых на VPS нет:

> Все боевые каналы (Telegram, очередь моста, мозг, журнал, БД, git push, рестарт, живой лист)
> проходят через одну функцию `outward(channel, payload)`, отказывающую, если процесс не помечен
> боевым. Умолчание — изоляция, боевой путь — явный флаг.

И развести две ручки, которые сегодня одна (`Б-41`): «логи в temp» ≠ «это проба». Пока они
слиты, боевой `trainer_run` объявляет себя тестом, а любая проба может объявить себя боевой —
и `tmp/probe_check.py:11-12` ровно это и делает.

### Правило В: «Одна карточка — одна операция; вторая красная операция прогон ОСТАНАВЛИВАЕТ»

Правила нет — значит его надо ЗАВЕСТИ, а не залатать три склейки по отдельности. Форма, которая
закрывает все три разом и уже проверена на соседней полосе:

> Первая красная операция прогона — **последняя**. Гард пишет ОДИН блок и завершает прогон
> (как монитор VPS убивает claude через ≤2 с); маркер перезаписывается, а не дописывается.
> Одобрение действует на ОДНУ операцию: класс + объект + одноразовость, а не класс на весь
> ре-ран.

Три следствия, каждое снимает свою склейку:
1. **По прогону** — `_write_marker` перестаёт дописывать; карточка не может нести чужую и уже
   отменённую операцию (144 и 145 не родились бы в нынешнем виде);
2. **По команде** — `decide()` обязан вернуть ВСЕ красные виды команды, а не первый по таблице;
   пока он возвращает один, «да» освобождает строку целиком;
3. **По классу** — `PRETOOL_APPROVED_KINDS` заменить на одноразовый талон
   (класс + объект + счётчик 1), тогда «да» на `env` не пропустит шесть операций подряд и тем
   более не пропустит ЗАПИСЬ там, где владелец читал слово «обратиться».

И перенести `py_write`-подобную строгость на секреты: сегодня `delete tmp/x.txt` — высший вид с
переписыванием объекта, а дописывание в файл секретов — обычный вид без объекта. Порядок обратный
цене.
