## 1. Теряется ли хвост навсегда

**Внутри репозитория — да, навсегда.** Полный stdout исполнителя живёт только в памяти процесса
демона: `run_claude` возвращает `(rc, out, err)` (`pc_orchestrator.py:1517`), и ни одна ветка не
пишет `out` в файл — греп по всем употреблениям `out_s` даёт 10 мест, все они читают, ни одно не
сохраняет. Обрезка стои́т на выходе `_run_task_impl`:

```
pc_orchestrator.py:2003    return "done", out_s[:RESULT_MAX]
pc_orchestrator.py:637     r = self._post("complete_task", id=tid, status=status, result=(result or "")[:RESULT_MAX])
```

Это ДВЕ независимые обрезки одним и тем же потолком: вторая — уже в клиенте Bridge. Все прочие
хранилища короче очереди, а не длиннее: `cowork_log` получает `_clip(result)` = **1500** символов
(`pc_orchestrator.py:366, 2917`), карточка в Telegram строится из того же обрезанного `result`
(`_notify_task(status, tid, result)`, там же). `reports/` в ПК-репозитории **нет**, `splinter.log`
— серверный файл, на ПК его нет. Тело журнальной записи (`docs/artifacts/journal/…`) хранит строку
журнала, а не отчёт задачи.

**Единственный кандидат вне репозитория** — собственный транскрипт сессии CLI: headless-исполнитель
запускается с `cwd=REPO`, поэтому его сессия пишется в `C:\Users\<user>\.claude\projects\D--turbobaby-bot\<uuid>.jsonl`
(формат подтверждён кодом репозитория — `dispatch_notify._summary_from_transcript`, :372). Каталог
существует, в нём 704 файла. **Я его не открывал: это выход за границу проекта.** Проверяется
владельцем одной командой (нужный файл — с временем изменения в окне задачи 473, 06:45–06:58):

```
Get-ChildItem $env:USERPROFILE\.claude\projects\D--turbobaby-bot\*.jsonl | Where-Object { $_.LastWriteTime -gt '2026-08-11 06:45' -and $_.LastWriteTime -lt '2026-08-11 07:00' }
```

Связи «id задачи → файл транскрипта» нигде не записано: демон не логирует uuid сессии ребёнка (в
`_task_started_child` уходит только PID). Поиск возможен лишь по времени.

**Побочная потеря, того же корня.** Проверенная строка `RESULT:` живёт в КОНЦЕ отчёта, а проверяется

срезается вместе с хвостом. По полосе ПК, `done` + `Filipp-*-dev`, 90 строк:

```

не упёрлись 45 → RESULT: уцелела у 44
```

То есть в 38 случаях из 45 демон подтвердил итог по строке, которой в очереди уже нет. Второй
побочный эффект — `pc_orchestrator.py:2913`: `result = (result + maybe_update_bots(…))[:RESULT_MAX]`;
если `result` уже 4500, приписка про обновление ботов отбрасывается целиком и молча.

## 3. Знает ли исполнитель, что его обрезали

**Нет, и знание никуда не уходит.** Три факта из кода:

1. Обрезка происходит ПОСЛЕ выхода процесса: `run_claude` уже вернул `(rc, out, err)`
   (`:1517`), `claude -p` завершён. Обратного канала к нему не существует в принципе.
2. Задание, которое видит исполнитель, о потолке не говорит ни слова. Преамбула требует
   «первая строка — сводка ≤400 символов» и «ПОСЛЕДНЯЯ строка — `RESULT:`» (`:332-333`); числа 4500
   в тексте задания нет (греп `4500` по `pc_orchestrator.py` — единственное вхождение это сама
   константа `:202`). Ограничение длины отчёта приходит только тогда, когда его впишет в ТЗ владелец.
3. Демон длину до обрезки не сохраняет и не логирует: `out_s[:RESULT_MAX]` — голый срез без
   сравнения `len`, строка METRICS (`task_metrics`) поля длины результата не несёт, в лог уходят
   только `COMPLETE id=… status=…` и превью карточки. Наверх (очередь → devbot → карточка 328)
   уходит обрубок, неотличимый от короткого отчёта.

Контраст внутри своего же репозитория: гард, обрезая тело карточки, пометку ставит обязательно —
`CARD_CUT_MARK = "…(тело карточки обрезано под штамп класса)"` с комментарием «обрезка обязана быть
заметна, иначе урезанная карточка читается как полная» (`pretool_guard.py:4754-4760`). Демон ПК тот
же принцип на своём потолке не применяет.

## 4. Что означает `unverified` и почему нет блока FACT

`unverified` — **серверная пометка, и она про формат, а не про проверку**.

```
tmp/srv/devbot.py:119   _FACT_RE = re.compile(r"\bFACT\s*:", re.IGNORECASE)
tmp/srv/devbot.py:123-128  dev-задача (from *-dev) со st=='done' и БЕЗ блока FACT: в result →
                           префикс карточки «⚠️ unverified (нет блока FACT:)»
```

Это чистый поиск подстроки `FACT:` в тексте `result`. Никто ничего не перепроверяет: пометка
означает ровно «в тексте нет слова FACT:», а не «работа не подтверждена».

Требование блока FACT живёт **только в серверной преамбуле** (`tmp/srv/orchestrator_daemon.py:944-948`:
«в выводе ОБЯЗАТЕЛЬНО включи блок «FACT:» … read-only задача без изменений: «FACT: read-only».
Задача без FACT: → карточка в 328 получит ⚠️ unverified»). **В `pc_orchestrator.py` строки `FACT`
нет вовсе** — греп даёт ноль совпадений. ПК-исполнителю про этот блок не говорят никогда, а судит
его серверный devbot по серверному правилу.

Измеренное следствие: `FACT:` встречается в **0 из 156** строк полосы ПК — и у обрезанных (0/45),
и у коротких (0/111). На сервере — 151 из 310. Значит `unverified` на 473 обрезкой **не вызвана**:
её получила бы и полная версия отчёта. Это зеркальная дыра ровно того вида, что описана правилом
«класс-фикс — сразу на обе полосы»: правило заведено на сервере 20.07, на ПК не отражено, и полоса
ПК помечена `unverified` целиком, по построению.

## 5. Что закрыло бы потерю

**Резать с пометкой длины — портировать серверный `cap_result` на ПК** (`tmp/srv/orchestrator_daemon.py:234-254`:
голова + машиночитаемый хвост «полная длина N, попало K, срезано M», итог по-прежнему ≤ потолка):
это единственный из трёх вариантов, который не требует ни менять потолок очереди, ни заводить новое
хранилище, и снимает главный вред — потерю **невидима**. Поднятие потолка вред лишь отодвигает
(15773-символьный отчёт с сервера не влез бы и в 15000), отдельная запись хвоста — новое хранилище
и новый вопрос «кто его чистит».
