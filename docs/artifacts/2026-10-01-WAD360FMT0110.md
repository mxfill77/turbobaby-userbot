**Итог. МОЖНО, и сделано на ветке.** До правки вход `POST /wa-webhook/d360/<секрет>` понимал только
плоский v1. Тело Cloud API (`object` + `entry` → `changes`), которое шлёт канал COEX, давало **0
событий**, ответ 200 и строку DEBUG при журнале на уровне INFO. Поток пропадал молча. Теперь:
- тело с `object` и `entry` идёт в `normalize_wa_payload`;
- плоский v1 идёт прежним разбором;
- тело третьей формы и любой нулевой разбор пишут строку **WARNING** с видом тела, без текста и
  номеров.

Попутно найдена и закрыта **вторая дыра того же класса**. Разбор Cloud API отбрасывал всё, что не
`field == "messages"`, а в режиме COEX эхо ответов менеджера с телефона приходит полем
`smb_message_echoes`, досинхрон — полем `history`. Без этой части «принять формат Cloud API»
означало бы: для входящих и квитанций поток есть, а эхо и история по-прежнему пропадают молча.

## Как применить при перезапуске wa-webhook и как откатить

Применение — **слово владельца**. Команды для серверной полосы, в живом дереве:

```
cd /root/turbobaby-manager-bot
git fetch origin wa-d360-cloud-0110
git merge --ff-only origin/wa-d360-cloud-0110     # main стоит на 0772f84 → чистая перемотка на 07200b9
systemctl restart wa-webhook                      # код доходит до процесса только рестартом
```

- Сливать и перезапускать **вместе**. О3 (`prod_drift.WATCHED` → `("wa-webhook", "wa_webhook.py")`)
  сравнивает байты коммита с процессом: слитый без рестарта файл станет честной заметкой
  «не применено».
- Правка касается только `wa_webhook.py` и двух файлов тестов. `wa_webhook.py` исполняет один
  `wa-webhook.service`: `health.py` и `wa_send.py` его не импортируют. Остальные юниты рестарта не
  требуют.
- Признак применения — строка старта `WA webhook listening on …` с новым временем.
- Признак работы — первое событие канала COEX даст в `wa_webhook.log` одну из строк:
  - `D360 POST: N events, M enqueued (form=cloud)`;
  - `D360 POST: … 0 events … (keys=… fields=[…] value_keys=[…])` — по полям видно, что пришло.

  Молчания, как до правки, быть не должно.

**Откат:**
```
git revert --no-edit 07200b9 && systemctl restart wa-webhook
```
Коммит 1e7fc3b трогает только тесты, откатывать его не нужно. Схема очереди не менялась, миграций
нет, строки, легшие по новой ветке, остаются валидными строками `wa_inbox`. До слияния откат — просто
не сливать.

## Чего здесь нет (НЕИЗВЕСТНО — названо)

- **Боевая форма тела 360dialog COEX живьём не видена.** Живых событий на вход не приходило ни одного
  (WASTATE3009), а 360dialog по запрету не звался. Образцы собраны по структуре документации Meta;
  сеть к документации не открывалась, структура взята по знанию. Что 360dialog для Cloud API
  пересылает тело Meta без обёртки и доставляет партнёрскому вебхуку поля `smb_message_echoes` и
  `history` — не проверено. Первое живое событие решит это строкой журнала: теперь она будет видна
  на любой ветке.
- **Куда прописан адрес вебхука канала и задан ли `WA_D360_PATH_SECRET`** — не проверялось:
  конфиги и `.env` под запретом. Без секрета пути вход d360 отвечает 404 fail-closed и в журнал не
  пишет (так было и до правки). Вход Meta без подписи нашего приложения ответит 403
  `bad/missing signature`. Правка работает только при адресе на вход d360 и заданном секрете.
- **Две разные «эхо»-адресации.** У эха Coexistence адрес строки — номер клиента (`to`). У прежнего
  эвристического эха в поле `messages` (`from == display_phone_number`) адрес по-прежнему наш номер.
  Второй путь не менялся: на Cloud API он практически не срабатывает.
- `smb_app_state_sync` (синхрон контактов COEX), `account_update` и другие служебные поля событий не
  дают. На входе d360 каждое такое тело теперь пишет WARNING с именем поля: это видимость, а не
  потеря.
- Нулевой разбор на входе Meta по-прежнему пишет DEBUG — за рамкой задания.
