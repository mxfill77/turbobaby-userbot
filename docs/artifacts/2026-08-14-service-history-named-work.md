## 1. Строка, где слова механика заменяются ярлыком

`splinter.py:6514` (ревизия `f70f186`), ветка «событие» внутри `_sp_write_done`:

```python

    lbl = _SP_KIND_LABEL.get(k, (k, k))[1]          # ← ЗДЕСЬ
```

Замена происходит не потому, что слова отбрасываются, а потому что **их тут уже нет**: в
`_sp_write_done` приходит `done` — список КЛЮЧЕЙ работ (`other`, `pads`, …), которые построил
`_service_kind` (`:5883`) поверх `_classify_work` (`:3610`). Слова механика к этому моменту лежат
в другом месте — в `note` заявки сегментом Z4 `WORKS:{…}` (кладёт `:6297`), и до этой строки они
не доезжали никогда.

### Забор Честертона: зачем ярлык нужен и что на нём завязано

Ярлык (точнее — ключ `k`, ярлык лишь его человеческое имя) **несущий**. На нём стои́т:

| что | где | почему нельзя тронуть |
|---|---|---|
| **адрес регистра** (расчёт) | `k in _SP_COL_KINDS` → `set_fleet_oil`/`set_fleet_service` кол. I/J/K/L + `service_upsert(interval_km=…)` | масло, редуктор, ABS и воздушный фильтр считаются ПО КЛЮЧУ; слова тут не при чём |
| **идемпотентность** | `msg_id=f"sp:{chat}:{topic}:{k}:{odo}"` → дедуп `botMsgExists_` на мосту | ключ по словам плодил бы дубли на каждой переформулировке |
| **квитанция обеих половин** | `service_receipt.receipt(written, failed, odo, _SP_KIND_LABEL)` (`:4382`, `:4463`, `:6270`) | RU/TH имена работ механику и владельцу |
| **карточка отмены** | `undo_last.reply/card(..., _SP_KIND_LABEL)` (`:5843`, `:5846`) | встала сегодня, 14.08 — не трогаем |
| **перечни заявки** | `_sp_labels_ru/_sp_labels_th` (`:5960`, `:5964`) | тайский текст механику |

**Вывод: ярлык не снимается.** Снять его — сломать расчёт регистров, дедуп и двуязычие разом.
Менять можно РОВНО одно — человекочитаемый текст `notes` в строке истории.

## 2. Что сделано: сохранены и ярлык, и слова

Дифф целиком — [`2026-08-14-service-history-named-work/splinter-named-work.diff`](2026-08-14-service-history-named-work/splinter-named-work.diff)
(+31 −3). Два куска:

1. **Новая чистая функция `_sp_event_note(kind, works, km)`** рядом с `_sp_note_set_works`:
   работа названа → слова механика; не названа → прежний ярлык. Совпадение слов с регистром
   ищется ТЕМ ЖЕ `_service_kind`, что построил `done` (иначе в строку попало бы чужое название);
   длина режется по 200 — как у соседней ветки `_write_info_works` (`:2205`), которая дословно
   писать умеет давно и **уже писала по этому же байку**.
2. **Ветка события** зовёт `_sp_event_note` вместо `lbl`, а слова читает **лениво и один раз на
   заход** — `_sp_open(...)` → `_sp_works_from_note(note)`.

**Живой эффект** (`show_before.py`, байк 9548):

```
БЫЛО  (origin/main), байк 9548: 'прочие работы — 36474 км'
СТАЛО (после правки)          : 'замена аккумулятора — 36474 км'
```

Три свойства, каждое проверено тестом:

- **Ленивое чтение** — колоночная запись (масло/редуктор/ABS/фильтр) за слова механика обращением
  к мосту **не платит вовсе** (`pending_get_calls == 0`), а событийная платит **одним** на заход,
  сколько бы позиций в нём ни было.
- **Fail-safe** — чтение заявки упало → `_sp_event_note` отдаёт прежний ярлык. Отказ моста
  поведение **не меняет**, а возвращает ровно сегодняшнее.
- **Слова не протухают** — `servicePendingFind_` (`bridge_prod/ServicePending.js:13`) отдаёт
  ТОЛЬКО НЕ-закрытую заявку («новый визит → новая строка»), а `service_pending_close` зовётся
  ПОСЛЕ цикла записи. Прочитанные слова всегда принадлежат текущему визиту.

## 5. Числа: что измерено, а что нет

**Измерено точно (по коду и контрфактом):**

- через `:6514` идут **4 класса работ из 8** — всё, чего нет в `_SP_COL_KINDS`: `filter`, `pads`,
  `chain`, `other`;
- из записей, прошедших этой веткой, название теряли **100%** — и это не оценка, а замер: на
  неправленом исходнике строка отдаёт `'прочие работы — 36474 км'` **даже когда слова механика
  в заявке ЕСТЬ** (`test_live_case_9548_battery` красный до правки). Выражение в строке ссылки на
  `works`/`note` не имело вовсе;
- подтверждённых живых случаев на руках — **1**: байк 9548, 14.08, «замена аккумулятора».

**НЕ измерено, и это честный статус:** сколько записей потеряли название *за наблюдение* и в
скольких из них механик называл работу словами. Счёт живёт в листе «события» (строки с
`msg_id` вида `sp:*`) и в `то_заявки` (сегмент `WORKS:{…}`); с полосы ПК он читается только
токеном моста из `.env` — для этой сессии красное. Локального корпуса нет: в `fixtures/`
серверного репозитория событий обслуживания не лежит (проверено `git ls-tree`). Оценку «на глаз»
не привожу — числа тут были бы выдуманные.

**Что нужно, чтобы число появилось:** один read-only проход по листу «события» с фильтром
`msg_id LIKE 'sp:%'` и сверкой `notes` с восемью значениями `_SP_KIND_LABEL`; доля совпавших —
искомое «потеряли название», пересечение с непустым `WORKS:{…}` той же заявки — «а слова были».

## 7. Как применить (за владельцем)

Полоса ПК приложить не может: серверный предпушевой гейт (`core.hooksPath=deploy/hooks` → `gate.py`
по абсолютному `/root/…`) на ПК не идёт, то есть «полный гейт» серверного репозитория здесь
физически не прогоняется. С VPS, из корня `turbobaby-manager-bot`:

```bash
git apply docs/artifacts/2026-08-14-service-history-named-work/splinter-named-work.diff   # дифф взять из ПК-репо
cp <…>/test_service_named_work.py tests/
python -m unittest tests.test_service_named_work && python gate.py && git commit -am "…" && git push
```

Дифф снят с `f70f186` — если серверный HEAD ушёл вперёд, `git apply` скажет об этом сам.
