## 3. Жив ли процесс задачи в момент подтверждения — НЕТ

Процесс исполнителя завершается, **породив** карточку: `orchestrator_daemon.py:948`
`log.info("id=%s guard-block → needs_approval: …")`. К моменту «да» его давно нет.

| таймаут | значение | строка |
|---|---|---|
| опрос очереди | 60 с | `:59 POLL_SEC` |
| процесс быстрой «задача:» | **600 с (10 мин)** | `:65 TASK_TIMEOUT` |
| процесс дев-ТЗ «тз:» | **2700 с (45 мин)** | `:66 TASK_TIMEOUT_DEV` |
| хардкод-операция красной зоны | 180 с | `:114 OP_TIMEOUT` |
| **окно на доведение после «да»** | **1800 с (30 мин)** | `:115 APPROVED_TTL` |
| жизнь карточки без ответа | **86400 с (24 ч)** | `:117 NA_LIFETIME` |
| напоминание | 10800 с (3 ч) | `:118 NA_REMINDER_SEC` |

**Расхождение:** карточка ждёт до 24 часов, процесс живёт 10–45 минут. Что происходит при
расхождении — `:2967-2969`:
```python
if _approved_expired(task.get("updated")):
    log.info("APPROVED id=%s ИСТЁК (>%ss) → failed", tid, APPROVED_TTL)
    bc.complete_task(tid, "failed", "approve истёк (>30 мин), повтори задачу")
```

## 7. Предложение починки разрыва — НЕ ПРИМЕНЯТЬ

1. **Убрать тихий выход.** `process_approved` `:2939-2940`:
   ```python
   r = bc.get_pending("approved")
   if not r.get("ok"):
       return          # ни строки в журнал
   ```
   То же в `process_na_reminders` `:3295-3296`. Отказ моста в этих ветках **невидим**: подтверждения
   молча не обрабатываются, и через 30 минут задача сгорает по TTL. Лечение: `log.warning` с текстом
   ошибки + счётчик подряд-неудачных опросов, после N — алерт владельцу.
2. **Не сжигать по TTL, если демон не видел очередь.** `APPROVED_TTL` считается от `updated`, но
   не учитывает, опрашивал ли демон мост всё это время. Лечение: гасить по таймауту только при
   подтверждённых успешных опросах в окне; иначе продлевать.
3. **Сузить слой 2.** `_HEADLESS_IMPOSSIBLE_RE` ловит **темы**, а не операции: `деньг`, `касс`,
   `байки`, `crm`, `календар`, `удал` — под них попадает и безобидное чтение («покажи отчёт по
   деньгам», «удалённый доступ»). Лечение: решать по `op=`-коду, а не по свободному тексту; либо
   разрешить явный маркер владельца, снимающий слой 2 для конкретной задачи.
4. **Писать причину в `result`.** Терминальный failed должен явно называть слой (1 или 2) и
   почему headless не может — тогда «>10 failed» читались бы с первого взгляда.
5. **Починить дефолт фолбэка в коде** (`:137` → `claude-fable-5`).
6. **Добавить в баннер `fallback` и `effort`** — иначе рестарт не подтверждает конфиг.
