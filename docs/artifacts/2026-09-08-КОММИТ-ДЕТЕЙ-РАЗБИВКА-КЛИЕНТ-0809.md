## 2. ВОПРОС 1. На каком коммите работает КАЖДЫЙ живой ребёнок

### Способ наблюдения — назван явно

Ребёнок — это python-процесс, а python читает исходник **в момент импорта**. Значит вопрос «на
каком коммите работает ребёнок» = «какое СОДЕРЖИМОЕ файлов лежало на диске в момент его старта».
Отсюда три факта, и приговор стои́т на всех трёх сразу, а не на одном:

1. **момент старта** — read-only `Get-CimInstance Win32_Process` (`CreationDate`), то есть тот же
   источник, которым пользуется сам демон (`pc_orchestrator._proc_started_at`);
2. **коммит на этот момент** — `git rev-list -1 --before=<момент> HEAD`, то есть дословно
   `pc_orchestrator._commit_at_time` (`pc_orchestrator.py:8308`);
3. **что дерево в тот момент равнялось коммиту** — `git status --porcelain` по боевым файлам пуст
   (дерево = HEAD сейчас) И mtime каждого боевого файла СТАРШЕ момента старта (значит с тех пор
   файл не переписывался, и содержимое на старте равно сегодняшнему).

Названная в задании ловушка «живой PID не равен работающему сервису» закрыта отдельно, пунктом 2.3.

### 3.4 Что при этом НЕ изменилось — и это главная мина ответа

Разбивка по суткам касается **коэффициента**, и только его. Приговор артефакта
`ГРАНИЦА-МЕСЯЦА-СЕЗОН-ПОТОЛОК-0809` про **потолок** к детям относится в полном объёме, потому что
код у них тот же самый: `low_season` по-прежнему считается по множителю периода **даты начала**
(`day_price`), потолок судится по месяцу даты начала и бьёт один раз. Дословно в докстринге
`term_total`, живущем у детей:

> «ЧЕГО ЭТА ФУНКЦИЯ НЕ ДЕЛАЕТ. Не трогает УСЛОВИЕ применения месячного потолка… Меняется только
> СУММА, которую этому условию подают.»

То есть «доехало» ровно то, что было прочитано на HEAD, — включая его открытый второй вопрос.

### 4.2 Замков на самом деле три, и они на разных этажах

1. **Слой 1 — модербот, `moderation_core._finalize`** (`moderation_core.py:124`): в TEST_MODE
   решение получает статус **`test_held`**, а не `ready`. Отправитель userbot выбирает из IPC
   только `fetch_ready()` — придержанная строка ему не видна ВОВСЕ.
2. **Слой 2 — reply-режим, `suggest.on_moderation_reply`** (`suggest.py:8999`): даже когда «+»
   пишет живой менеджер в группе модерации, ветка TEST_MODE `send_to_client` **не зовёт вообще**
   и отвечает менеджеру распиской «🧪 Принято (TEST_MODE — клиенту НЕ отправлено)».
3. **Слой 3 — сама `send_to_client`** (`suggest.py:8527`), см. выше. Её докстринг называет это
   вслух: «чтобы никакой путь не смог написать клиенту».

Четвёртый канал — WhatsApp — закрыт отдельно и по другой причине: `poll_and_send` на WA-строке
пишет `WA_SEND_DISABLED_MSG` («WA-отправка отключена (ключ не задан)») и ставит `failed`; двери
`wa_send` нет ни на ПК, ни на VPS.
