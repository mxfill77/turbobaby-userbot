**Дата:** 2026-09-02, headless-заход полосы ПК. **Ось задания:** обслуживание нас самих.
**Задание:** поднять копию рамки в мозге до редакции **02.09.2026 #1** — записать
`docs/tasks/frame-edition-20260902.txt` в узел `KB_shtab_frame` ЦЕЛИКОМ через доверенного
писателя, затем прочитать назад отдельным вызовом и сверить посимвольно.

**Итог одной строкой: рамка поднята до 02.09.2026 #1; живой док посимвольно равен файлу-источнику
(sha256 совпал), расхождений 0 из 30040 символов.** Прошлая редакция (01.09.2026 #1) в доке не
осталась ни одним вхождением. Других узлов мозга заход не касался, кода не менял.

## 1. Премиса задания проверена ДО любой записи

```
sha256 docs/tasks/frame-edition-20260902.txt
  = 969cdf9308d10b6062f8ab6c0034acfd9feeaed0c53c890c9e91233686612f70
ожидался префикс 969cdf9308d1 → СОШЁЛСЯ
```

Премиса сверена **дважды и разными руками**: сначала вручную (`sha256sum`, до чтения файла),
потом самим скриптом записи как стоп-условие — при несовпадении он выходит кодом 2 и не зовёт
`brain_writer` ни одной строкой. Байты и символы дают один и тот же хеш: в файле **CR = 0** и
BOM нет (замер разведкой), поэтому `sha256(байты файла) == sha256(текст.encode("utf-8"))` — это
и позволяет сравнивать хеш файла с хешем текста, вычитанного из мозга.

Источник: **30040 символов, 561 строка, CR 0, U+FFFD 0.**

## 2. Адрес — по ИМЕНИ, не по file id

Все три скрипта захода зовут док `name="KB_shtab_frame"`; числовой id в коде захода не появляется
нигде. Разрешение делает сам писатель (`имя KB_shtab_frame → ключ реестра shtab_frame`), и
запись идёт ровно по тому адресу, по которому состоялось чтение — `apply` фиксирует адрес
после `_read` и повторно его не разрешает.

## 4. Запись — ЦЕЛИКОМ, через доверенного писателя

Канал: `brain_writer.apply(mutate, name=…)` — движок, объявленный в CLAUDE.md для одноразовых
скриптов. `append` здесь не годится по существу задания: он ДОПИСЫВАЕТ, а нужна замена всего
тела, поэтому мутация — `lambda old: new` (старый текст в новый не входит ни куском).

Скрипт захода (`_scratch_frame0902_0902/write_frame.py`) держит только строковую логику: чтение
файла, сверка хеша, мутация, печать чисел. **Секретов он не читает** — ни `load_env`, ни
`BRIDGE_*` в нём нет; конфиг моста берёт сам процесс писателя. Единственная правка поведения —
`brain_writer.HTTP_TIMEOUT = 240` на время захода: штатных 30 с на плечо для узла этого размера
мало с запасом (известный класс — таймаут писателя на крупном узле).

Встроенные замки писателя, сработавшие штатно:

```
СТАТУС: ok; док name:shtab_frame; 25094 → 30040 символов
БЭКАП СТАРОГО ТЕКСТА: tmp/brain_backup_shtab_frame_0902_20260902-031920.txt
РАСПИСКА МОСТА: ok
ОБРАТНОЕ ЧТЕНИЕ (внутри apply): 30040 символов, sha256 = 969cdf9308d10b60…86612f70
ПОСИМВОЛЬНО РАВНО ИСТОЧНИКУ (чтение apply): True
```

`marker="версия 02.09.2026 #1"` требовал **ровно одно** вхождение — это ловушка на гибрид
редакций (известный вид отказа этого дока: шапка новая, тело склеенное). Маркер прошёл.
Расписка моста пришла `ok`, но судит здесь не она, а чтение (класс «расписка ≠ факт записи»).

**Откат** — запись файлом бэкапа `tmp/brain_backup_shtab_frame_0902_20260902-031920.txt` тем же
`apply`; бэкап снят писателем ДО записи, автоматически, и в git не попадает.

## 5. Обратное чтение — НЕЗАВИСИМЫМ процессом, сверка посимвольная

Чтение внутри `apply` доказательством по заданию не считается: это тот же процесс и та же
сессия. Поэтому второй скрипт (`_scratch_frame0902_0902/witness.py`) запущен **отдельным
вызовом**, читает док заново по имени и ничего не пишет:

```
ЖИВОЙ ДОК ПО ИМЕНИ KB_shtab_frame: 30040 символов, строк 561, U+FFFD 0, CR 0
ИСТОЧНИК: 30040 символов, строк 561
sha256 живого:    969cdf9308d10b6062f8ab6c0034acfd9feeaed0c53c890c9e91233686612f70
sha256 источника: 969cdf9308d10b6062f8ab6c0034acfd9feeaed0c53c890c9e91233686612f70
ПОСИМВОЛЬНАЯ СВЕРКА: РАВНО, расхождений 0 (сверено 30040 символов)
ШАПКА ЖИВОГО: ═══ РАМКА ПРОЕКТА TurboBaby — ИНСТРУКЦИИ ШТАБА (версия 02.09.2026 #1) ═══
«версия 02.09.2026 #1» в живом доке: 1 раз
«01.09.2026» (прошлая редакция) в живом доке: 0 раз
```

Сверка именно **посимвольная**, а не «текст найден в доке»: свидетель ищет позицию первого
расхождения по всей длине и печатает окрестность, если она есть. Проверка через `in` или через
одну длину не отличила бы усечённый док от целого — ровно та развилка, ради которой в `apply`
живёт сверка длины отправленного. Здесь сошлись все три независимых признака: длина, sha256 и
позиционное равенство.

Строка «`01.09.2026` → 0 раз» отвечает на отдельный вопрос: старая редакция не осталась хвостом
ниже новой. Замена, а не наслоение.
