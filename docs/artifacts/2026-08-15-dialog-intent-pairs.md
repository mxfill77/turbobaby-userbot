# Есть ли эталон «что клиент просил → что записали в бронь» (read-only, 15.08.2026)

Заход отвечает на ОДИН вопрос: есть ли из чего строить эталон. **Регрессия не строилась,
тренажёр не запускался и не правился, кейсы не заводились, бот не трогался, о работе
менеджеров выводов нет.** Мутаций ноль: единственный сетевой вызов — GET-экшен `clients`
боевым клиентом моста (`create_booking`/`close_booking`/`add_transaction` не звались ни разу).

**ВЕРДИКТ ОДНИМ СЛОВОМ: НЕ СУДИМО.** Пригодных пар «запрос → запись» — **0** при пороге 30.
Причина названа числом в §2: однозначного признака сцепки на разрешённом срезе нет ни одного.

## 0. Что читалось

| источник | что это | объём |
|---|---|---|
| `client_chats.anon.jsonl` | обезличенный корпус диалогов | 710 диалогов, 31 245 сообщений, 2025-06-01 02:27 … 2026-05-31 12:39 (замер этой сессии) |
| база броней | вкладка «клиенты» таблицы MANAGER, живой GET `clients` (`filter=all`) | 1278 строк, из них **Завершена 1260** |

Исходный необезличенный `client_chats.jsonl` **не открывался ни одной веткой** — ни один
скрипт захода его имени не содержит. Цена из диалогов не бралась вовсе (§5).

## 1. ШАГ 1 — потолок метода, ДО всякой работы

Окно корпуса — ровно год, 2025-06-01 … 2026-05-31. Завершённые брони по `date_start`:

```
ЗАВЕРШЁННЫХ: 1260
  в окне корпуса 2025-06-01..2026-05-31 : 356   (28.3 %)
  раньше окна                            : 884   (70.2 %)
  позже окна                             :  16   ( 1.3 %)
  без даты / битая дата                  :   4   ( 0.3 %)
```

**Потолок метода — 356 броней из 1260, то есть 28.3 %.** Семь броней из десяти лежат вне
годового окна корпуса просто по датам: база уходит на 2022-09, а корпус снят один раз
01.06.2026 и с тех пор не обновлялся. Это верхняя граница ДО любых потерь на WhatsApp
(владелец их знает и принимает) и ДО вопроса о сцепке.

**Край окна.** Разговор идёт РАНЬШЕ начала аренды, поэтому бронь, начавшаяся сразу после
конца окна, могла обсуждаться внутри него: таких **2** в пределах 7 суток, **5** — 14, **13** —
30. Обратный край (бронь внутри окна, а разговор до 2025-06-01) корпусом не измерим вовсе.
Оба края меняют 356 на единицы процентов и вывода не двигают.

## 2. ШАГ 2 — признак сцепки: искали В ДАННЫХ, а не придумывали

Живая строка базы отдаёт мостом 23 поля. Опознавательных среди них четыре, и каждое
проверено пробой против корпуса. Значения полей жили **только в памяти процесса**, на диск
не писались и ниже не приводятся — только счётчики.

| признак | что в базе (живой замер) | что в разрешённом корпусе | исход |
|---|---|---|---|
| **`@ник` телеграма** (колонка контактов + примечание) | заполнен у **632 строк из 1278** (49.5 %), **403 разных ника** | сверка всех 403 против текста и шапки 710 диалогов: **совпало 0** — и как `@ник`, и голой подстрокой | **мёртв** |
| **телефон** | **644** разных хвоста по 9 цифр | совпало **0**; `peer_phone` пуст у **710 из 710** | **мёртв** |
| **имя** (колонка D) | заполнено у **1277 из 1278**, 1143 словоформы | совпало 14 форм, но 5 из них живут в 4–24 диалогах каждая (обычные слова, не личности); ровно по одному диалогу дают **9 форм → 9 диалогов (1.3 %)** | **не сцепка** |
| **`booking_id`** (колонка Y) | **пуст у 1278 строк из 1278** | — | **мёртв в источнике** |

Ноль по нику — не сбой пробы, а **устройство обезличивания**: шапка записи заменена ярлыком
у всех 710 диалогов (`peer_name` → `Клиент_NNN`, `peer_username` → `профиль_NNN`, телефон
вычищен), в тексте уцелел ровно **1** ник в 5 вхождениях — публичный контакт самой компании.
Ключ сцепки существует в обоих источниках, но в разрешённом срезе он **стёрт по замыслу**, и
восстановить его можно только исходным необезличенным файлом — открывать его задача прямо
запрещает.

**Три исхода числом (единица счёта — диалог корпуса):**

```
ОДНОЗНАЧНАЯ  :   0  из 710
НЕОДНОЗНАЧНАЯ:   0  из 710   (9 диалогов ловятся редкой словоформой имени —
                              это подстрока, а не ключ, и за сцепку не выдаётся)
НЕ НАЙДЕНА   : 710  из 710
```

**Эвристика за сцепку не выдаётся.** Ближайший запасной ключ — «модель + дата начала» — измерен
и как ключ негоден даже при идеальном извлечении из текста: на 356 бронях окна он даёт **39
неоднозначных ключей, под которыми 87 строк — 24.4 %**; с добавлением даты конца остаётся
**15 ключей / 31 строка (8.7 %)**. Ключ, который в четверти случаев указывает на несколько
броней, эталона не даёт, а даёт тихо неверные пары.

## 3. Потолок ПОСЛЕ сцепки — на случай, если владелец её откроет

Это **проекция**, а не замер: она говорит, чего стоит ждать, если необезличенный файл будет
разрешён. Числа базы в ней живые, доли корпуса — измеренные, произведение — оценка сверху.

- из 356 броней окна **ник вообще есть только у 145 (40.7 %)** — остальные 211 не сцепятся и
  после расобезличивания;
- 145 строк дают **96 разных ников**; у **69** из них ровно одна бронь в окне, у **27** —
  больше одной (на них 76 строк базы: 69 + 76 = 145). С учётом броней ВНЕ окна ников с
  несколькими бронями в базе — **34 из 96**. То есть сцепка «диалог → бронь» по нику остаётся
  **один-ко-многим** для трети клиентов;
- значит однозначное ядро — **не больше 69 пар**, а строго — **62**: у семи ников из этих 69
  есть брони вне окна, и диалог мог относиться к ним. И это ДО проверки, что диалог такого
  клиента вообще попал в корпус;
- клиент называет дату хоть раз в **49.9 %** диалогов → пар с запросом **≈ 31–34**, то есть
  ровно у порога 30;
- пар, где клиент ПРАВИЛ запрос (§4, ≥3 разных дат — 19.5 % от называющих даты), выходит
  **≈ 6–7**.

Главный пункт задачи — «совпало ли ПОСЛЕДНЕЕ упоминание с записью» — держался бы, таким
образом, на **шести-семи** случаях. Расобезличивание порога не спасает.

## 4. ШАГ 3 — не выполнялся; что измеримо БЕЗ сцепки

Извлечение по сцепленным диалогам невозможно: сцепленных ноль. Два первых пункта шага 3 от
сцепки не зависят и замерены по корпусу — они показывают, что **сигнал на стороне диалога
есть, а нет именно сцепки**:

1. **клиент называет дату аренды хоть раз — 354 диалога из 710 (49.9 %)**;
2. **называет больше одной разной даты — 170 (23.9 %)**. Это ВЕРХНЯЯ граница «клиент правил
   запрос»: диапазон «с 3 по 10» сам по себе даёт две даты, и таких диалогов **123**. Более
   честный признак правки — **три и больше разных дат: 69 диалогов (9.7 %)**;
3. **совпадение последнего упоминания с базой — НЕ ИЗМЕРИМО** (нет сцепки). Это и есть главный
   пункт, и он остался без ответа;
4. попутно: модель парка клиент называет в **222** диалогах, и модель, и дату вместе — в **145**.

Распределение «разных дат у клиента»: 1 → 184, 2 → 101, 3 → 31, 4 → 16, 5 → 8, ≥6 → 14.

## 5. Цена из диалога не бралась

По постановке владельца: явную цену называют лишь 4.2 % ответов менеджера, а 25.4 % сверяемых
лежат вне полосы прайса ([`2026-08-15-client-dialog-corpus-recon.md`](2026-08-15-client-dialog-corpus-recon.md) §5).
Из диалога брались бы только даты и модель; цена — только из базы. Поскольку пар ноль, ни то,
ни другое в дело не пошло.

## 6. ШАГ 4 — вердикт и чего не хватает

**НЕ СУДИМО.** Пригодных пар **0** (порог 30). Не хватает ровно одного — **сцепки**, и это
развилка владельца, а не пробел разведки:

- **сигнал есть**: 354 диалога с датами, 222 с моделью, 145 с обоими; роли размечены фактом
  Telegram, а не догадкой;
- **запись есть**: 356 завершённых броней в окне корпуса;
- **связать их нечем**: 0 совпадений по нику (403 проверено), 0 по телефону (644), `booking_id`
  пуст у всех 1278 строк, имя даёт 9 диалогов подстрокой и ключом не является.

Развилка на решение владельца — **разрешить ли сцепку через необезличенный корпус** (пары
считались бы по `@нику`: он есть у 145 броней окна из 356). Ответ «да» стоит расобезличивания и
даёт по проекции §3 около 34 пар и около 7 случаев с исправлением клиента — то есть даже тогда
главный вопрос упирается в единицы наблюдений. Ответ «нет» закрывает тему эталона по этому
корпусу целиком. Заход решение НЕ принимает и ничего под него не готовит.
