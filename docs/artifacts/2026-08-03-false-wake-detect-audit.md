## 2. ЧЕМ ПРАВИЛЬНО МЕРИТЬ СОН

### 2.1 Боевой источник — `QueryUnbiasedInterruptTime`, и он уже лежит в этом файле

`kernel32.QueryUnbiasedInterruptTime` (Win7+) — несмещённое время прерываний: в S3/гибернации
оно **не тикает**. `time.monotonic()` на Windows — это `GetTickCount64`, смещённое, проспанное
в нём есть. Разница двух часов и есть сон ЧИСЛОМ.

Живая сверка этого захода (03.08.2026 04:53:22), два независимых источника:

```
GetTickCount64             = 358 581,9 c   (= time.monotonic на Windows)
QueryUnbiasedInterruptTime = 326 297,4 c
разница (проспано с загрузки) = 32 284,6 c = 8,97 ч
Power-Troubleshooter id=1     = 32 286   c = 8,97 ч
расхождение                   =      1,4 c
```

Почему этот источник **нельзя спутать с залипанием сети**: висящий сокет жжёт несмещённые часы
ровно так же, как настенные, — разница остаётся 0. Это свойство конструкции, а не порога.

**Где он уже есть и чего не хватает.** `pc_orchestrator.py:1067` `awake_monotonic()`; строка
`6785` уже считает `slept = gap - (awake_now - _loop_prev_awake)`. Но считает её **после того,
как решение принято**: сам детект `_woke_from_sleep` (`5513`) судит по
`(now - prev) > POLL_SEC + WAKE_JUMP_MARGIN` и о часах бодрствования не знает. Правильный
инструмент лежит на две строки ниже неправильного решения — `slept` идёт только в текст
WARNING'а и в `report_long_sleep`.

**Запас порога обязателен.** `slept > 0` не годится: суточная поправка службы времени (~2,8 с)
даёт фантомный сон — ровно так родилось единственное «сна 2с». Запас **≥ 60 с** (то же число,
что `WAKE_JUMP_MARGIN`) закрывает это с гарантией: наибольший ложный `slept` = 2 с, наименьший
настоящий сон в логе = 32 286 с. Между ними четыре порядка.

Применить критерий `slept > 60` к данным окна: **671 → 1 срабатывание.** Ровно тот, что правда.

### 2.2 Внешний источник — для разбора постфактум, не для цикла

```
Get-WinEvent -FilterHashtable @{LogName='System';
  ProviderName='Microsoft-Windows-Power-Troubleshooter'; Id=1}
```
Даёт дословно `Sleep Time` / `Wake Time` / `Wake Source`. В горячий цикл не годится — запрос
журнала стоит сотни мс.

**Замеренная ловушка: `Kernel-Power 107` для момента пробуждения НЕПРИГОДЕН.** Для сна 30.07
событие 42 стоит `03:43:15`, событие 107 — `03:43:16`: **одна секунда** на сон длиной 8 ч 58 м,
потому что 107 пишется до ресинхронизации часов. Годное деление: **42** — сколько раз и когда
машина УХОДИЛА в сон; **Power-Troubleshooter id=1** — интервал целиком.
`powercfg -lastwake` отдаёт только источник последнего пробуждения без времени — для счёта
бесполезен (проверено: «Кнопка питания», ни одной метки времени).

`powercfg /a` этого ПК: доступны **S3 и Гибернация** (+ быстрый запуск); S0 low-power не
поддерживается — то есть сон здесь всегда даёт настоящий разрыв, а не «современный ждущий».

## 3. ЧТО СЛОМАЕТСЯ, ЕСЛИ ДЕТЕКТ ВЫКЛЮЧИТЬ ВОВСЕ

Греп `_woke_from_sleep` / `_client_grace_until` по репозиторию: потребителей ровно **два**
(`pc_agent.py` читает только дисковый снимок надзора, grace не видит). Тестов, прибивающих
поведение, — три файла.

### Плечо 1: grace контур-вотчдога — снимается ТРЕТИЙ слой из трёх, и он же вредит

`_client_grace_until = now + WAKE_GRACE_SEC(120)` (`6783`), потребитель — `5364`.
Назначение по классу #171: на только что проснувшемся ПК CIM-поиск медленный, «пусто»
недостоверно → ложный вердикт «мёртв» → лишний старт → дубль → Conflict (синглтон).

Класс #171 держат **три** слоя, grace — слабейший:

| слой | строка | что делает |
|---|---|---|
| (а) finder различает три исхода | `5389` | `pids is None` → `check_failed` → пропуск БЕЗ рестарта |
| (б) «мёртв» = три условия | `5397-5404` | finder успешен И процесса нет И свой лог протух > 120 с |
| (в) grace после «пробуждения» | `5364` | 120 с без вердиктов |

Плюс анти-флап `cooldown 900 с` и halt после 3 смертей. Снятие (в) класс #171 **не открывает**.

**А в этом окне (в) стоило больше, чем спасло.** Подавлено **135 тиков** вотчдога. И подавленный
тик списывается как полноценный: `maybe_client_watchdog` ставит `_client_watch_last_run = now`
(`5465`) **до** вызова тела, а тело на grace выходит сразу (`5367`). Значит 120 с grace покупают
**300 с** отложенных вердиктов (`CLIENT_WATCH_SEC`):

```
135 подавленных тиков × 300 с = 40 500 с ≈ 11 ч 15 м слепоты за 7 суток (6,7 % окна)
```

Это не теория. В том же окне вотчдог сделал **4 настоящих подъёма**:

| время | кто | лежал |
|---|---|---|
| 30.07 01:20:08 | moderation_bot | лог 0 с назад |
| 31.07 12:58:42 | pc_agent | **1103 с** |
| 31.07 15:13:05 | userbot | 435 с |
| 31.07 15:33:36 | userbot | **1229 с** |

Последний случай — прямое касание: между 15:13 и 15:33 ложный детект сработал **4 раза**
(15:17:49 · 15:21:43 · 15:26:37 · 15:31:16), и в 15:18:27 в логе стоит
`контур-вотчдог: grace после пробуждения ПК (81с осталось) — вердикты отложены`. Проектный срок
обнаружения — 300 с, userbot пролежал 1229 с, вчетверо дольше.

И симметрично: вердиктов `СЛЕП` и `не смог проверить` за 7 суток — **0 и 0**. Та самая медленная
CIM, ради которой grace заведён, за неделю не случилась ни разу.

### Плечо 2: сигнал о долгом сне — ЕДИНСТВЕННЫЙ канал, его терять нельзя

`report_long_sleep` (`5566`): одна строка в журнал + одна карточка в тему 328 с числом
накопившихся задач lane=pc. Греп по репо: другого производителя карточки `🛌 ПК СПАЛ` **нет**.
Выключить детект целиком — значит, что настоящий восьмичасовой сон (когда контур ДЕЙСТВИТЕЛЬНО
стоял и клиентский бот ДЕЙСТВИТЕЛЬНО был недоступен) не увидит никто. Ровно это и произошло
30.07, до появления сигнала.

## 4. РЕКОМЕНДАЦИЯ (НЕ ПРИМЕНЕНО, решение за владельцем)

1. **Не выключать.** Плечо 2 — единственный канал о реальном простое контура.
2. **Развести два разных события.** Скачок wall-clock — это «ДЛИННЫЙ ВИТОК» (мост залип либо
   задача шла внутри цикла), а не пробуждение. Логировать его как длинный виток и уровнем
   `INFO`; имя «детект пробуждения ПК» в 670 случаях из 671 — неправда прямо в строке лога.
3. **Сном звать только `slept > 60` по часам бодрствования** (`awake_clock_available()` →
   иначе прежний разбор по скачку, fail-open). По данным окна: 671 → 1.
4. **Grace не должен жечь слот троттлинга.** Перенести `_client_watch_last_run = now` за
   проверку grace (или не штамповать при исходе `grace`), иначе 120 с тишины стоят 300 с
   слепоты — измерено 135 раз за неделю.

Ничего из перечисленного в этом заходе не сделано.
