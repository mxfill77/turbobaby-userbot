# Почему с ПК нет следов в мозге (разбор 14.08.2026, только чтение)

**Основание:** ожидание О4 на VPS звучит с 05:30 UTC — «с ПК нет ни одного следа», 16 часов
при пороге 16. Последняя запись ПК в `cowork_log` — 13.08 13:26 UTC. Владелец подтверждает:
машина работает.

**Итог одной строкой: не молчит НИКТО из троих. Контур ПК цел — молчит ИСТОЧНИК СОБЫТИЙ.**
Наблюдатель тикает, оркестратор крутит виток, мост с этой машины отвечает. За 16 часов на ПК
не произошло ничего, что по коду порождает строку журнала.

Все замеры сделаны только чтением. Ни один процесс не поднят, не погашен и не перезапущен,
код не менялся, `.env` не открывался.

## 1. Наблюдатель `TurboBabyExpectPC` — ЕСТЬ, тикает; метаданные задачи из этой сессии НЕ ЧИТАЮТСЯ

Прямой запрос отвечает отказом доступа, а не отсутствием:

```
schtasks /query /v /fo LIST /tn TurboBabyExpectPC
ERROR: Access is denied.                                   exit=1
```

**Контрольный опыт** (без него «Access is denied» читалось бы как «нет задачи»):

| запрос | ответ | вывод |
|---|---|---|
| `/tn NoSuchTaskZZZ99` (заведомо нет) | `ERROR: The system cannot find the file specified.` | так выглядит ОТСУТСТВИЕ |
| `/tn TurboBabyExpectPC` | `ERROR: Access is denied.` | так выглядит ЗАПРЕТ ЧТЕНИЯ при наличии |
| `/tn TurboBabyRC` (контроль-успех) | `Last Run Time: 06.08.2026 19:38:27`, `Last Result: 267009`, `Run As User: mxfill1` | читается свободно |

То же и вторым инструментом: `Get-ScheduledTask -TaskName TurboBabyExpectPC` → «не найдены
объекты», а `Test-Path C:\Windows\System32\Tasks\TurboBabyExpectPC` → `UnauthorizedAccessException`
(при `True` для `TurboBabyRC`). Оба API молча пропускают задачи, которые вызывающему не дают
прочитать: задача заведена под SYSTEM/`/RL HIGHEST`, сессия не повышена.

**`Last Run Time` и `Last Result` этой задачи назвать честно НЕЛЬЗЯ** — путь к ним закрыт правами.
Снять их можно только из повышенной сессии (это отдельное действие, здесь не выполнялось).

**Но работу наблюдателя видно косвенно и однозначно** — по его собственному файлу состояния:

```
D:\turbobaby-bot\tmp\expect_pc\state.json   276 байт   14.08.2026 15:14:40 (местное)
{"turn": {"raw": "2026-08-14T08:13:28.214808+00:00", ...}, "waits": {}, "open": {},
 "mod": {"mtime": 1786695267.1, ..., "silent": 0.0, ...}}
```

Замер сделан в 15:18 местного — файлу 4 минуты при интервале 10 минут. Писать его больше некому:
`pc_orchestrator.py` имя `expectations_pc` содержит **только в комментарии** (строка 8626), модуль
не импортирует и не зовёт. Значит state.json обновляет сам `expectations_pc_run.py`, запускаемый
задачей. `open: {}` — открытых эпизодов нарушений нет.

## 3. Мост с этой машины ОТВЕЧАЕТ

Одна проба, только чтение (`get_pending`, полоса pc). Взят штатный модуль наблюдателя: у флага
`--status` `dry=True`, поэтому состояние не пишется и заметки не отправляются; `.env` читает сам
процесс — агентский код секретов не касается.

```
venv\Scripts\python.exe expectations_pc_run.py --status
очередь ПК: движется · оборот демона: даёт оборот
модербот (работа, не жизнь): делает работу
нарушений: 0 []
exit=0        elapsed_sec=17
```

Мост ответил за **17 секунд**, очередь прочитана, застрявших строк нет. Канал записи в мозг с ПК
исправен.

## 4. Что на самом деле молчит: источник событий

Последняя строка ПК в журнале и её причина видны в логе демона дословно:

```
2026-08-13 20:24:51,381 INFO ревизор: since=2026-08-13T07:24:42.865586+00:00 → окон с активностью 1 (всего строк drafts 458)
```

(20:24 местного = 13:24 UTC.) Ей соответствуют две последние записи локального реестра
`cowork_log.ledger`:

```
{"ts": "2026-08-13T13:25:05.328639+00:00", "line": "NOTE ... Orchestrator: ревизор: 1 окон с активностью с прошлого прогона — пакеты собраны"}
{"ts": "2026-08-13T13:26:15.579101+00:00", "line": "NOTE ... Orchestrator: ревизор: 1 окон, чисто"}
```

Дальше ревизор отработал **трижды**, и каждый раз впустую — при нуле окон он в журнал не пишет:

```
2026-08-14 02:25:32,716 INFO ревизор: since=2026-08-13T13:24:51.340992+00:00 → окон с активностью 0 (всего строк drafts 458)
2026-08-14 08:26:47,834 INFO ревизор: since=2026-08-13T19:25:32.647617+00:00 → окон с активностью 0 (всего строк drafts 458)
2026-08-14 14:27:26,978 INFO ревизор: since=2026-08-14T01:26:47.803100+00:00 → окон с активностью 0 (всего строк drafts 458)
```

Три остальных источника строк тоже пусты:

- **Задачи очереди.** Последняя взятая — **#507, 13.08 06:07:09 UTC** (`pc_orchestrator.task_started.json`,
  pid 17044, файл с тех пор не менялся). После неё демон не брал ни одной — и при этом О1 говорит
  «очередь движется», то есть неразобранных строк в очереди нет. Нечего брать, а не «не берёт».
- **Сессии Claude Code.** `dispatch_notify.log` обрывается на `2026-08-13 17:48:00,088 | хук=stop`
  (10:48 UTC) — с тех пор до этой сессии ни одна не завершалась.
- **Неудачные записи.** Файла `cowork_log.spool` **нет**. Писатель кладёт в спул любую не ушедшую
  строку и чистит спул только после успеха; реестр (`ledger_add`) отмечает **успешно ушедшие**.
  Пусто и там, и там ⇒ записи не терялись — их просто не пытались делать.

## 5. Ошибки за 16 часов: есть, но не они закрыли канал

За окно 13.08 23:18 → 14.08 15:18 местного в логе демона **26 строк: 21 INFO, 5 WARNING,
ни одной ERROR/CRITICAL, ни одного `Traceback`, ни одного рестарта.** Все пять WARNING — известный
класс расписки моста (первое появление ещё **05.08.2026 12:39:55**, не новое):

```
2026-08-14 00:05:11,293 WARNING get_pending(in_progress) ошибка: BridgeTransportError — мост ответил, но обмен не завершён (BridgeTransportError): второе плечо моста (echo) бросает обратно на наш же /exec — ключ расписки мёртв. ... — связь есть (реапер молчит: не прочитал полосу — не сужу задачи)
2026-08-14 09:58:06,412 WARNING get_pending(in_progress) ошибка: TimeoutError — СВЯЗИ НЕТ: до моста не дошли — The read operation timed out [TimeoutError, предел ожидания 90с] (реапер молчит: не прочитал полосу — не сужу задачи)
```

Последние живые строки перед тишиной лога — вот эти две (09:58) и следом ревизор в 14:27.
Промежуток 09:58 → 14:27 без строк **остановкой не является**: heartbeat в это время обновлялся,
а «залипание витка» и «watchdog» печатаются только по событию, чистый виток строк не даёт.

**Отдельно назвать (деградация, а не поломка):** вечером 13.08 виток регулярно растягивался на
**354–592 с** на вызове моста — «залипание вызова моста (сна 0с, связь есть)», примерно каждые
5–8 минут с 19:08 до 21:43. Сегодня с 09:58 таких строк нет вовсе, и живая проба уложилась в 17 с.
Мост с ПК медленный волнами, но канал жив; на журнал это не повлияло.

## Остатки (НЕ делалось, требует решения владельца)

1. `Last Run Time` / `Last Result` задачи `TurboBabyExpectPC` из неповышенной сессии не читаются.
   Чтобы назвать их фактом, нужен один запрос `schtasks /query /v /tn TurboBabyExpectPC` из
   повышенной сессии.
2. Вопрос «почему в очереди ПК больше суток нет задач» — это сторона VPS, здесь не разбиралось.
3. Класс «залипание вызова моста на 350–590 с» живёт с 05.08 и по-прежнему не закрыт.
