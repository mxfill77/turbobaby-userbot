## Главный ответ

1. **Живых вызовов под тремя именами в этом заходе НЕТ, и это не «не успел».** Вызов под любым
   слотом требует загрузить секретный файл окружения сервера в процесс оболочки. Это класс `env`:
   красный и по гарду, и по блоку запретов самого задания («`.env` и конфиги не читать»).
   Headless-заход его не делает и обхода не ищет. Вместо обхода собрана **одна команда
   владельцу**, которая печатает ровно то, что просит п.2 (см. §5).
2. **Живым сейчас измерено всё, что меряется без секрета, и оно показывает: с последнего ответа
   поставщика не изменилось НИЧЕГО.**

| что | 71r (22.09 17:49–18:05 UTC) | сейчас (22.09 19:32 UTC) |
|---|---|---|
| файл окружения демона | 374 B, mtime `2026-09-19 16:46:26.930750239` | **то же до наносекунды** |
| копии `.bak-…` рядом (след инсталлятора 71s) | — | **нет ни одной**: инсталлятор не запускался |
| демон `orchestrator-daemon` | active, MainPID 2329989, NRestarts=0, старт 22.09 02:00:40 UTC | **то же самое** |

   Значит, последние ответы поставщика по слотам остаются последними. Действующее/B:
   **429** в 16:32:40 и 16:33:21 UTC («You've hit your weekly limit · resets Sep 27, 9am (UTC)»).

3. **Премиса задания о времени неверна.** «71r снят 7.5 часов назад» не так: на момент замера от

## 1. Что утверждал 71r (премиса, не приговор)

Одной строкой: **действующее = 429 недельный лимит (сброс 27.09 09:00 UTC); B = то же значение
побайтно, поэтому тот же 429; A = 401 «вход не принят»; основной учётки ни в одном имени нет.**

из лога демона и транскриптов (задача #53). Равенство «действующее == B» выведено из строки
демона `retry (слот=B, следующий=A)`: `active_slot()` сравнивает значения равенством. Вывод
законный, но это вывод, а не вызов.

## 3. Сверка со словами владельца (п.3)

* **«На текущем лимита нет» — по последнему ответу поставщика НЕ сходится.** Действующий вход
  получил 429 со сбросом 27.09 09:00 UTC. После этого не менялись ни файл, ни процесс демона,
  значит действующий — тот же вход. Недельный лимит раньше названной минуты могло снять только
  событие на стороне учётки: докупка, смена плана. Его отсюда не видно, и исключить его нельзя.
  Поэтому живой статус действующего **НЕИЗВЕСТЕН до пробы**, а не «429 точно».
* **«Живые ключи, на одном лимит» — сходится наполовину.** Лимит действительно на одном, но
  разных входов в трёх именах **два, а не три**. Второй (A) не «живой ключ с запасом», а **401**.
* **Итог: сошлось с 71r, а не со словами владельца** — по последнему ответу поставщика.
  Окончательно решит только живая проба, и она у владельца (§5).

### «Может, проблема с ПК-полосой» — что показывает ПК-сторона

* **ПК-полоса за 22–23.09 не получила ни одного 401/429.** Лог демона ПК: задачи полосы ПК #46–#58
  (номер 53 — серверный) взяты и закрыты `done`, кроме двух. Обе — коды закрытия, а не отказ входа:
  * **#54** (это 71p): `needs_approval`, карточку выписал гард;
  * **#56** (это 71r): `failed · unbacked_red · ✋` (строка `pc_orchestrator.log` 01:00:37 местного).
    Исполнитель напечатал заявку `NEEDS_APPROVAL: op=env | Выпустить годовой токен…`, гард
    карточки не выписывал, и демон по замку происхождения закрыл задачу «выполни вручную». Работа
    при этом сделана (коммитов 2, записей журнала 4). **Скорее всего, именно карточку «⚠️ задача
    #56 — закрытие не состоялось» владелец и прочёл как проблему ПК-полосы.**
* **ПК-полоса на вход сервера не влияет.** ПК ходит подпиской основного профиля (лог: «выбор
  учётки строителей: слово ОСНОВНОЙ — ключ CLAUDE_CONFIG_DIR снят»), сервер — токеном из своего
  файла окружения. `CLAUDE_CODE_OAUTH_TOKEN` в коде ПК встречается 0 раз (71r §4).

## 4. Если проба покажет, что действующий отвечает 200: где тогда искать (п.4, по коду сервера)

* **Ротация `limit_slot` первый заход не уводит — никогда.** Ребёнок получает копию окружения
  демона. Подмена `child_env[VAR_ACTIVE] = <слот>` (`orchestrator_daemon.py:1567–1570`) стои́т только
  на повторе. Повтор разрешён только на машинно доказанном 429 (`limit_slot.LIMIT_STATUSES =
  frozenset((429,))`; на любом другом конверте `plan()` отдаёт `ACT_NONE`). Действующий с ответом
  200 до слота A не доводит ни одной веткой.
* **Где тогда теряется рабочий вход:** в расхождении «файл ↔ процесс демона». Демон держит
  окружение со старта (22.09 02:00:40 UTC) и файл не перечитывает. Проба же читает ФАЙЛ. Поэтому
  проба печатает `file_mtime` против `daemon_start`. Сейчас файл старше старта (19.09 < 22.09),
  то есть файл и процесс совпадают. Если проба покажет 200 при неизменном файле, значит, вход
  починили на стороне учётки, и следующая задача сервера пойдёт сама, без рестарта.

## 5. Если действующий отвечает 429 (п.5)

По последнему ответу — **да, 429**. Слота с ответом 200 среди трёх имён по последним ответам
**нет** (A — 401). Единственный известный рабочий вход — основная учётка, но её годового токена
не существует (71r §4). Путь прежний: `vps_token_install.py` (71s) после `claude setup-token`
руками владельца, либо ждать 27.09 09:00 UTC.

### Команда владельцу (п.2 руками, одна строка, PowerShell из `D:\turbobaby-bot`)

```
venv\Scripts\python.exe vps_token_install.py --probe-slots
```

Что она делает: спрашивает у юнита адрес файла окружения (`systemctl show … -p EnvironmentFiles`)
и по каждому из трёх имён делает **один** ssh-заход `bash -s`. В каждом заходе:
* файл загружается в оболочку, поток ошибок закрыт — обломок токена не напечатается;
* значение сравнивается с действующим, наружу уходит 1/0;
* идёт **один** вызов `claude -p "Reply with exactly: OK" --model claude-opus-5 --output-format json
  --no-session-persistence --setting-sources project` из `/`, значение передаётся префиксом
  `CLAUDE_CODE_OAUTH_TOKEN=`, `ANTHROPIC_API_KEY` снимается, как у демона. Хуки сервера не
  зовутся, транскрипт не пишется.

Печатает: имя · действующий да/нет · `is_error` · статус (200/429/401) · текст поставщика. Потом
свод «200/429/401», приговор по действующему и признак «файл не менялся после старта демона».
Сырой вывод (без значений) — в `tmp/vps_slots_probe/`, откуда его прочтёт следующий заход ПК.
Файл не правится, демон не трогается. Цена: не больше 3 дешёвых вызовов, около минуты.
Модель `claude-opus-5` выбрана не случайно: этой головой ходит серверный исполнитель (лог
16:32:14 «запрошена=claude-opus-5»). Лимит может вестись по модели, и проба на другой голове
могла бы зеленеть там, где исполнитель упирается.

## 6. Попутно найден и починен дефект судьи инструмента 71s (он уже лежал на пути владельца)

`verdict_of_probe` читал машинное поле **`apiErrorStatus`**: так оно называется в ТРАНСКРИПТЕ
`.jsonl`. В живом конверте `--output-format json` поле называется **`api_error_status`** (замер
71r `probe_neg.json`; так же читает серверный `limit_slot.envelope`). Вторая беда — хвост хука
`SessionEnd hook … failed` под конвертом ронял `json.loads` («Extra data»).

Отрицательная сверка: новые голдены прогнаны на копии HEAD (`tmp/vps_slots_probe/old/`):

| вход | код HEAD (до правки) | после правки |
|---|---|---|
| конверт `api_error_status:401`, в тексте «weekly limit» | **«429 лимит» — неверно** | 401 вход не принят |
| чистый конверт `is_error:false` + строка хука ниже | **«иное» — неверно** | зелено |

Цена дефекта в живом ходу инсталлятора: чистый ответ с хвостом хука → «иное» → **откат только что
вписанного рабочего токена**. Правка: `parse_envelope` (`raw_decode`, хвост не читается) +
`status_of` (оба имени поля, змеиное первым). Регресс `test_vps_token_install`: **23 → 35 OK**,
`--selftest`: негодных 11 → отказано 11, позеленело на отказных конвертах 0.

## Границы захода

* **Живой статус каждого слота сейчас — НЕИЗВЕСТНО** (проба = класс `env`, за владельцем).
* Докупал ли владелец лимит или менял план второй учётки после 16:33 UTC — НЕИЗВЕСТНО.
* `probe()` самого инсталлятора (шаг «е» после вписывания) по-прежнему идёт из `/root` с
  пользовательскими настройками, то есть с хуками сервера. Его не трогал: остаток на следующий
  заход.
* Режим `--probe-slots` против боевого сервера **не запускался ни разу**. Проверен тестами на
  подменённом ssh и `bash -n` на всех трёх программах.
