**Заход:** read-only, 08.08.2026, ПК-полоса, HEAD `b2cb0b3`. Правок кода нет, коммита нет, пуша нет,
гейт не гонялся. Клиентский контур не трогался: живая БД `moderation_ipc.db` **не открывалась**

Источники: код проверки (`suggest.py`, `pc_orchestrator.py`, `client_contour.py`) и её собственные
журналы (`pc_orchestrator.log`, `moderation_bot.log`).

## Итог одним абзацем

Находка **ложная**, и это следует из кода, а не из правдоподобия. Чек сравнивает суммы депозита
**по всему тексту сразу**, не привязывая сумму ни к модели, ни к брони, ни к байку: ветка «две
разные суммы» работает на строке `s` целиком (`suggest.py:6512`). Шесть сумм из карточки — 3000,
5000, 7000, 15000, 20000, 25000 — это **дословно полный набор депозитных ступеней парка** из
прайс-блока, который печатает сам код (`suggest.py:280–285`, 20 моделей). Один объект шести ступеней
иметь не может; значит текст перечислял модели, а чек сложил их депозиты в одну кучу. Маршрутом
находка мимо ворот клиентского контура прошла не по решению, а **по устройству**: ворота стоят
только в ветке `act == "task"`, а `#92` рождается с `action="owner"` и пустым `task_text`.

## 1. Группирует ли проверка депозиты по объекту — НЕТ (строками кода)

`suggest.py:6501–6522`, `_smoke_deposit_conflict` — вся логика чека:

```python
def _smoke_deposit_conflict(text) -> str:
    """Противоречие депозита → строка-описание, иначе ''. Конфликт: ДВЕ разные суммы депозита ИЛИ
    сумма депозита и «паспорт» ТРЕБУЮТСЯ ОБА (KB: деньги ЛИБО паспорт, не оба).
    ...
    s = text or ""
    deps = sorted({int(m.group(1).replace(" ", "")) for m in _SMOKE_DEP_AMOUNT_RE.finditer(s)})
    if len(deps) > 1:
        return "разные суммы депозита: " + ", ".join(f"{v} ฿" for v in deps)
    for m in _SMOKE_DEP_PASSPORT_RE.finditer(s):
        clause = _clause_at(s, m.start())
        amount = _SMOKE_DEP_AMOUNT_RE.search(clause)
        if not amount or _SMOKE_DEP_CHOICE_RE.search(clause):
            continue                          # суммы в этой фразе нет ЛИБО выбор предложен — норма
        return (f"и сумма депозита ({int(amount.group(1).replace(' ', ''))} ฿), "
                f"и «паспорт» одновременно")
    return ""
```

Три факта прямо из этих строк:

1. **Ключа объекта в функции нет вообще.** На вход приходит один аргумент `text`; ни модели, ни
   `client_id`, ни брони, ни `_bike_key` в теле нет. Единственный якорь — слово `депозит|залог|
   deposit` в `_SMOKE_DEP_AMOUNT_RE` (`suggest.py:6476–6477`), то есть якорь **суммы**, а не объекта.
2. **Ветка «две суммы» смотрит ВЕСЬ текст.** `finditer(s)` по `s` целиком, множество → `set`, и
   `len(deps) > 1` — единственное условие. Ни клаузы, ни строки, ни абзаца.
3. **Понятие «в одной фразе» в этом же коде УЖЕ есть — но только для второй ветки.** Ниже, в паре
   «сумма + паспорт», текст сужается до клаузы: `clause = _clause_at(s, m.start())` (`:6516`), и
   поиск суммы идёт по `clause`, а не по `s` (`:6517`). Функция `_clause_at` (`:6492–6498`) заведена
   ровно затем, чтобы «судить о депозите по ТОЙ ЖЕ фразе, а не по соседней» — и это сужение к
   ветке двух сумм не применено. Асимметрия и есть материальная причина класса.

Вызывающий тоже ничего не группирует. `_smoke_checks` (`suggest.py:6525–6591`) берёт весь клиентский
текст одним куском:

```python
def _smoke_checks(draft, exp) -> list:
    client = client_facing_text(draft)
    ...
    # 6) депозит без самопротиворечия
    conflict = _smoke_deposit_conflict(client)
    checks.append({
        "name": "депозит без противоречий",
        "ok": not conflict,
        "expected": "депозит один: сумма ЛИБО паспорт, без двух значений",
        "fact": (conflict or "депозит согласован"),
    })
```

**Ответ на вопрос 1: нет, не группирует. Проверка не знает, к какому объекту относится сумма, — она
знает только, что сумма стоит рядом со словом «депозит».**

**Но на вывод это не влияет, и вот почему.** Шесть сумм из карточки — это **дословно** множество
депозитных ступеней прайс-блока, который печатает сам код (`suggest.py:275–290`, `CRITICAL_FACTS`):

|---|---|---|

| 25000 | XADV750, R7 | 2 |
| **итого** | | **20 моделей, 6 ступеней** |

Седьмой ступени в блоке нет вовсе: единственная модель вне прайса — `HONDA CLICK 125 — НЕ сдаём`
(`suggest.py:289`), у неё в блоке ни цены, ни депозита. Основание карточки («седьмая ступень 2000
отсутствует, потому что тот байк не сдаётся») кодом подтверждается.

Отсюда вывод, который не зависит от точного числа моделей в окне:

* каждая из шести сумм в коде принадлежит **своей** группе моделей, и ни одна модель не имеет двух
  депозитов ⇒ шесть сумм в одном тексте означают **минимум шесть разных объектов**;
* значит моделей в тексте **не меньше**, чем сумм (6 ≤ N ≤ 20), а «противоречия» нет ни при каком N;
* даже пограничный случай N = 6 (по одной модели на ступень) — это шесть разных байков с шестью
  разными депозитами, то есть **корректный прайс, а не самопротиворечие**.

**Ответ на вопрос 2 словом: находка ЛОЖНАЯ.** Гипотеза Штаба подтверждена: чек сравнил суммы, не
привязав их к моделям.

## 4. Маршрут: по какому признаку находку относят к замороженному контуру и почему эта не попала

**Признак — одна строка** (`pc_orchestrator.py:7459`):

```python
                cl_hit, cl_files, cl_det = _revizor_finding_touches_client(f.get("task_text"))
```

Она зовёт `_revizor_finding_touches_client` (`:7081–7088`) → `client_contour.mentions(task_text, REPO)`
(`client_contour.py:275–300`). Признак судит **по именам файлов, названным в ТЕКСТЕ дев-ТЗ**
(«suggest.py» и голое «suggest»), потому что ревизор ставит текст задачи, а не список файлов. Ярлык
«замороженный контур, нужна отмашка» вешает `_revizor_demote_client_task` (`:7091–7105`), строка
`:7103`:

```python
    g["evidence"] = f"[клиентский контур, нужна твоя отмашка; {why}] {ev}"[:_REVIZOR_EVIDENCE_MAX]
```

**Почему депозитная находка под признак не попала — не по содержанию, а по устройству маршрута.**
Признак стоит ВНУТРИ ветки `if act == "task":` (`:7452`) цикла по находкам **LLM-думателя**
(`:7442` `for pkg in pkgs: findings = _revizor_consult(pkg)`). Детерминированная находка #92 в этот
цикл не заходит вовсе: она создаётся раньше, в `_revizor_postrelease_findings` (`:7339–7342`)

```python

                        "check": name,
                        "evidence": (f"чек «{name}»: {c.get('fact')}")[:_REVIZOR_EVIDENCE_MAX],
                        "task_text": ""})
```

и кладётся в `owner_f` на `:7427` — **до** цикла. У неё `action="owner"` (в ветку `task` не
попадает) и `task_text=""` (признаку нечего читать). Ворота её не видят.

Ирония, проверяемая кодом: если бы признак всё-таки спросили, он ответил бы «клиентская».
`mentions("")` → ни одного имени → fail-closed (`client_contour.py:297–298`):

```python

        return True, [], False                         # ни одного имени → неопределимо → fail-closed
```

**Три соседние находки, ушедшие «заметкой».** Карточка tid=401 за свою жизнь собрала ровно три
находки с этим ярлыком и одну без него (`pc_orchestrator.log`):


Три «д/е/д» получили префикс `[клиентский контур, нужна твоя отмашка; …]` и читаются как заметка о

## 5. Что чинить

**Обе, и в этом порядке: сначала саму проверку (сузить сравнение сумм до объекта — той же клаузой
`_clause_at`, что уже применена к ветке «паспорт»), потом маршрут (детерминированные находки #92/#93
рождаются мимо ворот входа и приходят владельцу без ярлыка замороженного контура);** третьим,
копеечным шагом — писать имя чека в строку лога, иначе цена каждого чека в отдельности не
измеряется. Ничего из этого этим заходом не применено.
