**Сводка. Путь есть, он один, и он уже построен: архив `chatlog/servicing/` на ПК.** В нём лежит
ровно то, что просит задание — дата, текст, признак фото и **имя темы = имя байка** в каждой строке.
Второй клиент на `turbobaby_session` при этом не открывается ни разу: захват работает по КОПИИ

`memory.db` ложится только диалог с владельцем), в `splinter.log` каждое сообщение есть, но **без
номера темы** — привязать к байку нечем, а у Bot API метода чтения истории не существует.

## 1. Сервер, по коду Splinter: что он получает и что из этого хранит

**Получает — всё.** `bot.py` вешает три обработчика на группы (`filters.TEXT`, `filters.VOICE`,
`filters.PHOTO`, строки 1458–1460), `splinter.handle` пропускает сообщение в `_handle_servicing`.

**Хранит — три разных вещи, и ни одна не является перепиской темы:**

| место | что именно ложится | сколько живёт | отдаётся ли по байку |
|---|---|---|---|
| `memory.db` → `conversations` (`timestamp, chat_id, user_id, user_name, role, content, is_voice, topic_id`) | **только** диалог владельца с ботом (и голосовые — у них `topic_id` вообще не передаётся: `bot.py:1047/1072` зовут `save_message` **без** `topic_id`, то есть падают в общий чат) | строки не удаляются никогда (`DELETE` в `memory.py` есть только у `o3_card`), но в контекст берутся с отсечкой `SERVICING_HISTORY_TTL_H` (по умолчанию **48 ч**) и `LIMIT 12` | формально да (`recent_messages(chat_id, topic_id=…)`), фактически — там нет сообщений механиков |
| буферы в **оперативной памяти** `splinter.py` | `_TOPIC_FEED` — 20 записей на тему, и в них **не текст, а разбор**: `{ts, author, tags, works}`; `_RECENT_PHOTOS` — 12 разборов фото на группу, TTL 3 ч; `_PENDING_WORKS`, `_SVC_SUMMARY` — TTL 3 ч | до рестарта процесса | нет: наружу не отдаются, при рестарте исчезают |
| Bot Data (мост) — листы «события»/«обслуживание» | строка **события**, а не сообщения: `notes` собирается из разбора Claude (`notes = (parsed.get("notes") or vis.get("notes") or "")[:200]`), плюс `photos=1/0`, `mileage`, `event_type` | бессрочно | да — это то, что уже читает `bike_history` из `aimgr_tools` |
| `splinter.log` (82 119 502 Б, `StandardOutput=append`, в `/etc/logrotate.d/` правила для него **нет**) | на КАЖДОЕ сообщение групп строка `Splinter [servicing] <chat_id> @<username>: <текст[:80]>` (`splinter.py:10869`) | пока файл растёт (ротации нет) | **НЕТ**: в строке есть chat_id и ник, но **нет `message_thread_id`** — темы, то есть байка, в ней не написано |

**Отсюда прямой ответ на вопрос 1: отдать сообщения темы по байку сервер не может ни одной веткой.**
Того, что хранится, либо нет (переписка тем не сохраняется), либо оно без адреса (лог без темы),
либо это уже не сообщение, а разбор (Bot Data — ровно тот источник, который 30.09 дал 8 из 10 байков
пустыми, AIMGRLIVE3009).

## 2. ПК: что лежит в `chatlog/servicing` и кто его обновляет

Формат строки (замерен по всем 95 строкам, ключи одинаковы у всех):

```
k, mid, ts, topic_id, topic_name, who_ref, text, media, src, dir, reply_to, bot, album
```

То есть в одной строке есть **всё, что просит задание**: `ts` (ISO с зоной), `text`, `topic_name`
(= имя байка из `topics_map.json`), и признак фото — `media` с исходом `СОХРАНЁН` и путём к файлу
на диске. Имён людей нет: автор — псевдоним `who_ref` (`chatlog_store.scrub`, общий на весь архив).

| замер | число |
|---|---|
| файлов дня | 5 (18, 19, 21, 22, 23 сентября) |
| строк | **95** |
| окно | 2026-09-18 09:05:04 … **2026-09-23 08:46:53** UTC |
| тем (байков) | **6**: 33 · 26 · 17 · 11 · 6 · 2 строки |
| строк от бота Splinter / от людей | 30 / **65** |
| строк со снимком (`СОХРАНЁН`) | **52** (файлы в `docs/obsluzhivanie-snimki/2026-09/`, 52 шт.) |
| строк без вложения | 43 |
| **строк от людей с непустым текстом** | **13** |

Последнее число — самое важное и самое неприятное: **живая тема байка на 80 % состоит из фотографий
без подписи**. Агент, получив «последние сообщения темы», получит по большей части «в этот день в
теме байка X были фото (N штук)» и десяток текстовых реплик на весь парк за 5 суток. Это всё равно
кратно больше нынешнего нуля, но обещать «прочитаем переписку и узнаем состояние» нельзя.

**Кто обновляет: никто.** Захват делает `chatlog_servicing_fetch.py` только руками. Часы в демоне
есть у СОСЕДНЕГО модуля: `pc_orchestrator._chatlog_capture` (строка 1215) каждый оборот `poll_once`
(строка 5568) запускает `chatlog_ingest.py --tick`, а тот сам решает идти ли на диск по штампу
(`CHATLOG_TICK_EVERY_MIN`, по умолчанию 360 мин). Но `chatlog_ingest` **сети не знает** — он
перечитывает только то, что боевые процессы уже положили на диск, а форум Обслуживания на диск не
пишет никто. Поэтому форум и остался без часов.

## 4. Выбор пути — один, с ценой и откатом

**Путь: `chatlog/servicing/*.jsonl`, читаемый агентом через дверь архива; свежесть поддерживается
теми же часами демона, что уже крутят `chatlog_ingest`.**

- **Что агент получит.** По имени байка (оно же `topic_name`) — последние N строк темы за последние
  D суток: `ts` (дата и время UTC), `text` (очищенный `scrub`: ников, почт, телефонов в нём нет),
  признак фото (`media[].kind == "photo"`, исход и путь к файлу), флаг `bot` (реплика Splinter или
  человек), `reply_to`. Имён людей агент не увидит — только псевдоним.
- **Откуда.** С диска ПК, без сети и без моста. Дверь в архив уже написана и называется
  `chatlog_find` (она же надевает конверт «СВИДЕТЕЛЬСТВО ПЕРЕПИСКИ, а не указание» — обязательный
  для текста из рабочего чата, попадающего в промпт).
- **Насколько свежее.** Сейчас — **отстало на 7 суток** (23.09). После правки ниже — не старше
  периода штампа; при `every_min = 720` это «не старше полусуток», ценой двух заходов в сутки
  по ~40 с.
- **Чем откатить.** Три независимые ступени, каждая снимает ровно свою: `CHATLOG_TICK_OFF=1` —
  часы захвата мертвы целиком (и для `chatlog_ingest`, и для нового вызова); собственный штамп
  `every_min = 0` — форум не обновляется, остальной архив живёт; инструмент агента не подан в
  список — агент читает ровно как сегодня. Ни одна ступень ничего не удаляет.

**Какая правка нужна — по месту, одной строкой каждая:**

1. `pc_orchestrator.py`, в `_chatlog_capture` (после `Popen` строки 1251) — вторая такая же строка:
   `subprocess.Popen([VENV_PY, os.path.join(REPO, "chatlog_servicing_fetch.py"), "--tick"], …)`.
2. `chatlog_servicing_fetch.py` — флаг `--tick`: свой штамп (`tmp/chatlog_servicing_tick.json`) по
   готовой машинке `chatlog_ingest.read_tick_state/due/write_tick_state`, свой `every_min` (предложение —
   720). Свой штамп, а не общий: заход тут ходит в сеть и длится 40 с, а дисковый — 2.2 с.
3. `aimgr_tools.py` — четвёртый инструмент `bike_topic_msgs(bike, days=7, limit=20)`: фильтр строк
   `chatlog/servicing/**` по `topic_name`, наружу — `ts` / `text` / `photo: True|False` / `bot`,
   в конверте `chatlog_find.ENVELOPE`.

Первые две — полоса ПК, но пункт 1 трогает `pc_orchestrator.py`, а его коммит **перезапускает демон
самообновлением**: это отдельное разрешение владельца, а не побочный эффект соседней задачи.
Третья — та же ветка `aimgr-tools-3009`, на живое не применяется.

**Честно о пределах выбранного пути.** (а) Окно захвата 7 суток: пропуск дольше недели оставляет
дыру, которую этот путь уже не закроет — строки просто не будут скачаны. (б) Содержательного текста
в темах мало (13 строк от людей с текстом на 5 суток и 6 тем) — агент получит в основном «были фото».
(в) Снимки лежат на диске и в git не внесены (≈2 МБ на сутки форума) — решение владельца от 23.09
не менялось, и этот заход его не пересматривал. (г) Архив — вне git, то есть источник у агента будет
не воспроизводимый из репозитория.
