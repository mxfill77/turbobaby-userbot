## СВОДКА В ЧЕТЫРЁХ СТРОКАХ

1. Разделение потерялось **одной регуляркой** в счётчике базы:
   `_scratch_basePrice_0816/lib.py:11` → `_RE_MODEL = ^\s*(.+?)\s*(\d{2,4})\s*[CСcс]{2}\b`.
   Имя юнита `XMAX 300CC **NEW** BLACK PHUKET 8969` разбирается до `CC`, а слово `NEW`
   стоит **после** `CC` — и выбрасывается. Оба поколения падают в один ключ `XMAX 300`.
2. Источник поколения **разведён и лежит на диске**: сырой срез 1278 броней несёт поле `bike`
   со словом `NEW`; `lib.load()` его даже **возвращает наружу** (`"bike": r.get("bike")`) —
   потеря происходит на шаг позже, при группировке.
3. **Премиса «790 и 939» — числа ДРУГОЙ природы.** Это колонка **B** листа (базовая ставка
   ДО скидки категории). Цена суток — колонка **C**: 593 и 704. Связь: `C = B × (1 − 0.25)`.
4. Разделение **впервые измерено этим заходом**: OLD 560 (n=11) · NEW 641 (n=33). И оно
   **не чинится одним числом** — см. §5: слитое 623 против уплаченных денег даёт −2.2 %,
   а наивно разделённое — **−3.5 %**, то есть хуже. NEW чинится в ноль, OLD ломается.

### ШАГ ПЕРЕНОСА, НА КОТОРОМ ОНИ СЛИЛИСЬ — назван точно

`_scratch_basePrice_0816/lib.py:10-25`, функция `model_of()`:

```python
# Имя байка в листе — «<МОДЕЛЬ> <объём>CC <цвет> <город> <номер>». Модель = всё до объёма+CC.
_RE_MODEL = re.compile(r"^\s*(.+?)\s*(\d{2,4})\s*[CСcс]{2}\b", re.IGNORECASE)

def model_of(bike):
    m = _RE_MODEL.match(str(bike or ""))
    if m:
        return ("%s %s" % (m.group(1).strip().upper(), m.group(2))).replace("  ", " ")
```

Регулярка — `.match()`, то есть якорится в начало и **потребляет строку только до `CC`**.
Всё, что правее, отбрасывается по построению. Проверка на живых именах:

| вход | `.+?` | цифры | результат |
|---|---|---|---|
| `XMAX 300CC BLUE PHUKET 5773` | `XMAX` | `300` | `XMAX 300` |
| `XMAX 300CC **NEW** BLACK PHUKET 8969` | `XMAX` | `300` | `XMAX 300` ← **NEW стоит ПОСЛЕ `CC` и не доходит до ключа** |

**Ключевая деталь: данные не терялись, терялся только КЛЮЧ.** `lib.load()` (строка 72)
кладёт в каждую разобранную строку **сырое имя обратно**:

```python
out.append({"model": mod, "start": a, "ym": ..., "mon": a.month, "days": d,
            "price": float(p), "paid": r.get("paid"), "bike": r.get("bike")})
```

Поколение доехало до самого конца и было отброшено не разбором, а **группировкой по
`model_of(bike)` вместо `(model_of(bike), "NEW" in bike)`**. Это и есть искомый шаг.

## 3. Числа 790 и 939 против найденного — ЧИСЛА ДРУГОЙ ПРИРОДЫ

Не совпали и совпасть не могли: это **разные ступени одной цепочки**.

### Устройство листа `цены альт` (снято 15.08, `2026-08-15-manager-price-sheet.md`)

- **B — базовая цена**, **C — цена с глобальной скидкой**, **G — скидка за срок**, **H — депозит**.
- Коэффициент категории — ячейка `B19` (скутеры), живое значение 15.08 — **+25 %**.
- `sign_rule` правила, дословно: `"formula": "C = B * (1 - g)"`, при `g = 0.25` →
  `"factor_to_base": 0.75`.

### Разложение по ступеням

| ступень | что это | OLD 2020-2022 | NEW 2023- | разрыв |
|---|---|---:|---:|---:|
| **B** — базовая ставка листа | до скидки категории | **790–791** | **938–939** | +18.7 % |
| **C** — цена суток, низкий сезон | `= B × 0.75`, до скидки за срок (срок ≤5 сут) | **593** | **704** | +18.7 % |
| **C × G(8 сут)** — цена листа на 8 суток | скутерная кривая: `6 % + (8−7)×1 % = 7 %` | **551** | **655** | +18.7 % |
| **правило** `base_thb_per_day` | медиана денег, приведена к корзине 7-13 | **623** | **623** | **+0.0 %** |

**Ответ по пунктам:**

- **790 и 939 — это колонка B**, базовая ставка. Проверка арифметикой:
  `593 / 0.75 = 790.67` → «790–791»; `704 / 0.75 = 938.67` → «938–939». Сходится до бата.
- **Клиенту в низкий сезон эти числа не называются** — он платит по C. 790/939 равнялись бы
  цене суток только при `g = 0` («в ноль», майские праздники, `sign_rule.examples`).
- Тем не менее **790/939 живут в боевом коде как цена суток**: `suggest.py:283-284`,
  блок `CRITICAL_FACTS` (источник — `turbobaby_faq_v1.md`, «прайс из CRM»):

  ```
  - Скутеры: … FORZA300 690/5000; XMAX300(2020-2022) 790/5000;
    XMAX300(NEW 2023+) 939/7000; ADV350 998/7000; XADV750 2788/25000.
  ```

  **Это ЧЕТВЁРТОЕ место репозитория, где поколения разведены** — и единственное живое,
  где они разведены **ценой**. Блок помечен «Прайс-ОРИЕНТИР ДЛЯ МЕНЕДЖЕРА (клиенту цену
  НЕ называть)», то есть уходит в промпт, а не в число ответа.

- **623 против 704 — сравнение через ступень срока.** 623 живёт в корзине 7-13, а 704 —
  цена при сроке ≤5 суток. Честное сравнение на одном сроке (8 суток): **623 против 655**
  = −4.9 %, а не −11.5 %. Для старого поколения на том же сроке: **623 против 551** = **+13.0 %**.
  То есть слитая база **завышает старое поколение сильнее, чем занижает новое.**

- Отдельная примета, что ступени срока в двух источниках **противоречат друг другу
  направлением**: правило меряет корзину 1-3 как `0.97` (короткая аренда ДЕШЕВЛЕ недельной),
  а кривая листа даёт при `d ≤ 5` скидку `0 %` против `6–12 %` на 7-13 (короткая ДОРОЖЕ).
  Это отдельный класс, к поколениям не относится, но он и объясняет, почему прямое
  «623 против 704» преувеличивает разрыв.

## 4. Откуда берутся 623 и 704 — обе цепочки дословно

### Цепочка 623 (правило) — ОДНА запись на оба поколения

```
1. rows.json (1278 строк, 1243 годных, срез 16.08)
2. lib.load(completed_only=True)     → status == "Завершена", цена = pay_per_day (колонка H),
                                        срок = duration (колонка G), НЕ разность дат
3. lib.model_of(bike)                → «XMAX 300CC NEW BLACK…» И «XMAX 300CC BLUE…» → "XMAX 300"
                                        ← ЗДЕСЬ СЛИЯНИЕ (§2)
4. base.py: W0="2024-01", LOW_MONTHS=(6,7,8,9,10)   → n = 44 брони
5. base.py: приведение к опорной корзине REF="7-13",
   LADDER = {1-3: 97, 4-6: 103, 7-13: 100, 14-29: 82, 30+: 53}
   нормированная цена = price × 100 / LADDER[корзина]
6. медиана 44 нормированных цен     → 623        ← ПРОВЕРЕНО ПОВТОРОМ (см. §5)
7. price_source.json → base.models[«XMAX 300»].base_thb_per_day = 623
8. price_source.json → formula.expr:
   "price_per_day = base[model] * season[period(start_date)] * term[bucket(days)]"
9. пример голдена №7 (XMAX 300, старт 2026-07-16, 8 суток):
   season["ИЮНЬ-СЕНТЯБРЬ"].multiplier["скутер"] = 1.0 ; term["7-13"].multiplier = 1.0
   623 × 1.0 × 1.0 = 623 ฿/день ; × 8 = 4984 ฿
   ← и это число уходит ОБОИМ поколениям, различается только депозит (5000 / 7000)
```

**Какая запись даёт число:** `base.models` — единственная строка `"XMAX 300"`.

### Цепочка 704 (лист) — ДВЕ записи, по одной на поколение

```
1. лист «цены альт» таблицы «менеджеру Байки», блок «Скутеры» (строки 20-30)
2. строка A = «YAMAHA XMAX 300 NEW 2023-»          (для OLD: «YAMAHA XMAX300 2020-2022»)
3. колонка B (базовая цена)              = 938.67   (OLD: 790.67)
4. ячейка B19 = зеркало «Календарь бронирования»!J3, живое значение g = +25 %
5. колонка C = B × (1 − g) = B × 0.75    = 704      (OLD: 593)      ← ЦЕЛОЕ, так в листе
6. снято живой дверью quote_price (GET) 15.08 по конкретному юниту:
   {"bike": "XMAX 300CC NEW BLACK PHUKET 8969", "model": "YAMAHA XMAX 300 NEW 2023-",
    "day_price": 704, "cap_price": 9900}
7. скидка за срок — колонка G, кривая «scooter», перенесена в код моста 1-в-1
   (QuotePrice.js:87): d<=5 → 0; d=6 → 5%; d<=13 → 6%+(d-7)*1%;
                       d<=30 → 18%+(d-14)*1.0625%; >30 → 35%
8. на 8 суток: 704 × (1 − 0.07) = 654.7 ≈ 655 ฿/день
```

**Какая запись даёт число:** строка листа `YAMAHA XMAX 300 NEW 2023-`, колонка C.
В правиле ей соответствует **только** запись капа (`sheet_model` совпадает дословно) —
у базы соответствия по поколению нет.

### Где эти цепочки встречаются в проде

`price_source.py` — докстринг модуля, дословно:

> **«ИСТОЧНИК ПЕРЕКЛЮЧЁН 20.08.2026 — ветка живёт БЕЗ ФЛАГА.»** … «Ручка
> `PRICE_SOURCE_SEASON` СОХРАНЕНА, но сменила знак: теперь она ВЫКЛЮЧАЕТ».

`enabled()` (строка 63): `return (os.getenv(ENV_FLAG) or "").strip().lower() not in _FALSE`
— ручка не выставлена → `""` → `""` не в `_FALSE` → **ВКЛЮЧЕНО**.

**Следствие для денег: с 20.08.2026 цену клиенту называет ПРАВИЛО, а лист источником быть
перестал.** Значит слитое 623 — это не черновик, а число, которое бот произносит сегодня.
Строка `status.verdict` в самом `price_source.json` («ДАННЫЕ. НЕ ПОДКЛЮЧЕНО И НЕ ЧИТАЕТСЯ
НИКЕМ») **протухла 20.08** и осталась непоправленной.
