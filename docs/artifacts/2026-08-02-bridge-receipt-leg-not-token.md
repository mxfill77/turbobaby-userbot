## 1. Что именно отвечает мост — дословно

**Код HTTP — всегда 200.** Apps Script не умеет ставить статус: `Bridge.js` → `jsonResponse`

```js
function jsonResponse(obj, httpStatus) {
  // httpStatus идёт в тело — Python будет на это смотреть
  obj._status = httpStatus || 200;
  return ContentService.createTextOutput(JSON.stringify(obj, null, 2))
                       .setMimeType(ContentService.MimeType.JSON);
}
```

Значит `401` — **поле в теле**, а не код ответа. Подтверждено с другой стороны: `Bridge._post`
в `pc_orchestrator.py` на исключении возвращает `type(e).__name__`; в логе стоит `unauthorized`,
а не `HTTPError` → исключения не было → HTTP был 200.

**Тело, дословно** (получено писателем журнала 14:41 UTC):

```json
{"ok": false, "error": "unauthorized", "message": "Invalid or missing token", "_status": 401}
```

**Заголовки — сняты живой read-only пробой** (GET БЕЗ токена: `doGet` отвергает его до всякого
действия, проба ничего не пишет):

```
ПЛЕЧО 1  /exec
  код: 302 Found
  Location: https://script.googleusercontent.com/macros/echo?<user_content_key,lib>
  Content-Type: text/html; charset=UTF-8
  Server: GSE
  Cache-Control: no-cache, no-store, max-age=0, must-revalidate
ПЛЕЧО 2  расписка

```

**ОТПЕЧАТОК, который решает дело.** В `Bridge.js` два отказа с одним `error`, но РАЗНЫМ телом:

```js
// doGet, строки 27-32
return jsonResponse({ ok: false, error: 'unauthorized',
                      message: 'Invalid or missing token' }, 401);
// doPost, строка 234
return jsonResponse({ ok: false, error: 'unauthorized' }, 401);
```

Поле `message` есть ТОЛЬКО у `doGet`. Асимметрия одинакова во всех трёх снимках моста, что
лежат на ПК (`tmp/bridge_gs` 29.07, `tmp/bridge_v75`, `tmp/bridge_head` 30.07). Ответ на нашу
ЗАПИСЬ пришёл **с `message`** — то есть его выдал **`doGet`, а не `doPost`**.

Прочитать это можно ровно одним способом: запрос-запись где-то по цепочке редиректов
превратился в голый GET на `/exec` без параметров, и `doGet` честно сказал «токена нет».
Токен при этом не «невалидный» — он просто оказался не там, где `doGet` его ищет.

## 2. Чтение проходит, запись нет — разница в чём

**Не в токене.** `cowork_log_append.py:391` читает `BRIDGE_URL`/`BRIDGE_TOKEN` ОДИН раз и
передаёт ОДНУ переменную `token` и в `read_doc` (строка 407, GET), и в `write_doc` (строка 433,
POST) — в одном процессе, с разницей в секунды. У `pc_orchestrator.Bridge` тем же образом один
`self.token` на `_get` и `_post`. Чтение прошло — значит строка равна `CONFIG.TOKEN`.
Значения токена не читались.

**Не в адресе и не в деплое.** Проба показала, что ПК стучится в `/exec` того самого
прод-деплоя, что закреплён в `clasp_prod_pins.json` (`AKfycb…hXNOqw`, `pinned_version: 76`).
Совпадает маскированный хвост.

**Разница — в МЕСТЕ токена и в том, что переживает редирект.**

| | чтение | запись |
|---|---|---|
| метод | GET | POST |
| где токен | **query-строка** | **тело JSON** |
| кто проверяет | `doGet` → `verifyToken(params.token)` | `doPost` → `verifyToken(body.token)` |
| что делает редирект 302 | query-строка теряется вместе с адресом, но ответ уже посчитан | `urlopen` переигрывает POST как **GET и без тела** — токен исчезает |

`verifyToken` (`Config.js:99`) для обоих один и тот же:
`if (!providedToken) return false; return providedToken === CONFIG.TOKEN;`
Пустой токен и неверный токен дают ОДИН ответ. «Invalid or **missing**» — второе.

**И чтение тоже болеет — просто дешевле.** Живой замер, 12 одинаковых `get_pending(new)` подряд:


Медиана 2,3 с — и один залипший вызов на 122,6 с. А до этого замера чтение журнала через
`brain_writer.read_text` дважды дало разное: первый прогон вернул документ (236955 символов),
второй упал —

```

...
TimeoutError: The read operation timed out
brain_writer.BrainWriterError: read_doc(name:cowork_log) упал: TimeoutError: The read operation timed out
```

Падение стоит **внутри `http_error_302`** — то есть на автоматическом переходе по редиректу,
без всякой ручной сборки. Это второе плечо, `script.googleusercontent.com/macros/echo`.

**Вывод: «запись отбита при живом чтении» — не то, что происходит.** Второе плечо (доставка
расписки) нестабильно для ОБОИХ методов. Чтение платит за это задержкой и редким повтором;
запись платит задачей, потому что демон ветвится по расписке, а обратного чтения у него нет.

и одноразовый `user_content_key` мог протухнуть сам. Доказательно (без ручной сборки) —
`TimeoutError` внутри `http_error_302`, залипание на 122,6 с и 404, который автоматический
`cowork_log_append` получил в 20:11:53.

## 5. Чего на ПК нет, а на VPS уже есть

Греп `allow_redirects|HTTPRedirectHandler|build_opener|Location` по `pc_orchestrator.py`,
`cowork_log_append.py`, `brain_writer.py` → **ноль совпадений**. Все три ходят голым
`urllib.request.urlopen`, который следует за 302 молча и переигрывает POST как GET без тела.

VPS-клиент закрыл ровно этот класс **07.07.2026**. `tmp/srv/bridge_client.py`: `allow_redirects=
False`, ручной обход цепочки до 6 хопов, флаг `_unauthorized`, отдельная ветка «unauthorized на
редиректе → РОВНО одна пересылка». Дословно из шапки его теста
(`tests/test_bridge_durable.py`): «DURABLE-слой bridge_client (фикс intermittent 404 Google,
07.07.2026)… (г) unauthorized/«Invalid or missing token» на редиректе → РОВНО одна пересылка
запроса с токеном».

**Но и у VPS посылка неверна.** Его `_durable_request` объясняет безопасность пересылки так:
«Bridge проверяет токен ДО исполнения действия, значит запрос НЕ исполнен и одна пересылка
с токеном безопасна для ЛЮБОГО действия». Сегодняшний замер это опровергает: `write_doc`
**исполнился**, а расписка пришла как отказ `doGet`. Пересылка в таком случае положит ВТОРУЮ
запись. Посылка верна только для редиректа ДО исполнения; случай «исполнилось, расписка
потерялась» она не покрывает. Точка касания: `bridge_client.py` → `_durable_request`,
ветка `if unauthorized and auth_resend_left > 0`. На ПК этой ветки нет вовсе, так что зеркальной
течи нет — есть отсутствие всей защиты.

## 6. Рекомендация (НЕ применено, решение за владельцем)

1. **Не трогать токен и не передеплоивать мост.** Ни то, ни другое не сломано: чтение проходит
   тем же токеном по тому же адресу, прод-деплой совпадает с пином.
2. **Дать ПК то, что у VPS с 07.07:** ручной обход редиректа (`allow_redirects=False` /
   собственный `HTTPRedirectHandler`) в `pc_orchestrator.Bridge` и в паре `get`/`post`
   журнального писателя. Это правка кода на ПК-полосе.
3. **Судить по ФАКТУ, а не по расписке.** `claim_task`/`complete_task` при отказе обязаны
   перечитать статус задачи — ровно как `cowork_log_append` уже перечитывает документ. Сегодня
   расписка теряется и задача теряется вместе с ней (193).
4. **Отдать VPS-полосе поправку посылки** из §5: «unauthorized ⇒ не исполнено» неверно, пересылка
   может дублировать запись.
5. **Ложный «детект пробуждения ПК» объяснён.** Залипание одного вызова моста на 122,6 с при
   пороге `POLL_SEC + WAKE_JUMP_MARGIN = 120 с` — этого достаточно, чтобы виток «проснулся».
   201 срабатывание за сутки — это не сон и не медленный CIM, это второе плечо Google.

Ничего из перечисленного в этом заходе не сделано.
