# Методика менеджеров: как живой диалог доходит до брони

**Источник — ФАКТ, не выдумка.** Разбор локального дампа `client_chats.jsonl`
(710 личных диалогов, роль `company` = наш менеджер @turbophuket, роль `client` =
клиент). Отобраны окна, дошедшие до выдачи байка: строки `268, 99, 257, 139, 224,
270, 421, 178, 526` (9 успешных окон, ноябрь 2025 — март 2026). Обезличено: имена,
телефоны, ссылки на жильё и реквизиты в этот документ НЕ переносятся.

Повод: живой ТЕСТ-7 (22.07.2026) — бот назвал цену и доставку и **замолчал**,
хотя паспорт / телефон / время и точка подачи собраны не были. Диалог к брони
никто не двигал.

## 1. Что показала частотка по всему корпусу (15 845 сообщений менеджера)

| Приём | Диалогов | Раз |
|---|---|---|
| «с какого числа / подскажите даты» | 560 | 858 |
| «на чём ранее ездили» (опыт) | 443 | 633 |
| строка расчёта `МОДЕЛЬ \| дней: N стоимость: X, депозит: Y` | 359 | 878 |
| чек-лист брони (паспорт + апартаменты + шлемы + телефоны) | 125 | 137 |
| «бронируем?» / «можем забронировать» / «ставим бронь» | 70 | 80 |
| «доставка нужна будет?» | 50 | 50 |
| «во сколько удобно принять байк?» | 46 | 60 |
| «ожидаем данные» (мягкое напоминание) | 21 | 21 |

**Длина и вопросы.** Медиана сообщения менеджера — **27 символов**, 91 % ≤ 120
символов. Вопросов в одном сообщении: **0 — 84 %, ровно 1 — 14 %, два и более —
≈0 %**. Менеджер никогда не вываливает анкету: он задаёт **один** вопрос и ждёт.

## 2. Скелет успешного окна (одинаков во всех 9 разобранных)

1. **Приветствие-шаблон — РОВНО ОДИН раз**, первым ответом: «Здравствуйте, спасибо,
   что выбрали нас 🤝 … напишите, что хотели бы арендовать, с какого числа и на
   какой срок … кратко про опыт вождения» + ссылки на точки и отзывы.
   Соц-доказательство (точки/отзывы) дальше в диалоге **не повторяется ни разу**.
2. **Даты и срок** — если клиент их не назвал, следующий ход менеджера всегда
   именно этот и никакой другой: «С какого числа ?», «Подскажите даты».
3. **Модель + расчёт** одной строкой из Календаря, без комментариев.
4. **Доставка**: «Доставка нужна будет ?» → «Локацию пожалуйста» → сумма по
   району + «от вас бесплатный забор».

   > **‼️ Поправка 31.07 — «бесплатный забор» БЕЗУСЛОВНО обещать нельзя.** Живой код считает
   > эту формулировку дефектом: бесплатный забор — перк **ОПЛАЧЕННОЙ доставки**; при самовывозе
   > обратный забор стоит столько же, сколько доставка в ту же зону. В промпте это стоит
   > жёстко («при самовывозе бесплатного забора НЕ обещай»), и сверху работает код-страховка
   > `postcheck_free_pickup` (`suggest.py`), которая снимает ложное обещание из черновика.
   > То есть цитата этого пункта — ровно та фраза, которую контур ловит и вырезает.
   > Читать как: «сумма по району + бесплатный забор **при оплаченной доставке**».
5. **Закрытие**: «Бронируем ?» / «Можем забронировать тогда для вас».
6. **Чек-лист брони** — дословная формула, повторяется в 125 диалогах почти
   слово-в-слово:
   > «Для бронирования понадобятся: качественное фото паспорта, название
   > апартаментов, количество шлемов, номера телефонов.»
   Уточнения по ходу: паспорт — **загран**; телефон — «главное с доступом в вотсапп».
7. **Время подачи — ОТДЕЛЬНЫМ, следующим вопросом**, уже после адреса/телефона:
   «Во сколько удобно принять байк ?» → менеджер называет слот («11-12 ранний
   слот»).
8. **Итог**: сумма одной строкой (`6872+5000+490=12.362`) и реквизиты.
9. Данные не пришли — **не давят и не молчат**, а держат бронь: «Хорошо, ожидаем
   информацию», «Да, ждём данные», «Принято, ожидаем данные и ставим бронь».

## 3. Правило, которое из этого следует

Порядок недостающего, по которому менеджер выбирает свой следующий ход:

```
даты подтверждены → фото паспорта → телефон → время и точка подачи → подтверждение брони
```

> **Поправка 31.07 — эта сводная строка НЕПОЛНА (сам метод выше описан верно).**
> Живая воронка (`suggest.py` → `next_step`) содержит два шага, которых в стрелке нет:
> `dates` → **`dates_fix`** (починка кривых дат) → `model` → **если бронь не готова, выход в
> `offer`** («Бронируем?», п. 5 выше) → `passport` → `phone` → `pickup` → `confirm`.
> И это **ветвление**, а не линейная цепочка: стрелки создают ложное впечатление, что шаги
> идут строго подряд.
> Ложный диагноз: «бот спросил не то ⇒ воронка сломана» — шаги `dates_fix` и `offer`
> просто не видны по этой строке. Уточнение: сам документ прав, неполна одна сводка.

- ответ **всегда заканчивается ОДНИМ следующим шагом** — менеджер не отвечает
  «в пустоту» (случай ТЕСТ-7);
- **ровно один вопрос** за сообщение (в корпусе 2+ вопросов практически нет);
- **уже собранное не переспрашивается** (фильтр #241 / трекер `collected_facts`);
- этап не забегает вперёд: паспорт/апартаменты/шлемы просят **только** когда
  клиент готов бронировать;
- **гейт дат приоритетнее воронки**: назван прошедший старт → завершающий вопрос
  это уточнение дат, а не следующий шаг (иначе бронь оформляется на несуществующие
  даты).

Реализация: `suggest.next_step()` / `next_step_note()` (правило в промпт) и
детерминированная страховка `ensure_closing_question()` — если LLM закончил ответ
без вопроса, код дописывает ровно один вопрос по этому приоритету.
