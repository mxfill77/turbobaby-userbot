# RC_BRAIN_BRIDGE — мост RC-сессии → мозг

## Правило (ОБЯЗАТЕЛЬНО)

**Каждая RC-сессия** (Claude Code Remote Control: канал с телефона, задача Планировщика
`TurboBabyRC`) **финальным шагом пишет итог в мозг** через `cowork_log_append.py`.

**Без этой записи сессия считается НЕЗАВЕРШЁННОЙ** — даже если код закоммичен и проверен по
факту. Штаб (Claude-на-сайте, владелец) видит RC-сессию только через мозг: нет строки — для
штаба работы не было. Секреты Bridge берёт САМ процесс писателя, агентский код их не читает.

## Формат строки

```
DONE RC <дата> <время>: <что сделано, с фактами и хешами>
```

Боевой пример (полный вызов):

```
D:\turbobaby-bot\venv\Scripts\python.exe D:\turbobaby-bot\cowork_log_append.py "DONE RC 2026-07-24 05:30: гард manager-bot приземлён коммитом a5c148e, живьём проверен (красные слова -> defer, секреты -> deny, вне-репо -> ask), не пушен, демон не рестартован"
```

Развилка (нужен выбор владельца) — тот же формат с префиксом **`ASK`** вместо `DONE`:

```
ASK RC <дата> <время>: <суть развилки> — варианты <а / б / в>; жду решения
```

> **⚠️ Поправка 31.07.2026: что из этого формата доживает до мозга.**
> Писатель штампует дату **сразу после типа** (`cowork_log_append.py` → `stamp_line`), поэтому
> строка ложится как `DONE <дата время> UTC: RC <дата> <время>: …`.
> Следствия:
> - **искать RC-итоги по `^DONE RC` бесполезно** — совпадений ноль всегда; это НЕ значит, что
>   RC-сессии не пишут журнал. Ищи `RC` в теле строки;
> - `ASK` — валидный тип у ПК-писателя (`LOG_TYPES`), но **у серверного `cclog` типа `ASK`
>   нет**: при двойной фиксации (раздел ниже) развилка на VPS ляжет мимо типа, и поиск
>   развилок по `ASK` даст ноль на половине общей памяти. На VPS развилку помечай словом в
>   теле строки, а не рассчитывай на тип.
>
> Приведение формата к коду — правка кода; в сверке 31.07 не делалась, записана в остатки.

## Дисциплина

- Пиши строку **в самом конце** — после коммита/действия; время локальное, хеш коммита короткий.
- **Факты, а не пересказ:** PID, короткий хеш, вывод команды, статус гейта — не «сделано».
- Вызов с таймаутом ~30с; журнал повис — скажи прямо («журнал повис, DONE позже») и не блокируйся.
  > **Поправка 31.07:** внешний `timeout 30` на ручном вызове **опаснее, чем ожидание**.
  > Внутренний бюджет писателя больше: два запроса (чтение+запись), на каждом свой сокет-таймаут,
  > плюс повтор на транспортных ошибках (`RETRY_TRIES`, `with_retry`). Внешний килл наступает
  > ДО ветки `except`, и строка не уходит **ни в мозг, ни в спул** — тихая потеря записи при
  > честном рапорте «журнал повис». Ограничиваешь — бери ≥150с. К `SessionEnd`-хуку не
  > относится: там запись идёт отдельным процессом.
- Автоматика (`SessionEnd`-хук `dispatch_notify.py`) **страхует, но НЕ заменяет**: развёрнутый
  FACT-отчёт владельцу + строка журнала — по-прежнему за сессией.

## Если RC-работа шла на VPS — фиксируй ДВАЖДЫ

1. **ПК-мозг** — `cowork_log_append.py` строкой выше (наблюдаемость штабом).
2. **VPS `cc_log` + `pulse`** — на самом VPS одной командой (пишет и журнал, и пульс; `cclog` сам
   грузит `.env`):

   ```
   venv/bin/python3 <cclog> DONE "<итог>" --pulse "<строка пульса по факту>"
   ```

   Имя `cclog` бери из `git ls-files ':(glob)cclog*'` (в SSH-команде `.py`-литерал не печатай).
   `--pulse` перезаписывает doc `pulse` целиком — это ОДНОСТРОЧНЫЙ текущий статус (история — в
   `cc_log`), перезапись здесь штатная.

## Живучесть RC-канала: пороги сторожа (заведено 31.07.2026)

До этой правки **ни один нормативный документ не описывал ни одного механизма живучести
RC-канала** — диагноз строился по артефактам 24.07, а они устарели. Значения ниже сняты с
`rc_supervisor.py` 31.07; искать по ИМЕНИ константы, не по номеру строки.

| имя | знач. | что задаёт |
|---|---|---|
| `CHECK_INTERVAL` | 30с | период тика сторожа |
| `RESTART_DELAY` | 15с | пауза между выходом процесса и подъёмом |
| `NOT_READY_DELAY` | 300с | пауза, когда канал ещё не готов |
| `GRACE_SECONDS` | 180с | льгота свежеподнятому процессу — под пробу живости не попадает |
| `LIVENESS_MAX_AGE` | 1200с | **только дефолт** для ветки без собственного ключа |
| `SERVER_LIVENESS_MAX_AGE` | 3600с | порог серверной ветки |
| `NAMED_LIVENESS_MAX_AGE` | 43200с (12ч) | порог именованной ветки |
| `LIVENESS_STRIKES` | 3 | сколько подряд неудачных проб нужно, чтобы гасить |

**Три ложных диагноза, которые это снимает:**

1. **«Сторож гасит канал каждые 20 минут»** — неверно по построению: 1200с давно не общий
   порог, у веток свои значения, и одной неудачной пробы мало — нужно **три страйка подряд**.
2. **«0 TCP-соединений ⇒ процесс-зомби»** — неверно: свежий живой RC-процесс приходит к нулю
   соединений примерно за 15 минут. Проба по соединениям сама однажды ложно гасила сервер.
3. **«Канал не поднимается ⇒ протухла среда»** — сред RC накапливается по одной на каждый
   рестарт, и они мертвы по построению (каждый старт регистрирует НОВУЮ). Третья причина
   рестартов — протухшие учётные данные; её ловит отдельный модуль `rc_auth_detect.py`,
   **включённый по умолчанию** (`ENABLED`, выключается только явным `RC_AUTH_WATCH=0`).
   Он уже написан и проведён в сторожа — не пиши его второй раз.
